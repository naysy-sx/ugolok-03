## Часть A. Починка

### T1. Профили в карточках (дешёвое, сразу меняет картину)

`src/ui/screens/discovery.jsx:33` зовёт `ensureProfilesFetched`, которая
кэширует `null` навсегда (`src/ui/signals/contacts.js:277–283`). Каналы от
этого уже ушли на `ensureProfilesFresh` (пометка «CHANNEL-V2 часть A2/A3» в том
же файле), discovery забыли перевести. Итог: карточка — обрезанный hex вместо
имени, без аватара и без био, даже когда всё остальное работает.

Сделать:

- Заменить на `ensureProfilesFresh(discoveryPubkeys, fetchProfiles, { force: true })`
  — «экран только что открыли», ровно тот же вызов, что в
  `moderation-panel.jsx:69`.
- Убрать `.catch(() => {})`: ошибка обязана попасть в `connectionError`
  экрана. Молчаливое проглатывание здесь — половина причины, по которой
  раздел выглядит мёртвым.

### T2. Событие kind 30073 не переиздаётся никогда

Два дефекта, вместе дающие «у всех пусто»:

1. `publishDiscoverySettings` (`src/domain/discovery/discovery.js`) глотает
   провал публикации пустым `catch {}`. Локальная запись `visible: true`
   сохраняется, в сеть не уходит ничего, пользователь уверен, что
   транслируется.
2. `VisibilitySection` (`src/ui/screens/profile.jsx:39`) не вызывает
   `ensureConnected` перед `publish`. При отсутствии соединения `publish()`
   бросает «нет активного соединения» — см. п. 1.
3. Переиздания при следующем входе нет. Сравнить с `connect()`
   (`src/ui/signals/transport.js`, ~432): kind:10002 и kind:10050 переиздаются
   **при каждом подключении** именно потому, что replaceable-событие дёшево и
   идемпотентно. Для 30073 такого блока нет.

Сделать:

- `publishDiscoverySettings`: убрать пустой `catch`, пробрасывать ошибку
  наверх. Локальное сохранение остаётся первым (best-effort порядок не
  меняется — тест «сбой publish не мешает локальному сохранению» должен
  продолжать проходить, но теперь вызывающий код узнаёт об ошибке).
- Вызывающий код: `await ensureConnected(...)` перед публикацией, ошибку
  показывать в UI.
- В `connect()`, рядом с переизданием kind:10002/10050: прочитать локальные
  `discoverySettings` и, если трансляция ещё не истекла (см. T4), переиздать
  событие. Без флага «announced» — по той же логике, что уже записана в
  комментарии к kind:10002.
- Событие, попавшее в outbox при провале, должно доезжать через
  `drainOutboxSafely`. Проверить, что путь публикации discovery в outbox
  вообще заходит; если нет — завести.

### T3. Гонка EOSE стирает локальный кэш

**Воспроизведено на стенде, не гипотеза.** `fetchDiscoveryProfiles`
(`src/ui/signals/transport.js:994`) делает реконсиляцию: всё, чего не было в
этом REQ, удаляется через `bulkDelete`. При этом пул считает финальным ПЕРВЫЙ
пришедший EOSE (инвариант П4, `relay-pool.js:212–218`).

С двумя read-реле: быстрое пустое отдаёт EOSE → подписка закрывается →
события медленного приходят после CLOSE в уже удалённую очередь → `seenPubkeys`
пуст → `bulkDelete` сносит весь кэш целиком. Каждый заход на экран.

Сделать (выбрать одно, обосновать выбор в CONTRACTS.md):

- **Вариант 1 (проще, рекомендую для этой итерации).** Убрать реконсиляцию
  удалением. Причина, ради которой её вводили — «автор перестал публиковать, а
  карточка висит вечно» — после T4 решается сроком годности: протухшая запись
  отсеивается по времени, стирать её по факту отсутствия в снимке не нужно.
  Оставить только `put`.
- **Вариант 2 (правильнее, дороже).** Собирать EOSE со ВСЕХ read-реле пула, а
  не с первого, и только тогда реконсилировать. Требует правки инварианта П4 в
  `relay-pool.js`, то есть трогает общий транспорт всех остальных подписок.

Критерий выбора: если менять транспорт в этой итерации не хочется — вариант 1.
Если реконсиляция нужна по другим причинам, которых я не вижу — вариант 2, но
тогда отдельным этапом и с тестом на многореленый пул.

## Часть B. Срок трансляции

### T4. Схема с TTL

Сейчас `visible` — вечный булев флаг. Того, что нужно (10 минут / час /
сутки), в данных нет.

**Контент события kind 30073** (остаётся открытым JSON, не шифруется):

```json
{
  "visible": true,
  "visibleUntil": 1756500000,
  "showChannels": true,
  "channels": [{"id": "...", "name": "...", "description": "..."}],
  "bio": "текст до N символов"
}
```

- `visibleUntil` — unix-секунды. Обязателен при `visible: true`.
- Тег `["expiration", String(visibleUntil)]` (NIP-40) — рядом с `["d","discovery"]`.
  Шаблон уже есть в `src/core/transport/blossom-client.js:13`, взять оттуда.
- `bio` — **новое поле, обязательно для части D**. Сейчас био подтягивается из
  kind:0 через `ContactIdentity`, то есть текст, который надо
  предмодерировать, в самом discovery-событии не лежит. Для фильтра на реле
  (T8) текст обязан быть внутри события. Ограничить длину (предлагаю 300
  символов), обрезать при сборке.

**`parseDiscoveryEvent`:** добавить разбор `visibleUntil` (число, иначе
считать событие невалидным при `visible: true`) и `bio` (строка, обрезка по
лимиту, отсутствие → `""`). Коэрсинг мусора — как сейчас, не бросать на чужом
кривом клиенте.

**`refreshDiscoveryProfiles`** (`src/ui/signals/contacts.js:460`): добавить в
фильтр `r.visibleUntil > nowSec`. Реле может не поддерживать NIP-40 — читатель
обязан отсеивать сам, не полагаться на сервер.

**Локальная схема:** `db.version(30)`, таблица `discoverySettings` получает
поле `visibleUntil`; апгрейд существующих строк — `visible: false`,
`visibleUntil: 0` (никого не выкидываем в ленту на неопределённый срок при
обновлении).

**Длительности:** константа в домене, например
`DISCOVERY_DURATIONS = [600, 3600, 86400]` (10 мин / 1 ч / 1 сутки). Задел под
платные тарифы — это то, что длительность стала числом из списка, а не
булевым флагом. **Явно записать в CONTRACTS.md:** клиент не может обеспечить
платный срок, это может только реле, проверяя чек. Никакой платёжной логики
сейчас не закладывать.

**Автоистечение в UI:** таймер на экране «Знакомства», по истечении —
переключатель сам возвращается в «невидим», карточка исчезает из чужих лент.
Событие с `visible: false` при истечении **публиковать не нужно** —
`expiration` и фильтр читателя делают это сами.

## Часть D. Модерация

### T7. Где фильтр стоять НЕ должен

Записать в CONTRACTS.md прямо, чтобы к этому не возвращались:

Фильтр в клиенте публикующего — декоративный. kind 30073 — открытое
нешифрованное событие, его отправит на реле любой сторонний Nostr-клиент.
Скрипт, который крутится в приложении нарушителя, — единственный, который
нарушитель не запустит.

Работают два места: **write-policy плагин своего strfry** (сервер, контент
открытый, читается и отклоняется) и **клиент читателя** (работает даже для
событий с чужих реле). Делать оба. В клиенте отправителя — только
предупреждение «этот текст не пройдёт», как удобство.

И назвать вещь своим именем в комментарии к словарю: он обходится пробелами,
гомоглифами, заменой букв на цифры. Ловит ленивых, упорных не ловит.

### T8. Словарный фильтр

**Общий модуль** `src/domain/discovery/wordfilter.js` — без зависимостей от
браузерного API, чтобы его можно было импортировать и из клиента, и из
серверного плагина Node:

```js
export function normalize(text)   // lowercase, NFKD, схлопывание пробелов,
                                  // цифры-гомоглифы (0→о, 3→е, 1→і и т.п.)
export function findMatches(text, dictionary) // → [{term, index}]
export function isClean(text, dictionary)
```

Словарь — отдельный JSON, не в коде: `src/domain/discovery/stopwords.json`.
Правится без пересборки серверной части.

**Реле:** новый плагин по образцу `server/strfry/whitelist-plugin.mjs` (тот же
построчный JSON-протокол stdin/stdout). Логика: если `event.kind !== 30073` —
`accept` и не мешать. Иначе разобрать `content`, прогнать `bio` и
`channels[].name/description` через `isClean`; при попадании — `reject` с
внятным `msg`. strfry поддерживает один write-policy плагин, поэтому
объединить с существующим whitelist в одну цепочку, а не заводить второй.

**Читатель:** в `refreshDiscoveryProfiles` отсеивать карточки, не прошедшие
`isClean`. Тихо, без объяснений — это не пользовательская ошибка.

**Отправитель:** в блоке видимости (T5) показать предупреждение до публикации,
с указанием, какое поле не проходит. Не блокировать кнопку намертво — сообщить
и дать исправить.
