**Статус:** редакция 2, этап 1 проектирования. Правки внесены по итогам алгоритмического разбора (`FILES-ALGO.md`); изменённые решения помечены в журнале §10. Кода нет, контрактов нет.

## 1. Три слоя и почему их нельзя путать

Модуль состоит из трёх слоёв с **разной алгеброй**. Большинство ошибок в файловых системах — это применение операции одного слоя к структуре другого.

| Слой | Структура | Идентичность | Операция |
|---|---|---|---|
| Имена | лес, ч.у.-множество | `NodeId` | перемещение, переименование |
| Контент | фактор-множество по хешу, DAG ссылок | `Digest` | запись, дедупликация, сборка мусора |
| Доступ | цепь-решётка прав | грант `(user, node, perm)` | выдача, отзыв |

Главное практическое следствие: **пространство имён — дерево, а хранилище — DAG.** Два узла дерева могут ссылаться на один блоб. Копирование папки не копирует байты (§3), удаление узла не удаляет байты (§3, GC).

## 2. Слой имён

### 2.1 Определения

Пусть `N` — множество узлов. Заданы тотальные отображения

```
par  : N → N ∪ {⊥}          родитель, ⊥ только у корня
name : N → Σ*                имя
kind : N → {dir, file}       тип
```

Тотальность `par` означает, что состояние всегда есть **функциональный граф**: исходящая степень каждой вершины ровно 1 (у корня — 0). Это не то же самое, что дерево. Древовидность — дополнительный инвариант, а не следствие типа данных, и в §5 показано, как он нарушается сам собой.

### 2.2 Инварианты слоя

- **I-ACYCLIC.** `∀ n ∈ N : n ∉ par⁺(n)`, где `par⁺` — транзитивное замыкание.
- **I-UNIQUE-NAME.** `name` инъективна на каждом слое `par⁻¹(d)`.
- **I-REACHABLE.** Каждый живой узел достижим из корня.

При выполнении I-ACYCLIC отношение `⪯` («является предком»), то есть транзитивно-рефлексивное замыкание `par`, — частичный порядок с характеристическим свойством леса: **для любого `n` множество его предков `{m : n ⪯ m}` линейно упорядочено (является цепью).** Это свойство используется в §6 при выводе эффективных прав и в §4 при проверке предусловия перемещения.

### 2.3 Путь — производная величина

Путь до узла есть конкатенация имён вдоль цепи предков, элемент свободного моноида `(Σ*)*`. Инъективность отображения «узел → путь» обеспечивается инвариантом I-UNIQUE-NAME.

**Путь не является идентификатором.** Он меняется при переименовании или перемещении любого предка. Все внутренние ссылки — вложения в чат, аватар профиля, гранты доступа, буфер обмена — хранят `NodeId`, а путь вычисляется только для отображения.

### 2.4 Обход

Листинг папки — слой `par⁻¹(d)`. Полный обход — структурная рекурсия по дереву. Требуется явный предел глубины: без него рекурсия упирается в стек, а при нарушенном I-ACYCLIC (что штатно возможно, см. §5) — не завершается вовсе. Любой обход обязан быть устойчив к циклу, а не полагаться на его отсутствие.

**Предел глубины применяется к выходу `R`, а не ко входу.** Слияние глубину не контролирует: сырое состояние `S` может содержать цепочку длины `Θ(n)` и циклы неограниченной длины. Ограничение `D_max = 64` относится к отображаемому дереву, то есть к результату проекции. Алгоритмы, работающие над сырым `S` — прежде всего сам ремонт (§5.5), — обязаны быть корректны без этого предположения. Поставить предел не в том месте и решить, что проблема закрыта, — типичная ошибка; отсюда явная формулировка.

## 3. Слой контента

### 3.1 Дедупликация как фактор-множество

Содержимое — элемент `B*` (последовательность байтов, разбитая на чанки). Криптографический хеш `h : B* → Digest` задаёт отношение эквивалентности «одинаковое содержимое». Хранилище держит представителей фактор-множества `B*/~`.

Отображение «узел → блоб» `f : N_file → Digest` **не инъективно**. Число ссылок на блоб `b` есть мощность слоя `|f⁻¹(b)|`.

### 3.2 Копирование — изоморфизм поддерева

Копирование папки есть биекция `φ` на множестве узлов поддерева, удовлетворяющая

```
par'(φ(x)) = φ(par(x))
f'(φ(x))   = f(x)          указатели на блобы не меняются
```

Стоимость — `O(число узлов)`, независимо от объёма данных. **Копирование папки на 4 ГБ обязано быть мгновенным.** Если оно не мгновенное — слои перепутаны, и это регрессия, а не оптимизация.

### 3.3 Сборка мусора

Поскольку структура ссылок — DAG, а не дерево, счётчики ссылок ненадёжны при слиянии реплик (реплика может не знать о ссылке, созданной на другом устройстве). Корректный механизм — **достижимость из корней** (mark-and-sweep) в ориентированном графе.

Корни для GC: корень дерева, корзина, `lost+found`, все расшаренные поддеревья и множество `pinned`.

**`pinned` — монотонное множество дайджестов (G-Set).** Первая редакция документа задавала последний корень как «все вложения в неудалённые сообщения». Формулировка неверна по двум причинам: она требует обхода всей истории переписки при каждой сборке, что может превосходить `n` на порядки, и она вводит зависимость файлового модуля от внутреннего устройства модуля сообщений — то есть нарушает границы, ради которых существует `CONTRACTS.md`.

Вместо этого модуль сообщений при отправке вложения **дописывает** дайджест в `pinned`, а файловый модуль его только читает. G-Set сливается тривиально, координации не требует, корни доступны за `O(1)`.

Плата: множество только растёт, закреплённый блоб не освобождается никогда — даже после удаления сообщения. Для v0.1 это правильный компромисс: вложение в переписке должно переживать чистку файлового менеджера, иначе удаление файла молча ломает старое сообщение у собеседника. Открепление требует счётчиков или согласования и отложено.

**Возрастной порог — условие корректности, а не оптимизация.** Блоб записывается раньше, чем ссылающийся на него узел (иначе узел указывал бы в пустоту). Окно между двумя записями равно времени загрузки файла, то есть секундам или минутам. GC, запущенный в этом окне, считает блоб недостижимым и удаляет его — файл теряется.

Инвариант: блоб не подлежит сборке, пока его возраст меньше `T` (порядка часа). Требует хранить время записи блоба. Альтернатива — явная таблица «в процессе загрузки» — точнее, но требует восстановления после аварийного закрытия приложения; для v0.1 порог проще и не имеет состояния.

Решение для v0.1: достижимость. При ожидаемых объёмах стоимость несущественна, а корректность не зависит от порядка слияний.

### 3.4 Хеши и чанкинг

- Дайджест не обрезается. Обоснование — парадокс дней рождения: для 64-битного дайджеста коллизия ожидается около 2³² объектов, для 256-битного не ожидается никогда.
- **Чанкинг фиксированного размера.** Content-defined chunking (скользящий хеш Рабина, модульная арифметика) даёт дельта-эффективность на изменяемых больших файлах — не требуется, пока нет сценария редактирования файла на месте. Дополнительный и более сильный аргумент: при переменном чанкинге отображение «байтовое смещение → индекс чанка» перестаёт быть арифметическим и требует таблицы кумулятивных смещений с двоичным поиском. При фиксированном размере это `idx = ⌊off / chunkSize⌋`, то есть `O(1)`.

### 3.5 Независимая расшифровка чанка — требование v0.1

Первая редакция относила чанкинг к отложенным вопросам. Это была ошибка постановки: чанкинг рассматривался только как механизм дедупликации, тогда как он определяется требованием к плееру.

Пользователь смотрит видео и перематывает на середину. Файл зашифрован. Если файл зашифрован **как единый поток**, то есть каждый блок зависит от предыдущего, то перемотка требует расшифровать всё от начала до точки — `O(размер файла)` на каждое движение ползунка. Заявленная функция «встроенный плеер» при такой схеме не существует.

**Инвариант I-CHUNK-INDEP.** Каждый чанк шифруется независимо от остальных: ключ выводится из ключа файла, nonce — детерминированно из индекса чанка, аутентификационный тег на каждый чанк. Никаких сцепляющих режимов.

Побочная выгода: чанки можно скачивать, проверять и расшифровывать параллельно и не по порядку.

**Это решение о формате хранения, а не о реализации.** Перешифровать хранилище позже — миграция, а не правка. Поэтому оно принимается сейчас, а не откладывается.

### 3.6 Манифест

Узел-файл ссылается не на содержимое напрямую, а на **манифест** — блоб, описывающий разбиение:

```
Manifest = {
  size      : int,          // байт в исходном файле
  chunkSize : int,          // константа для данного файла
  chunks    : Digest[],     // c = ⌈size / chunkSize⌉ элементов
  keyId     : KeyId,
  mime      : string
}
```

Манифест сам адресуется дайджестом, то есть подчиняется тем же правилам дедупликации и сборки мусора, что и любой блоб.

Поскольку `chunkSize` записан в манифесте, а не зафиксирован глобально, его значение можно менять для новых файлов, не ломая старые. Это свойство сохраняется сознательно: конкретный размер (диапазон 256 КБ – 1 МБ) подбирается замером, а не рассуждением.

## 4. Операции как частичные функции

Каждая операция — частичная функция на состоянии с явным предусловием. Список предусловий — прямой источник unit-тестов.

**`move(n, d)`** определён ⟺ `d ∉ subtree(n)` и `name(n)` свободно в слое `par⁻¹(d)`.

Первое условие — единственная нетривиальная проверка модуля. Стоимость `O(глубина)`: подъём от `d` по цепи предков с проверкой на встречу с `n`.

**`rename(n, s)`** определён ⟺ `s` свободно в слое `par⁻¹(par(n))`.

**`copy(n, d)`** — тотальна при выполненном предусловии на имя; создаёт изоморфную копию по §3.2. Условие `d ∉ subtree(n)` здесь **не требуется** (копирование папки внутрь себя корректно и конечно, поскольку копируется исходный снимок).

**`delete(n)`** ≡ `move(n, /trash)`. Обоснование в §5.6.

**`purge(n)`** — установка монотонного флага, необратимо.

### 4.1 Буфер обмена

Автомат на трёх состояниях, размещается в существующей FSM-инфраструктуре проекта:

```
Empty ──copy(S)──▶ Copied(S) ──paste(d)──▶ Empty     ; paste ≡ copy-операция
Empty ──cut(S)───▶ Cut(S)    ──paste(d)──▶ Empty     ; paste ≡ move-операция
```

Инвариант: узел, попавший в `Cut(S)` и затем удалённый другой репликой, при вставке даёт no-op, а не ошибку.

## 5. Репликация

Основная часть документа. Здесь сосредоточена вся нетривиальная математика модуля.

### 5.1 Основание

Причинный порядок событий (happens-before) — строгий частичный порядок. Метка Лампорта с разрывом связей по идентификатору устройства даёт его линейное расширение.

**L-TOTAL (критический инвариант).** Метка есть пара `(counter, deviceId)` с лексикографическим сравнением, где `deviceId` — публичный ключ устройства. Тогда порядок меток **строгий тотальный**. Весь детерминизм §5.4 держится на этом. Нарушение уникальности `deviceId` ломает сходимость молча, без исключений и без падения тестов на малых объёмах.

Сходимость реплик требует, чтобы слияние `⊔` было коммутативно, ассоциативно и идемпотентно, то есть чтобы состояние жило в **полурешётке**. LWW-регистр и G-Set этому удовлетворяют.

### 5.2 Контрпример: LWW на `par` не сохраняет древовидность

Пусть `par` — LWW-регистр. Реплика A перемещает `x` внутрь `y`. Реплика B **одновременно** перемещает `y` внутрь `x`. Каждая операция по отдельности корректна и сохраняет I-ACYCLIC на своей реплике.

После слияния: `par(x) = y`, `par(y) = x`. Цикл, оторванный от корня. LWW при этом не нарушен — оба значения последние для своих регистров.

Это не редкий сценарий: при мультидевайсе достаточно двух устройств, работавших офлайн.

Известное каноническое решение — журнал операций в тотальном порядке с undo-do-redo хвоста при получении опоздавшей операции (Kleppmann, Mulligan, Gomes, Beresford, *A highly-available move operation for replicated trees*, 2021 — **ссылка по памяти, требует сверки**). Отклонено для v0.1: неограниченный рост журнала, нерешённая задача компактации, недели работы.

### 5.3 Принятое решение: ремонт как проекция

```
хранится   S        — сырое CRDT-состояние, может содержать циклы
показывается R(S)   — дерево
```

`R` — **чистая функция от слитого состояния. Результат ремонта никогда не записывается обратно в реплицируемое состояние.**

**Момент вычисления.** Первая редакция формулировала это как «вычисляется на чтении». Как алгебраическое утверждение формулировка верна, но она провоцирует нерабочую реализацию: `R` — три прохода по всему состоянию, `Θ(n)`, а листинг папки происходит с частотой рендера. Точная формулировка:

> `R` вычисляется **при изменении `S`** — при локальной операции или при слиянии — и результат кэшируется. Чтение обращается к кэшу. Кэш живёт в оперативной памяти, не реплицируется и не сериализуется в состояние.

Семантика не меняется: `R` остаётся чистой функцией от `S`, кэш — мемоизация чистой функции, то есть семантически невидим. Свойства `I-CONVERGE` и `I-STABLE` сохраняются дословно. Смысл фразы «на чтении» был в том, что результат не пишется в реплицируемое состояние — и это остаётся в силе.

**Следствие, упрощающее реализацию: локальная операция не может создать цикл.** Предусловие `move(n, d)` требует `d ∉ subtree(n)` (§4) и проверяется до применения. Следовательно единственный источник циклов — слияние, и полный проход шага 1 нужен только после `merge`; при локальных операциях достаточно точечно обновить производные индексы.

**Пакетность слияния — требование, а не оптимизация.** Пересчёт `R` после каждой входящей операции даёт `Θ(m·n)` на пачку из `m` операций; при возврате из офлайна `m` достигает тысяч. Корректный порядок: применить все входящие операции к `S` (по `O(1)` каждая), затем однократно вычислить `R`. Это законно, поскольку `⊔` коммутативна и ассоциативна: промежуточные состояния не наблюдаемы и материализовывать их не требуется. См. инвариант `I-BATCH` в §9.1.

Обоснование записью-назад-нельзя. Если реплика A чинит цикл и пишет `par(x) = root` с меткой `t_A`, а реплика B чинит тот же цикл и пишет то же самое с меткой `t_B`, то возникают две конкурирующие легитимные записи. Они распространяются, участвуют в следующих слияниях и порождают новые конфликты. Детерминированный ремонт превращается в источник расхождения.

Доказательство сходимости при ремонте-как-проекции занимает одну строку: `S` сходится по свойству полурешётки, `R` — функция, следовательно `R(S)` сходится. Ни одного нового рассуждения не требуется. Это и есть причина выбора данного варианта.

Цикл остаётся в хранилище неограниченно долго, и это допустимо: отображаемый вид стабилен, а первое же реальное перемещение пользователя даёт свежую метку, перекрывающую конфликт естественным образом.

**Цена решения.** Пользователь иногда видит, что папка оказалась в корне вместо ожидаемого места. Намерение пользователя не сохраняется полностью (в отличие от журнала операций). Расхождения между репликами при этом не возникает.

### 5.4 Структурная теорема

Поскольку `par` тотальна, состояние есть функциональный граф. Такой граф имеет жёсткую форму: **каждая компонента связности содержит ровно один цикл, на котором висят деревья.**

Доказательство. Из любой вершины идём по `par`; множество конечно, значит траектория зацикливается или упирается в `⊥`. Из единственности исходящего ребра следует, что цикл в компоненте не более одного.

Три следствия, снимающих целый класс тревог:

1. Циклы **вершинно-непересекающиеся**. Одного прохода достаточно, чтобы найти все.
2. Разрыв одного цикла не может породить другой. Ремонт **минимален по построению**, задачи оптимизации нет.
3. Число ремонтов = число нецикловых компонент. Измеримая величина, пригодна как метрика здоровья репликации.

### 5.5 Определение `R`

Три шага в фиксированном порядке. **Порядок шагов — часть определения детерминизма, а не деталь реализации.**

**Шаг 1. Разрыв циклов.** Обход с покраской, `Θ(n)`.

```
color[n] ∈ {white, gray, black}, изначально white
pos = Map<NodeId, int>                            // позиция узла в текущем path

для каждого n с color[n] = white:
    path = []; pos.clear(); cur = n
    пока cur ≠ ⊥ и color[cur] = white:
        pos.set(cur, path.length)
        color[cur] = gray
        path.push(cur)
        cur = par[cur]
    если cur ≠ ⊥ и color[cur] = gray:            // наткнулись на собственный путь
        cycle = path.slice(pos.get(cur))          // O(1) поиск начала цикла
        break_edge( argmin_{x ∈ cycle} t(par[x]) )
    для всех m ∈ path: color[m] = black
```

Таблица `pos` не декоративна. Наивное `path.indexOf(cur)` — линейный поиск по `path`, длина которого во входном состоянии не ограничена ничем (§2.4) и может достигать `Θ(n)`; общая стоимость поднялась бы до `Θ(n²)`. С таблицей позиций каждая вершина красится в серый ровно один раз и в чёрный ровно один раз, а `argmin` суммарно пробегает по вершинно-непересекающимся циклам, то есть не более `n` элементов за весь проход. Итог — `Θ(n)` без скрытых констант и без амортизации.

**Критерий разрыва: ребро с МИНИМАЛЬНОЙ меткой в цикле.** Узел, чьё ребро разорвано, отображается в корне.

Обоснование критерия. Весь остальной модуль работает по LWW, то есть «последняя запись побеждает». Разрыв максимального ребра отменял бы более позднюю операцию, то есть вводил бы для перемещений правило «последний проигрывает». Смешение двух противоположных правил в одном модуле — источник неотлаживаемого поведения. Единственность минимума гарантирована инвариантом L-TOTAL.

**Шаг 2. Сироты.** Проверка достижимости из корня после шага 1. Недостижимое (дети очищенных узлов, отвалившиеся поддеревья) детерминированно перевешивается в системный узел `lost+found`.

**Шаг 3. Коллизии имён.** Внутри каждого слоя `par⁻¹(d)` конфликтующие узлы сортируются по `(t, id)` — тотальный порядок — и всем, кроме первого, приписывается различающий суффикс. **Суффикс существует только в проекции и не пишется в состояние.**

Шаг 1 обязан быть первым: обход по циклическому графу на шагах 2–3 без предварительной очистки не завершается.

### 5.5.1 Порядконезависимость `R`

Внешний цикл перебирает вершины в порядке итерации хеш-таблицы, и этот порядок между репликами различается. Если бы результат от него зависел, сходимость сломалась бы **молча**: без исключений, без падения тестов на малых данных, с расхождением, проявляющимся только на больших состояниях у реальных пользователей. Поэтому утверждение доказывается, а не подразумевается.

**Утверждение.** Выход `R` не зависит от порядка обхода во внешнем цикле.

**Доказательство.** *Шаг 1.* По структурной теореме (§5.4) множество циклов графа `par` определено самим графом и вершинно-непересекающееся; любой восходящий путь, входящий в компоненту, упирается в её единственный цикл, поэтому каждый цикл обнаруживается ровно один раз независимо от точки входа. Разрываемое ребро выбирается как `argmin` по строгому тотальному порядку меток (`L-TOTAL`), то есть определяется множеством рёбер цикла, а не порядком их посещения. Следовательно множество разорванных рёбер есть функция от графа. *Шаг 2.* Множество недостижимых вершин — свойство графа; все они получают одного и того же родителя. *Шаг 3.* Сортировка по `(t, id)` — тотальный порядок, результат единствен. ∎

Доказательство опирается на `L-TOTAL` в шагах 1 и 3. Это ещё одна причина считать `L-TOTAL` не деталью реализации меток, а несущим инвариантом всей модели.

### 5.6 Корзина как обычная папка

`deleted` **не** делается LWW-булевым полем. Такое поле порождает гонки воскрешения и требует отдельной логики восстановления.

Вместо этого:

- «Удалить» = `move(n, /trash)` — уже доказанная операция с уже проверенными предусловиями.
- «Восстановить» = `move(n, d)` обратно.
- Настоящее надгробие `purged` ставится только при очистке корзины. Флаг монотонен (`false → true`, обратно нельзя), то есть тривиальная полурешётка, сливается без конфликтов, воскрешение невозможно.

Два механизма схлопнулись в один, при этом UX стал богаче.

### 5.7 Форма данных

```
Node = {
  id     : NodeId,               // неизменяемо
  kind   : 'dir' | 'file',       // неизменяемо
  blob   : Digest | null,        // неизменяемо для файла
  par    : LWW<NodeId | ⊥>,
  name   : LWW<string>,
  purged : MonotonicFlag
}
```

Каждое поле, объявленное неизменяемым, — это класс случаев слияния, который не нужно доказывать и не нужно тестировать. Неизменяемость `kind` и `blob` означает, что файл не может стать папкой, а конкурирующие слияния не могут подменить содержимое.

## 6. Доступ

### 6.1 Решётка прав

```
none ⊏ read ⊏ write ⊏ own
```

Цепь, то есть вырожденная решётка. Грант — тройка `(u, n, p)`.

### 6.2 Развилка семантики — принято аддитивное наследование

**Аддитивная семантика (принята):** `eff(u, n) = ⊔ { p(u, m) : m ⪰ n }` — супремум по цепи предков, существующей по §2.2. Функция монотонна и принимает значения в полурешётке, следовательно коммутирует со слиянием CRDT. Сходимость эффективных прав — бесплатное следствие.

**Семантика переопределения (отклонена):** «ближайший предок с явным грантом выигрывает», позволяет отзывать доступ к подпапке внутри расшаренной папки. **Не монотонна**, несовместима с наивным слиянием: две реплики могут разойтись в эффективных правах. Потребовала бы оформления отзыва как отдельной операции в тотальном порядке.

Аддитивная семантика беднее по выразительности, но её корректность доказывается в две строки.

**Третий аргумент, обнаруженный при анализе стоимости.** Из монотонности следует рекуррентность

```
eff(child) = eff(par(child)) ⊔ localGrant(child)
```

то есть при листинге папки достаточно вычислить `eff` для самой папки один раз подъёмом по цепи предков, а права `k` детей получить одним объединением каждое: `Θ(D + k)` вместо `Θ(k·D)`. Права проверяются для каждого отрисованного элемента, то есть это одна из самых частых операций модуля.

При семантике переопределения такой свёртки не существует — каждому узлу требовался бы собственный подъём по цепи. Решение, принятое ради сходимости, оказалось верным и алгоритмически. Совпадение такого рода обычно означает, что модель выбрана правильно.

### 6.3 Утечка при перемещении — свойство модели, а не баг

Право наследуется по цепи предков. Операция `move` меняет цепь предков. Следовательно:

**Инвариант «множество субъектов, имеющих доступ, не меняется при `move`» НЕ выполняется.**

Перемещение приватного файла в расшаренную папку молча раздаёт его контактам. Это не устраняется на уровне модели. Единственное решение — смена видимости должна быть явным событием UI с подтверждением. Требование фиксируется здесь, чтобы не потеряться при проектировании экрана.

### 6.4 Комбинаторика ключей

NIP-44 — попарное шифрование. Наивный шаринг `m` файлов `k` контактам даёт `m·k` шифротекстов.

Правильная схема: один симметричный ключ на расшаренное поддерево, `k` попарных обёрток этого ключа, файлы шифруются им однократно. Итого `m + k` вместо `m·k`.

Отзыв доступа: ротация ключа поддерева и `k−1` новых обёрток.

**Жёсткий инвариант, не устранимый математически: отзыв не отзывает уже скачанное.** Ротация защищает только будущие версии. Формулировка должна присутствовать в UI, а не только в проектной документации.

### 6.5 Частичная видимость — нерешённая задача модели

Всё предыдущее рассуждение о сходимости неявно предполагает, что все реплики наблюдают **одно и то же состояние `S`**. При шаринге это неверно: получатель видит только расшаренное поддерево. Его локальное состояние — проекция `S` на подмножество узлов, а его `R` работает над лесом с виртуальным корнем, а не над полным деревом.

Два следствия, ни одно из которых первая редакция документа не рассматривала.

**Выход за границу видимости.** Узел, перемещённый из расшаренного поддерева наружу, у получателя выглядит как исчезновение без объяснения — неотличимо от удаления. Требуется явный маркер пересечения границы шаринга, иначе получатель сохранит у себя фантомный узел либо ошибочно интерпретирует перемещение как удаление. Симметрично: множество получателей операции `move` определяется объединением расшаренных предков **старого и нового** родителя; отправка только новым получателям оставляет призраки у старых. Это та же утечка, что в §6.3, но со стороны маршрутизации, а не доступа — оба следствия проистекают из одного свойства модели и обрабатываться должны в одном месте.

**Ремонт над частичным состоянием.** Цикл, часть которого лежит вне видимого поддерева, получателю не виден целиком. Его `R` даст результат, отличный от результата у владельца. **Сходимость проекций для наблюдателей с разной видимостью не доказана и не сформулирована.**

*Статус: открытая задача.* Для v0.1 закрывается ограничением — **расшаривается только поддерево целиком, а перемещение через границу шаринга оформляется как отдельное событие**, а не как обычный `move`. Ограничение фиксируется явно, чтобы не всплыть впоследствии как баг.

## 7. Интеграция с профилем и чатами

Пикер — фильтр-предикат `p : N → {0,1}` и частичная функция выбора. Композиция фильтров — пересечение предикатов. Математически тривиально.

Нетривиально другое требование:

**Вложение в чат и аватар профиля передают `Digest` блоба, а не копию байтов.**

При копировании байтов один файл, отправленный трём контактам, породил бы четыре независимых блоба; дедупликация сломалась бы, а семантика вложений разошлась бы с семантикой шаринга. Ссылка на блоб сохраняет обе.

### 7.1 Отмена

Требование «всё как обычно» подразумевает `Ctrl+Z`. Раздел отсутствовал в первой редакции, при этом почти бесплатен.

При LWW отмена выражается как **обратная операция с новой меткой**, а не как откат состояния. Обратная к `move(n, a→b)` — это `move(n, b→a)`. Обратная к `rename` — прежнее имя. Обратная к `delete` — извлечение из корзины, то есть снова `move` (ещё одно следствие решения №4: корзина как обычная папка сократила и этот механизм). Стек отмены — массив обратных операций в памяти, не реплицируется.

Групповое действие кладётся в стек одной записью и разворачивается в `p` операций.

**Почему нельзя через версии состояния.** Соблазнительный вариант — хранить снимки и «отменять» переходом к предыдущему. В распределённой системе это неверно: между действием и отменой могло прийти слияние, и возврат к снимку отбросил бы чужие изменения. Отмена обязана быть операцией.

**Честное ограничение.** Отмена корректна как операция, но не гарантирует возврата к прежнему виду, если пришедшее слияние затронуло тот же узел: она не откатывает время, а подаёт более позднюю запись. Отсюда практическое следствие — стек ограничивается по глубине и по времени, операции старше нескольких минут к отмене не предлагаются. Иначе пользователь получит «отмену», молча перезаписывающую чужое свежее изменение.

## 8. Загрузчик по ссылке (вне периметра v0.1)

Раздел сохранён для полноты и для будущего возврата к теме.

**Формализуемая часть.** Множество распознаваемых URL каждого сервиса — регулярный язык, распознаватель — ДКА. Объединение регулярных языков регулярно, следовательно добавление нового сервиса есть композиция автоматов без переписывания диспетчера. Задание — автомат `queued → resolving → downloading → muxing → done | failed`. Ограничение частоты — token bucket, экспоненциальный backoff при отказах.

**Неформализуемая часть.** Cloudflare-челлендж и антибот-защиты не решаются математикой. Варианты: headless-браузер с cookie-jar либо ручное подтверждение пользователем. Проектировать следует как «иногда не работает», а не как задачу с решением.

**Причина выноса за периметр.** Реализация опирается на внешний бинарь (`yt-dlp` + ffmpeg), который не запускается в браузере принципиально: нет процессов, нет сети вне CORS, нет файловой системы. Это первый настоящий потребитель слоя `platform/`, которого в проекте пока нет. Дополнительно — риск для дистрибуции и для формулировок грантовой заявки.

## 9. Инварианты и стратегия тестирования

### 9.1 Список инвариантов

| Код | Формулировка | Где проверяется |
|---|---|---|
| I-ACYCLIC | выход `R` ацикличен | постусловие `R` |
| I-REACHABLE | каждый живой узел достижим из корня или `lost+found` | постусловие `R` |
| I-UNIQUE-NAME | имена уникальны в пределах слоя | постусловие `R` |
| L-TOTAL | порядок меток строгий тотальный | инвариант типа метки |
| I-IDEMPOTENT | `S ⊔ S = S` | property-тест |
| I-CONVERGE | `R(merge π₁) = R(merge π₂)` для любых перестановок | property-тест |
| I-STABLE | `R(R(S))` даёт то же дерево | property-тест |
| I-DIGEST | прочитанный блоб соответствует своему дайджесту | тест хранилища |
| I-MONOTONE-PERM | `eff` монотонна по цепи предков | property-тест |
| I-GC | после сборки мусора нет недостижимых блобов | тест хранилища |
| I-COPY-O1 | копирование папки не зависит от объёма данных | бенчмарк |
| I-ORDER-FREE | выход `R` не зависит от порядка внешнего обхода | доказано в §5.5.1 + property-тест |
| I-CHUNK-INDEP | каждый чанк расшифровывается независимо от остальных | тест крипто-слоя |
| I-BLOB-AGE | блоб не собирается, пока его возраст меньше `T` | тест GC |

**Инварианты производительности.** Нарушаются так же тихо, как инварианты корректности, и так же не видны на тестовых объёмах — поэтому вынесены в тот же список, а не в комментарии.

| Код | Формулировка | Где проверяется |
|---|---|---|
| I-BATCH | массовая операция и пачка слияния выполняются с однократным пересчётом `R`, а не с пересчётом на элемент | бенчмарк, счётчик вызовов `R` |
| I-NO-QUADRATIC | стоимость вставки `p` узлов в одну папку линейна по `p` | бенчмарк при `p = 10³` |
| I-R-BUDGET | полный `R` укладывается в бюджет кадра при проектном `n` | бенчмарк при `n = 10³, 10⁴, 10⁵` |
| I-MAIN-THREAD | ни одна операция не блокирует главный поток дольше установленного порога | профилирование |

Порог для `I-R-BUDGET` и `I-MAIN-THREAD` не выбирается умозрительно: он ставится по результатам замеров на целевой машине. Инфраструктура в проекте есть — `bench/`, `scripts/*-bench.mjs`.

### 9.2 Property-based, а не unit

Ключевое: баги репликации возникают на конкретных перестановках доставки, которые не угадываются вручную. Требуется генератор.

**Генератор.** Случайная последовательность операций, распределённая между `k` репликами; доставка в случайном порядке, с дублями и с задержками.

**Основное свойство** — I-CONVERGE, включая повторную доставку тех же операций.

Место в проекте: `tests/tree-crdt.test.js`, в той же технике, что существующие `lww.test.js`, `lamport.test.js`, `g-set.test.js`.

| 8 | GC по достижимости | счётчики ссылок | счётчики некорректны при слиянии реплик |
| 9 | Загрузчик — вне v0.1 | включить в v0.1 | требует `platform/`, невозможен в PWA |

## 12. Открытые вопросы

1. **Сходимость при частичной видимости** (§6.5). Единственный содержательный пробел самой модели, а не реализации. В v0.1 обойдён ограничением, но не решён.
2. **Ленивая загрузка состояния.** При `n > 10⁵` держать всё в памяти нельзя, а `R` определена над полным состоянием. Как считать ремонт над частично загруженным деревом — не проработано. Потолок масштаба, не блокер v0.1.
3. **Показывать ли пользователю факт ремонта.** «Папка всплыла в корень» без объяснения читается как потеря данных. Флаг «перемещено из-за конфликта синхронизации» вычислим внутри `R` бесплатно. Решение отложено; принять до вёрстки экрана, не после.
4. **Границы `lost+found`.** Отдельный системный узел или подпапка корзины. Влияет на набор корней GC.
5. **Политика квот.** Ограничение объёма на пользователя и на расшаренное поддерево не формализовано.
6. **Схема событий Nostr.** Отображение операций на кинды — отдельный этап, к математическим основаниям не относится.
