## Уроки предыдущих этапов — как работать дальше

**Воркер (qwen2.5-coder:7b) — паттерны брака, не удивляться заново:**
- Крупные JSX-экраны со связанным состоянием между шагами/вкладками
  (auth-подобная логика) воркер регулярно ломает на 2-й-3-й правке —
  такие файлы писать/дорабатывать напрямую с самого начала (прецеденты:
  `onboarding.jsx`, `unlock.jsx`, `profile.jsx`, `docs/verify.md`).
  Признак "такой файл": ошибка в нём стирает пользовательский шаг
  (пропуск экрана подтверждения) или роняет секрет не туда.
- Частые классы брака: неверные относительные пути импорта (проверять
  руками, не доверять на слово); при большом `--ctx` — обрезание ответа
  на середине файла (лимит токенов у 7B-модели) — держать `--ctx`
  минимальным, для доработок слать фрагмент, не весь файл; на
  тривиальных полностью специфицированных микрозапросах иногда
  возвращает нерелевантный мусор — тогда просто применить готовый код
  напрямую, а не повторять вызов в надежде на удачу; точечная правка
  соседней (незатронутой) строки — воркер иногда меняет форматирование
  рядом, не только целевой фрагмент — сверять диффом весь файл, не
  только то, что просили.
- Два брака подряд на переписывание ЦЕЛОГО файла → не третья попытка
  того же; либо просить только фрагмент без `--ctx`, либо писать
  вручную (лимит из п.9 skill включает этот выбор явно).

**TECH.md — устаревшие детали окружения (факт, не решение, не гадать —
сверять с фактически установленной версией пакета):**
- `@noble/hashes` (2.2.0 в проекте): пути импорта требуют `.js`
  (`hmac.js`, `sha2.js` вместо `sha256`, `utils.js`, `hkdf.js`).
- `@scure/bip39`: wordlist требует `.js` (`wordlists/english.js`).
- Не проверено ещё для `@scure/bip32`, `ts-mls`, `comlink` — при первом
  использовании каждого сверить фактические пути экспорта до контракта,
  не полагаться на код-сниппеты TECH.md §16 буквально.

**Вёрстка (`minimal.css`):**
- `<label>Текст<input/></label>` (оборачивающий) НЕ подпадает под
  `label:not(:has(input,select,textarea))` — только раздельные
  `label[for]` + `input[id]`. Уже стандарт для всех форм проекта.
- Автотесты не ловят такие несоответствия стилей — обязательна
  визуальная/скриншот-проверка (Playwright) для каждого нового экрана,
  не только функциональная.
- `role="tab"` переопределяет неявную ARIA-роль `button` — селекторы
  `getByRole("tab", …)`, не `"button"`, для элементов с явной ARIA-ролью.

**Тестирование:**
- `localStorage` и вообще DOM API недоступны в чистом `node --test` —
  разделять функции на чистые (юнит-тесты) и DOM-зависимые (только
  интеграционно, Playwright). Шаблон уже есть — `src/ui/signals/auth.js`.
- `document.body.innerText` НЕ отражает текущее значение
  `<textarea>`/контролируемого `<input>` (только исходное DOM-содержимое)
  — для живого значения `locator.inputValue()`.
- Адверсарная фаза (п.19 skill) систематически находит реальные баги,
  не формальность для галочки — минимум 6 реальных находок именно на
  ней за первые 12 этапов (Symbol-кэш `verifyEvent`, `$`-паттерны в
  `replaceAll`, `since=0` falsy-баг, race в `g-set`, преждевременный
  `login()` до done-экрана, отсутствие лимита размера файла аватара).
  Не сокращать этот шаг ради скорости.

**Важная находка при переработке плана:** бюджет TECH.md §7.2
(~190–250 КБ итого, запас 30–90 КБ) посчитан ДО решения профиля B
добавить MLS — `ts-mls` сам по себе **65 КБ** (TECH.md §13.1, измерение

30–90 КБ "запаса" (та цифра сама по себе была нижней и верхней
оценкой без MLS). Это факт из документа, требующий пересмотра, не
пробел решения — TECH.md §7.2 просто не обновили при ревизии 6.0.

внимательно; если к этапу транспорта (16) запас будет заметно
проседать — эскалировать пользователю до, а не после, этапов 8 (MVP).
