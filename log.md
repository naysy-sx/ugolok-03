## Этап 9. Подпись + NIP-44 + NIP-59

Пользователь дал мета-инструкцию: TECH.md реализуется впервые, возможны расхождения с реальностью — применять инженерное/математическое суждение и здравый смысл, не гадать, спрашивать при нехватке данных. **Эмпирическая проверка вместо веры в документ.** Склонирован

прецеденту §16.1-16.4 (не векторы, а базовая работоспособность
интеграции при каждом обычном прогоне).

**Пробел в TECH.md, закрыт по первоисточнику NIP-EE (WebSearch/WebFetch
github.com/nostr-protocol/nips/blob/master/EE.md), не угадан:**
TECH.md называет только kind 445; реально нужны ещё три (443
KeyPackage, 444 Welcome — без подписи, gift-wrap NIP-59, 10051 список
relay) — добавлены в `kinds.js`, проверено на пересечение с уже
занятыми (30050-30072 и стандартные) — свободны. Также обнаружено и
подтверждено: подписывающий MLS-ключ участника ОБЯЗАН отличаться от
Nostr-идентичности — не архитектурное решение проекта, а математическое
ограничение (secp256k1/schnorr не входит ни в один ciphersuite MLS);
`generateKeyPackage` генерирует Ed25519-пару сама.

**Решение: ciphersuite** `MLS_128_DHKEMX25519_AES128GCM_SHA256_Ed25519`
— единственный вариант без ДОПОЛНИТЕЛЬНЫХ npm-зависимостей (бюджет и
так плотный), базовый аудированный набор, без post-quantum (модель
угроз TECH.md §1.6 не называет quantum-adversary).

**Находка: `ts-mls` не даёт продакшен-пригодной `authService`.**
Единственный публичный экспорт — `unsafeTestingAuthenticationService`,
безусловно возвращает `true` (проверено чтением исходника). Настоящая
проверка Nostr-подписи физически не может быть завершена внутри
`ts-mls` (нет доступа к внешнему событию) — задокументировано как

`kinds.js` — воркер, 4 константы, зелёный с первого раза.

## Довесок: адверсарная проверка экрана профиля (по запросу пользователя после этапа 15)

По следам находки этапа 15 (скрытый баг session-reset обнаружен именно
через углублённое browser-driven тестирование) — прогнана та же
дисциплина на `profile.jsx` (этап 12, довесок), где раньше проверялся
только happy path + отклонение плохого файла. Три сценария, выбранные
как наиболее вероятные источники скрытых багов для async-компонента с
мультиаккаунтом:

1. **Изоляция между аккаунтами.** Алиса задаёт аватар+био → релоад →
   "Другой способ входа" → регистрация Боба → Боб видит СВОИ (пустые)
   данные, не Алисины. Возврат к Алисе → её данные не повреждены
   визитом Боба.
2. **Гонка при быстрой смене аватара.** Файл A, сразу файл B (без
   ожидания завершения первого) → релоад (чтение РЕАЛЬНО
   персистированного значения из IndexedDB, не оптимистичного UI-
   состояния) → сохранился именно последний выбранный файл.
3. **Уход со страницы до завершения сохранения.** Клик "Сохранить" →
   немедленный переход на другую вкладку (реальный unmount компонента
   с pending-промисом) → данные всё равно корректно сохранились.

Все три сценария прошли чисто, консоль браузера чистая на всём
прогоне — багов не найдено. `getProfile`/`updateProfile` (этап 12,
довесок) и React/Preact эффект с зависимостью `[id]` в `profile.jsx`
корректно изолируют аккаунты и переживают unmount с pending-записью.
Скрипт — `check-profile-adversarial.mjs` (scratchpad, не входит в
постоянный `npm test` — разовая адверсарная проверка по прецеденту
этапа 15, не регрессионный тест).

сам по себе не принуждает к AUTH, принуждение — задача
`writePolicy.plugin` (пока пуст, реальный whitelist — этап 17).
Зафиксировано как важный входной факт для дизайна автомата соединения
на этапе 16 (ветка "challenge не пришёл" должна быть штатной, не
крайним случаем).

## Этап 16: Relay pool + pluggable транспорт

Формализация — DESIGN.md, раздел "Этап 16". Контракты — CONTRACTS.md,
тот же раздел.

**Главная находка этапа — правка контракта TECH.md §9.3, не
буквальная реализация.** Автомат `connecting+OPEN→authenticating`
безусловно + `authenticating+TIMEOUT→disconnected` — при буквальной
реализации давал бы бесконечный цикл отказов против УЖЕ ПОДНЯТОГО
тестового relay проекта (strfry не шлёт AUTH-challenge проактивно
никогда — подтверждено чтением исходников: `sendAuthChallenge()` имеет
ровно один call site, срабатывает только на попытку опубликовать
NIP-70 "protected event"). Сверено с официальной спецификацией NIP-42
(WebFetch, не только с одной реализацией): "At any moment the relay
may send an AUTH message" — протокол СОЗНАТЕЛЬНО не требует challenge
сразу после открытия, таймаут ожидания протоколом не определён вовсе.
Решение: `OPEN` ведёт сразу в `connected`; `authenticating` —
временное реактивное состояние (вход по `AUTH_CHALLENGE` из
`connected` ИЛИ `subscribed`, в любой момент), из которого ВСЕ три
исхода (`AUTH_OK`/`AUTH_FAIL`/`TIMEOUT`) возвращают в `connected`, не
в `disconnected` — провал/отсутствие аутентификации не обязан рвать
всё соединение целиком, это отдельная app-level политика (этап 17).

`transport.js` — тривиальная функция (round-robin по списку
endpoint), воркер дал явный мусор на полностью специфицированный
запрос (сгенерировал файл, ИМПОРТИРУЮЩИЙ САМ СЕБЯ вместо определения
функции) — применено готовое решение напрямую, повторный вызов не
делался (та же практика, что уже не раз в проекте).

`relay-pool.js` — написан напрямую (не через воркера): стыковка
`machine.js` (этап 14) с реальными WS-событиями и таймером
реконнекта — цена ошибки высокая (некорректный реконнект = либо
DDoS собственного relay частыми попытками, либо зависшее приложение).
Тесты — с инжектируемым `WebSocketImpl` (фейковый класс в тесте,
имитирует `onopen`/`onclose`/`onerror`/`send`) и встроенными
mock-таймерами `node:test` (`t.mock.timers`) — детерминированные,
без сети, без реального relay в `npm test`.

**Живая проверка против реального strfry (не только фейковый WS —
именно ради этого поднимали relay в предыдущем шаге):** `connect()`
→ `connecting` → `connected` НАПРЯМУЮ (не зависает в `authenticating`
— подтверждает исправление автомата на практике, не только в тесте);
`send(['EVENT', ...])` реального подписанного события → реальный
`OK ... true` от живого relay; `close()` — асинхронно (как и настоящий
WebSocket), `onStateChange` корректно даёт `connected → disconnected`
после завершения закрытия сокета (не синхронно — не баг, особенность
async WS API, проверено явно, чтобы не спутать с реальной ошибкой).

Регрессия: `npm test` (169/169, было 152), `npm run build` (124.56 КБ
gzip, без изменений — `relay-pool.js`/`transport.js` вне app-графа,
реальный потребитель — publisher/subscriber и bootstrap, этапы 18-19).
Адверсарная фаза: повторный `connect()` на уже подключённом
соединении бросает (F2 из этапа 14 — недопустимый переход, не тихий
no-op); `send()` бросает вне `connected`/`subscribed`; намеренный
`close()` не планирует реконнект даже после полного backoff-окна;
неожиданный обрыв планирует реконнект ТОЛЬКО после задержки, не
немедленно.

## Правка после этапа 20: живая UX-обратная связь по diagnostics.jsx

Пользователь визуально осмотрел страницу диагностики в браузере и указал
4 конкретные проблемы (не новый этап PLAN.md — доводка уже принятого).

1. **P-SPIKE выглядит зависшим первые секунды.** Причина: `usePSpikeBenchmark.run()`
   вызывал `setStatus(...)`, затем СРАЗУ `generateSyntheticEvents(5000)` —
   функция помечена `async`, но внутри циклов ни разу не `await`-ит ничего
   промис-подобного (`sign`/`nip44Encrypt`/`nip59Wrap` синхронны), поэтому весь
   generation-проход выполняется одним синхронным блоком (~7-18с) и браузер
   физически не успевает перерисовать уже выставленный статус до его начала.
   Фикс: `await new Promise(r => setTimeout(r, 0))` сразу после `setStatus`
   (гарантирует прорисовку до тяжёлой работы) + периодический `yieldToMain()`
   каждые 250 итераций внутри всех 4 циклов `generateSyntheticEvents`
   (`synthetic-fixtures.js`) — вкладка не виснет на всю длительность генерации,
   не только в начале. Замеряемая фаза P-SPIKE не затронута (генерация в неё
   не входит по контракту, `t0` ставится после).
2. **Кнопка transport-check таймаутит на "disconnected" без запущенного relay.**
   Пользователь: `npm run dev` должен сам поднимать живой relay. Добавлен
   `devRelayPlugin()` в `vite.config.js` (`apply: "serve"`) — на
   `configureServer` создаёт `strfry-db/` при отсутствии, спавнит
   `server/strfry/run.sh`, пробрасывает его stdout/stderr в терминал vite с
   префиксом `[strfry]`, убивает процесс при закрытии dev-сервера. Если
   strfry не собран — warn и no-op, dev-сервер не падает. Заодно
   `BUILD_DEFAULT_RELAYS` в dev-режиме (без явного env override) переключён
   с продакшн-плейсхолдера `wss://relay.example` на `ws://127.0.0.1:7777` —
   раньше header диагностики и сам self-check били в несуществующий

## Этап 24: Личные сообщения — ядро

Триаж (п.13a): **алгоритмическая**, по трём причинам — ДКА сообщения
(§9.1, PLAN.md прямо требует), оркестровка MLS-сессии (createGroup/
addMember/Welcome/kind 445 — самая рискованная часть проекта, DESIGN.md
этапа 13), протокол запроса на добавление контакта (дополнение
пользователя после реального использования этапа 23).

**Исследование перед кодом (не гадание)**: реальный NIP-EE (WebFetch,
github.com/nostr-protocol/nips/blob/master/EE.md) подтвердил то, что
DESIGN.md этапа 13 уже нашло: kind 444 (Welcome) ВСЕГДА gift-wrapped
через NIP-59, kind 445 (Group Message) публикуется НАПРЯМУЮ с
эфемерным одноразовым ключом на каждое событие. Прочитаны исходники
`ts-mls` (`clientState.d.ts`) — подтверждено, что `createGroup`/
`joinGroup` возвращают `ClientState` НАПРЯМУЮ (не `{newState:...}`, в
отличие от `createCommit`/`createApplicationMessage`/`processMessage`).
NIP-EE не даёт готового рецепта старта 1:1-разговора — последовательность
(KeyPackage → createGroup+addMember → Welcome, commitWireBytes
отброшен за ненадобностью для новой 2-местной группы) — решение этого
этапа, зафиксировано явно, не выведено из протокола домыслом.

**Ключевое архитектурное решение**: `groupId` для 1:1-чата вычисляется
ДЕТЕРМИНИРОВАННО как `SHA-256(sorted([pubkeyA, pubkeyB]).join(":"))` —
обе стороны получают одно и то же значение независимо, без отдельной
"chatId→groupId" таблицы-маппинга. `chatId` в БД — pubkey контакта
(человеко-осмысленный, matches `openChat(pubkey)` этапа 23), не
groupId. MVP-упрощение (явное, не молчаливое): один Nostr-identity =
одно устройство = один MLS-leaf — полная модель "owner + device-members"
(TECH.md §4.9/SM-3) уже отложена этапом 13, здесь та же граница;
1:1-группа строго двухместная, отправитель сообщения всегда однозначен
без обращения к MLS-credential.

Реализация: `machine.js`/`requests.js` — воркер, оба с первого раза
(кроме забытого `export` у константы в `requests.js` — точечная
правка). `chat.js` (MLS-оркестрация) — написан напрямую. Диспетчер
входящих gift-wrap + подписка на kind 445 в `transport.js` — тоже
напрямую (session-critical, тот же класс кода, что и остальной
`transport.js`).

**Четыре реальных бага найдены и исправлены тестами/живой проверкой,
не гаданием**:
1. `nip44Encrypt`/`nip44Decrypt` ожидают HEX-строку получателя,
   `deriveNostrEnvelopeKeys` (этап 13) возвращает `publicKey` сырыми
   байтами — несовпадение форматов, поймано первым же тестом round-trip.
2. `db.table("mlsGroups").put(...)` перезаписывает ВСЮ строку — два
   места (`sendMessage`, `receiveGroupMessageEvent`) теряли
   `contactPubkey` при обновлении состояния после каждого сообщения.
   Поймано отдельным регресс-тестом, написанным именно против этого
   класса бага (Dexie `put` — не partial update).
3. Собственный баг теста (не реализации): тест изначально писал
   состояние Алисы и Боба в одну и ту же строку `mlsGroups` (общий
   `groupId`, единая тестовая БД) — в реальности у каждого своя база;
   переписан на явную симуляцию "чьё сейчас устройство" (`asBob`
   helper). Проявлялось как криптографическая ошибка ts-mls ("Desired
   gen in the past"), не как логическая — заняло отдельное расследование.
4. **Найдено только живой проверкой через настоящий relay** (не
