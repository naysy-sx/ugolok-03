# Push Probe — зонд для П0.4/П0.6 (Э-PUSH)

Минимальное Android-приложение, НЕ часть Уголка. Единственная цель — измерить, как реально ведёт себя foreground-service с постоянным сетевым соединением на конкретном телефоне владельца в разных состояниях (Doze, свайп из списка задач, перезагрузка и т.д.), прежде чем строить на этом поведении push-архитектуру Уголка. См. `PROCESS-DOCS/NATIVE-APPS/TZ-PUSH-ANDROID.md` (П0.4, П0.6) и `PROCESS-DOCS/NATIVE/PUSH-E0-REPORT.md`.

## Что делает

Держит открытым live-поток `https://ntfy.sh/<топик>/sse` (публичный ntfy — свой сервер ещё не поднят, это не тест нашей инфраструктуры, а тест поведения ОС Android) через foreground-service типа `connectedDevice` (решение П0.5). На каждое пришедшее сообщение:
- показывает уведомление;
- пишет строку в лог-файл на диске телефона с двумя метками времени: `epoch_ms` (миллисекунды устройства) и `server_time_s` (время сервера ntfy, секунды) — это и есть измеряемая задержка доставки.

Лог переживает сворачивание/перезапуск процесса — путь показан на экране приложения и в логе:
`/sdcard/Android/data/tech.ugolok.pushprobe/files/probe-log.txt`

## Сборка

```
cd native/push-probe-android
./gradlew assembleDebug
```

APK: `app/build/outputs/apk/debug/app-debug.apk`. Проверено на эмуляторе (полный цикл: старт службы → живое SSE-подключение к ntfy.sh → приём тестового сообщения → уведомление → запись в лог) — для целей самого теста П0.4 эмулятор не годится (см. `PUSH-E0-REPORT.md`), нужен реальный телефон.

## Установка на телефон

```
adb install -r app/build/outputs/apk/debug/app-debug.apk
```

Или скопировать APK на телефон и установить вручную (потребуется разрешить установку из неизвестных источников).

## Протокол теста (ТЗ, П0.4)

1. Открыть приложение, оставить топик как есть (уникальная случайная строка сгенерирована автоматически) или задать свой — записать его.
2. Нажать «Начать» (при первом запуске разрешить уведомления).
3. С другого устройства (или отсюда, с компьютера) в момент отправки зафиксировать точное время и выполнить:
   ```
   curl -d "тест <метка>" https://ntfy.sh/<топик>
   ```
4. Дождаться уведомления на телефоне / посмотреть лог — сравнить `epoch_ms` записи с временем отправки curl.
5. Повторить для каждого состояния из таблицы ТЗ, каждый раз с новой меткой в тексте сообщения, чтобы не перепутать записи в логе:

| ID | Состояние | Как воспроизвести |
|---|---|---|
| S1 | приложение открыто | оставить экран приложения открытым |
| S2 | свёрнуто 5 мин | нажать «Домой», подождать 5 минут, отправить |
| S3 | экран погашен 30 мин | заблокировать экран, подождать 30 минут, отправить |
| S4 | принудительный Doze | `adb shell dumpsys deviceidle force-idle`, отправить; повторить с телефоном, добавленным в исключения оптимизации батареи, и без |
| S5 | закрыто свайпом из списка задач | смахнуть приложение из списка недавних, отправить |
| S6 | после перезагрузки | перезагрузить телефон, **вручную открыть приложение и нажать «Начать» заново** (автозапуска после ребута в этом зонде нет — не проверяет автостарт, только базовую доставку после холодного старта; для прод-версии Уголка автозапуск через `BOOT_COMPLETED` — отдельный вопрос, у Android 15+ есть ограничения на запуск foreground-service некоторых типов из `BOOT_COMPLETED`, не входит в объём этого зонда) |
| S7 | «Принудительно остановить» в настройках приложения | ожидаемо не работает — правило Android, значение теста — подтвердить факт, а не измерить задержку |

Для выхода из принудительного Doze: `adb shell dumpsys deviceidle unforce`.

## Что передать в отчёт

После прогона всех состояний — файл `probe-log.txt` (через `adb pull /sdcard/Android/data/tech.ugolok.pushprobe/files/probe-log.txt .`) и список: в какое время какая метка отправлена curl'ом для каждого S. По этим двум спискам считается задержка доставки на состояние — из этого П0.4 и П0.6 (интервал keepalive) закрываются в `PUSH-E0-REPORT.md`.

Ворота П0 (ТЗ) требуют: S2–S4 с исключением из оптимизации батареи доставляют за ≤ 60 с. Если нет — зафиксировать цифры, не продолжать П1 без решения владельца.
