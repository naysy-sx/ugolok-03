# ЧАСТЬ A. Доставка сообщений

---

## 0. Диагноз (прочитать перед началом, не пропускать)

### RC-1 — атрибуция отправителя зашита константой

`src/domain/messaging/chat.js`, `receiveGroupMessageEvent`: каждое успешно
расшифрованное kind:445 пишется с `senderPubkey: contactPubkey` — безусловно.
С этапа 72 в MLS-группе состоят ВСЕ устройства ОБЕИХ identity. Живое 445 от
sibling-устройства владельца расшифровывается штатно и приписывается контакту.
Симптом: своё сообщение из другого браузера отображается как входящее.

Payload `sendMessage` = `{text, lamportTs, msgId, sentAt}` — отправителя в нём
НЕТ, восстановить не из чего. Публичный API ts-mls (`ProcessMessageResult`,
ветка `applicationMessage`) leaf-индекс отправителя НЕ отдаёт (проверено по
`node_modules/ts-mls/dist/src/processMessages.d.ts`; `IncomingMessageCallback`
срабатывает только на commit/proposal). Аутентифицированный отправитель из
библиотеки недоступен без её патча — см. решение T1 и ограничение L-1.

### RC-2 — дедупликация цементирует неверную строку

`upsertMessage` = `add()` + проглатывание `ConstraintError` (first-writer-wins
по `[ownerPubkey+chatId+msgId]`). Зеркало kind:446 от устройства-отправителя
несёт ПРАВИЛЬНЫЙ `senderPubkey: ownerPubkey`, но живое 445 (с неверной
атрибуцией из RC-1) почти всегда приходит раньше → правильное зеркало
становится no-op. Неверное направление сохраняется навсегда.

### RC-3 — две вкладки одного браузера = два писателя в одно MLS-состояние

`deviceId` и всё состояние — в IndexedDB, общей на профиль браузера. Две
вкладки — НЕ два устройства: один deviceId, один leaf, одна строка mlsGroups.
Межвкладочной координации в коде нет (проверено: `navigator.locks`,
`SharedWorker`, leader election — отсутствуют). Обе вкладки принимают одно
445, обе выполняют `processMessage` от одного сохранённого состояния, обе
делают `put()` → last-writer-wins, потерянная генерация ратчета, рассинхрон
envelope-ключей, каскад decrypt failures. Это отдельный дефект: T1 его НЕ
чинит, T2 обязателен.

### Побочное (фиксируется, исправление опционально)

`receiveGroupMessageEvent` зеркалирует каждое принятое сообщение → при N
sibling-устройствах O(N) дублей kind:446 на релее на каждое сообщение. БД
защищена дедупликацией, но релей замусоривается. См. T4.

### T1 — senderPubkey внутри MLS-payload + атрибуция на приёме

**T1.1 — отправка.** В `sendMessage` расширить `messagePayload`:
`{text, lamportTs, msgId, sentAt, senderPubkey: ownerPubkey}`.
Поле едет ВНУТРИ MLS-шифртекста — на проводе не видно, утечки метаданных нет.
`senderDeviceId` НЕ класть: идентичность устройства не нужна для атрибуции
направления и была бы лишним раскрытием сведений внутри группы контакту.

**T1.2 — приём.** В `receiveGroupMessageEvent` заменить константу:

```js
const senderPubkey = parsed.senderPubkey === ownerPubkey ? ownerPubkey : contactPubkey;
```

Именно нормализация к одному из двух легальных значений, НЕ сырое
`parsed.senderPubkey`: в 1:1-группе других identity нет, любое третье значение
в payload — мусор/атака и сводится к contactPubkey. Старый формат payload без
`senderPubkey` (сообщения до этого этапа, приходящие при catch-up) →
`contactPubkey` (прежнее поведение; для старых сообщений от sibling это
воспроизводит старый баг на исторических данных — принятый остаточный риск,
см. L-2).

**T1.3 — зеркало на приёме.** Тот же вычисленный `senderPubkey` передать в
`mirrorBestEffort` (сейчас там жёстко `senderPubkey: contactPubkey` — та же
ошибка вторым экземпляром).

**T1.4 — UI-инвариант.** Найти все места в UI/сигналах, где направление
определяется НЕ через `senderPubkey === ownerPubkey` (например, сравнением с
chatId или флагом «я отправил в этой сессии»), и привести к единственному
источнику истины: `row.senderPubkey === ownerPubkey` ⇔ исходящее.
Ожидаемые точки входа: `src/ui/signals/chat.js`, `message-bubble.jsx`.
Если таких мест нет — зафиксировать это утверждение в отчёте задачи явно.

**Тесты T1 (chat.test.js / новый m2-sender-attribution.test.js):**
- отправка устройством A1 (identity Алисы) → приём устройством A2 той же
  identity живым 445 → строка в messages A2 имеет `senderPubkey === alice`;
- отправка Бобом → приём A1 → `senderPubkey === bob`;
- payload старого формата (без senderPubkey) → `senderPubkey === contact`
  (обратная совместимость);
- payload с посторонним senderPubkey (не owner, не contact) →
  нормализован в contactPubkey;
- зеркало, порождённое приёмником, несёт тот же senderPubkey, что и строка.

### T2 — единственный писатель MLS-состояния (Web Locks)

**T2.1.** Новый модуль `src/core/store/mls-lock.js`:

```js
export function withGroupLock(ownerPubkey, groupIdHex, fn) {
  const name = `mls:${ownerPubkey}:${groupIdHex}`;
  if (navigator?.locks?.request) {
    return navigator.locks.request(name, fn);
  }
  return withInProcessMutex(name, fn); // fallback: карта промисов-цепочек
}
```

Fallback обязателен: тестовая среда node/jsdom и Node-скрипты не имеют
`navigator.locks`. In-process mutex — та же техника, что `drainInFlight`
(chat.js) и `handleDeviceAnnounceInFlight` (devices.js): карта
`name -> promise`, новый вызов ждёт хвост цепочки. Межвкладочную гарантию
даёт только Web Locks; fallback честно защищает лишь внутри процесса —
задокументировать в шапке модуля.

**T2.2.** Обернуть в `withGroupLock` ЦЕЛИКОМ каждую read-modify-write
последовательность над `mlsGroups` (чтение строки → криптооперация → put),
а не только put:
- `sendMessage` (chat.js),
- `receiveGroupMessageEvent` (chat.js),
- `recordGroupDecryptFailure` (chat.js),
- `addSiblingToGroup` / ветки `syncDeviceMembership` (devices.js),
- `acceptWelcome` + `ensureChatEstablished` — лочатся тоже: гонка
  «две вкладки одновременно принимают один Welcome» существует.

Захват лока — ПЕРЕД `db.table("mlsGroups").get(...)`, освобождение — после
`put`. Вложенных захватов одного имени не допускать (Web Locks не
реентерабелен — дедлок): проверить, что обёрнутые функции не вызывают друг
друга; если вызывают (drainPending → sendMessage) — лочить только внутренний
уровень (sendMessage), внешний оставить без лока.

**T2.3 — дедупликация обработки событий между вкладками.** Лок делает
конкурентную обработку БЕЗОПАСНОЙ, но обе вкладки всё ещё обработают одно
445 ПОСЛЕДОВАТЕЛЬНО — второй `processMessage` того же wire-сообщения от уже
продвинутого состояния упадёт (replay-защита MLS) и засчитается как decrypt
failure. Добавить перед обработкой проверку по журналу обработанных event.id:
таблица `processedGroupEvents` `[ownerPubkey+eventId]`, запись ПОСЛЕ успешной
обработки, внутри того же лока. Проверка `has` → тихий return null. TTL/чистка
— по прецеденту буфера недешифруемых (transport.js), чтобы таблица не росла
неограниченно.

**Тесты T2 (mls-lock.test.js + расширение chat.test.js):**
- два конкурентных `receiveGroupMessageEvent` одного события: ровно одна
  обработка, ноль decrypt failures, состояние продвинуто ровно один раз;
- конкурентные send+receive разных сообщений: оба успешны, состояние
  консистентно (следующий приём от контакта расшифровывается);
- fallback-mutex сериализует при отсутствии navigator.locks.

### T3 — ремонт уже испорченных строк

Строки с неверным `senderPubkey`, записанные до фикса, «прилипли» (RC-2).

**T3.1.** В `upsertMessage` добавить ветку коррекции: при `ConstraintError`
читать существующую строку по `[ownerPubkey+chatId+msgId]`; если новая строка
пришла ИЗ ЗЕРКАЛА (флаг-параметр `source: "mirror"`, по умолчанию
`"live"` — старые вызовы не меняются) и `senderPubkey` отличается —
перезаписать ТОЛЬКО поле senderPubkey существующей строки. Зеркало
авторитетнее для атрибуции: его пишет само устройство-отправитель под ключом,
выводимым из privKey владельца — подделать может только владелец identity.
Живой путь существующие строки НЕ корректирует (иначе форджибл-payload из T1
получил бы право переписывать историю).

**T3.2.** Вызовы `buildMirroredMessageRow` → `upsertMessage` в
`syncMirroredHistory` и `refreshLiveMirrorSubscription` (transport.js)
передают `source: "mirror"`. Тогда исторический catch-up зеркал при первом же
запуске после обновления чинит испорченные строки без отдельной миграции.

**Тесты T3:** строка с неверным senderPubkey в БД → приход зеркала с верным →
поле исправлено, остальные поля нетронуты; повторный приход того же зеркала —
no-op; live-дубликат НЕ меняет существующую строку.

### T4 — зеркало только от отправителя (опционально, отдельный коммит)

В `receiveGroupMessageEvent` НЕ зеркалировать сообщения, чей вычисленный
`senderPubkey === contactPubkey`... — СТОП, это неверно: зеркало входящих —
единственный канал доставки входящих на устройства владельца, НЕ состоящие в
группе на момент сообщения (новое устройство, catch-up). Правильная
минимизация: зеркалировать входящее должен ровно один sibling. Дешёвая
детерминированная конвенция без координации: зеркалирует то устройство, чей
deviceId лексикографически минимален среди knownDevices владельца на момент
приёма. При устаревшем списке возможны дубли (безвредны, дедуп) или пропуск
зеркала (деградация к сегодняшнему best-effort). Если оценка покажет, что
условие «минимальный deviceId» нетривиально из-за жизненного цикла
knownDevices — задачу отложить, зафиксировав решение в DESIGN.md. Не блокирует
этап.

# ЧАСТЬ B. Синхронизация профилей (аватар/био, свои и контактов)

## Диагноз

### P-1 — приём профилей контактов без LWW: побеждает последний ПРИБЫВШИЙ, не последний СОЗДАННЫЙ

Три пути записи в `profiles.value`, ни один не сравнивает `created_at`:
- `fetchProfiles` (transport.js): `results.set(event.pubkey, parsed)` в порядке
  прибытия. Комментарий «relay сам отдаёт только последнюю версию» верен для
  ОДНОГО корректного relay и ложен для пула: при нескольких relay (или
  некорректном relay) в один REQ приезжают РАЗНЫЕ версии kind:0, и старая,
  пришедшая позже, затирает новую.
- `refreshLiveProfileSubscription` onBatch: `next[event.pubkey] = parsed` —
  тот же порядок прибытия; `isNewEvent(event.id)` дедуплицирует лишь повтор
  ТОГО ЖЕ события, версии не упорядочивает. REQ-backlog при переподписке
  (добавлен контакт → resubscribe тем же subId) реиграет старые версии
  поверх новых.
- `refreshProfiles` (contacts.js): безусловная перезапись результатом
  `fetchProfiles` — наследует его слабость.

Симптом: у контакта отображается СТАРЫЙ аватар/био, «плавает» между
перезаходами в зависимости от того, какой relay ответил последним.

### P-2 — профили контактов living only in memory

`profiles = signal({})` — нигде не персистится. Каждый холодный старт —
инициалы и пустые био до завершения сетевого round-trip; медленный/недоступный
relay — деградация на всю сессию. Симптом «аватары контактов инициалами, био
не видно» — это он.

### P-3 — устаревший локальный data-url кэш затеняет новый аватар

Рендер: `avatar || avatarUrl` (sidebar-profile-card.jsx, profile.jsx), где
`avatar` — локальный data-url, записанный в keystore В МОМЕНТ ЗАГРУЗКИ ФАЙЛА
НА ЭТОМ УСТРОЙСТВЕ. `hydrateOwnProfile` обновляет ТОЛЬКО `avatarUrl` и не
инвалидирует `avatar`. Сценарий: устройство B когда-то загружало аватар
(кэш заполнен) → устройство A сменило аватар → B получает новый avatarUrl,
но рендерит свой старый data-url вечно. Симптом «био загрузилось, а аватар
висит старый» — ровно это.

### P-4 — свой kind:0 не имеет живой подписки

`hydrateOwnProfile` вызывается один раз в connect(). `live-profiles`
подписан на `authors: contactPubkeys` — СВОЙ pubkey туда не входит.
Изменение профиля на устройстве A при работающем B доезжает до B только
после перезапуска B. Симптом «синхронизировалось частично» — комбинация
P-3/P-4 с тем, в каком порядке устройства перезапускались.

## Задачи

### T5 — LWW и персист профилей контактов

**T5.1.** Кэш профилей хранит `created_at` рядом с данными:
`{ name, about, picture, createdAt }`. Все три пути записи (P-1) применяют
запись ТОЛЬКО если `incoming.created_at` строго больше хранимого `createdAt`
(при равенстве — tiebreak по event.id, использовать существующий `lwwWinner`
из core/sync/lww.js, не дублировать логику).

**T5.2.** Персист: новая таблица `contactProfiles`
`[ownerPubkey+contactPubkey] -> { name, about, picture, createdAt }`.
Шифрование строк — ПО ПРЕЦЕДЕНТУ таблицы contacts (посмотреть, encrypted ли
она через toEncryptedRow, и сделать ИДЕНТИЧНО: сами данные kind:0 публичны,
но состав графа контактов — чувствительная информация; режим защиты обязан
совпадать с contacts). При старте `profiles.value` гидрируется из таблицы ДО
любых сетевых запросов; сетевые обновления пишут и в signal, и в таблицу
(через тот же LWW-гейт T5.1).

**T5.3.** `ensureProfilesFetched` больше не кэширует `null` («не найден»)
навсегда в персисте — null остаётся ТОЛЬКО сессионным значением signal
(иначе контакт, чей relay был недоступен один раз, никогда не получит
профиль на этом устройстве).

**Тесты T5:** старое kind:0 после нового (любой из трёх путей) → не
применяется; равный created_at, больший id → применяется; холодный старт
без сети → профили из таблицы видны сразу; null-кэш не персистится.

### T6 — инвалидация локального аватар-кэша + живая подписка на свой kind:0

**T6.1.** В `hydrateOwnProfile` (и в новом живом пути T6.2): если входящий
`picture` НЕПУСТОЙ и отличается от хранимого `avatarUrl` — вместе с
`avatarUrl` очищать `avatar` (data-url кэш устарел, изображение заменено).
Пустой входящий picture локальные поля не трогает (правило этапа 57
сохраняется без изменений).

**T6.2.** Живая подписка на собственный kind:0. Вариант реализации — добавить
`ownerPubkey` в authors существующей `live-profiles` подписки и в её onBatch
ветвить: `event.pubkey === ownerPubkey` → путь hydrate (keystore, с T6.1 и
правилом этапа 57), иначе → путь контактов (T5.1). Один subscriber, не два.
Эхо собственной публикации (relay возвращает только что изданный kind:0)
обязано быть no-op — проверить, что применение идентичных значений не
дёргает лишних ре-рендеров (сравнение до записи).

**T6.3.** Правка контракта рендера НЕ требуется: `avatar || avatarUrl`
остаётся; корректность обеспечивает инвалидация T6.1. Зафиксировать это
решение комментарием у рендера (иначе следующий читатель кода «починит»
приоритет и сломает превью при загрузке).

**Тесты T6:** смена аватара на «устройстве A» (эмуляция: kind:0 с новым
picture) при непустом локальном avatar-кэше «устройства B» → кэш очищен,
рендер получает новый URL; пустой picture → локальные avatar/avatarUrl
нетронуты; эхо своей публикации → состояние не изменилось.

### T7 — устранение расхождения LWW-семантик (унификация)

`lwwWinner` уже используется в fold-путях (handlers.js, latestByDTag) —
профильные пути после T5 обязаны использовать ЕГО ЖЕ. Запрещено вводить
вторую реализацию сравнения версий. Если сигнатура не подходит (события vs
строки кэша) — адаптер в lww.js, тестируемый отдельно.

# ЧАСТЬ C. Обязательные проверки критичных мест (директивы, диагноза нет)

Каждый пункт: прочитать код → письменно зафиксировать вердикт в отчёте
(«дефект найден: …» / «дефекта нет, потому что …» с указанием строк) →
при дефекте согласовать правку контракта с оркестратором ДО кода. Пустых
вердиктов («посмотрел, вроде ок») не принимать.

**C-1. Каналы: доезжает ли на второе устройство сам ФАКТ подписки на канал.**
`refreshChannelContentSubscription` строит фильтр из локальной таблицы
`channels`. Проверить: как таблица `channels` наполняется на втором
устройстве той же identity (какой kind, какой rebuild в connect()); есть ли
живой путь (не только connect-time rebuild), когда устройство A подписалось
на новый канал при работающем B. Если live-пути нет — контент нового канала
не появится на B до перезапуска: это кандидат в «содержимое каналов не
синхронизировалось». Тест: A подписывается на канал → B без перезапуска
получает и канал в списке, и его контент.

## 2. Изменения контрактов

- `messagePayload` (внутри MLS): +`senderPubkey` (hex identity pubkey).
  Обратная совместимость на приёме обязательна (payload без поля валиден).
- `upsertMessage(row, dbKey, source = "live")` — аддитивный параметр.
- Новая таблица `processedGroupEvents` → миграция версии Dexie-схемы по
  существующему прецеденту (database.js), не редактирование старых версий.
- `withGroupLock` — новый примитив core/store; ключ лока включает
  ownerPubkey (мульти-аккаунт в одном профиле не должен сериализоваться
  межаккаунтно).
- Кэш профилей: `profiles.value[pk]` получает поле `createdAt` — проверить
  всех читателей signal на терпимость к новому полю (deepEqual-тесты).

- `hydrateOwnProfile`: аддитивное поведение (инвалидация avatar-кэша) —

## 3. Известные ограничения (внести в DESIGN.md)

- **L-1.** `senderPubkey` в payload аутентифицирован MLS лишь как «отправитель
  — участник группы». Контакт технически может пометить своё сообщение как
  ваше: оно отрисуется исходящим в ВАШЕЙ ленте. Конфиденциальность и
  подлинность членства не нарушаются; это UI-спуфинг внутри 1:1. Устраняется,
  когда ts-mls раскроет leaf-индекс отправителя application-сообщений
  (отслеживать релизы после 2.0.0-rc.14); тогда сверять с credential
  `pubkey:deviceId` листа вместо доверия payload.
- **L-2.** Исторические сообщения от sibling-устройств со старым payload при
  повторном catch-up живым путём атрибутируются по-старому (контакту);
  корректируются зеркалом через T3.
- **L-3.** Fallback-mutex не защищает от второй вкладки в средах без Web
  Locks API (все целевые браузеры и Electron его имеют; риск — только
  экзотика).

## 4. Критерии приёмки этапа

1. Матрица 2 identity × 2 устройства (4 клиента): любое сообщение отображается
   с верным направлением на всех четырёх, включая устройства отправителя.
2. Две вкладки одного профиля браузера: обмен 20+ сообщениями в обе стороны
   без decrypt failures и без роста `consecutiveDecryptFailures`.
3. Строки, испорченные до фикса, исправлены после первого catch-up зеркал.
4. Профили: матрица 2 устройства одной identity — смена аватара и био на
   любом отражается на втором БЕЗ перезапуска; старая версия kind:0,
   доставленная после новой (эмуляция второго relay), не откатывает ни свой
   профиль, ни профиль контакта; холодный старт офлайн показывает
   закэшированные профили контактов, не инициалы.
5. Часть C: по каждому пункту C-1..C-6 в отчёте письменный вердикт со
   ссылками на строки; найденные дефекты либо исправлены в этом этапе, либо
   внесены в DESIGN.md как известные ограничения с обоснованием отсрочки.
6. Полная регрессия существующих тестов зелёная; новых flaky нет (три прогона).
7. DESIGN.md дополнен разделом этапа: RC-1..RC-3, P-1..P-4, L-1..L-3,
   вердикты C-1..C-6.
