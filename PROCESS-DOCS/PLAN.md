## Уроки предыдущих этапов — как работать дальше

**Воркер (qwen2.5-coder:7b) — паттерны брака, не удивляться заново:**
- Крупные JSX-экраны со связанным состоянием между шагами/вкладками
  (auth-подобная логика) воркер регулярно ломает на 2-й-3-й правке —
  такие файлы писать/дорабатывать напрямую с самого начала (прецеденты:
  `onboarding.jsx`, `unlock.jsx`, `profile.jsx`, `docs/verify.md`).
  Признак "такой файл": ошибка в нём стирает пользовательский шаг
  (пропуск экрана подтверждения) или роняет секрет не туда.
- Частые классы брака: неверные относительные пути импорта (проверять
  руками, не доверять на слово); при большом `--ctx` — обрезание ответа
  на середине файла (лимит токенов у 7B-модели) — держать `--ctx`
  минимальным, для доработок слать фрагмент, не весь файл; на
  тривиальных полностью специфицированных микрозапросах иногда
  возвращает нерелевантный мусор — тогда просто применить готовый код
  напрямую, а не повторять вызов в надежде на удачу; точечная правка
  соседней (незатронутой) строки — воркер иногда меняет форматирование
  рядом, не только целевой фрагмент — сверять диффом весь файл, не
  только то, что просили.
- Два брака подряд на переписывание ЦЕЛОГО файла → не третья попытка
  того же; либо просить только фрагмент без `--ctx`, либо писать
  вручную (лимит из п.9 skill включает этот выбор явно).

**TECH.md — устаревшие детали окружения (факт, не решение, не гадать —
сверять с фактически установленной версией пакета):**
- `@noble/hashes` (2.2.0 в проекте): пути импорта требуют `.js`
  (`hmac.js`, `sha2.js` вместо `sha256`, `utils.js`, `hkdf.js`).
- `@scure/bip39`: wordlist требует `.js` (`wordlists/english.js`).
- Не проверено ещё для `@scure/bip32`, `ts-mls`, `comlink` — при первом
  использовании каждого сверить фактические пути экспорта до контракта,
  не полагаться на код-сниппеты TECH.md §16 буквально.

**Вёрстка (`minimal.css`):**
- `<label>Текст<input/></label>` (оборачивающий) НЕ подпадает под
  `label:not(:has(input,select,textarea))` — только раздельные
  `label[for]` + `input[id]`. Уже стандарт для всех форм проекта.
- Автотесты не ловят такие несоответствия стилей — обязательна
  визуальная/скриншот-проверка (Playwright) для каждого нового экрана,
  не только функциональная.
- `role="tab"` переопределяет неявную ARIA-роль `button` — селекторы
  `getByRole("tab", …)`, не `"button"`, для элементов с явной ARIA-ролью.

**Тестирование:**
- `localStorage` и вообще DOM API недоступны в чистом `node --test` —
  разделять функции на чистые (юнит-тесты) и DOM-зависимые (только
  интеграционно, Playwright). Шаблон уже есть — `src/ui/signals/auth.js`.
- `document.body.innerText` НЕ отражает текущее значение
  `<textarea>`/контролируемого `<input>` (только исходное DOM-содержимое)
  — для живого значения `locator.inputValue()`.
- Адверсарная фаза (п.19 skill) систематически находит реальные баги,
  не формальность для галочки — минимум 6 реальных находок именно на
  ней за первые 12 этапов (Symbol-кэш `verifyEvent`, `$`-паттерны в
  `replaceAll`, `since=0` falsy-баг, race в `g-set`, преждевременный
  `login()` до done-экрана, отсутствие лимита размера файла аватара).
  Не сокращать этот шаг ради скорости.

**Важная находка при переработке плана:** бюджет TECH.md §7.2
(~190–250 КБ итого, запас 30–90 КБ) посчитан ДО решения профиля B
добавить MLS — `ts-mls` сам по себе **65 КБ** (TECH.md §13.1, измерение

30–90 КБ "запаса" (та цифра сама по себе была нижней и верхней
оценкой без MLS). Это факт из документа, требующий пересмотра, не
пробел решения — TECH.md §7.2 просто не обновили при ревизии 6.0.

внимательно; если к этапу транспорта (16) запас будет заметно
проседать — эскалировать пользователю до, а не после, этапов 8 (MVP).

   только если отправитель знал, куда его публиковать. Нужен kind из
   NIP-17 (ориентировочно 10050 — номер СВЕРИТЬ по спеке перед
   реализацией, не гадать, п.9a skill). При отправке — публиковать
   gift-wrap не только на свой relay, но и на опубликованный
   inbox-relay получателя. Рассмотреть вместе с backlog-пунктом 4
   (утечка метаданных kind 30053 — тот же класс: открытые теги).
8. **Этап 61 — Bootstrap-вход по мнемонике (координатор-индекс).**
   Экран логина перестаёт спрашивать у пользователя relay (протекающая
   абстракция — он не может и не должен на это отвечать). Вводится
   только мнемоника → клиент идёт на зашитый список bootstrap-relay
   (включая ugolok.tech) → находит kind:10002 (+kind:0, возможно
   kind:10063 списка Blossom-серверов, BUD-03 — номер сверить) по
   pubkey → подключается напрямую к найденным relay. Это "координатор"

   **НЕ реализовано в этой сессии, сознательно отложено:** серверный патч

   300/документы 100 МБ) и TTL/last-accessed background job — ОТДЕЛЬНЫЙ
   репозиторий (`server/blossom/blossom-src`, сторонний upstream
   `sebdeveloper6952/blossom-server`, свой `.git`, не отслеживается этим
   репозиторием), другой язык (Go), нет `node --test`/`worker.sh`-конвейера —
   откладывается до реального деплоя ugolok.tech. Self-hoster'ская гибкость
   уже полностью достигнута клиентской частью (апстримный `config.yml` уже
   самодостаточен через BUD-06) — откладываемое нужно ТОЛЬКО для собственного
   деплоя ugolok.tech, не блокирует ничьи self-hosted инстансы.

   **Контекст решения:** первоначальные 10-20 МБ отвергнуты пользователем
   как нереалистично мало (WhatsApp/Signal — 16-100 МБ, Telegram —
   гигабайты); Blossom-сервер ugolok.tech будет жить на арендованном VPS
   (не объектное хранилище с оплатой по трафику) с БЕЗЛИМИТНЫМ трафиком
   и ~250-300 ГБ NVMe — значит реальный ограничитель не деньги за
   передачу данных, а место на диске со временем, и здесь работает TTL,
   не потолок на файл сам по себе.

   **Согласованные значения для ugolok.tech (не для чужих инстансов —
   см. ниже):** потолок на файл по типу — фото 50 МБ, аудио 100 МБ
   (голосовые/музыка — тот же бакет), видео 300 МБ, документы
   (PDF/docx/xlsx/pptx/text) — ОТДЕЛЬНЫЙ бакет 100 МБ (сейчас в коде
   молча делят лимит с фото — найденный по ходу обсуждения пробел, не
   осознанное решение). TTL по вложениям — 90 дней, но НЕ "с момента
   загрузки", а "с последнего РЕАЛЬНОГО обращения" (просмотр/скачивание
   кем угодно сбрасывает счётчик) — устраняет саму задачу "чистить
   неактивные аккаунты" как отдельный механизм: файл, который кто-то
   всё ещё смотрит, не удаляется, даже если отправитель давно пропал;
   файл, который никому не нужен, истекает сам, независимо от чьей-либо
   "активности". Переписка/профиль/контакты (текст, килобайты) НИКАКОЙ
   чистке по активности НЕ подлежат ни при каком дизайне — это сломало
   бы восстановление по мнемонике для человека, просто давно не
   заходившего, что прямо противоречит цели надёжности всего этого
   блока этапов. Каналы — по-прежнему исключение (свой Blossom автора,
   TTL не применяется, не меняется относительно раннего решения).

   **Найденный по ходу обсуждения архитектурный факт, меняющий скоуп
   этапа:** self-hoster'ская гибкость лимитов НЕ требует новой
   инфраструктуры — она уже встроена в протокол. `server/blossom/
   blossom-src` (Go, `sebdeveloper6952/blossom-server`) уже реализует
   BUD-06 (`HEAD /upload` с заголовками `X-SHA-256`/`X-Content-Type`/
   `X-Content-Length`, защищён тем же `nostrAuthMiddleware`, что и
   реальная загрузка) — сервер отвечает на основе СВОЕЙ настройки
   `max_upload_size_bytes` (`config.yml`), и та же проверка
   (`ValidateFileSizeMaxBytes`) реально применяется на BUD-02 (сама
   загрузка) и BUD-04 (mirror), не только на BUD-06. То есть КАЖДЫЙ,
   кто поднимает свой инстанс, УЖЕ сегодня может поставить в своём
   конфиге любое число — код self-hoster'а трогать не нужно вовсе.

   **Реальная проблема — наоборот, в клиенте.** `attachment-validation.js`
   (`domain/files/`) проверяет размер ЛОКАЛЬНО, до всякой сети, по
   зашитым в сборку константам (`MAX_IMAGE_FILE_SIZE`/`MAX_VIDEO_SIZE`/
   `MAX_VOICE_SIZE`) — единый клиент, раздаваемый с ugolok.tech,
   отбраковывает файл СВОИМ мнением прежде, чем запрос вообще доходит
   до чужого сервера, даже если тот настроен на куда больший лимит. Это
   и есть настоящий пробел, который отбирает у self-hoster'ов ту самую
   гибкость, которую просил сохранить пользователь.

   **Принятое решение по разделению труда:**
   - **Клиент** — переходит с локальной жёсткой константы на BUD-06-
     дискавери: перед загрузкой спрашивает ФАКТИЧЕСКИ подключённый
     Blossom-сервер (свой или чужой — без разницы) через `HEAD /upload`,
     и уважает ЕГО ответ, а не свою старую константу. Сервер не
     поддерживает BUD-06 (404/405/сетевая ошибка) — прогрессивное
     улучшение, не хардстоп: просто нет раннего фидбека, реальная
     проверка (PUT /upload) остаётся источником истины и никуда не
     девается.
   - **Сервер ugolok.tech** — единственное место, где нужна доработка
     САМОГО Go-бинарника (текущий `max_upload_size_bytes` — одно общее
     число на все MIME, без разделения по типу): добавить per-MIME-type
     лимиты именно в ЭТОТ конкретный деплой. Self-hoster, которому
     разделение по типам не нужно, спокойно остаётся на простом едином
     числе апстрима — форк не обязателен для всех, только для
     конкретно ugolok.tech.
   - **TTL/last-accessed-очистка** — тоже настройка СТОРОНЫ СЕРВЕРА
     (конфиг + фоновый job, не клиент): у ugolok.tech — 90 дней, у
     self-hoster'а — что сам решит, вплоть до "никогда не чистить".

## Этап 60 — Inbox-релеи для входящих (доставка на relay ПОЛУЧАТЕЛЯ)

Контракты — CONTRACTS.md, раздел "Этап 60". Kind сверен по спеке
(NIP-17): `10050`, тег `relay` (не `r`, как у kind:10002).

Новый файл `domain/identity/dm-relay-list.js` (build/parse kind:10050).
Новый примитив `relay-pool.js`'s `publishToRelay(url, event, options)` —
эфемерное one-shot соединение для доставки на relay, не входящий в
собственный пул (этап 58). `ui-settings.js` — рядом с kind:10002
публикует kind:10050 (только read-relay). `signals/transport.js` —
backfill на `connect()`, `fetchInboxRelays` (с кэшем, TTL 5 мин, и
`pickLatest` — replaceable событие), `deliverToInboxRelays` (внутренняя,
best-effort), правка `publish()` (авто-доставка по `#p`-тегу, покрывает
ЛЮБОЙ адресованный kind, не только gift wrap), новый `publishToContact`
для kind:445 (нет `#p`, адресат передаётся явно). `chat.jsx` — три
места (отправка/удаление/правка сообщения, все — `chat.js`'s
`sendMessage` под капотом) обёрнуты в `publishToContact`.

**Уточнение скоупа при реализации:** "читать чужой kind:10002 при
входе" из исходной формулировки PLAN.md для этапа 59 фактически
реализовано здесь, не там — читается не kind:10002, а kind:10050
(отдельный, более узкий NIP-17 kind именно "куда слать личные
события"), и именно в момент доставки конкретному получателю, не при
входе.

**Найден и исправлен реальный баг, обнаруженный ТОЛЬКО живой E2E-
проверкой (не поймали бы юнит-тестами модуля):** первая версия этапа
предполагала, что `contacts.jsx`/`channels.jsx`/`moderation-panel.jsx`
и т.д. продолжают работать "как раньше" через уже существующий
`publish()`, раз их вызывающий код не менялся. Предположение оказалось
неверным — `connect()` во ВСЕХ восьми местах инъекции runtime-объектам
(`configureContactRuntime` и семь других) передавал СЫРОЙ
`publisher.publish`, а не обогащённый модульный `publish` — новая
логика доставки попросту никогда не вызывалась для контактов/звонков/
Welcome/channel-grant backfill и т.д. Обнаружено разворачиванием
настоящего двух-relay E2E (два независимых временных strfry-инстанса,
127.0.0.1:7777 и 127.0.0.1:7779, два реальных тестовых аккаунта без
единого общего relay) — заявка в контакты не долетала вообще никуда,
даже до собственного relay отправителя; временный `console.log` внутри
`publish()` подтвердил, что функция не вызывается для этого пути.
Исправлено заменой всех восьми мест инъекции на модульный `publish`
(два backfill self-announce намеренно оставлены как есть — не несут
`#p`, разницы в поведении нет).

**Живая проверка (два реальных временных strfry-relay, отдельные от
основного тестового, три тестовых аккаунта, ZERO общих relay между
отправителем и получателем):** после фикса — заявка в контакты от
аккаунта на relay А реально долетела и была видна во входящих у
получателя, подключённого ИСКЛЮЧИТЕЛЬНО к совершенно другому relay Б,
через обнаружение kind:10050 (предварительно "посеянного" на relay А
вручную — симуляция будущего bootstrap-координатора, этап 61, которого
ещё не существует) и последующую `publishToRelay`-доставку на
relay Б. Ровно тот сценарий "переписка не доходит между relay", ради
которого весь этот блок этапов затевался.

Regression: `npm test` 1191/1191 (было 1182). Сборка: 556.63 КБ gzip.

**Явно не в скоупе (см. CONTRACTS.md):** bootstrap-координатор —
автоматическое обнаружение relay-списка БЕЗ ручного "посева" на общий
relay, вход по мнемонике с чистого устройства/relay — этап 61.

## Этап 61 — Bootstrap-вход по мнемонике (координатор-индекс)

Контракты — CONTRACTS.md, раздел "Этап 61".

**Уточнение скоупа при реализации:** формулировка PLAN.md для этого
этапа предполагала ещё и "убрать селектор relay с экрана логина" —
проверка кода (`unlock.jsx`, единый экран онбординга+входа) показала,
что такого селектора там нет и никогда не было (0 упоминаний "relay"
в файле). Похоже, эта часть плана была основана на предположении из
обсуждения архитектуры с Claude 5, не на реальном UI — убирать
нечего. Реальная работа этапа — только обнаружение relay-списка при
входе, когда локальной истории для pubkey ещё нет вовсе.

Новый build-time дефолт `BUILD_BOOTSTRAP_RELAYS` (vite.config.js/
config.js, тот же паттерн, что `BUILD_DEFAULT_RELAYS`) — сегодня
совпадает с дефолтным relay (свой сервер = bootstrap-relay), но
отдельная env-ручка на будущее (координатор ugolok.tech). Новый
примитив `fetchFromRelay` (relay-pool.js) — симметричен `publishToRelay`
(этап 60), но для чтения (REQ+EOSE). Новый `hasLocalUiSettings`
(ui-settings.js) — прямая проверка существования локальной записи,
`loadUiSettings` для этого не годится (фолбэк неотличим снаружи от
настоящей записи). `signals/transport.js`'s `connect()`: если локальной
записи нет вовсе — параллельный запрос kind:10002 по всем
bootstrap-relay (`Promise.allSettled`, один недоступный не блокирует
остальных), `pickLatest` по всем ответам, найденный список — сразу
локально сохранён (`saveUiSettings` с заведомо падающим `publish`,
`publisher` на этот момент ещё не создан). Ничего не найдено (свежий
аккаунт или bootstrap недоступен) — поведение как раньше (build-time
дефолт).

**Живая проверка (полный цикл, реальная сеть, не моки):** создан
тестовый аккаунт на relay А (127.0.0.1:7777, = bootstrap-relay по
умолчанию в dev), затем переведён на ВТОРОЙ, отдельный временный relay
Б (127.0.0.1:7780, не входящий в build-time дефолт) — relay А убран
из списка. Подтверждено `strfry scan` напрямую: на bootstrap-relay А
лежит актуальный kind:10002 с единственным тегом `["r","ws://…:7780"]`.
Далее — локальные данные ЭТОГО аккаунта стёрты целиком (IndexedDB,
владелец-скоуп), мнемоника сохранена заранее. Вход по мнемонике на
"чистом устройстве": приложение подключилось РОВНО к relay Б (не к
дефолтному А) — подтверждено экраном Профиль (relay-серверы = только
127.0.0.1:7780) и прямой проверкой сырой записи `uiSettings` в
IndexedDB (появилась сразу после входа, до какой-либо ручной правки
настроек). Консоль браузера чистая на всех шагах.

Regression: `npm test` 1199/1199 (было 1191). Сборка: 557.07 КБ gzip.

**Явно не в скоупе (см. CONTRACTS.md):** обнаружение kind:0 отдельно
от bootstrap (приходит естественно через обычный `runBootstrap` после
подключения к найденному relay); kind:10063 (список Blossom-серверов,
BUD-03) — нет ни одного места в проекте, публикующего/читающего этот
