# ТЗ: CI/CD и реорганизация поставки «Уголок» (локальный этап, до покупки VPS)

Версия ТЗ: 1.2  
Дата: 2026-09-01  
Адресат: агент в терминале (supergrok / аналог)  
Репозиторий: https://github.com/naysy-sx/ugolok-03  
Рабочая машина: Apple Mac Mini M2, всё крутится на localhost / LAN  
Публичный VPS пока **не куплен**. Домены зарезервированы концептуально, DNS на них не настраивать.

---

## 0. Зачем это ТЗ

Нужно **сейчас**, на домашней машине:

1. Развести исходники, релизы, окружения и будущие домены.
2. Подготовить каркас CI/CD так, чтобы перенос на VPS был сменой URL и runner-а, а не переписыванием проекта.
3. Не реализовывать магазин приложений, Capacitor-мастер установки VPS, почту и продакшен-TLS.

Итог этапа: репозиторий знает, как собирается, проверяется, версионируется и документируется. Локально это можно прогнать руками и (по возможности) через GitHub Actions. Позже тот же каркас переедет на `git.ugolok.tech` (Forgejo).

**Факт на старте:** в проекте **нет никакого CI/CD**. Нет `.github/workflows`, нет `.forgejo/workflows`, нет runner-а, нет автовыкладки. Есть только ручные команды (`npm test`, `npm run build`, `scripts/release-hash.sh`) и текстовые runbook-и. Каркас пишется с нуля, ничего «подключать к существующему пайплайну» не нужно. Не искать скрытый Jenkins/GitLab/Actions — его нет.

## 1. Контекст проекта (не выдумывать иное)

«Уголок» — мессенджер на Nostr.

Клиент:

- Preact + signals, Dexie, Vite + `vite-plugin-singlefile`
- Артефакт веба: `dist/index.html` + `dist/service-worker.js`
- Бюджет бандла и запрет тяжёлых зависимостей — см. `CLAUDE.md` (лимит NF-11)
- Тесты: `npm test` → `node --test tests/*.test.js`
- Сборка: `npm run build`
- Подпись релиза уже есть: `scripts/release-hash.sh`

Сервер (сейчас без Docker, только setup.sh/run.sh):

- `server/strfry` — relay `ws://127.0.0.1:7777`
- `server/blossom` — blob `http://127.0.0.1:8080`
- `server/coturn` — STUN/TURN `127.0.0.1:3478`
- `npm run dev` уже поднимает часть dev-инфры через плагины Vite

Документы процесса разработки (не ломать, не смешивать с пользовательскими docs):

- `CLAUDE.md`, `PROCESS-DOCS/*`, `FEATURE-SPECS/`, `FILES-DOCS/`
- Регламент UI: `PROCESS-DOCS/REGLAMENT.md`

Существующие пользовательские docs:

- `docs/RUNBOOK.md`
- `docs/self-hosting.md`
- `docs/verify.md`

Ветки и GitHub:

- Сейчас код периодически пушится на GitHub, чтобы не потерять.
- Целевая модель веток (уже согласована):
  - долгоживущая только `main` (допускается ещё `develop`, если без неё нельзя сохранить текущий ритм работы — тогда явно описать в docs);
  - фичи — короткие `feature/*` через PR;
  - `test` и `prod` — **окружения, не ветки**;
  - релиз — semver-тег на `main` (`vX.Y.Z`).
- Пока VPS нет, не переносить origin насильно. Добавить файлы так, чтобы они были валидны и для GitHub Actions, и для Forgejo Actions.

Будущая карта хостов (только документировать, не внедрять DNS):

| Хост | Назначение |
|---|---|
| `ugolok.tech` | рабочий веб-клиент (PWA), то что открывает пользователь |
| `git.ugolok.tech` | Forgejo: исходники, PR, Actions, git-теги. Не публичная витрина сборок |
| `updates.ugolok.tech` | канал обновлений: `version.json`, веб-артефакты, позже нативные пакеты и OTA |
| `docs.ugolok.tech` | документация (желательно; можно позже как Pages у Forgejo) |
| `mail.ugolok.tech` | почта, **вне скоупа** |

Разведение ролей обязательное:

- `git.ugolok.tech` — контроль версий и CI. Клиенты сюда за обновлениями **не ходят**.
- `updates.ugolok.tech` — единственный публичный endpoint, который клиент спрашивает «есть ли новая версия» и откуда качает артефакты.
- CI после тега публикует сборку в два места по смыслу: служебная копия может остаться на Forgejo Release (удобно людям и для аудита), **канон для клиентов** — дерево на `updates.ugolok.tech`.
- Пока VPS нет, имитировать `updates` локально: каталог `dist-release/` или локальный static server на порту, например `http://127.0.0.1:8787`. В docs это называть «local updates endpoint».

## 6. Контракты файлов

### 6.1. `version.json`

Публичный манифест версии клиента/инстанса. Пример:

```json
{
  "name": "ugolok",
  "version": "0.0.0",
  "gitTag": "v0.0.0",
  "gitSha": "REPLACE",
  "buildHash": "REPLACE",
  "releasedAt": "1970-01-01T00:00:00Z",
  "minClientVersion": "0.0.0",
  "channels": {
    "web": { "url": "/index.html" }
  },
  "notesUrl": "https://updates.ugolok.tech/changelog.md",
  "updatesBaseUrl": "https://updates.ugolok.tech"
}
```

Правила:

- В релизе генерируется из тега и выхода `release-hash.sh`.
- Публичное место файла: `https://updates.ugolok.tech/version.json` (прод) и `https://updates.ugolok.tech/vX.Y.Z/version.json` (конкретная версия).
- Пока VPS нет: `http://127.0.0.1:8787/version.json` как локальный стенд канала обновлений.
- Клиент в будущем сверяет свою версию с `updates.* /version.json`. На этом этапе достаточно контракта + пример + docs. Вшивать проверку в UI **не обязательно**, если это риск для текущего UX. Если вшивается — за feature-flag / тихим `console` уровнем, без блокировки мессенджера.

### 6.2. `config.json` (runtime инстанса)

Пример:

```json
{
  "instanceName": "local",
  "relays": ["ws://127.0.0.1:7777"],
  "bootstrapRelays": [],
  "blossomServers": ["http://127.0.0.1:8080"],
  "iceServers": [
    { "urls": "stun:127.0.0.1:3478" },
    {
      "urls": "turn:127.0.0.1:3478",
      "username": "ugolok",
      "credential": "ugolok-dev"
    }
  ]
}
```

Правила:

- Это **runtime**, не секретный файл с паролем VPS.
- TURN credential для dev может быть в примере; для прод-доков — отдельный секрет/env, не зашивать «боевой» пароль.
- Build-time `__BUILD_DEFAULT_*` в `vite.config.js` остаются дефолтом для `npm run dev` и оффлайн-сборки без config.
- Если клиент уже умеет читать endpoints из настроек — задокументировать приоритет:
  1. явные настройки пользователя в UI;
  2. `config.json` с того же origin (или заданного URL);
  3. build-time defaults.
- Не делать обязательную пересборку `index.html` под IP.

### 6.3. Куда кладутся файлы релиза

Два слоя, не путать:

1. **Аудит / люди:** GitHub Release сейчас, позже Forgejo Release на `git.ugolok.tech` — удобно смотреть тег, notes, скачать вручную.
2. **Клиенты:** `updates.ugolok.tech` — канон.

Предлагаемое дерево канала обновлений:

```text
https://updates.ugolok.tech/
  version.json                 # всегда последняя стабильная
  changelog.md
  latest/
    index.html
    service-worker.js
    SHA256SUMS
    SHA256SUMS.asc             # если есть ключ
    version.json
  v0.4.0/
    index.html
    service-worker.js
    SHA256SUMS
    SHA256SUMS.asc
    version.json
```

Позже в тот же хост добавятся `android/`, `ios/`, `desktop/` — не в этом этапе.

Минимум файлов в каждом каталоге версии:

- `index.html`
- `service-worker.js`
- `SHA256SUMS`
- `SHA256SUMS.asc` (если в CI нет GPG-ключа — файл опционален, но слот и инструкция должны быть)
- `version.json`
- `config.example.json`
- короткий changelog

Локальная имитация на Mini: `scripts/release-pack.sh` собирает то же дерево в `dist-updates/` (каталог в `.gitignore`) и может поднять `npx serve dist-updates -p 8787`.

## 7. Ветвление и окружения (зафиксировать в docs)

Рабочий поток **сейчас**:

```text
feature/<коротко>  --PR-->  main
hotfix/<коротко>   --PR-->  main
release            = git tag vX.Y.Z на main
```

Окружения:

| Имя | Где физически сейчас | Откуда код |
|---|---|---|
| local | Mini M2, localhost | рабочая копия |
| test | позже VPS или тот же Mini на другом порту/compose profile | `main` |
| prod | позже `ugolok.tech` | тег `vX.Y.Z` |

Правила:

- Не создавать ветки `test` и `prod`.
- `main` должна собираться.
- Пока один человек работает локально, PR на GitHub желательны, но не блокируют создание каркаса. Документировать оба пути: «один разработчик на Mini» и «потом PR на Forgejo».

Версии: semver. Пока продукт не стабилен — допустим `0.Y.Z`. Тег всегда с `v`.

## 8. CI/CD, который можно сделать без VPS

### 8.1. Локальная «CI» на Mini M2 (обязательно)

Скрипт `scripts/ci-check.sh`:

1. `npm ci`
2. `npm test`
3. `npm run build`
4. Проверка, что в `dist/` есть `index.html` и `service-worker.js`
5. Оценка размера `dist/index.html` (gzip, если доступен) и печать его; лимит брать из `CLAUDE.md` / существующего NF-11. Если точная цифра в коде уже проверяется — вызвать ту же проверку, не плодить вторую.
6. Код выхода ≠ 0 при падении любого шага.

Этот скрипт — источник истины и для человека, и для workflow.

### 8.2. GitHub Actions (обязательно, т.к. код уже на GitHub)

Файл `.github/workflows/ci.yml`:

- Триггер: pull_request и push в `main`.
- `runs-on: ubuntu-latest`
- checkout, setup-node по версии из проекта (смотреть по `package.json` / фактическому движку; не гадать «latest»), cache npm, запуск `scripts/ci-check.sh` или эквивалент шагов.

Файл `.github/workflows/release.yml`:

- Триггер: теги `v*.*.*`
- Те же проверки
- `npm run build` + `scripts/release-hash.sh` **без обязательного GPG**, если секрета нет: скрипт сейчас падает без `gpg`. Нужно аккуратно:
  - либо научить `release-hash.sh` делать хеш всегда, а подпись — если есть ключ/секрет `GPG_PRIVATE_KEY`;
  - либо сделать `scripts/release-pack.sh`, который вызывает сборку+хеш, а GPG опционален.
- Upload artifacts / создание GitHub Release с файлами из §6.3.
- Не коммитить `dist/` обратно в репозиторий.

Не ломать текущий `release-hash.sh` для ручного локального релиза с GPG на Mini (у пользователя GPG, скорее всего, есть локально).

### 8.3. Forgejo-заготовка (обязательно как файлы, не как живой сервер)

- `.forgejo/workflows/` с тем же смыслом, что GitHub.
- Docs: «когда появится `git.ugolok.tech`, включить Actions, поставить runner, скопировать секреты».
- Не требовать установки Forgejo в этом ТЗ как обязательный passing-критерий. Разрешено добавить `deploy/forgejo-compose.yml` **опционально**, если это не расползается в неделю работы.

### 8.4. Что на Mini можно прогонять руками каждый день

```bash
git checkout main
npm ci
./scripts/ci-check.sh
./scripts/release-pack.sh    # или release-hash.sh
```

Опционально, если поставлен Docker Desktop / Colima / OrbStack:

```bash
docker compose -f deploy/compose.yml up --build
```

Если Docker на машине не ставили — compose-файлы всё равно создать, запуск не блокирует приёмку.

## 9. Локальный стек → будущий VPS

### 9.1. Принцип

Одни и те же имена сервисов и портов:

- web: 443/80 позже, сейчас `8088` или `4173` (не конфликтовать с Vite `5173`, strfry `7777`, blossom `8080`, turn `3478`)
- relay: 7777
- blossom: 8080
- turn: 3478
- proxy: запас под Caddy

Сейчас на Mini можно:

A. Оставить голые `run.sh` как dev.  
B. Добавить compose-каркас, который на VPS станет основным.

Оба пути должны быть описаны в `docs/local-cicd.md` и `deploy/README.md`.

### 9.2. `deploy/compose.yml`

Минимальный каркас даже с `build: TODO` / `image: FIXME` допустим, но файл должен:

- перечислять сервисы;
- брать домен/IP из env;
- монтировать `config.json` и статику веб-клиента;
- иметь `env.example`.

Не обязательно в этом этапе успешно собрать strfry внутри Docker на darwin/arm64. Если агент может сделать рабочий compose за разумный объём — хорошо. Если нет — каркас + честный список блокеров (сборка strfry, cgo, coturn на ARM).

### 9.3. Перенос на VPS потом (только задокументировать)

Когда появится сервер:

1. Поставить Docker + Caddy/Traefik.
2. Поднять Forgejo на `git.ugolok.tech` (только git/CI).
3. Поднять static/host для `updates.ugolok.tech` и выкладывать туда дерево релиза из CI.
4. Выложить рабочий клиент на `ugolok.tech` (может быть копия `updates/.../latest/`, но пользовательский origin — этот домен).
5. Добавить remote, включить runner.
6. Секреты (GPG, token выкладки на updates) перенести в Forgejo Secrets.

Этот чеклист — в `docs/environments.md`, без претензии, что он уже исполнен.

## 10. Документация, которую агент обязан написать

Канон поставки — `docs/delivery.md`. Без этого файла этап не считается сделанным.

`docs/delivery.md` должен ответить коротко и однозначно:

1. Что является релизом (тег).
2. Что является источником артефактов (Release, не дерево git).
3. Какие ветки существуют.
4. Какие окружения существуют.
5. Как клиент получает обновление: спрашивает `https://updates.ugolok.tech/version.json`, качает артефакты с того же хоста; PWA дополнительно через service worker на `ugolok.tech`. Натив и OTA — будущий этап, но URL канала уже этот.
6. Почему клиент не пересобирается под каждый IP.
7. Как соотносятся GitHub сейчас, Forgejo потом (`git.ugolok.tech`) и канал обновлений (`updates.ugolok.tech`).
8. Как self-hosted инстанс обновляется отдельно от официального клиента (свой compose/образа, не подмена `updates.ugolok.tech`).

Также обновить `docs/RUNBOOK.md`: ссылка на новую схему, не дублировать противоречащие инструкции про теги.

Не переносить `PROCESS-DOCS` в `docs/`. Это разные аудитории.

## 11. Порядок работ для агента (исполнять сверху вниз)

1. Прочитать `CLAUDE.md`, `docs/RUNBOOK.md`, `docs/self-hosting.md`, `scripts/release-hash.sh`, `package.json`, `vite.config.js` (define defaults), `.gitignore`.
2. Составить краткий `docs/delivery.md` и согласовать структуру каталогов (в этом этапе согласование = сделать согласно ТЗ, не ждать человека после каждого файла).
3. `.gitignore` и примеры `config`/`version`.
4. `scripts/ci-check.sh` + прогнать локально в своей среде. Если среды нет как у пользователя — хотя бы синтаксис и shebang, команды те же.
5. Опционально смягчить GPG в упаковке релиза, не ломая ручной подписанный путь.
6. GitHub Actions CI + release workflow.
7. Заготовка Forgejo workflows + абзац в docs.
8. Каркас `deploy/`.
9. Обновить RUNBOOK / self-hosting ссылками, убрать противоречия «прод = ветка».
10. Прогнать `npm test` и `npm run build` если среда позволяет. Зафиксировать в отчёте, что прогнано, а что нет.

Коммиты: логические, сообщения на русском или английском — как принято в последней истории репозитория. Не делать один огромный «всё сразу», если можно 3–6 понятных коммитов. Не пушить, если нет явной просьбы в сессии (по умолчанию только локальные изменения / патчи).

## 12. Критерии приёмки

Этап принят, если:

- [ ] Есть `docs/delivery.md` с моделью веток/тегов/окружений/артефактов.
- [ ] Есть примеры `config.json` и `version.json` и описание приоритета конфига.
- [ ] Есть `scripts/ci-check.sh`, он повторяет проверку CI.
- [ ] Есть GitHub Actions на PR/`main` и на тег `v*.*.*`.
- [ ] Есть заготовка под Forgejo.
- [ ] В git нет `dist/` и серверных баз как артефактов релиза.
- [ ] `npm test` и `npm run build` не сломаны (если агент мог запустить — запущены).

- [ ] `scripts/release-hash.sh` либо сохранён, либо обёрнут с обратной совместимостью.
- [ ] В документации нет веток `prod`/`test` как git-веток.
- [ ] Есть честный список «сделаем после покупки VPS».
