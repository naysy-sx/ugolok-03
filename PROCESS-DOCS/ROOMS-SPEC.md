# ROOMS-SPEC.md — техническое задание: раздел «Быстрая связь»

Версия 2. Учтены результаты разведки по существующему коду (сигналинг, звонковый
слой, relay-pool). Основано на ROOMS-MATH-v2.md (структуры, инварианты) и
ROOMS-ALGO.md (операции, сложность).

Метки задач: **[C]** — писать Claude напрямую (риск/крипто/связанное состояние),
**[W]** — можно отдать воркеру (изолированная функция с полной спецификацией).

**Изменения против версии 1:** сигналинг остаётся на NIP-44 без симметричного
режима (§5.3); контракт супервизора дополнен владением медиапотоком и клонами
треков (§4.3); риск «синглтоны в звонковом слое» снят разведкой, вместо него
внесён риск остановки общего трека (§9); §10 сокращён до одной оставшейся
проверки.

## 0. Главное архитектурное решение

**Комната — второй, независимый транспортный клиент, а не режим основного
приложения.**

Обоснование. Основной путь приложения устроен так: `connect()` в
`ui/signals/transport.js` держит module-level синглтон соединения, от него зависят
publish, восемнадцать подписчиков, teardown и outbox. Он же на входе делает
`ensureProfilePublished`, `ensureOwnKeyPackagePublished`, восемь `rebuild*` и
bootstrap. Всё это нужно аккаунту и не нужно комнате.

Соблазн — добавить в `connect()` флаг «облегчённый режим». Это плохо по двум
причинам: флаг размножается вниз по всем восемнадцати подписчикам, и любая ошибка
в гостевой ветке ломает основную переписку.

Разведка подтвердила, что независимый путь существует и уже используется:
`createRelayConnection`, `createPublisher`, `createSubscriber` — все три принимают
своё соединение явным параметром, `diagnostics.jsx:569` этим пользуется. Комната
идёт тем же путём (§4.2).

Следствия, каждое из которых снимает пласт работы:

- **Никаких изменений в `transport.js`.** Основная переписка не может сломаться
  от работы над комнатами.
- **Никакого `db.version(25)`.** Комната не пишет в IndexedDB вообще.
- **Никакого owner-scoping.** Нет строк — нет владельца.
- **Никакого `encrypted-table`.** Нет персистентности — нечего шифровать at rest.
- **Никакого keystore для гостя.**

Комната — объект в памяти вкладки со своим соединением, живущий от входа до
выхода. Закрытие вкладки — конец, без уборки.

**Личность в комнате всегда эфемерная, в том числе у залогиненного
пользователя.** Одна причина техническая (один путь кода вместо двух), вторая
важнее: иначе человек, зашедший «поболтать в котиках», светит незнакомцам свой
настоящий pubkey, по которому его находят как контакт. Это надо написать в UI:
«вы входите анонимно, ваш аккаунт не раскрывается».

## 2. Инъекция времени — обязательное требование

Каждый чистый модуль, которому нужно «сейчас», получает его параметром или
принимает функцию-часы в конструкторе. Ни один не вызывает `Date.now()` внутри.

```js
// НЕТ
export function present(state) { const now = Date.now(); ... }

// ДА
export function present(state, now) { ... }
```

Без этого тест на `τ = 45 с` требует сорока пяти секунд реального ожидания, тест
на рост интервала Trickle — нескольких минут, а тест на обрезку невозможен вовсе.
С этим — весь временной контур проверяется мгновенно подстановкой чисел.

Тот же принцип для случайности: `random` инжектируется, иначе тест на выбор точки
передачи в Trickle недетерминирован.

## 3. Контракты чистого ядра

### 3.1. `room-keys.js` **[C]**

```js
deriveRoomKeys(name, password, suffix, argon2) -> Promise<{
  kBase, kRv, kSess: null, hTopic, hDisc
}>
deriveSessionKey(kRv, salt) -> kSess
```

`argon2` — инжектируемая функция (в бою — вызов в воркере, в тесте — заглушка).
Единственный медленный шаг — `kBase`; `hDisc`, `kRv`, `hTopic` выводятся быстрыми
HMAC/HKDF (ROOMS-ALGO §8).

В закрытом режиме `hDisc` вычисляется, но не публикуется.

### 3.2. `presence.js` **[C]**

```js
emptyPresence() -> state
mergeHeartbeat(state, {pubkey, nick, at}) -> state
mergeExit(state, {pubkey, at}) -> state
present(state, now, tau) -> Array<{pubkey, nick, joinedAt}>
prune(state, now, tau) -> state
```

Все функции чистые, возвращают новое состояние. `merge` идемпотентна,
коммутативна, ассоциативна (И1). `prune` удаляет записи с `a < now − tau`
(ROOMS-ALGO §2, И12).

Порядок в выдаче `present` — по `joinedAt` возрастанию, стабильный. Иначе список
участников прыгает при каждом обновлении.

### 3.3. `trickle.js` **[W]**

```js
createTrickle({iMin, iMax, k, random}) -> {
  onInterval(now), onConsistent(), onInconsistent(), shouldTransmit(now)
}
```

RFC 6206 буквально (ROOMS-ALGO §4.2). Параметры: `iMin = 15000`, `iMax = 60000`,
`k = 1`.

Полностью изолирован от того, что именно передаётся — знает только «пора/не
пора». Идеальный кандидат для воркера: спецификация полная, побочных эффектов
нет.

### 3.4. `mesh.js` **[W]**

```js
edges(pubkeys) -> Array<[initiator, responder]>   // отсортировано, i < j
diffEdges(oldEdges, newEdges) -> {toOpen, toClose}
```

Чистая функция от отсортированного списка. Одинаковый вход у всех участников ⟹
одинаковый выход ⟹ И5 выполняется без согласования (ROOMS-ALGO §6).

### 3.5. `message-log.js` **[W]**

```js
createLog({maxBacktrack = 200}) -> {
  insert(msg) -> boolean,   // false = дубликат
  toArray()
}
```

Вставка с хвоста, `Set` идентификаторов для дедупа (ROOMS-ALGO §5). И14: `m`
сообщений по порядку дают ровно `m` сравнений.

Порядок — по `(createdAt, id)`. **Lamport здесь не используется сознательно:** он
требует персистентного состояния, которого у гостя нет, и не даёт выигрыша там,
где все участники онлайн одновременно. Цена — расхождение часов может слегка
перемешать сообщения, отправленные в одну секунду. Для комнаты на пятерых это
косметика; записать как принятый компромисс, не как недоделку.

### 3.6. `room-machine.js` **[C]**

Автомат по ROOMS-MATH §5.1 поверх существующего `core/fsm/machine.js`. Состояния:
`empty → alive(k) → draining → dead`. `draining` обязано быть явным — интервал
между уходом последнего и смертью существует всегда, и если его не назвать, он
живёт неявно в таймерах.

## 4. Контракты адаптеров

### 4.1. `room-identity.js` **[C]**

```js
createEphemeralIdentity() -> {pubkeyHex, privKey, dbKey: null}
```

Генерирует случайный ключ, выводит только то, что нужно для подписи событий.
**Ничего не пишет в Dexie. Не создаёт keystore. Не вызывает `login()`.**

И7 проверяется прямо: после закрытия вкладки в IndexedDB нет ни следа.

### 4.2. `room-transport.js` **[C]**

```js
openRoomTransport({relayUrl, hTopic, selfPubkey, onEvent}) -> {publish, close}
```

Собрать из существующих примитивов, каждый из которых принимает соединение явным
параметром:

```js
const conn = createRelayConnection(relayUrl, { onStateChange });  // relay-pool.js:36
conn.connect();
await waitForConnState(conn, s => s === "connected", 8000);
const publisher  = createPublisher(conn);                          // core/transport/publisher.js
const subscriber = createSubscriber(conn, {verifyBatch, onBatch, onEose});
```

Одна подписка `{kinds:[...ROOM_KINDS], "#h":[hTopic]}`. Никакого доступа к
module-level `connection` из `transport.js`.

**Предфильтр обязателен.** События сигналинга адресованы конкретному участнику и
зашифрованы NIP-44 на его ключ (§5.3). Транспорт отсеивает чужие **по тегу `p` до
попытки расшифровки** — расшифровка чужого события бросит исключение, и ловить
его как штатный поток управления недопустимо.

Реконнект — переиспользовать существующий backoff-автомат соединения, он уже
написан и протестирован (этап 16). `createRelayPool` — на будущее, комнате на
первое время хватит одного релея.

### 4.3. `mesh-supervisor.js` **[C]** — ключевое решение по переиспользованию

**Существующий звонковый слой не переписывается.** Голосовая комната — это
`n(n−1)/2` экземпляров уже работающего парного автомата под управлением
супервизора.

Разведка подтвердила, что это возможно без правок: `call-fsm.js` — чистая
`reduce(state, event) → {state, commands}` без module-level состояния;
`createMediaController` и `createCallRuntime` — фабрики с состоянием в замыкании.
n экземпляров не конфликтуют.

Существующий FSM разрешает glare сравнением pubkey — это в точности ориентация
ребра в турнире (ROOMS-MATH §4.2). На каждом отдельном ребре он уже делает
правильную вещь без единой правки.

```js
createMeshSupervisor({
  selfPubkey, selfPrivKey, hTopic, publish, maxVoice, getUserMedia
}) -> {
  joinVoice(), leaveVoice(), updateRoster(pubkeys),
  onSignal(payload, senderPubkey), getEdgeStates()
}
```

**Владение микрофоном — у супервизора, не у дочерних экземпляров.**

`media-controller.js:47-54` при команде `ACQUIRE_MIC` сам вызывает
`getUserMediaImpl`. Если пустить каждое ребро по обычному пути FSM, получится
`n−1` независимых запросов микрофона на одном устройстве. Браузеры это обычно
допускают, но работа выброшена, а поведение хрупкое.

Решение не требует правки файлов: `getUserMediaImpl` уже инъецируется
(`media-controller.js:13`). Супервизор захватывает поток один раз при
`joinVoice()` и передаёт каждому потомку свой `getUserMediaImpl`, возвращающий
готовый поток.

**Но передавать надо клон, а не сам поток.** Если `media-controller` на teardown
вызывает `track.stop()`, закрытие одного ребра погасит микрофон у всех
одновременно — трек общий. Один участник с плохим NAT отваливается, звук
пропадает во всей комнате, отладка такого занимает вечер.

```js
const childGetUserMedia = () => Promise.resolve(sharedStream.clone());
```

`clone()` разделяет источник, но останавливается независимо. Накладных расходов
не добавляет: в mesh браузер всё равно кодирует поток отдельно на каждое
соединение.

Освобождение общего потока — один раз, в `leaveVoice()`.

**Изоляция отказов.** Падение одного ребра не трогает остальные. Ребро
пересоздаётся по своему собственному backoff, состав комнаты при этом не
меняется.

`MAX_VOICE_PARTICIPANTS = 5` — **одна именованная константа в одном месте** (Р4).
Число будет меняться после замеров на VPS; ничто в коде не должно предполагать
конкретно пятерых.

### 4.4. `audio-graph.js` **[C]**

```js
createAudioGraph() -> {
  addStream(pubkey, stream), removeStream(pubkey),
  setMasterGain(v), getSpectrum(), getLevels()
}
```

Ровно один `AnalyserNode` с `fftSize = 2048` на сведённой шине — для
спектрограммы. Уровни по участникам — `getByteTimeDomainData` с `fftSize = 256`,
RMS, **без FFT** (ROOMS-ALGO §7.3). Громкость — `setTargetAtTime`, не присваивание
(щелчок).

И15: `getByteFrequencyData` вызывается не более раза на кадр независимо от числа
участников.

## 5. Протокол: события

### 5.1. Событийные kind комнаты

Четыре kind, все эфемерные (20000–29999), все с тегом `h`.

| Событие | Шифруется на | Кто публикует | Частота |
|---|---|---|---|
| `ROOM_ANNOUNCE` | `k_rv` | один по Trickle | ~1/интервал |
| `ROOM_PROBE` | `k_rv` | входящий | 1 при входе |
| `ROOM_PRESENCE` | `k_sess` | каждый за себя | 1/δ |
| `ROOM_CHAT` | `k_sess` | отправитель | по факту |

Плюс существующий kind 20075 для сигналинга голоса (§5.3).

**Анонс и presence — разные события, и это требование, а не стиль.** Анонс
идентичен у всех и потому подавляется Trickle; presence утверждает присутствие
конкретного человека и подавлению не подлежит. Слияние их в одно уничтожает
возможность подавления (ROOMS-ALGO §4.4).

Анонс шифруется на `k_rv`, а не на `k_sess` — иначе новичок не сможет его
прочитать, ведь `k_sess` выводится из соли, которая лежит внутри анонса.

**Номера kind брать из нового `src/domain/events/kind-registry.js`.** В проекте
уже есть коллизия 3007 между `files/sync.js` и `channel-access.js` ровно потому,
что номера выбирались локально в доменных файлах. Реестр завести этой задачей,
существующие номера в него перенести.

### 5.2. Проба — исправление к ROOMS-ALGO

Trickle растит интервал до 60 секунд. Новый гость, подписавшись, ждал бы до
минуты до появления анонса — для «Быстрой связи» неприемлемо.

Решение: вход публикует `ROOM_PROBE`. Присутствующие трактуют пробу как
**несогласованность** в терминах Trickle, сбрасывают интервал в `iMin` и
отвечают анонсом немедленно.

Побочный эффект приятный: **если за 3 секунды ответа нет — комнаты нет.** Форма
«создать комнату» показывается по таймауту, отдельной логики обнаружения
отсутствия не требуется.

### 5.3. Сигналинг остаётся на NIP-44 — решение и обоснование

Разведка установила: `signaling-adapter.js:15` шифрует
`nip44Encrypt(plaintext, privKey, peerPubkey)` — асимметрично, на пару ключей;
`buildCallSignalEvent(:16)` ставит `tags: [["p", peerPubkey]]`.

Напрашивающийся вывод — завести симметричный режим на `k_sess` по образцу
`channel-key.js` — **отвергается**.

Обоснование. Сигналинг парен по своей природе: offer, answer и ICE-кандидаты
ребра `(A, B)` не имеют смысла ни для кого, кроме A и B. Ключи участников
комнаты — обычные nostr-ключи, просто эфемерные, и NIP-44 работает с ними так же,
как с постоянными. Шифрование менять не нужно вовсе.

Шифрование на `k_sess` дало бы всем участникам комнаты доступ к чужому
сигналингу. Для пятерых в голосе это почти безразлично — они всё равно узнают
адреса друг друга через ICE напрямую. Но участник, сидящий **только в чате**,
получил бы ICE-кандидаты всех голосовых, ни в чём не участвуя. Попарное
шифрование закрывает это бесплатно. Плюс не появляется второй режим внутри
адаптера, а значит нет развилки, которую надо тестировать дважды.

Требуемые правки — минимальные:

1. `buildCallSignalEvent` принимает необязательный `hTopic` и добавляет **второй
   тег**: `tags: [["p", peerPubkey], ["h", hTopic]]`. Первый адресует получателя,
   второй ловится подпиской комнаты. `nip44Encrypt` не трогается.
2. `call-runtime.js:119` пробрасывает `hTopic` в `ctx` рядом с `peerPubkey`.
3. Предфильтр по тегу `p` в `room-transport.js` (§4.2).

`toFsmEvent`, `call-fsm.js`, `media-controller.js` не трогаются вообще.

### 5.4. Последствия эфемерности — записать в UI

Гость, вошедший в 15:00, **не видит ничего, сказанного до 15:00.** Истории нет,
скроллбэка нет, догрузки нет. Это следствие эфемерных событий и оно снимает целый
пласт работы (нет пагинации, нет backfill, нет `since`).

Второе: сообщение, отправленное в момент, когда получатель на секунду отвалился,
**теряется навсегда** — outbox и ретраи в комнате отсутствуют.

Оба факта — в интерфейсе словами: «сообщения не сохраняются и не догружаются».

## 7. Деградация и изоляция отказов

| Отказ | Поведение |
|---|---|
| TURN недоступен | голос не поднимается, **текст работает**, в UI явное сообщение |
| Одно ребро mesh не соединилось | остальные работают, у пары взаимная тишина с пометкой |
| Одно ребро закрылось | **микрофон и остальные рёбра не затронуты** (клон трека, §4.3) |
| Релей отвалился | реконнект существующим backoff; presence истекает у всех, комната «замирает», при возврате оживает |
| Микрофон запрещён | вход в комнату разрешён в режиме слушателя |
| Голосовая часть занята | вход в комнату разрешён, только чат |

Общий принцип: **текст не зависит от голоса ни в одном сценарии.** Голосовая
часть — надстройка, её отказ не должен уводить пользователя из комнаты.

## 8. Чего в этой фиче не будет

Явный список экономит время, которое иначе уйдёт в достройку.

- Файлы и вложения (Р3).
- История и скроллбэк (§5.4).
- Роль создателя, модерация, изгнание (Р5).
- Видео.
- Запись разговора.
- Более пяти в голосе (Р4).
- Персистентность любого рода.
- Уборщик мусора на релее — смерть комнаты есть отсутствие событий, удалять
  нечего.
- Симметричный режим шифрования сигналинга (§5.3).

## 9. Реестр рисков

| # | Риск | Вероятность | Цена | Как снимается |
|---|---|---|---|---|
| R1 | strfry не рассылает эфемерные события | средняя | вся модель | спайк 0.1, **до всего** |
| R2 | mesh не тянет пятерых на мобильной сети | **высокая** | лимит вниз до 3–4 | замер на VPS, константа в одном месте |
| R3 | Открытая запись на релее (`whitelist:["*"]`) уедет на VPS | **подтверждён актуальным** | открытый релей в интернете | отдельный пункт чек-листа деплоя |
| R4 | Argon2 в 100 мс на слабом телефоне окажется 500 мс | средняя | UX входа | замер на реальном устройстве, подстройка параметров |
| R5 | `media-controller` останавливает общий трек на teardown | средняя | звук пропадает у всех при уходе одного | клон трека (§4.3); проверка в спайке 0.3 |
| R6 | Гостевые события засоряют релей | низкая | рост базы | эфемерность решает; подтверждается спайком 0.1 |

**Снят разведкой:** «синглтоны в звонковом слое помешают n экземплярам» —
`call-fsm` чист, `media-controller` и `call-runtime` фабричны.
