# MEDIA-ALGO.md — алгоритмический фундамент медиа-подсистемы

Продолжение `MEDIA-MATH.md`. Там доказано, *что* должно быть верно; здесь
выбирается, *как* это считать, и сколько это стоит.

Порядок работы принят обычный: сначала перепись операций с частотой, потом
поиск горячих точек и скрытых квадратов, потом структуры данных под
найденное, и только потом алгоритмы. Обратный порядок («возьмём красивый
алгоритм и найдём ему применение») даёт красивый код, решающий не ту
задачу.

Обозначения из `MEDIA-MATH.md` §1 сохранены. Дополнительно: `m` — число
сообщений в области, `k` — число постов в ленте, `N = ⌈S/C⌉` — число
чанков.

---

## §1. Перепись операций

Частота — порядок величины на одну пользовательскую сессию. «На кадр»
означает, что операция может попасть в путь перерисовки.

| # | Операция | Частота | Вход | Наивная стоимость |
|---|---|---|---|---|
| O1 | Собрать `L(Ω)` | ~10 | дерево области | `Θ(m + \|L\|)` |
| O2 | Вычислить `B(Ω)` — набор кнопок | **на кадр**, для каждого поста ленты | область | `Θ(m)` каждый раз |
| O3 | `next` / `prev` | ~10³ | `L`, позиция | `Θ(\|L\|)` наивно |
| O4 | Клик по вложению → индекс в классе | ~10² | `L`, позиция | `Θ(\|L\|)` |
| O5 | Пересчёт `Alloc` при смене позиции | ~10³ | окно `W(i)` | `Θ(\|W\|)` |
| O6 | Чтение диапазона (перемотка, буферизация) | ~10⁴ | `(d, κ, [a,b])` | `Θ(⌈ℓ/C⌉)` сетевых чанков |
| O7 | Расшифровка чанка | ~10⁵ | чанк | `Θ(C)`, ЦП |
| O8 | Загрузка файла (шифрование+отправка) | ~10² | `S` байт | `Θ(S)`, ЦП+сеть |
| O9 | Переход автомата | ~10³ | `(q, событие)` | `Θ(1)` |
| O10 | Поддержка индекса классов в дереве файлов | ~10³ | операция CRDT | `Θ(1)` при индексе |
| O11 | Миниатюры папки | ~10³ | манифест + байты | `Θ(S_i)` на файл |

Из таблицы сразу видно распределение: **тяжёлое — это O6–O8** (там байты,
сеть и криптография), **опасное — это O2** (там перерисовка и скрытый
квадрат), **остальное — мелочь**, которую легко испортить, но которая при
правильных структурах стоит `Θ(1)`.

## §2. Где на самом деле тяжело

### 2.1. Три настоящие горячие точки

**Г1. Криптография на каждый байт (O7, O8).** Сейчас загрузка делает по
файлу **три полных прохода**: ChaCha20 (шифрование), sha256 по каждому
чанку, sha256 по всему шифротексту. Чтение делает два: sha256 чанка и
затем расшифровка с проверкой Poly1305.

Если подтвердится гипотеза `MEDIA-MATH.md` §8.3 (массив дайджестов чанков
избыточен, потому что AEAD уже аутентифицирует), это снимает **один полный
проход sha256 и при записи, и при чтении** — треть работы на записи и
примерно треть на чтении. При пропускной способности sha256 в JS порядка
сотен МБ/с (оценка, требует замера) на четырёх гигабайтах это десятки
секунд. Ни один другой пункт этого документа не даёт такой экономии.

**Г2. Пропускная способность сети при воспроизведении (O6).** Здесь
алгоритм почти ничего не решает — решает глубина упреждающей подкачки.
Она выводится: чтобы воспроизведение не прерывалось, следующий чанк должен
приехать раньше, чем кончится текущий. При битрейте `b`, полосе `B` и
задержке `RTT` время проигрывания одного чанка равно `C/b`, время его
доставки — `RTT + C/B`. Требуется глубина

    k ≥ (RTT + C/B) · b / C

При `RTT = 100 мс`, `B = 10 Мбит/с`, `b = 5 Мбит/с`, `C = 512 КиБ`
получается `k ≈ 0.6`, то есть `k = 1` (нынешнее «один чанк вперёд»)
достаточно **с запасом вдвое**. Но при `b → B` формула расходится: на
слабой сети либо растить `k`, либо честно признать, что файл не играется
в реальном времени. Вывод: нынешняя подкачка на один чанк — не заглушка,
а обоснованное значение для нормальной сети; менять её надо только по
замеру, а не «на всякий случай».

**Г3. Первый кадр (O6 + манифест).** Разобрано в `MEDIA-MATH.md` §8.2:
стоимость старта `2√(h·S)` при `C = C*(S)`. Алгоритмическая часть здесь
тривиальна — таблица размеров чанка по размеру файла.

### 2.2. Два скрытых квадрата

**Q1. Кнопки в ленте канала — Θ(k·m).** Это не гипотеза, это возврат уже
случившейся в проекте ошибки. В истории кода счётчик «Комментарии (N)»
сначала считался внутри каждой карточки поста, и его пришлось переделать в
**один скан таблицы на всю ленту** (`countCommentsByPost`), потому что
`k` отдельных полных сканов давали квадрат.

Кнопки «Аудио / Видео / Картинки» над постом требуют ровно того же
входа — медиа поста *и его комментариев*. Если каждая карточка ленты будет
собирать свои комментарии, получится тот же квадрат, только дороже
(вложения, а не счётчики).

**Решение:** одна функция `mediaClassesByPost(ownerPubkey, dbKey)` — один
проход по таблице комментариев и один по постам, результат
`Map<postId, Int32Array(4)>` со счётчиками классов. Стоимость `Θ(m)` на
всю ленту вместо `Θ(k·m)`. Пересчёт — при изменении набора сообщений, не
на кадр; в терминах Preact это `computed`, зависящий от сигнала списка, а
не вычисление в теле компонента.

**Q2. Дозаливка `mime` в старые узлы.** Ленивая дозаливка
(`MEDIA-MATH.md` §7.3) безопасна по сходимости, но если её запускать «для
всех узлов без `mime`» на каждое открытие папки, получится повторный
обход всего дерева. Дозаливка должна быть событийной: манифест всё равно
загружен (миниатюра, открытие файла) → записали `mime` заодно. Никаких
фоновых проходов.

## §3. Структуры данных

Каждый пункт: что берём, почему, и от чего отказались.

### 3.1. Плейлист — плоский неизменяемый массив + три индекса

    L      : Array<MediaItem>       // снимок, |L| ≤ ~10⁴
    idx[c] : Int32Array             // позиции элементов класса c, по возрастанию
    rank   : Int32Array(|L|)        // позиция → её номер внутри своего класса
    class  : Uint8Array(|L|)        // позиция → класс (0..3)

Это **правка к `MEDIA-MATH.md` §4.2.** Там сказано «не хранить три
плейлиста, хранить `L` + позицию + класс», и это верно про *данные*: три
копии элементов не нужны. Но три массива *индексов* — не копии данных, а
индекс, и они превращают O3 и O4 из `Θ(|L|)` в `Θ(1)`:

- `next` внутри класса `c` из позиции `p`: `idx[c][rank[p] + 1]`;
- клик по позиции `p`: класс `class[p]`, номер `rank[p]` — сразу, без
  подсчёта предшественников.

Стоимость построения — один проход `Θ(|L|)` в момент снимка, то есть один
раз за открытие. Память при `|L| = 10⁴`: `4·|L| + 4·|L| + |L| ≈ 90 КБ`.
Типизированные массивы, а не обычные — не из педантизма, а потому что
обычный `Array` чисел в JS хранит указатели на боксированные значения;
на `10⁴` разница невелика, но `Int32Array` здесь ничего не усложняет.

Неизменяемость снимка — не эстетика: она **уничтожает целый класс ошибок
инвалидации**. Индексы нельзя рассинхронизировать с данными, если данные
не меняются.

*Отвергнуто:* связный список (нужен произвольный доступ по индексу для
клика), сбалансированное дерево (нет вставок), пропускающий список (то же).

### 3.2. Учёт ресурсов — мультимножество по дайджесту

    alloc : Map<digest, refcount>

Из неинъективности «позиция → дайджест» (`MEDIA-MATH.md` §3.4) следует,
что множества здесь мало: два соседних элемента окна могут указывать на
один блоб. Освобождение по счётчику ссылок, а не по факту выхода позиции
из окна.

*Отвергнуто:* `Set<digest>` — ломается ровно на дубликатах, то есть
редко, и потому диагностируется тяжело.

### 3.3. Окно предзагрузки по бюджету — префиксные суммы и два указателя

Окно `W(i)` определено как наибольшее по включению окно вокруг `i`,
укладывающееся в бюджет байтов. Размеры элементов известны заранее
(лежат в дескрипторе), значит можно один раз построить префиксные суммы:

    pref : Float64Array(|L|+1),  pref[j+1] = pref[j] + size(L[j])

Тогда суммарный размер `[l, r)` — это `pref[r] - pref[l]` за `Θ(1)`, а
границы окна ищутся либо двоичным поиском (`Θ(log |L|)`), либо — что
уместнее — **двумя указателями**: при переходе `i → i±1` границы окна
двигаются монотонно, значит суммарная работа за всю сессию линейна, а не
`Θ(log |L|)` на каждый шаг.

Float64, а не Int32: суммарный размер плейлиста легко превышает 2 ГБ.
Это ровно та ошибка на границе типа, которая проявляется только у
пользователя с большой папкой.

*Отвергнуто:* дерево отрезков (обновлений нет — снимок), фенвиково дерево
(то же).

### 3.4. Кэш чанков — окно вместо LRU

Сейчас: общий LRU на 32 МБ, ключ `blobSha256:index`.

Наблюдение, вытекающее прямо из инварианта единственности
(`MEDIA-MATH.md` Утв. 5): **одновременно играет ровно один файл**. Значит
кэш не обслуживает конкуренцию между файлами — он обслуживает одну
последовательность обращений, и эта последовательность **предсказуема**:
воспроизведение идёт вперёд монотонно, изредка прерываясь скачком.

Когда будущее известно, оптимальная политика вытеснения известна тоже —
это Белади: вытесняй то, что понадобится позже всего. Для последовательного
чтения Белади вырождается в «вытесняй уже проигранное». LRU делает ровно
обратное: держит недавно прочитанное, то есть **самое ненужное**. Это
классическое «загрязнение LRU последовательным сканом».

Практический вывод, однако, скромный, и я не буду его раздувать: при
последовательном чтении промах кэша всё равно закрывается сетевым
запросом, который браузер и так делает; выгода LRU здесь близка к нулю, но
и вреда, кроме удержания 32 МБ, нет. Поэтому:

- **Держать окно `[i-2, i+k]` чанков текущего файла** — назад немного, на
  случай короткой перемотки назад, вперёд по формуле Г2.
- Бюджет снизить с 32 МБ до `(k+3)·C` — при `C = 512 КиБ` и `k = 2` это
  2.5 МБ вместо 32.
- Отдельно и навсегда держать **чанк 0**: с него начинается любое
  повторное открытие файла.

Это не оптимизация ради скорости — это освобождение 30 МБ на телефоне.

*Отвергнуто:* ARC, 2Q, LIRS — все они умны там, где будущее неизвестно; у
нас оно известно, и платить за адаптивность нечем.

### 3.5. Индекс классов в дереве файлов

    classCount : Map<parentId, Int32Array(4)>

Ровно по образцу уже существующих в `tree.js` производных индексов
`children` и `namesInDir`: живёт в памяти, не в БД, поддерживается за
`Θ(1)` на операцию, восстанавливается при загрузке состояния.

Поддержка проще, чем у `namesInDir`, потому что **класс узла неизменяем**
(`MEDIA-MATH.md` Утв. 8): `create` увеличивает счётчик, `purge` уменьшает,
`setPar` уменьшает у старого родителя и увеличивает у нового,
`setName` не трогает вовсе. Четыре строки, ни одного разбора случаев.

`B(папка)` = `Θ(1)`: три сравнения счётчиков с нулём.

### 3.6. Карта загруженных чанков — битовая маска

Для возобновляемой загрузки (если выбран вариант «блоб на чанк»,
`MEDIA-MATH.md` §8.4):

    uploaded : Uint8Array(⌈N/8⌉)

При `S = 4 ГиБ`, `C = 512 КиБ`: `N = 8192`, маска — **1 КБ**. Хранится в
IndexedDB рядом с черновиком загрузки. Возобновление — найти первый
нулевой бит, продолжить оттуда; проверка «всё ли загружено» — сравнение с
маской единиц.

Альтернатива «спросить сервер, какие чанки есть» стоит `N` запросов
HEAD — 8192 запроса только чтобы узнать, с чего продолжить. Локальная
битовая маска дешевле на четыре порядка.

### 3.7. Таблица переходов автомата

    δ : Map<(состояние_ярлык, событие), функция>

Именно таблица, а не `switch`. Причина не в стиле, а в §4.6: таблицу можно
**обойти как граф** и проверить исчерпывающе, а `switch` — нет.

### 3.8. Медиа-индекс личного чата — материализованное представление

Открытый вопрос 4 из `MEDIA-MATH.md`: брать медиа только из загруженного
окна или из всей истории. Алгоритмически ответ определяется ограничением,
которого нет ни в одном учебнике по БД:

**По зашифрованному полю нельзя построить индекс.** Вложения лежат внутри
шифруемых полей строки сообщения. Значит запрос «все аудио этого чата»
при `m = 10⁵` сообщений требует расшифровать `10⁵` строк — секунды ЦП, и
не один раз, а при каждом открытии плеера.

Выход — не индекс, а **материализованное представление**: отдельная
таблица `chat_media (ownerPubkey, contactPubkey, lamportTs, msgId,
attachmentIndex, digest, класс, mime, name, size)`, дописываемая при
отправке и при получении сообщения. Стоимость поддержки `Θ(1)` на
сообщение, стоимость запроса — `Θ(|результат|)` вместо `Θ(m)`.

Содержимое строки такое же чувствительное, как исходное сообщение, и
шифруется тем же ключом БД — но ключ выборки (`contactPubkey`, `lamportTs`)
остаётся открытым, ровно как в существующих таблицах проекта. То есть
приём не новый, а уже принятый в этом коде.

*Замечание о честности:* это не бесплатно. Появляется вторая копия
метаданных, которую надо чистить при удалении сообщения и при очистке
истории — то есть новая пара инвариантов «не осталось сирот». Если
решишь, что область плейлиста в чате — только загруженное окно, всей этой
структуры не нужно вовсе. Размен: **полнота плейлиста против второй
таблицы, которую надо держать согласованной.**

## §4. Алгоритмы

### 4.1. Сбор плейлиста — итеративный прямой обход

Прямой обход дерева комментариев с **явным стеком**, не рекурсией.

Причина конкретна: глубина вложенности ответов ничем не ограничена, а в
коде уже отмечен случай «осиротевшего» комментария, чей родитель
отсутствует локально — то есть структура пришедших данных не под нашим
контролем. Цепочка ответов длиной `10⁴` при рекурсии кладёт стек, при
явном стеке — нет. Стоимость одинакова, `Θ(m)`; страховка бесплатна.

    сбор(T):
      L ← []
      стек ← [корень]
      пока стек не пуст:
        x ← стек.pop()
        для каждого вложения a из A(x): L.push(a)
        дети ← отсортированные_дети(x)
        для j от |дети|-1 до 0: стек.push(дети[j])   # обратный порядок
      вернуть L

Обратный порядок при укладке в стек — то место, где ошибка даёт
зеркальный порядок трека и не ловится глазами на двух комментариях.
Тест: дерево «корень → A, B; A → A1, A2» должно дать `A, A1, A2, B`.

Сортировка братьев — **той же функцией сравнения**, что и отрисовка
(`MEDIA-MATH.md` Утв. 2). Не «такой же», а той же: общий экспорт.

Дедупликация (для аудио и видео, по соглашению §3.4 матдокумента) —
`Set<digest>` в том же проходе, `Θ(|L|)` ожидаемо.

### 4.2. Построение классовых индексов — один проход, два прохода по счётчику

Классический приём «подсчёт, затем размещение» (тот же, что в основе
сортировки подсчётом):

    проход 1: cnt[c] ← число элементов класса c
    выделить idx[c] ← Int32Array(cnt[c])
    проход 2: для p от 0 до |L|-1:
                c ← class[p]; r ← pos[c]++; idx[c][r] ← p; rank[p] ← r

Два прохода вместо одного — ради точного выделения памяти без
перевыделений. `Θ(|L|)` времени, `Θ(|L|)` памяти, ноль перевыделений.

Наивная альтернатива `idx[c] = L.map(...).filter(...)` для каждого из трёх
классов — это `3|L|` с тремя промежуточными массивами и ростом по мере
push. Разница на `10⁴` невелика, но приём стоит одну строку.

### 4.3. Кнопки — один скан на ленту

Разобрано в §2.2 (Q1). Алгоритм:

    mediaClassesByPost():
      acc ← Map<postId, Int32Array(4)>
      один проход по всем постам:      учесть вложения поста
      один проход по всем комментариям: учесть вложения по comment.postId
      вернуть acc

`Θ(k + m)` на всю ленту. `B(пост)` = три сравнения с нулём.

Для папки — `classCount` из §3.5, `Θ(1)`.
Для чата — счётчики из материализованного представления §3.8 либо из
загруженного окна, `Θ(1)` после свёртки.

### 4.4. Окно ресурсов — два указателя и разность мультимножеств

    при переходе i → i':
      (l', r') ← сдвинуть_границы(l, r, i')       # два указателя, амортизированно Θ(1)
      для p ∈ [l, r) \ [l', r'):  release(digest(L[p]))   # refcount--
      для p ∈ [l', r') \ [l, r):  acquire(digest(L[p]))   # refcount++

`release` физически освобождает ресурс только при обнулении счётчика.
Инвариант Утв. 7 матдокумента выполняется по построению: живые ресурсы —
в точности те, у кого счётчик положителен, а счётчик — функция от
`[l, r)`, то есть от состояния.

При скачке (`seek` на произвольную позицию, а не соседнюю) окна могут не
пересекаться — тогда работа `Θ(|W|)`, что при бюджетном окне из
единиц элементов несущественно.

### 4.5. Перемотка — гашение устаревших запросов монотонным жетоном

Протаскивание ползунка порождает поток `seek`. Классическая гонка: ответ
на ранний запрос приходит позже, чем на поздний, и перетирает его.

Мост «страница ↔ service worker» уже корректирует *параллельные* запросы
по `requestId`, но не решает, какой из ответов актуален. На стороне плеера
нужен монотонный счётчик поколений:

    generation ← generation + 1 при каждом seek
    ответ принимается ⟺ его generation == текущему

Плюс `AbortController` на отменяемые сетевые запросы (в `putStream`
`signal` уже проброшен — тот же приём). Это буквально «побеждает
последний», записанное явно, а не подразумеваемое.

### 4.6. Проверка автомата — исчерпывающий обход в ширину

Самый выгодный пункт документа по соотношению «польза / трудозатраты».

Пространство состояний автомата из `MEDIA-MATH.md` §5 конечно и мало:
`3` класса × `2` вида отображения × `3` режима воспроизведения + `⊥`,
в произведении с состоянием звонка (`активен` / `нет`) — порядка
**40 абстрактных состояний** и порядка **11 событий**, то есть ~440
переходов. Это не «слишком много, чтобы перебрать» — это меньше, чем
строк в одном компоненте.

Значит проверка инвариантов делается не рассуждением и не выборочными
тестами, а **обходом в ширину по графу достижимости**:

    проверить():
      очередь ← [q₀]; посещённые ← {q₀}
      пока очередь не пуста:
        q ← очередь.shift()
        для каждого события e ∈ Σ:
          q' ← δ(q, e)                      # тотальность: δ определена всегда
          проверить И1: не более одного активного микроприложения
          проверить И2: playing ⟹ звонок неактивен
          проверить И3: q' = ⊥ ⟹ Alloc(q') = ∅
          если q' ∉ посещённые: добавить

Это ограниченная проверка модели «в лоб» — метод старый, простой и здесь
исчерпывающий, потому что граф целиком помещается в память. Даёт то, чего
не даст ни один набор сценарных тестов: **гарантию, что не существует
последовательности событий, приводящей к нарушению**. И одновременно
проверяет тотальность `δ` — ту самую забытую ветку, из-за которой
«звонок ставит на паузу, а человек жмёт play».

Тест чистый, без DOM, идёт в `node --test` — ровно тот стиль, который в
проекте уже принят («чистая логика отдельно от браузерной обвязки»).

### 4.7. Загрузка — конвейер с ограниченной очередью

Из `MEDIA-MATH.md` Утв. 11: выигрыш даёт перекрытие стадий, а не их
порядок. Реализация — классический «производитель–потребитель» с
ограниченным буфером:

    производитель: срез файла → шифрование → инкрементальный хеш → очередь
    потребитель:   очередь → отправка
    |очередь| ≤ 2

Ограничение очереди двойкой — это и есть граница памяти: `≤ 2C` в очереди
плюс `2C` в работе производителя, итого `Θ(C)`, как требует Утв. 10.
Неограниченная очередь мгновенно возвращает нас к «файл целиком в памяти»,
только окольным путём.

Порядок файлов при мультизагрузке: по возрастанию размера. Обоснование не
в правиле Джонсона (оно здесь вырождается, и выигрыш ограничен одной
стадией одного файла), а в отзывчивости: мелкие файлы появляются в списке
сразу, и процесс выглядит живым.

Шифрование — в Web Worker (`Comlink` в проекте уже есть). Иначе
`Θ(S)` ChaCha20 держит главный поток и интерфейс замирает ровно тогда,
когда пользователь ждёт прогресса.

### 4.8. Выбор размера чанка — таблица, а не формула в бою

`C*(S) = √(h·S)` (`MEDIA-MATH.md` §8.2), округлённое до степени двойки и
зажатое в `[64 КиБ, 4 МиБ]`:

    C(S) = clamp(2^round(log₂ √(h·S)), 64 КиБ, 4 МиБ)

Функция около минимума пологая: отклонение `C` вдвое даёт рост стоимости
на 25%. Значит ступеней достаточно грубых, и никакой подстройки в бою не
нужно. `chunkSize` хранится в манифесте — старые файлы читаются как
читались.

### 4.9. Буферизованные диапазоны в полосе прокрутки

Показ «сколько уже загружено» — это объединение отрезков, классическая
задача: отсортировать по левой границе, слить пересекающиеся,
`Θ(n log n)`.

Но у `<video>`/`<audio>` уже есть свойство `buffered` (`TimeRanges`),
которое браузер поддерживает сам и бесплатно, причём в единицах времени,
а не байтов — то есть без пересчёта через битрейт. **Свой алгоритм здесь
не нужен**; я упоминаю его только чтобы явно отказаться, а не забыть.

## §6. Что мерить (критерии готовности)

В стиле уже принятого в проекте: не «выглядит быстро», а число на реальной
сборке.

1. **Плейлист поста с 10⁴ комментариями** строится за < 50 мс. Проверяет
   отсутствие квадрата в обходе.
2. **Лента из 100 постов** вычисляет все наборы кнопок одним сканом:
   время не растёт при увеличении числа постов вдесятеро больше, чем
   линейно. Прямая проверка на Q1.
3. **`next` при `|L|` от 10 до 10⁴** — время не растёт. Проверяет, что
   индексы реально используются, а не построены и забыты.
4. **Папка на 10⁴ узлов**: набор кнопок известен в том же кадре, что и
   список. Проверяет `classCount`.
5. **Загрузка файла 2 ГБ**: пиковая резидентная память вкладки < 100 МБ.
   Это единственная проверка гипотезы о выгрузке `Blob` на диск
   (`MEDIA-MATH.md` §8.4) — рассуждением она не закрывается.
6. **Дерево ответов глубиной 10⁴** не роняет стек.
7. **Обход автомата**: все достижимые состояния перебраны, три инварианта
   выполнены, `δ` тотальна. Тест падает, если добавлено событие без
   обработки.
8. **Воспроизведение 4 ГБ видео**: время до первого кадра, перемотка в
   середину, перемотка назад. Три числа, к которым потом можно
   возвращаться.
9. **Пиковая память при просмотре 50 изображений подряд** — не растёт
   монотонно. Прямая проверка Утв. 7.

## §7. Что рассмотрено и отвергнуто

Раздел нужен, чтобы через полгода не вернуться к тем же идеям.

- **ARC / 2Q / LIRS** для кэша чанков — адаптивность к неизвестному
  будущему, а будущее известно (§3.4).
- **Дерево отрезков / фенвиково дерево** для окна по бюджету — нет
  обновлений, снимок неизменяем; префиксные суммы достаточны.
- **Правило Джонсона в общем виде** — вырождается при стадиях,
  пропорциональных размеру (`MEDIA-MATH.md` Утв. 11).
- **Приоритетная очередь загрузок** — приоритет фиксирован (по
  возрастанию размера), очередь FIFO после сортировки достаточна.
- **Индекс БД по `mime` вложения** — невозможен: поле зашифровано (§3.8).
- **Своё объединение отрезков для полосы буферизации** — нативный
  `TimeRanges` (§4.9).
- **Библиотека плеера** — не алгоритмический вопрос, но повторю вывод из
  матдокумента: она подразумевает источник, читаемый целиком, что
  противоречит `Θ(√(h·S))` старту.
- **Фоновая дозаливка `mime` по всему дереву** — Q2; только событийно.

## §9. Соблазнительное, но неверное

**«Плейлист — это же просто отфильтрованный массив. `L.filter(m => m.class
=== c)` внутри компонента, и всё; на нескольких десятках треков разницы
никакой».**

Притягательно тем, что это правда — на нескольких десятках. Ломается
дважды. Во-первых, `filter` внутри тела компонента выполняется на **каждый
кадр перерисовки**, а не на каждое изменение данных: `Θ(|L|)` умножается
на частоту обновления полосы воспроизведения, то есть примерно на 60 в
секунду. Во-вторых, `filter` порождает новый массив с новой ссылкой на
каждом вызове, что для сравнения по ссылке (а на нём стоит вся
реактивность Preact) означает «данные изменились» — и запускает
перерисовку, которая снова вызовет `filter`. Получается не квадрат по
`|L|`, а самоподдерживающийся цикл, который проявляется как «интерфейс
греет телефон» и не находится профилированием на десяти треках.

**Вторая приманка того же класса:** «раз только один плеер активен, кэш
можно просто увеличить — памяти на телефоне много». Наоборот: именно
потому, что активен один файл и обращения последовательны, большой кэш
хранит **уже проигранное**, то есть заведомо ненужное. Увеличение бюджета
здесь монотонно ухудшает положение, не улучшая ни одного показателя, —
случай, когда интуиция «больше кэш — лучше» прямо противоположна истине.
