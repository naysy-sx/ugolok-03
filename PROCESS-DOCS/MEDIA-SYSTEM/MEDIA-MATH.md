# MEDIA-MATH.md — математические основания медиа-подсистемы

Область: мультизагрузка вложений, сбор медиа по области просмотра, три
микроприложения (аудио / видео / изображения), единственность активного
воспроизведения, потоковая загрузка.

Документ формализует задачу и доказывает то, что можно доказать до кода.
Всё, что не доказано, помечено как **гипотеза** или **соглашение** (выбор,
который ничем не вынужден и делается по вкусу — но делается ОДИН раз и
записывается).

---

## §0. Дано

Аксиомы взяты не из воздуха — это факты, прочитанные в текущем коде.
Дальнейшие рассуждения опираются только на них.

**A1 (адресация содержимого).** Всякий файл в системе однозначно задаётся
парой `(d, κ)`, где `d` — дайджест манифеста (`manifestDigest`, он же
`Node.blob` в дереве «Файлы»), `κ` — ключ файла. Манифест содержит
`size`, `mime`, `name`, `chunkSize`, `blobSha256`, массив дайджестов
чанков. Из A1 следует: источники «Файлы», «вложение чата», «вложение
поста», «вложение комментария» — одного типа, различаются только
происхождением, а не природой.

**A2 (потоковое чтение уже есть).** Существует отображение
`(d, κ, [a,b]) → байты [a,b] исходного файла`, реализованное как
`getRange`, и его же — через виртуальный путь `/files-content/{d}`,
перехватываемый service worker'ом. Стоимость чтения диапазона длины `ℓ`
из файла размера `S` при размере чанка `C` равна `⌈ℓ/C⌉ + 1` сетевым
чанкам, а не `S` — то есть перемотка стоит O(1) от размера файла.

**A3 (неизменяемость `blob`).** В CRDT-дереве файлов поля `par`, `name`,
`origin` — LWW-регистры с метками Лампорта; поля `id`, `kind`, `blob`
записываются один раз операцией `create` и ни одной операцией не
изменяются. Проверено: `applyOp` обрабатывает `setPar`/`setName`/
`setOrigin`/`purge`, но не `setBlob`.

**A4 (кардинальность вложений).** В домене каналов вложения уже
множественны (`attachments: []` у поста, комментария, сообщения чата
канала); в домене личного чата — единственны (`attachment` в MLS-payload).
Версии у payload нет. Опубликованных сборок нет, следовательно множество
клиентов, которые нельзя обновить, пусто — **вариант «заменить на массив»
допустим без оговорок о совместимости.**

**A5 (звук уже имеет владельца).** Звонок — глобальное состояние уровня
приложения (`CallOverlay` вне разметки экранов, сигналы `call.js`).
Инлайновые `<audio controls>` / `<video controls>` в пузырях сообщений —
тоже источники звука, но БЕЗ общего владельца.

**A6 (виртуализация).** Личный чат рендерится окном (`loadChatWindow`,
`useVirtualWindow`) — в памяти лежит не вся история. Комментарии поста,
напротив, читаются целиком (`getCommentsTree` — один скан таблицы).

**A7 (принятые решения пользователя, вход для этого документа).**
Плейлист — снимок на момент открытия. Звонок вытесняет любое
воспроизведение. Белый список MIME не расширяется. `mime`
денормализуется в узел дерева. Порядок вложений в личном чате
переводится на массив без слоя совместимости.

## §1. Обозначения

| Знак | Смысл |
|---|---|
| `M` | медиа-элемент, кортеж `(d, κ, μ, ν, σ)`: дайджест, ключ, mime, имя, размер |
| `𝔐` | множество всех медиа-элементов |
| `c(M)` | класс элемента: `c: 𝔐 → {a, v, i, o}` (аудио, видео, изображение, прочее) |
| `Ω` | область просмотра (scope): пост+комментарии, окно чата, папка |
| `L(Ω)` | плейлист области — конечная **последовательность** элементов `𝔐` |
| `L_c` | подпоследовательность класса `c` |
| `S` | размер файла в байтах |
| `C` | размер чанка |
| `h` | стоимость одной записи о чанке в манифесте, байт |
| `n` | число живых детей папки |

Различение, на котором всё держится: `L(Ω)` — **последовательность**, а не
множество. Один и тот же файл (один `d`) может встретиться в области
дважды — при дедупликации это буквально тот же блоб. Значит отображение
«позиция в плейлисте → дайджест» **не инъективно**, и всё, что адресуется
дайджестом (ресурсы, регистрация в мосте плеера), нельзя путать с тем,
что адресуется позицией (текущий трек, переход «дальше»).

## §2. Найти

- **З1.** Определить `L(Ω)` так, чтобы порядок был тотальным,
  детерминированным и совпадал с визуальным порядком на экране.
- **З2.** Определить правило показа кнопок «Аудио / Видео / Картинки» и
  правило перехода «клик по файлу → открыть микроприложение на этом
  файле».
- **З3.** Построить автомат, в котором одновременно звучит не более
  одного источника, и доказать этот инвариант, включая взаимодействие со
  звонком и с инлайновыми элементами.
- **З4.** Указать инвариант владения ресурсами (память, ObjectURL,
  регистрация в мосте), из которого невозможность утечки следует по
  построению, а не по дисциплине программиста.
- **З5.** Доказать, что денормализация `mime` в узел дерева не нарушает
  сходимость CRDT, и оценить стоимость.
- **З6.** Найти размер чанка как функцию размера файла; указать границу
  резидентной памяти при потоковой загрузке; определить порядок файлов
  при мультизагрузке.

## §3. Решение З1 — плейлист как плоское представление дерева

### 3.1. Область есть корневое дерево

Каждая из трёх областей — корневое дерево `T = (V, E, r)` с тотальным
порядком на детях каждой вершины:

- **Пост:** `r` = пост, дети `r` = комментарии верхнего уровня, дети
  комментария = ответы. Порядок братьев — по `(createdAt, id)`.
- **Окно чата:** вырожденное дерево — путь. `r` = фиктивный корень, дети =
  сообщения окна в порядке `(lamportTs, msgId)`. Глубина 1.
- **Папка:** `r` = папка, дети = файлы (папки в плейлист не входят).
  Порядок — тот, что уже показан на экране (текущая сортировка).

Каждой вершине `x` сопоставлен конечный список её вложений `A(x)`
(в личном чате после перехода на массив — тот же список).

### 3.2. Определение

**Опр. 1.** `L(Ω) := concat_{x ∈ preorder(T)} A(x)`, где `preorder` — обход
в прямом порядке (вершина, затем поддеревья детей слева направо).

Эквивалентно: `L(Ω)` тотально упорядочен лексикографически по паре
`(p(x), j)`, где `p(x)` — номер `x` в прямом обходе, `j` — индекс вложения
внутри `x`.

**Утв. 1 (корректность).** Порядок из Опр. 1 тотален и детерминирован.

*Доказательство.* Лексикографическое произведение двух тотальных порядков
тотально. `p` тотален, поскольку прямой обход задаёт биекцию `V → {1..|V|}`
при условии тотального порядка на братьях; последний тотален, потому что
ключ `(createdAt, id)` разрешает совпадение времени по `id`, а `id`
уникален. `j` тотален как индекс в списке. ∎

**Утв. 2 (совпадение с экраном).** Порядок `L(Ω)` совпадает с порядком, в
котором пользователь видит вложения сверху вниз, тогда и только тогда,
когда отрисовка треда тоже идёт прямым обходом с тем же порядком братьев.

*Замечание.* Это не тавтология, а **проверяемое условие на код**: если
`buildTree` сортирует братьев иначе, чем сортирует их сборщик плейлиста,
пользователь получит «следующий трек» не тот, который видит ниже. Условие
надо закрыть тем, что оба используют одну функцию сравнения — не две
одинаковые на вид.

### 3.3. Снимок

По A7 плейлист — снимок. Формально: `L` вычисляется один раз в момент
перехода в состояние `open` и далее является частью состояния автомата
(§5), а не производной от состояния экрана. Следствие: закрытие
микроприложения — единственный способ обновить плейлист; вновь пришедшее
сообщение в него не попадает.

**Утв. 3.** При снимке индекс текущего элемента `i` остаётся корректным
при любых изменениях области.

*Доказательство.* `L` неизменен по построению, `i ∈ [0, |L|)` — инвариант
переходов «дальше/назад» (§5). Изменения `Ω` на `L` не влияют, т.к.
зависимость снята копированием. ∎

Это и есть содержательная цена снимка: предсказуемость куплена ценой
устаревания.

### 3.4. Ловушка идентичности

Из неинъективности «позиция → дайджест» следуют два разных вопроса, которые
легко перепутать:

1. **Дедуплицировать ли плейлист?** Соглашение (не выводится ни из чего):
   для аудио и видео — да, оставлять первое вхождение (человек не хочет
   слышать один трек дважды потому, что его процитировали в комментарии);
   для изображений — нет, порядок чтения важнее (картинка, повторённая в
   ответе, стоит на своём месте в ленте). Если выберешь единообразие —
   выбирай «не дедуплицировать», оно честнее отражает область.
2. **Освобождение ресурса.** Ресурс адресуется дайджестом. Освобождать `d`
   можно только если `d` не встречается ни в одной из позиций, которые
   сейчас должны быть загружены (§6). Иначе получишь «картинка исчезла,
   потому что её дубликат уехал из окна префетча».

## §4. Решение З2 — кнопки как образ классифицирующей функции

### 4.1. Разбиение

`c: 𝔐 → {a, v, i, o}` — классификация по `mime`. Она индуцирует
разбиение `L` на четыре подпоследовательности `L_a, L_v, L_i, L_o`
(подпоследовательность — сохраняет относительный порядок).

**Опр. 2.** Множество кнопок области: `B(Ω) := c(L(Ω)) ∩ {a, v, i}`.

То есть кнопка класса показывается тогда и только тогда, когда прообраз
класса непуст: `L_c ≠ ∅`. Это ровно требование «если картинок нет — кнопку
не показывать», записанное как образ функции. Класс `o` (документы) кнопки
не даёт по определению — для него нет микроприложения.

### 4.2. Переход «клик по файлу»

**Утв. 4.** Клик по вложению `m` в позиции `p` открывает микроприложение
класса `c(m)` с плейлистом `L_{c(m)}` и индексом
`i = |{ q ∈ L : q < p, c(q) = c(m) }|`, и этот индекс корректен.

*Доказательство.* `L_c` — подпоследовательность, значит её элементы
сохраняют относительный порядок из `L`; число элементов класса `c`, строго
предшествующих `p`, и есть позиция `m` в `L_c`. Вычисляется одним проходом
за `O(|L|)`. ∎

Следствие для реализации: не нужно хранить три плейлиста и три индекса.
Достаточно `L`, текущей позиции `p` в `L` и класса — всё остальное
производно. Это устраняет целый класс ошибок рассинхронизации трёх
списков.

### 4.3. Кнопки над папкой: почему денормализация `mime` обязательна

Здесь единственный настоящий счёт в этом разделе. Существенный параметр —
не объём папки в байтах, а число детей `n`. Проект уже заявляет цель
`n ≤ 10⁴` («папка на 10⁴ элементов не рендерится целиком»).

Без денормализации `c(m)` требует манифеста, то есть похода в IndexedDB
или в сеть. При `n = 10⁴`, задержке сети `τ ≈ 100 мс` и параллелизме
очереди `k = 3`:

    T = n·τ/k = 10⁴ · 0.1 / 3 ≈ 333 с ≈ 5.5 минуты

до того, как станет известен состав кнопок. Даже при `n = 10³` это ~33 с.
Никакая ленивая догрузка это не спасает: кнопка, появляющаяся через минуту
после входа в папку, читается как сбой, а не как оптимизация.

С денормализацией `c(m)` — поле узла, уже загруженного в память вместе с
деревом. `B(Ω)` — один проход, `O(n)`, при `n = 10⁴` порядка микросекунд.

**Усиление.** `B(Ω)` можно вычислять за `O(1)`, а не `O(n)`, тем же
приёмом, что уже применён в `tree.js` к `children` и `namesInDir`:
инкрементальный индекс `classCount: (parentId, class) → ℕ`, обновляемый
при `create`/`setPar`/`purge`. Кнопка показывается ⟺ счётчик > 0.
Обоснование то же самое, что зафиксировано в коде для `namesInDir`:
производный индекс, живёт в памяти, не в БД, поддерживается за `O(1)` на
операцию.

## §5. Решение З3 — автомат единственного владельца

### 5.1. Пространство состояний

    Q = {⊥} ∪ { (c, L, i, D, P) }

- `c ∈ {a, v, i}` — класс микроприложения;
- `L` — снимок плейлиста, `i ∈ [0, |L|)`;
- `D ∈ {full, mini}` — развёрнуто / свёрнуто;
- `P ∈ {playing, paused, suspended}` — определено только при `c ∈ {a, v}`;
  для `c = i` компонента `P` отсутствует.

`⊥` — закрыто. Заметь: `⊥` — **единственное** состояние «ничего не
играет», а не одно из многих; в этом весь фокус доказательства ниже.

Алфавит событий:

    Σ = { open(c, L, i), next, prev, seek(t), toggle, minimize, restore,
          close, callStart, callEnd, ended }

### 5.2. Ключевое свойство функции переходов

**Опр. 3.** `δ(q, open(c, L, i)) = (c, L, i, full, playing)` — **для любого
`q`**, включая непустое.

То есть `open` — это *сброс*, а не помещение в стек. Отсюда:

**Утв. 5 (единственность).** В любой достижимой конфигурации активно не
более одного микроприложения.

*Доказательство.* Пространство состояний — не произведение `Q × Q`, а
само `Q`; конфигурация приложения содержит ровно одну переменную типа `Q`.
Число активных микроприложений равно `[q ≠ ⊥] ∈ {0,1}` — это функция
состояния, а не накапливаемая величина. Никакой переход не может сделать
её равной двум, поскольку кодомен `δ` есть `Q`. ∎

Это тавтология — и в этом её ценность. Требование «одновременно запущено
только одно» либо гарантировано типом состояния, либо не гарантировано
вообще. Три независимые модалки с локальным состоянием (нынешняя форма
`image-modal.jsx` / `file-player.jsx`) дают конфигурацию из `{0,1}³` —
там инвариант приходится *поддерживать*, и он ломается на первой же
неучтённой ветке.

**Следствие.** Требование «свёрнутое окно переживает переход между
разделами» вынуждает разместить переменную состояния вне дерева
компонентов экрана — иначе размонтирование экрана уничтожает `q`. Образец
для этого в проекте уже есть (`CallOverlay` + сигналы `call.js`).

### 5.3. Вытеснение звонком

По A7 звонок безусловно приоритетен. Формально: на множестве претендентов
на звук `{call, media}` задан линейный порядок `media < call`, вытеснение —
приоритетное.

    δ((c,L,i,D,playing), callStart) = (c,L,i,D,suspended)
    δ(q, callStart) = q                     для остальных q
    δ((c,L,i,D,suspended), callEnd) = (c,L,i,D, X)

Значение `X` не выводится, это соглашение. Два варианта и критерий:

- `X = paused` — «прерванное не возобновляется само». Ничто не начинает
  звучать без явного действия человека. Цена: после короткого звонка
  музыку надо перезапускать руками.
- `X = playing` — «восстановить то, что было». Обосновано тем, что пауза
  была недобровольной. Цена: после сорокаминутного разговора внезапно
  играет музыка, о которой человек забыл.

Разумный компромисс, если не хочется выбирать одно: `X = playing` только
при `c = a` (музыка) и только если длительность звонка меньше некоторого
порога; иначе `paused`. Помечаю как соглашение, а не как вывод.

**Утв. 6.** Инвариант «звонок и медиа не звучат одновременно» сохраняется
всеми переходами.

*Доказательство.* Единственные переходы в `P = playing` — это `open`,
`toggle`, `next`/`prev` и `callEnd`. Первые три должны быть определены как
запрещённые при активном звонке (`δ(q, toggle) = q`, если звонок активен),
четвёртый по определению срабатывает только при `callEnd`. Тогда
`P = playing ⟹ звонок неактивен` — индукцией по длине пути от начального
состояния. ∎

Обрати внимание, что доказательство *требует* от реализации явного
запрета в `toggle`. Это то место, где формализация приносит пользу: без
неё «звонок ставит на паузу» реализуется как разовый вызов `pause()` на
`callStart`, и пользователь спокойно жмёт «play» посреди разговора.

### 5.4. Инлайновые медиаэлементы — противоречие, которое надо снять

Из A5: пузыри сообщений содержат собственные `<audio controls>` и
`<video controls>`. Каждый из них — независимый источник звука вне `Q`.
Утв. 5 их не покрывает: реальное число одновременных источников есть
`[q ≠ ⊥] + (число играющих инлайновых элементов)`.

Формально требование «одновременно звучит не более одного» **несовместимо**
с сохранением инлайновых элементов в их нынешнем виде. Варианты:

- **(а) Снять инлайновое воспроизведение.** Вложение в пузыре становится
  превью (постер видео, полоса-заглушка аудио, картинка), клик открывает
  микроприложение. Это ровно телеграмная модель. Цена: одно лишнее
  действие, чтобы послушать голосовое сообщение — а голосовые слушают
  часто и коротко.
- **(б) Сделать инлайновые элементы участниками автомата.** Расширить `Q`
  идентификатором инлайнового источника, `open` вытесняет его так же, как
  всё прочее. Цена: сложнее; но голосовые остаются в один клик.
- **(в) Исключение для голосовых.** Голосовые (`voice`, ≤32 КБ, инлайн в
  payload) играют по-старому, всё остальное — по (а). Обоснование:
  голосовое — реплика в диалоге, а не медиафайл; оно не попадает в
  плейлист «Музыка» по смыслу.

Мой выбор — **(в)**, и он же требует явного решения: попадают ли голосовые
в `L_a`. Считаю, что нет: иначе «Аудио» в переписке превращается в
пересказ разговора вперемешку с музыкой.

### 5.5. Ортогональность `D` и `P`

`D` (свёрнуто/развёрнуто) и `P` (играет/пауза) независимы: `minimize` и
`restore` не трогают `P`, `toggle` не трогает `D`. Это то, что делает
свёрнутое окно осмысленным — переход `full → mini` не должен прерывать
звук. Единственное ограничение: `⊥` поглощает оба (`close` уничтожает всё
состояние).

Для `c = i` компонента `P` отсутствует, значит `mini` для просмотрщика
изображений семантически пуст (нечему продолжаться в фоне). Соглашение:
просмотрщик изображений сворачивать нельзя — кнопка `minimize` у него не
показывается. Иначе получится свёрнутая полоска, которая ничего не делает.

## §6. Решение З4 — ресурсный инвариант

### 6.1. Ресурсы

- `R₁` — записи в реестре моста плеера (`registerPlayerFile(d)`);
- `R₂` — ObjectURL'ы расшифрованных изображений;
- `R₃` — сам медиаэлемент DOM и его буфер.

Утечка — это ресурс, живой при `q = ⊥`, либо ресурс, о котором никто не
помнит.

### 6.2. Принцип

**Опр. 4.** Множество допустимых ресурсов есть **функция состояния**:

    Alloc(⊥) = ∅
    Alloc(c, L, i, D, P) = { d(L[j]) : j ∈ W(i) }

где `W(i)` — окно префетча: `W(i) = {i}` для аудио и видео (браузер сам
буферизует вперёд через Range), `W(i) = {i-1, i, i+1} ∩ [0,|L|)` для
изображений (нужен мгновенный переход в обе стороны).

**Утв. 7 (невозможность утечки).** Если после каждого перехода
выполняется `release(Alloc(q_старое) \ Alloc(q_новое))` и
`acquire(Alloc(q_новое) \ Alloc(q_старое))`, то в любой момент множество
живых ресурсов равно `Alloc(q)`; в частности при `q = ⊥` оно пусто.

*Доказательство.* Индукция по числу переходов. База: до открытия ресурсов
нет, `Alloc(⊥) = ∅`. Шаг: по предположению живые ресурсы = `Alloc(q)`;
после применения разностей живые = `Alloc(q) \ (Alloc(q)\Alloc(q')) ∪
(Alloc(q')\Alloc(q)) = Alloc(q')`. ∎

Ценность формулировки в том, что она переносит ответственность с «не
забыть освободить в каждой ветке» на «вычислить множество по состоянию».
Веток много, состояние одно.

**Поправка на неинъективность (§3.4).** `Alloc` определён как множество
*дайджестов*, а окно `W` — множество *позиций*. Освобождение `d`
допустимо только при `d ∉ d(W(i))` — если дубликат остался в окне, ресурс
живёт. Иначе получится ошибка вида «удалили ресурс, который ещё нужен по
другой позиции», и она проявится только при дедупликации, то есть редко и
непонятно.

**Оценка памяти.** Для изображений: не более `3·max_размер_изображения`.
При потолке 50 МБ на файл это 150 МБ — многовато. Разумно ограничить окно
предзагрузки не числом элементов, а суммарным объёмом (тот же приём, что
уже применён в `attachment-memory-cache.js`: бюджет в байтах, вытеснение
по LRU). Тогда `W(i)` — наибольшее по включению окно вокруг `i`,
укладывающееся в бюджет.

## §7. Решение З5 — денормализация `mime` в CRDT

### 7.1. Постановка

Требуется добавить полю узла значение `μ(x) ∈ MIME`, доступное без
обращения к манифесту. Вопрос: не ломает ли это сходимость (SEC — все
реплики, применившие одно множество операций, приходят к одному
состоянию).

### 7.2. Теорема

**Утв. 8.** Добавление к узлу поля `μ`, записываемого один раз операцией
`create` и не изменяемого ни одной операцией, сохраняет сходимость дерева
без изменения закона слияния.

*Доказательство.* Состояние узла есть кортеж `(I, R)`, где `I` —
неизменяемая часть (`id, kind, blob`), `R` — набор LWW-регистров
(`par, name, origin`). Слияние определено покомпонентно: `I` берётся из
операции `create` (единственной, порождающей узел с данным `id` —
`id` уникален), `R` сливается по `compareLabels`. Сходимость доказывается
для `R` (коммутативность/ассоциативность/идемпотентность LWW) и тривиальна
для `I` (значение одно). Добавление `μ` в `I` расширяет `I`, не затрагивая
`R`, следовательно не меняет ни одного условия доказательства. ∎

По A3 условие «не изменяется ни одной операцией» выполнено для `blob`
буквально; `μ` встаёт рядом с ним.

### 7.3. Старые узлы: плоская решётка

Узлы, созданные до изменения, не имеют `μ`. Формально
`μ: V → MIME ∪ {⊥}`, где `⊥` — «неизвестно». На этом множестве —
плоская решётка: `⊥ ⊑ v` для всех `v ∈ MIME`, элементы `MIME` попарно
несравнимы.

**Утв. 9.** Ленивая дозаливка (`⊥ → v` по мере того, как манифест всё
равно потребовался) бесконфликтна.

*Доказательство.* Требуется, чтобы две реплики, независимо вычислившие
значение для одного узла, получили одно и то же. `μ` вычисляется как
`mime(манифест(blob))`; `blob` неизменяем (A3), манифест
контентно-адресуем, следовательно `blob ↦ mime` — **функция**, а не
отношение. Значит независимые вычисления дают равные значения, и
операция взятия точной верхней грани в плоской решётке никогда не
встречает конфликта `v₁ ⊔ v₂` с `v₁ ≠ v₂`. Монотонность (`⊥ → v`, но
никогда `v → v'`) даёт сходимость по стандартной теореме о монотонных
CvRDT. ∎

Существенно именно детерминизм: если бы `μ` определялся, например,
расширением имени файла (которое переименуемо — LWW-регистр!), утверждение
было бы ложным.

### 7.4. Стоимость

Дополнительное поле в операции `create` и в узле. При `10⁴` узлов и
~24 байтах на строку mime — порядка 240 КБ в журнале операций и столько же
в памяти. Пренебрежимо.

**Отдельно проверить:** операция `create` уходит в реле. Если тело
операции зашифровано, добавление `mime` метаданных не раскрывает; если
нет — реле узнаёт распределение типов файлов у пользователя. Это не
математический вопрос, а вопрос модели угроз, но он возникает именно
здесь и его легко пропустить.

## §8. Решение З6 — геометрия чанков и потоковая загрузка

### 8.1. Размер манифеста растёт линейно по числу чанков

Число чанков `N = ⌈S/C⌉`. Каждый чанк представлен в манифесте
шестнадцатеричным дайджестом sha256: 64 символа + кавычки и запятая в
JSON, то есть `h ≈ 67` байт. Размер манифеста:

    M(C) = h·S/C

Манифест **скачивается целиком до первого кадра**. Значит он входит в
задержку старта наравне с первым чанком.

При `C = 256 КиБ` (текущее значение по умолчанию):

| `S` | `N` | `M` |
|---|---|---|
| 100 МиБ | 400 | 27 КБ |
| 1 ГиБ | 4 096 | 274 КБ |
| 4 ГиБ | 16 384 | 1.1 МБ |
| 10 ГиБ | 40 960 | 2.7 МБ |

Мегабайт манифеста перед первым кадром четырёхгигабайтного фильма — это
уже заметно, и это чистые накладные расходы.

### 8.2. Оптимальный размер чанка

Стоимость старта (в байтах, которые надо получить до первого кадра) —
манифест плюс один чанк:

    T(C) = h·S/C + C

Минимизируем: `T'(C) = -h·S/C² + 1 = 0`, откуда

    **C* = √(h·S)**,  причём в оптимуме M(C*) = C* и T(C*) = 2√(h·S).

| `S` | `C*` | ближайшая степень двойки |
|---|---|---|
| 100 МиБ | ≈ 84 КБ | 64 КиБ |
| 1 ГиБ | ≈ 268 КБ | **256 КиБ** |
| 4 ГиБ | ≈ 536 КБ | 512 КиБ |
| 10 ГиБ | ≈ 848 КБ | 1 МиБ |

Три вывода:

1. Текущее значение 256 КиБ **оптимально ровно для гигабайтного файла** —
   выбранное когда-то по рекомендации, а не по замеру, оно оказалось
   удачным для нынешнего потолка.
2. Размер чанка должен зависеть от размера файла как `√S`, а не быть
   константой. Достаточно ступенчатой таблицы по степеням двойки —
   точность здесь не нужна, функция около минимума пологая (при отклонении
   `C` вдвое от `C*` стоимость растёт лишь на 25%).
3. `chunkSize` уже хранится **в манифесте**, а не зашит в код — значит
   изменение не ломает чтение уже загруженных файлов. Это надо
   проверить фактически, но по структуре манифеста выглядит так.

*Модель, не замер.* Стоимость меряется в байтах и предполагает, что
задержки запросов сопоставимы. Если задержка сети велика, а полоса широка,
оптимум сдвигается в сторону бо́льших чанков (меньше запросов).

### 8.3. Гипотеза: массив дайджестов чанков избыточен

Каждый чанк шифруется ChaCha20-Poly1305, то есть несёт AEAD-тег, и
расшифровка чанка с подменёнными байтами **проваливается по определению
AEAD**. Индекс чанка участвует в выводе одноразового значения, значит
перестановка чанков местами тоже обнаруживается. Целостность блоба
целиком закрыта `blobSha256`.

Отсюда гипотеза: проверка `sha256(чанк) == manifest.chunks[i]`
криптографически ничего не добавляет — она лишь даёт другое сообщение об
ошибке и обнаруживает подмену на шаг раньше расшифровки. Если это так,
массив можно убрать, заменив `count` на `⌈size/chunkSize⌉`, и тогда
`M(C) = O(1)`, а весь §8.2 перестаёт быть ограничением: размер чанка
выбирается только из соображений гранулярности перемотки.

**Помечаю как гипотезу, требующую твоего решения**, а не как вывод: это
касается безопасности, а я вижу только код, но не модель угроз, ради
которой проверка вводилась. Если она вводилась против недоверенного
Blossom-сервера — она всё равно избыточна (AEAD ловит то же самое). Если
против чего-то ещё — надо это «ещё» назвать вслух.

### 8.4. Потоковая загрузка: граница резидентной памяти

Сейчас `putStream` принимает `Uint8Array` целиком, затем склеивает весь
шифротекст (`concatBytes`) и отправляет одним запросом. Пиковая
резидентная память ≈ `2S` (открытый текст плюс шифротекст).

**Утв. 10.** Существует алгоритм загрузки с резидентной памятью `O(C)`,
не требующий второго прохода по файлу и не требующий потокового тела
HTTP-запроса.

*Построение.* Пусть `F` — объект `File`.

    hasher ← sha256.create()
    parts ← []                          // список Blob'ов, НЕ байтов
    для i от 0 до N-1:
        plain  ← await F.slice(i·C, min((i+1)·C, S)).arrayBuffer()   // O(C)
        cipher ← encryptChunk(plain, key, i)                          // O(C)
        hasher.update(cipher)
        parts.push(new Blob([cipher]))
        // plain и cipher выходят из области видимости
    blobSha256 ← hasher.digest()
    body ← new Blob(parts)              // склейка ссылок, не байтов
    upload(body)

Резидентно живут одновременно только `plain` и `cipher` текущего шага —
`O(C)`. Инкрементальный хеш снимает необходимость второго прохода:
дайджест шифротекста известен к моменту, когда шифрование закончено, то
есть до отправки — а Blossom требует его заранее.

**Где эта конструкция опирается на неспецифицированное поведение:**
`new Blob([...])` формально не обязан выгружать данные на диск. На
практике браузеры так делают для крупных Blob'ов. Помечаю как
**обоснованную гипотезу**: работоспособность подтверждается замером
(загрузить 2 ГБ и посмотреть на потребление памяти вкладки), а не
рассуждением.

**Запасной вариант, свободный от этой гипотезы:** перейти от «один блоб на
файл» к «один блоб на чанк». Манифест уже хранит дайджест каждого чанка —
модель к этому подготовлена. Тогда каждая отправка мала и независима,
память `O(C)` гарантированно, и дополнительно появляется **возобновляемая
загрузка** (упавшую можно продолжить с недостающих чанков) — то, чего
нынешняя схема не даёт в принципе. Цена: `N` объектов на сервере вместо
одного и `N` HTTP-запросов вместо одного; при `S = 4 ГиБ` и `C = 512 КиБ`
это 8192 запроса. Размен: **память и возобновляемость против числа
запросов и нагрузки на реестр объектов Blossom.**

Критерий выбора: если ты планируешь хостинг хранилища как услугу (ты сам
назвал это жилкой для монетизации), возобновляемая загрузка стоит дороже
восьми тысяч запросов — люди грузят с телефона по плохой сети, и «упало на
97% и начинай сначала» убивает продукт вернее, чем медленный старт.

### 8.5. Мультизагрузка как двухстадийный конвейер

Загрузка `k` файлов — задача о расписании с двумя машинами: шифрование
(процессор) и отправка (сеть). Это `F2‖C_max` — классическая задача,
решаемая **правилом Джонсона** (1954): сначала, по возрастанию времени
первой стадии, все работы с `a_i ≤ b_i`; затем, по убыванию времени второй
стадии, остальные.

Но у нас обе стадии пропорциональны размеру: `a_i = α·s_i`, `b_i = β·s_i`.
Тогда условие `a_i ≤ b_i` выполняется либо для всех работ сразу, либо ни
для одной, и правило Джонсона вырождается:

- если `α ≤ β` (шифрование быстрее отправки — обычный случай): грузить по
  **возрастанию размера**;
- иначе — по убыванию.

**Утв. 11 (честная оценка выигрыша).** Выигрыш от правильного порядка не
превосходит `max_i min(a_i, b_i)` — времени одной стадии одного файла.

Практический смысл: **порядок почти не важен, важно наличие конвейера.**
Последовательная загрузка стоит `Σ(a_i + b_i)`; конвейерная —
`≈ max(Σa, Σb) + (заполнение и слив)`. Ускорение ограничено двойкой и
достигается при `Σa ≈ Σb`. Порядок добавляет к этому единицы процентов.

Отсюда приоритет работ: сначала сделать перекрытие «шифруем следующий,
пока отправляется текущий», и только потом, если захочется, сортировать
по возрастанию размера (у этого есть и побочная польза: мелкие файлы
появляются в списке быстро, и загрузка выглядит живой).

## §10. Открытые вопросы

1. Возобновлять ли воспроизведение после звонка (§5.3) — соглашение, не
   вывод.
2. Дедуплицировать ли плейлист (§3.4) — соглашение; предложение:
   дедуплицировать аудио и видео, не дедуплицировать изображения.
3. Судьба инлайновых медиаэлементов (§5.4) — три варианта, выбран (в)
   предварительно.
4. Область плейлиста в личном чате: загруженное окно или вся история
   (A6). Второе требует новой доменной функции — прохода по БД чата.
5. Избыточность `manifest.chunks[]` (§8.3) — вопрос модели угроз.
6. Один блоб на файл против одного на чанк (§8.4) — вопрос о
   возобновляемости.
7. Раскрывает ли `mime` в операции `create` что-либо реле (§7.4).

## §11. Соблазнительное, но неверное решение

**«Сделай три отдельные модалки — по одной на плеер, видео и просмотрщик,
каждая владеет своим состоянием; это ровно тот стиль, что уже есть в
`image-modal.jsx` и `file-player.jsx`».**

Притягательно тем, что это буквальное продолжение существующего кода,
минимум правок, никакого нового глобального состояния и никаких
рассуждений про автоматы. Ломается математически: конфигурация становится
элементом `{0,1}³`, инвариант единственности перестаёт быть свойством типа
и превращается в свойство, которое надо *поддерживать* на каждой ветке
переходов (Утв. 5 неприменимо), а состояние, живущее в дереве компонентов
экрана, уничтожается размонтированием — то есть требования «свернуть» и
«пережить переход в другой раздел» невыполнимы в принципе, а не «сложны».

**Вторая приманка того же рода:** «раз бюджет вырос, возьми готовый плеер и
корми его blob-URL'ом». Ломается на A2: blob-URL требует расшифровать файл
**целиком** до первого кадра, то есть стоимость старта становится `O(S)`
вместо `O(√(h·S))` — четырёхгигабайтный фильм не откроется никогда. Ровно
ради этого и был построен путь через service worker.
