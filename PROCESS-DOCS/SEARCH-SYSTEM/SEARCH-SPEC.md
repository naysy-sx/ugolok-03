# Глобальный поиск. Техническое задание

**Редакция 1, финальная для этапа проектирования.**
Основано на `SEARCH-MATH.md` и `SEARCH-ALGO.md`. Правки, которые алгоритмический разбор потребовал внести в математический документ (`SEARCH-ALGO.md` §16), считаются внесёнными и учтены здесь.

**Как пользоваться.** §3 (контракты) замораживается перед началом работ. §9 (И0) выполняется до первой строки кода. §10 — план работ с маршрутизацией по сложности. §2 — что сознательно выброшено из проектных документов и почему; читать до того, как захочется вернуть.

## 0. Указания оркестратору

Конвейер прежний: Claude оркестрирует, локальные работники исполняют. Три правила, специфичные для этого модуля.

**Маршрутизация.** `[C]` — задача с рассуждением: обход с досрочным прекращением, отмена, взаимодействие кэша с частичным заполнением, property-тесты. `[W]` — механика с готовым контрактом: экран, разметка, строки локализации, обвязка сигналов.

**Главная ловушка этого модуля — правдоподобно неверная выдача.** Поиск, который молча теряет часть результатов, выглядит абсолютно нормально: экран не пустой, записи настоящие, ошибок в консоли нет. Ни один ручной прогон это не поймает. Поэтому property-тесты §8 пишутся **до** реализации обхода и подтверждаются на заведомо сломанном коде: тест, зелёный с первого запуска, здесь ничего не проверяет.

**Запрет на догадки действует жёстче обычного.** Модуль читает семь чужих таблиц. Любое «предположительно поле называется так» — основание остановиться и выполнить проверку из §9.

## 1. Что строим

Глобальный поиск по локальной истории аккаунта. Человек набирает текст в существующем поле сайдбара; пока набирает — это прежний фильтр списка навигации, ничего не меняется. По Enter открывается экран результатов: контакты, каналы, сообщения, посты, комментарии, найденные по подстроке.

Запрос разбивается по пробелам, и запись подходит, если **каждая** часть входит подстрокой в её текст. `работ деньг` находит и «заработал деньги», и «сделал работу и ему дали деньги». Это поиск по корням, привычный по ленте соцсети, а не поиск по словам.

Поиск однократный. Результат замирает до следующего Enter. Живого поиска по мере набора нет и не будет — решение №10 матдока.

## 2. Что выброшено и почему

Проектные документы содержат больше механики, чем нужно первой версии. Здесь перечислено вырезанное — чтобы через полгода не восстанавливать рассуждение.

| Выброшено | Куда делось | Основание |
|---|---|---|
| **Кэш расшифрованных стогов** (`ALGO` §8) | этап И4, только после замера | это единственное место модуля, где живёт риск тихой потери результатов (§8.3 алгодока: частично заполненный кэш). Строить его одновременно с обходом — совмещать две новые вещи, из которых одна опасная |
| **Воркер** (`ALGO` §6) | этап И4, только если замер потребует | лишний поток, лишняя граница сериализации, лишний путь для ключа БД. Порционный обход проще и, вероятно, достаточен |
| **Поиск по узлам файлового дерева** | v0.2 | таблицы файлов в И0 не проверены, а модуль и без них закрывает оба заявленных сценария. Источник добавляется одним файлом (§3.2) |
| **Подсветка совпадений** | v0.2 | считается отдельным проходом по показанным записям (`ALGO` §11), к движку отношения не имеет |
| **Фильтры выдачи** (`MATH` §5) | v0.2 | пересечение коммутирует с сопоставлением, добавляется без переделки |
| **Ахо–Корасик, КМП, n-граммы, суффиксные структуры** | никуда | `ALGO` §3: оптимизируют слагаемое, которого не видно |

**Что не выброшено и выброшено быть не может:** досрочное прекращение обхода (§3.4) и отмена идущего поиска (§3.5). Первое — единственная оптимизация, дающая порядок. Второе алгоритмический документ оставил открытым вопросом, и это ошибка: поиск, который нельзя прервать, замораживает приложение ровно тогда, когда человек передумал и набрал другой запрос. Это не улучшение, а условие работоспособности.

## 3. Замороженные контракты

### 3.1 Чистое ядро: `src/domain/search/matching.js`

Ни одной зависимости — ни базы, ни сигналов, ни Preact. Всё тестируется без IndexedDB.

```
normalize(str) -> string
    NFKD, отбрасывание категории Mn, нижний регистр.
    Идемпотентна: normalize(normalize(s)) === normalize(s).

parseQuery(raw) -> { parts: string[], isEmpty: boolean }
    Разбиение по пробелам, нормализация каждой части, отбрасывание пустых,
    удаление дубликатов, сортировка по убыванию длины.
    Пустой запрос -> { parts: [], isEmpty: true }.

buildHaystack(fields: string[]) -> string
    Нормализация каждого поля и склейка через SEPARATOR.

matches(haystack, parts) -> boolean
    parts.every(p => haystack.includes(p)).
    Пустой parts НЕ обрабатывается здесь — вызов с пустым списком
    запрещён контрактом (см. I-EMPTY-NOOP).

SEPARATOR = "\u001F"
```

**Запрещено:** регулярные выражения, собственные реализации поиска подстроки, любые библиотеки. `String.prototype.includes` и только он.

### 3.2 Источник: `src/domain/search/sources/*.js`

Единый интерфейс. Движок про конкретные таблицы не знает ничего.

```
{
  type: "contact" | "channel" | "message" | "post" | "comment" | "channelMessage",
  order: "recent" | "unordered",
  async *scan(ctx, { signal }) -> yields { key, sortKey, fields: string[] }
}
```

- `ctx` — `{ ownerPubkey, dbKey }`.
- `scan` — асинхронный генератор, выдающий записи **порциями по 200**, между порциями уступающий управление.
- `order: "recent"` — генератор обязан выдавать записи от свежих к старым. Только для таких источников движок применяет досрочное прекращение.
- `order: "unordered"` — источник читается целиком всегда. Для мелких таблиц это дешевле, чем заводить индекс.
- `fields` — сырые строки **до** нормализации. Нормализацией занимается движок, источник её не делает.
- Записи с открытым флагом `deleted` источник не выдаёт вовсе.

Распределение по источникам зафиксировано так:

| Источник | Порядок | Чем обходится | Поля |
|---|---|---|---|
| `contacts` | unordered | вся таблица `contactProfiles` | имя, «о себе» |
| `channels` | unordered | вся таблица `channels` | название, описание, правила |
| `messages` | recent | обратный курсор по `seq` | текст |
| `posts` | recent | индекс `[ownerPubkey+createdAt]`, обратный | заголовок, текст |
| `channelMessages` | recent | индекс `[ownerPubkey+createdAt]`, обратный | текст |
| `comments` | unordered | вся таблица | текст |

`comments` помечены `unordered` не по выбору, а по факту: в `COMMENTS_PLAINTEXT_FIELDS` нет поля времени, обходить их по времени нечем. При ожидаемых `10²–10³` комментариях это приемлемо. Заводить ради них индекс — не сейчас.

### 3.3 Движок: `src/domain/search/engine.js`

```
async *search(ctx, rawQuery, { signal, limitPerType }) 
    -> yields { type, key, sortKey } по мере нахождения
```

Асинхронный генератор. Форма выбрана не для красоты: она **одновременно** даёт порционную выдачу, досрочное прекращение и отмену, и не даёт им разъехаться. Потребитель прекращает читать — генератор останавливается.

Порядок обхода источников фиксирован и соответствует стоимости: `contacts`, `channels`, `comments`, `posts`, `channelMessages`, `messages`. Дешёвые первыми, чтобы экран заполнился до того, как человек заметит задержку.

### 3.4 Досрочное прекращение

Для источника с `order: "recent"` обход прерывается после `limitPerType` совпадений. Для `unordered` — не прерывается никогда.

**Условие корректности:** порядок обхода источника совпадает с порядком показа группы. Нарушишь одно из двух — выдача потеряет записи молча.

Следствие, которое обязано быть отражено в интерфейсе: **общее число найденного не показывается.** Никаких «найдено 1483». Допустимо «показано 100» и кнопка «ещё».

### 3.5 Отмена

`AbortSignal` протаскивается до самого внутреннего цикла. Проверка сигнала — на границе каждой порции в 200 записей, не реже. Новый Enter отменяет предыдущий поиск до того, как запустит следующий.

Гонка, которую надо закрыть явно: результаты отменённого поиска не должны попасть в состояние экрана. Механизм — счётчик запусков; выдача с устаревшим номером отбрасывается.

### 3.6 Состояние: `src/ui/signals/search.js`

```
searchState = signal({
  runId: number,
  query: string,          // зафиксированный по Enter, не то, что в поле
  status: "idle" | "running" | "done" | "cancelled",
  groups: { [type]: { hits: [], exhausted: boolean } },
})
```

**Строка в поле сайдбара и зафиксированный запрос — два разных значения.** Первое живёт локально в `nav-groups.jsx` и меняется на каждое нажатие клавиши; второе меняется только по Enter. Их слияние в один сигнал — самая вероятная ошибка этого этапа и причина, по которой контракт написан явно.

### 3.7 Навигация

Новый вид места: `{ kind: "search", query }` в `src/ui/signals/place.js`, плюс `openSearch(query)` рядом с существующими `openChat`/`openChannel`. Диспетчеризация в `src/app.jsx` тем же способом, что и остальные экраны, и `"search"` добавляется в `KNOWN_KINDS`.

Поведение поля:

- Enter при непустом запросе — `openSearch(query)`.
- Enter при пустом — ничего. Инвариант `I-EMPTY-NOOP`.
- Вход на экран поиска — поле показывает зафиксированный запрос.
- Правка поля на экране результатов — снова локальный фильтр сайдбара; выдача не трогается до следующего Enter.
- Последней строкой отфильтрованного списка сайдбара — кликабельная подсказка «Искать „текст“ в сообщениях», делающая то же, что Enter. Без неё про Enter никто не догадается: контрол выглядит как фильтр.

## 4. Изменение схемы

Одно, версия 33.

```js
// Поиск, И3 — глобальный обход по времени. Существующие индексы
// [ownerPubkey+channelId+createdAt] дают порядок ТОЛЬКО внутри канала,
// а поиску нужен обход всех постов владельца от свежих к старым
// (SEARCH-ALGO.md §5). Аддитивно: обе таблицы переопределяются целиком,
// как требует Dexie при изменении хотя бы одного индекса.
db.version(33).stores({
  posts: "[ownerPubkey+id], [ownerPubkey+channelId+createdAt], [ownerPubkey+createdAt], deleted",
  channelMessages: "[ownerPubkey+id], [ownerPubkey+channelId+createdAt], [ownerPubkey+createdAt]"
});
```

Списки индексов выше — **черновик**, подлежащий сверке с фактическим состоянием таблиц на момент работы (проверка П-6). Dexie требует полного перечисления индексов таблицы при изменении любого из них, и пропущенный индекс тихо исчезнет.

Новых таблиц нет. Ничего производного от содержимого на диск не пишется — инвариант `I-NO-INDEX-AT-REST`.

## 5. Интерфейс

Экран `src/ui/screens/search.jsx`.

Группы в фиксированном порядке: контакты, каналы, сообщения, посты, комментарии, сообщения каналов. Пустые группы не показываются. Каждая группа — заголовок, до `limitPerType` строк, кнопка «показать ещё», если группа не исчерпана.

Строка результата ведёт в место, где запись живёт: контакт — в чат, канал — в канал, сообщение — в чат с прокруткой к сообщению, пост — на страницу поста.

Состояния экрана: идёт поиск (группы приходят по готовности, каждая со своим индикатором), готово, ничего не найдено, поиск отменён.

Строки локализации — во все двенадцать локалей `src/ui/i18n/locales/`. Русская и английская заполняются по-настоящему, остальные — ключами по существующему в проекте порядку.

## 6. Нефункциональные требования

| Метка | Требование |
|---|---|
| `N-FIRST` | первая группа (контакты, каналы) отрисована не позднее 100 мс после Enter |
| `N-FRAME` | главный поток не занят непрерывно дольше 50 мс |
| `N-CANCEL` | отмена вступает в силу не позднее одной порции (200 записей) |
| `N-NO-PERSIST` | после поиска в IndexedDB нет ни одной новой строки |

`N-NO-PERSIST` проверяется не рассуждением, а тестом: снимок списка таблиц и числа строк до и после поиска.

## 7. Инварианты

| Метка | Формулировка | Чем проверяется |
|---|---|---|
| `I-NORM-IDEMPOTENT` | `normalize ∘ normalize = normalize` | property-тест |
| `I-DIACRITIC-SYM` | `ещё` находит `еще` и наоборот | unit |
| `I-SEPARATOR` | склейка полей не даёт совпадений через границу | unit: поля `кот` и `ёл`, запрос `котёл` — не находит |
| `I-ANTITONE` | добавление части только сужает выдачу | property-тест |
| `I-MONOTONE-EXTEND` | удлинение части только сужает выдачу | property-тест |
| `I-ORDER-FREE` | `M("а б") = M("б а")` | property-тест |
| `I-EMPTY-NOOP` | пустой запрос не запускает поиск | unit |
| `I-STABLE-ORDER` | порядок внутри группы детерминирован при равном времени | unit с равными метками |
| `I-EARLY-EXIT` | выдача с досрочным прекращением совпадает с первыми `k` записями полного прохода | property-тест |
| `I-NO-INDEX-AT-REST` | производные структуры не персистятся | `N-NO-PERSIST` |

`I-EARLY-EXIT` — главный. Именно его нарушение даёт правдоподобно неверную выдачу.

## 8. Property-тесты, а не примеры

Порождается случайный корпус (записи со случайными текстами из ограниченного словаря) и случайные запросы. Зерно фиксируется, сценарий воспроизводится по номеру — приём уже применён в `tree-crdt.test.js`.

1. **Антитонность.** `M(q + " " + p) ⊆ M(q)`.
2. **Независимость от порядка частей.** `M("а б") = M("б а")`.
3. **Досрочное прекращение против полного прохода.** Результат обхода с обрывом совпадает с первыми `k` записями полного обхода того же источника.
4. **Симметрия диакритики.** Для строк с `ё`/`й` запрос находит текст в обе стороны.

Тест №3 обязан быть красным на реализации, где обход идёт от старых к свежим. Если он зелёный и там, и там — он ничего не проверяет, и это повод остановиться.

## 9. И0: блокирующие проверки

Выполняются до первой строки кода. Запрашиваются **факты, а не вердикты**: вопрос «работает ли» слабая модель закроет уверенным «да».

**П-1. Обратный обход `messages` по `seq`.**
Показать: код, которым Dexie отдаёт записи таблицы `messages` в обратном порядке первичного ключа с фильтром по `ownerPubkey`; замер времени на 10⁴ строках; подтверждение, что курсор действительно идёт от больших `seq` к меньшим, а не сортирует после выборки.
*Если обратного курсора нет и выборка идёт целиком:* досрочное прекращение не работает, §3.4 требует пересмотра. **Стоп.**

**П-2. Стоимость одной строки, разложенная на три части.**
Показать три отдельных числа: чтение строки из IndexedDB, `chacha20poly1305` расшифровка, `JSON.parse` с ревайвером. Суммарное число не годится — оно не подскажет, что чинить.
*Ожидание, требующее проверки:* ревайвер вызывается движком на каждое значение дерева и на коротких строках может стоить не меньше шифра.
*От результата зависит:* нужен ли этап И4 вообще (кэш и воркер).

**П-3. Флаг `deleted`.**
Показать: для каждой из шести таблиц-источников — есть ли `deleted` в списке plaintext-полей, индексируется ли, и как его сейчас фильтруют существующие читатели.
*Если у части таблиц флага нет:* удалённые записи полезут в выдачу. Нужна отдельная правка до И2.

**П-4. Заполнены ли профили и каналы на практике.**
Показать: содержимое `contactProfiles` и `channels` на реальном аккаунте — сколько строк, у скольких непустое «о себе» и непустые правила.
*Зачем:* оба заявленных сценария («kukusya» по имени, «протух» по правилам канала) опираются на то, что эти поля вообще хранятся локально. Если kind 0 не гидратируются, первая группа выдачи будет пустой всегда, и об этом надо знать до, а не после.

**П-5. Нормализация в целевом рантайме.**
Показать: результат `"ещё".normalize("NFKD")` в виде списка кодовых точек; то же для `"й"`; результат после отбрасывания категории `Mn`.
*Достаточный ответ:* кодовые точки. *Недостаточный:* «нормализация работает».

**П-6. Текущая схема БД.**
Показать: номер последней версии в `database.js`; полные строки индексов таблиц `posts` и `channelMessages` в том виде, в каком они действуют сейчас, с учётом всех переопределений.
*Зачем:* §4 требует перечислить индексы целиком, и пропущенный индекс исчезнет молча.

## 10. Этапы и декомпозиция

Порядок не переставляется. Применяется существующий DoD проекта и `PROCESS-DOCS/REGLAMENT.md`.

### И1. Чистое ядро `[C]` целиком

Ни базы, ни сети, ни интерфейса.

| Задача | Марш. | Готово, когда |
|---|---|---|

## 11. Чего работник делать не должен

Список нужен потому, что каждый пункт — естественный первый порыв.

- Подключать библиотеку полнотекстового поиска. Её сериализованный индекс хранит слова открытым текстом и обнуляет шифрование БД.
- Писать свой Кнута–Морриса–Пратта или Бойера–Мура. `String.prototype.includes` реализован в движке нативно и выигрывает.
- Строить регулярное выражение из пользовательского ввода. Скобка в запросе даст исключение, звёздочка — катастрофический откат.
- Сохранять что-либо производное от содержимого в IndexedDB.
- Показывать общее число найденного.
- Добавлять дебаунс и запускать поиск по вводу.
- Вводить минимальную длину запроса ради скорости. Стоимость от длины запроса не зависит.
- Сортировать выдачу после обхода. Обход уже идёт в нужном порядке; повторная сортировка её только испортит.
- Собирать `unshift` массив результатов. При тысяче попаданий это миллион перемещений.

## 12. Открытые вопросы, не блокирующие старт

1. **Escape на экране результатов** — очистить поле и остаться либо вернуться в прежнее место. Принять до И3.4.
2. **Виртуализация выдачи.** После нескольких нажатий «показать ещё» список вырастет до объёмов, где нужен виртуализованный вывод. Порог не определён; в проекте уже есть виртуализация в файловом менеджере, брать оттуда.
3. **Кэш при смене локального аккаунта без блокировки.** Актуально только с этапа И4, но продумать раньше: сценарий мультиаккаунта в проекте поддержан, а `dbKeySig` при смене аккаунта не обнуляется так же явно, как при блокировке.
4. **Поиск по файлам.** Добавляется одним источником; требует своей проверки И0 по таблицам файлового модуля.
