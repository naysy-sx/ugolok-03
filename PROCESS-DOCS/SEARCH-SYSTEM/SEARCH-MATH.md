# Глобальный поиск. Математические основания

**Статус:** редакция 1, этап 1 проектирования. Кода нет, контрактов нет.
**Назначение:** зафиксировать модель поиска и её алгебраические свойства до появления типов и интерфейсов. Источник для будущего раздела «Поиск» в `CONTRACTS.md` и для набора property-тестов.
**Не входит в документ:** вёрстка экрана результатов, схема таблиц IndexedDB, формат сетевых событий, поведение поля в сайдбаре сверх того, что влияет на модель.

---

## 0. Периметр

**В периметре v0.1.** Поиск по локальной расшифрованной истории одного аккаунта: личные сообщения, посты каналов, комментарии, сообщения общего чата каналов, профили контактов, метаданные каналов, узлы файлового дерева. Запуск однократный, по Enter. Результат замирает до следующего запуска.

**Вне периметра v0.1.** Поиск по сети (NIP-50) — принадлежит экрану «Знакомства», отдельная задача с другой моделью доверия. Живой поиск по мере набора. Морфология, исправление опечаток, ранжирование по релевантности, дизъюнкция и поиск фразы. Персистентный индекс любого вида.

**Не путать с уже существующим.** Поле в сайдбаре сегодня фильтрует список навигации по названиям (`nav-groups.jsx`, функция `matches`). Это другая задача: `n ≈ 10²`, работа по каждому нажатию клавиши, область — только имена. Она остаётся как есть. Настоящий документ описывает то, что запускается **поверх** неё по Enter.

## 1. Три раздельные задачи

| Задача | Область | Масштаб | Момент запуска | Модель |
|---|---|---|---|---|
| Навигация | названия чатов и каналов | `10²` | каждый ввод | существует, `matches` |
| Содержимое | вся локальная история | `10⁴–10⁵` | Enter | настоящий документ |
| Сеть | публичные события реле | внешний | отдельный экран | NIP-50, вне периметра |

Разделение не косметическое. У задач разные множества, разные стоимости и разные утечки. Смешение первых двух даёт подвисающий ввод; смешение второй и третьей даёт обещание, которое протокол выполнить не может: содержимое переписок и каналов зашифровано, реле ищет по полю `content`, значит для реле оно неотличимо от шума.

## 2. Нормализация

### 2.1 Определение

Пусть `Σ*` — множество строк. Нормализация есть отображение

```
ν : Σ* → Σ*
```

реализуемое как разложение NFKD, отбрасывание комбинирующих знаков категории `Mn` и приведение к нижнему регистру.

`ν` задаёт на `Σ*` **отношение эквивалентности** `u ∼ v ⟺ ν(u) = ν(v)`. Всё дальнейшее определено не на строках, а на фактор-множестве `Σ*/∼`. Это и есть содержательный смысл `normalizeForSearch` из `src/domain/files/filter.js`: не «приведение к виду», а выбор представителя класса.

### 2.2 Инварианты

- **I-NORM-IDEMPOTENT.** `ν ∘ ν = ν`. Нормализация уже нормализованной строки ничего не меняет. Нужно, потому что запрос и корпус нормализуются в разных местах и в разное время.
- **I-NORM-BOTH.** Сопоставление применяется только к парам `(ν(запрос), ν(текст))`. Ни одна сторона не сравнивается в исходном виде.

### 2.3 Почему отбрасывание `Mn` обязательно, а не желательно

Текущий код делает NFKD, но комбинирующие знаки не отбрасывает. Разложение NFKD переводит `ё` в `е` + комбинирующая диереза, а `й` в `и` + комбинирующая бреве. Отсюда прямое следствие для подстрочного сопоставления:

- запрос `еще` **находит** `ещё`, потому что `е,щ,е` — префикс строки `е,щ,е,◌̈`;
- запрос `ещё` **не находит** `еще`, потому что лишний комбинирующий знак не с чем сопоставить.

То есть без отбрасывания `Mn` отношение «найдётся» **несимметрично относительно диакритики**, и симметрия ломается ровно в ту сторону, которая раздражает: человек, аккуратно набравший `ё`, получает меньше результатов, чем набравший небрежно. Отбрасывание `Mn` закрывает это одним правилом и снимает нужду в отдельной подстановке `ё → е`.

**Цена, которую надо принять сознательно:** после отбрасывания `Mn` запрос `и` совпадает с `й`, `citroen` — с `citroën`. Для поиска это скорее польза, но это именно решение, а не побочный эффект.

## 3. Корпус

### 3.1 Размеченное объединение, а не однородное множество

Корпус — не набор документов одного вида, а **размеченное объединение** типов:

```
D = ⨆ D_τ ,  τ ∈ T = {контакт, канал, сообщение, пост, комментарий, сообщение канала, узел файла}
```

Для каждого типа задан свой набор извлекателей текста

```
φ_τ : D_τ → (Σ*)^{k_τ}
```

например, для контакта это `(имя, о себе)`, для канала — `(название, описание, правила)`, для поста — `(заголовок, текст)`, для сообщения — `(текст)`.

Фиксация `φ` — главное практическое содержание этого раздела. Всё остальное в модели из неё выводится, а спорить о том, «ищем ли мы по правилам канала», нужно один раз и здесь, а не в каждом месте кода.

### 3.2 Стог: свёртка полей в одну строку

Для каждой записи определён **стог** — конкатенация её нормализованных полей через разделитель:

```
H(d) = ν(φ_τ(d)₁) ⋅ s ⋅ ν(φ_τ(d)₂) ⋅ … ⋅ s ⋅ ν(φ_τ(d)_{k_τ})
```

Свёртка в одну строку — не оптимизация, а требование к семантике. Она даёт ровно то поведение, которого ждёт человек, привыкший к поиску в ленте: запрос `работ деньг` находит запись, где одна часть встретилась в заголовке, а другая в теле. Если сопоставлять по каждому полю отдельно и требовать совпадения всех частей внутри одного поля, такая запись не найдётся, и объяснить это пользователю нечем.

- **I-SEPARATOR.** Разделитель `s` — символ, который не может появиться в нормализованном запросе (годится `U+001F`). Без него возникают ложные срабатывания через границу: поля `кот` и `ёл`, склеенные впритык, дают совпадение с запросом `котёл`, которого в записи нет.

### 3.3 Скрытые записи

Удалённые записи помечаются открытым флагом `deleted` (см. `table-fields.js`) и исключаются из `D` **до** сопоставления, а не после. Это влияет на границу цикла и потому относится к модели, а не к отображению.

## 4. Соответствие

### 4.1 Разбиение запроса

Запрос `q` разбивается по пробельным символам в **множество** частей:

```
P(q) = { ν(p) : p — непустой фрагмент q между пробелами }
```

Именно множество, а не последовательность: порядок частей и их повторы на результат не влияют (§4.3).

### 4.2 Предикат

Пусть `u ⊑ v` означает «`u` есть подстрока `v`». Тогда

```
match(q, d) ⟺ ∀ p ∈ P(q) : p ⊑ H(d)
M(q) = { d ∈ D : match(q, d) }
```

Конъюнкция подстрочных вхождений в стог. Это в точности та форма, которой человек пользуется в поиске по ленте: `работ деньг` находит и `заработал деньги`, и `сделал работу и ему дали деньги`, потому что каждая часть ищется как корень, независимо от места и порядка.

**Что подстрока даёт бесплатно.** Запрос `протух` находит `протухшее`, потому что первое — подстрока второго. Никакой морфологии для этого не нужно. **Что она не даёт:** `работа` не найдёт `рабочий` — общая часть `работ`/`рабоч` расходится раньше конца запроса. Границу полезно понимать точно: подстрока покрывает словоизменение суффиксами (падежи, числа, времена) и не покрывает чередования в основе.

### 4.3 Алгебраические свойства

Пусть `M` рассматривается как отображение из множества частей в множество результатов.

- **Коммутативность и идемпотентность.** `M` зависит только от множества `P(q)`, поэтому перестановка частей и дублирование части ничего не меняют. Это оправдывает определение `P` как множества.
- **I-ANTITONE.** `P ⊆ P′ ⇒ M(P′) ⊆ M(P)`. Добавление части только сужает.
- **I-MONOTONE-EXTEND.** Если `p ⊑ p′`, то замена части `p` на `p′` только сужает: `p′ ⊑ H(d) ⇒ p ⊑ H(d)`.
- **Гомоморфизм пересечения.** `M(P ∪ P′) = M(P) ∩ M(P′)`. Отображение `M : (2^{частей}, ⊇) → (2^D, ⊆)` — гомоморфизм полурешёток.

Практическое следствие двух инвариантов: **уточнение запроса законно искать внутри предыдущей выдачи.** Дописал символ или добавил часть — результат гарантированно подмножество прежнего, полный проход не нужен.

Свойство держится **только** потому, что в v0.1 нет дизъюнкции. С «ИЛИ» оба инварианта неверны, и кэш прежней выдачи начнёт молча терять записи. Если дизъюнкция когда-нибудь появится, инкрементальное сужение отключается вместе с ней; это связанная пара, не два независимых решения.

### 4.4 Пустой запрос

По определению конъюнкции над пустым множеством `M(∅) = D`: пустому запросу удовлетворяет всё. Формально безупречно и практически бесполезно — выдача была бы всей историей.

- **I-EMPTY-NOOP.** Пустой запрос не запускает поиск. Enter на пустом поле — операция без эффекта.

Это не защита от глупости, а разрешение вырожденного случая, который иначе разрешился бы сам и не в ту сторону.

## 5. Фильтры

Фильтры (по типу записи, по автору, по каналу, по интервалу дат) задают подмножества `F₁, …, F_m ⊆ D`, и итог есть

```
M(q) ∩ F₁ ∩ … ∩ F_m
```

Пересечение коммутативно и ассоциативно, поэтому:

- порядок применения фильтров произволен и на результат не влияет;
- фильтр можно применять к уже полученной выдаче, не перезапуская сопоставление;
- добавление фильтра только сужает — то же свойство, что I-ANTITONE, и та же выгода.

Фильтры — независимые измерения; их совокупность образует произведение решёток подмножеств. Никакого взаимодействия между измерениями модель не предусматривает и предусматривать не должна.

## 6. Порядок вывода

### 6.1 Между типами порядка нет

Совпадение в имени контакта и совпадение в тексте сообщения **несравнимы**. Общей шкалы не существует: любое число, ставящее их в один ряд, назначено, а не выведено. Формально — на `M(q)` естественно определяются частные порядки внутри каждого `D_τ`, а их объединение есть частичный порядок, у которого несравнимы ровно межтиповые пары. Любая линеаризация такого порядка — выбор, и выбор произвольный.

**Решение: не выбирать.** Выдача разбивается на классы по типу (фактор-множество `M(q)/τ`), классы показываются в фиксированном порядке, сравнение между классами не производится вовсе. Это не решение задачи ранжирования, а корректный отказ от неё.

### 6.2 Внутри типа — предпорядок, не порядок

Внутри класса записи упорядочены по времени. Отношение «не позже» — **предпорядок**: равные метки времени законны и неизбежны (мультиустройство тикает один и тот же логический момент — тот же класс, что уже закрыт тайбрейком по `id` в таблице `messages`).

- **I-STABLE-ORDER.** Порядок внутри класса задаётся парой `(время, id)`, где `id` — детерминированный добивающий признак. Без него порядок совпадающих по времени записей зависит от порядка обхода хранилища и меняется между отрисовками.

### 6.3 Ограничение выдачи

Из каждого класса показывается не более `k` записей, остальные догружаются по требованию.

Ограничение ставится **на вывод, а не на запрос**. Стоимость сопоставления определяется объёмом корпуса и почти не зависит от длины запроса (§7), поэтому запрет коротких запросов не экономит ничего, зато отсекает осмысленные короткие корни, которых в русском много (`долг`, `ключ`, `код`, `файл`). Взрывается не поиск, а отрисовка тысяч карточек — там и ограничиваем.

## 7. Стоимость и кэш

### 7.1 Что доминирует

Пусть `N = |D|`, а `L = Σ_d |H(d)|` — суммарный объём текста. Один запрос стоит

```
Θ(N)  расшифровок строк  +  Θ(L · |P(q)|)  сопоставления
```

Расшифровка доминирует с большим отрывом; проверка вхождения по уже расшифрованной строке на её фоне не измеряется. По оценке из `MEDIA-ALGO.md` §3.8 расшифровка `10⁵` строк — секунды процессора.

**Прямое следствие, которое стоит записать явно:** запросы `ро` и `работ деньг` стоят практически одинаково. Интуиция «короткий запрос дешевле» здесь неверна, и на ней нельзя строить ни порогов, ни оптимизаций.

### 7.2 Кэш вместо индекса

Поскольку поиск однократный, а не живой, бюджета кадра нет, и постоянной структуры не требуется. Взамен — **кэш расшифрованных стогов на сессию**: массив пар `(ключ записи, H(d))`, собираемый при первом поиске и живущий до блокировки.

Это не индекс. У него нет собственной структуры доступа, он не отвечает на запрос быстрее линейного прохода, он лишь избавляет от повторной расшифровки. Первый запрос платит полную цену, последующие идут по памяти.

- **I-NO-INDEX-AT-REST.** Ни одна производная от содержимого структура не сохраняется в IndexedDB. Кэш существует только в памяти и уничтожается при блокировке. Это то, что отличает решение от библиотечного полнотекстового поиска: сериализованный индекс любой популярной библиотеки хранит исходные слова открытым текстом и обнулил бы шифрование БД (этапы 39–41).
- **I-CACHE-FRESH.** Любая запись в источник обязана отразиться в кэше. Источники почти только дописываются, поэтому поддержка сводится к добавлению стога новой записи; удаление отрабатывается открытым флагом `deleted` при чтении. Без этого инварианта пришедшее во время сессии сообщение не находится, и выглядит это как потеря данных.

Материализованная таблица по образцу `MEDIA-ALGO.md` §3.8 остаётся запасным ходом на случай, когда история перерастёт память. Её цена там же и описана: вторая копия, которую надо держать согласованной.

## 8. Чего модель не обещает

Перечислено, чтобы ожидания не строились задним числом.

| Не поддерживается | Следствие для пользователя |
|---|---|
| морфология и лемматизация | `работа` не находит `рабочий` |
| исправление опечаток | `протх` не находит ничего |
| дизъюнкция и поиск фразы | нельзя «или», нельзя точную цитату |
| ранжирование по релевантности | внутри типа только хронология |
| смешение алфавитов | `pa6ota` и `работа` — разные строки |
| поиск по содержимому файлов | ищутся имена узлов, не содержимое блобов |

Первые три — сознательный размен на простоту и на сохранение I-ANTITONE. Последняя строка — не упущение, а следствие §0: содержимое файлов не расшифровано и не находится в памяти.

## 9. Инварианты и стратегия проверки

### 9.1 Список

| Метка | Формулировка |
|---|---|
| I-NORM-IDEMPOTENT | `ν ∘ ν = ν` |
| I-NORM-BOTH | сопоставляются только нормализованные пары |
| I-SEPARATOR | разделитель полей не встречается в нормализованном запросе |
| I-ANTITONE | добавление части только сужает выдачу |
| I-MONOTONE-EXTEND | удлинение части только сужает выдачу |
| I-EMPTY-NOOP | пустой запрос не запускает поиск |
| I-STABLE-ORDER | порядок внутри типа детерминирован при равном времени |
| I-NO-INDEX-AT-REST | производные от содержимого структуры не персистятся |
| I-CACHE-FRESH | запись в источник отражается в кэше |

### 9.2 Property-тесты, а не примеры

Четыре свойства проверяются порождением случайных корпусов и запросов, а не подобранными случаями:

1. **Антитонность.** Для случайных `q` и части `p`: `M(q ⋅ " " ⋅ p) ⊆ M(q)`. Ловит и ошибку в разбиении запроса, и потерю записей при инкрементальном сужении.
2. **Инвариантность к порядку частей.** `M("а б") = M("б а")` для случайных пар.
3. **Согласие кэша с прямым проходом.** Результат по прогретому кэшу совпадает с результатом по холодному. Ловит нарушения I-CACHE-FRESH.
4. **Симметрия диакритики.** Для случайных строк с `ё`/`й`: запрос находит текст в обе стороны. Ловит регресс §2.3.

| № | Решение | Отклонённые варианты | Основание |
|---|---|---|---|
| 1 | Поиск только локальный, по расшифрованной истории | поиск через NIP-50 | содержимое зашифровано, реле видит шум |
| 2 | Вход — то же поле сайдбара, переход по Enter | отдельное поле на своём экране | плавный вход; цена — скрытая клавиша, гасится строкой-подсказкой в списке |
| 3 | Подстрочное сопоставление | префиксное; n-граммы; лемматизация | покрывает реальный сценарий «поиск по корням»; лемматизация не решает даже исходный пример |
| 4 | Конъюнкция частей по склеенному стогу | сопоставление по каждому полю отдельно | иначе запись с частями в разных полях не находится |
| 5 | Отбрасывание `Mn` после NFKD | оставить как есть; отдельное правило `ё → е` | без него отношение несимметрично по диакритике (§2.3) |
| 6 | Кэш расшифрованных стогов на сессию | персистентный индекс; расшифровка на каждый запрос | индекс на диске обнуляет шифрование БД; повторная расшифровка — секунды на каждый запрос |
| 7 | Ключ выборки через HMAC — отвергнут | searchable symmetric encryption | утечка частот и совместной встречаемости; несоразмерно v0.1 |
| 8 | Группировка выдачи по типу | единый балл релевантности | межтиповое сравнение не выводится, а назначается |
| 9 | Ограничение на вывод, не на длину запроса | минимум 5 символов | стоимость не зависит от длины запроса; порог отсекает частотные русские корни |
| 10 | Однократный запуск, замирающая выдача | живой поиск с дебаунсом | живой требует индекса в памяти и прячет стоимость до худшего момента |

## 12. Открытые вопросы

1. **Escape на экране результатов.** Очистить поле и остаться либо вернуться в прежнее место. Совместить нельзя. К модели не относится, но принять до вёрстки.
2. **Порог длины для больших источников.** Принято решение №9 (порога нет). Остаётся вариант мягкой формы: два символа минимум для сообщений и постов, без порога для контактов и каналов. Не решено, вопрос вкуса к выдаче, не корректности.
3. **Потолок памяти под кэш.** При какой величине `L` кэш перестаёт помещаться и включается материализованная таблица — не измерено. Порог назначать после бенчмарка на `10³/10⁴/10⁵`, как это уже делалось для файлового дерева.
4. **Поиск по содержимому файлов.** Требует расшифровки блобов, то есть другой модели стоимости. Вне v0.1, но повлияет на `φ`, если появится.
5. **Подсветка совпадений в выдаче.** Позиции вхождений считаются в §4 бесплатно, но их надо донести до отображения, не разрушая границу «модель ничего не знает о вёрстке». Форма передачи не определена.
6. **Дизъюнкция.** Если появится — отключает I-ANTITONE и вместе с ним инкрементальное сужение (§4.3). Это связанная пара; принимать оба решения разом.
