# Глобальный поиск. Алгоритмические основания

**Статус:** черновик, этап 2 проектирования. Продолжение `SEARCH-MATH.md`.
**Отношение к предыдущему документу:** `SEARCH-MATH.md` отвечает на вопрос «что корректно». Этот документ отвечает на вопрос «что выполнимо за приемлемое время и какими структурами». В §16 перечислены места, где алгоритмический разбор **требует правок в математическом документе**.
**Не входит:** схема IndexedDB сверх необходимых индексов, вёрстка экрана, формат сетевых событий.

## 0. Дисциплина документа

Асимптотика без указания размеров задачи — гадание. Каждое утверждение о сложности сопровождается допущением о масштабе (§2), и там, где величина мала, прямо сказано, что оптимизировать нечего.

Три вещи, способные сломать этот экран, и ни одна из них не про выбор алгоритма сопоставления строк:

1. Чтение и расшифровка всей истории в главном потоке (§4, §6).
2. Обход, который нельзя прервать досрочно (§5).
3. Пересборка нормализованных строк на каждый запрос вместо одного раза (§12).

Всё остальное — гигиена.

## 1. Профиль нагрузки

| Операция | Что вызывает | Порядок частоты |
|---|---|---|
| Фильтр сайдбара по названиям | каждое нажатие клавиши | **очень высокая** |
| Поиск по содержимому | Enter | низкая (человеческий темп, единицы за сессию) |
| Уточнение запроса | Enter после правки | низкая, но следует сразу за предыдущим |
| «Показать ещё» | прокрутка выдачи | низкая |
| Поддержка кэша при приёме сообщения | сетевое событие | средняя |

**Вывод: профиль здесь обратный файловому модулю.** В файлах чтения доминировали над записями на три порядка, и стратегия была «предвычислять всё». Тут дорогая операция запускается единицы раз за сессию, по явному действию человека, который **уже готов подождать**, потому что сам нажал Enter.

Отсюда главный вывод всей алгоритмической части: **дешевле сделать один честный проход, чем содержать структуру.** Индекс окупается частотой запросов, а частоты нет.

## 2. Допущения о масштабе

Числа ниже — предположения, требующие проверки, а не измеренные факты.

| Величина | Ожидаемо | Проектный потолок | Комментарий |
|---|---|---|---|
| Сообщений `n_msg` | 10³–10⁴ | 10⁵ | доминирующий источник |
| Постов и комментариев | 10²–10³ | 10⁴ | |
| Сообщений общего чата каналов | 10²–10³ | 10⁴ | |
| Контактов | 10–10² | 10³ | |
| Каналов | 10–10² | 10³ | |
| Узлов файлового дерева | 10³–10⁴ | 10⁵ | уже принято в `FILES-ALGO.md` §2 |
| Длина стога `\|H(d)\|` | 10²–10³ байт | 10⁴ | сообщение, пост, описание канала |
| Частей в запросе `k` | 1–3 | 8 | больше человек не набирает |
| Показывается на группу | 50–100 | — | §6.3 матдока |

**Ключевое следствие:** источники расходятся по величине на три порядка. Контакты и каналы — сотни записей, сообщения — десятки тысяч. Это не мелочь для таблицы, а причина, по которой обход строится не единым циклом, а очередью источников (§7).

## 3. Ответ на прямой вопрос: есть ли готовый алгоритм

Есть, и не один. Поиск подстроки — одна из самых разработанных задач в информатике: Кнут–Моррис–Пратт даёт `Θ(|h| + |p|)` за счёт предподсчёта префикс-функции, Бойер–Мур на практике пропускает куски текста и часто работает быстрее линейного, Рабин–Карп сводит сравнение к скользящему хешу, Ахо–Корасик ищет **все** `k` образцов за один проход, суффиксный автомат отвечает на запрос за `Θ(|p|)` после `Θ(|h|)` предобработки.

**И почти ничего из этого тебе не нужно.** Три причины, по убыванию важности.

**Первая.** `String.prototype.includes` уже реализован в движке на C++ (V8 переключается между простым поиском и вариантом Бойера–Мура–Хорспула в зависимости от длины образца). Написанный на JavaScript КМП соревнуется с ним из заведомо проигрышной позиции: он платит за интерпретацию каждого шага цикла, тогда как встроенный работает на нативной скорости по компактному представлению строки. **Обоснованная гипотеза,** а не измеренный факт: рукописный КМП в JS проиграет `includes` в разы. Проверяется одним замером (§15) и до замера считается гипотезой.

**Вторая.** Все перечисленные алгоритмы оптимизируют слагаемое, которого не видно на фоне другого (§4).

**Третья.** Суффиксный автомат и индекс n-грамм — структуры, которые надо **хранить**, а хранить производные от содержимого запрещено инвариантом I-NO-INDEX-AT-REST. Строить их заново на каждый запрос дороже, чем один раз пройти сканом.

### 3.1 Про «поиск по массиву — тяжёлое действие»

Утверждение из Венгроу верное, но относится к другой задаче. Там сравниваются линейный поиск `Θ(n)` и двоичный `Θ(log n)`, и вывод такой: если данные отсортированы, линейный поиск — расточительство.

**Условие «если отсортированы» здесь не выполнимо в принципе.** Двоичный поиск требует, чтобы искомое сравнивалось с ключом сортировки целиком, по тому же порядку. Отсортировать историю по тексту сообщений можно, но запрос `деньг` — не префикс и не полное значение ключа, он может стоять в середине строки. Множество строк, содержащих `деньг` как подстроку, в лексикографическом порядке **не является отрезком**, а двоичный поиск умеет находить только отрезки. Свести подстрочный поиск к двоичному можно лишь через суффиксный массив, то есть предварительно построив структуру размером с текст — см. третью причину выше.

Так что `Θ(n)` здесь не признак лени, а нижняя граница для выбранной семантики без предобработки. Отказаться от неё можно только отказавшись от подстроки, а это решение №3 матдока и оно принято.

## 4. Главная находка: сопоставление — не то слагаемое

Один запрос раскладывается на три статьи расхода:

```
Θ(n) чтений из IndexedDB   +   Θ(n) расшифровок   +   Θ(L · k) сопоставления
```

где `L` — суммарная длина стогов, `k` — число частей запроса.

Третье слагаемое — это `includes` по строке в памяти, работающий на нативной скорости. Первые два — обращение к хранилищу и криптография. Разрыв между ними, по моей оценке, два-три порядка.

Расшифровка одной строки в этом проекте — не только шифр. `decryptRow` делает три вещи: ChaCha20-Poly1305 с проверкой тега Poly1305 (`@noble/ciphers`, чистый JS), декодирование UTF-8 и `JSON.parse` **с ревайвером**. Последнее стоит отметить особо: ревайвер вызывается движком на **каждое значение дерева**, а не на корень. Для строки сообщения с вложениями это десятки вызовов функции JS на одну запись.

**Обоснованная гипотеза, требующая замера:** на маленьких строках `JSON.parse` с ревайвером сопоставим по стоимости с самим шифром или дороже его. Если гипотеза подтвердится, самая результативная оптимизация всего экрана — не трогать криптографию, а избавиться от ревайвера там, где в строке заведомо нет двоичных полей. Пока не измерено — не оптимизировать.

**Практический вывод:** любые рассуждения о выборе алгоритма сопоставления — это спор о третьем слагаемом. Даже двукратный выигрыш там незаметен. Всё, что реально влияет на время ответа, лежит в том, **сколько строк мы прочитали и расшифровали**, и именно это должно быть предметом оптимизации.

## 5. Единственная оптимизация, дающая порядок: досрочное прекращение

Из §6.2 и §6.3 матдока: выдача внутри группы упорядочена по времени, показывается не более `k` записей.

Значит если обходить источник **от свежих к старым**, то после `k` найденных совпадений остаток обходить незачем — ни одна более старая запись в первую страницу не попадёт. Не эвристика, а следствие совпадения порядка обхода с порядком показа.

| Сценарий | Прочитано строк |
|---|---|
| Частый запрос (`деньг`) | порядка `k`, то есть сотни |
| Редкий запрос (имя, встретившееся дважды) | весь источник |
| Запрос без совпадений | весь источник |

То есть выигрыш есть на частых запросах и отсутствует на редких. Худший случай не улучшается вовсе — и это надо принять сразу, а не обнаружить: **приложение обязано оставаться живым во время полного прохода** (§6), потому что полный проход неизбежен на любом запросе, ничего не нашедшем.

### 5.1 Чем платим

Досрочное прекращение **несовместимо с показом общего числа найденного**. Чтобы написать «найдено 1483», нужно досчитать до конца, то есть отказаться от всей экономии. Выдача может показывать «показано 100» и кнопку «ещё», но не мощность результата.

Это правка в матдок (§16).

### 5.2 Продолжение обхода

«Показать ещё» возобновляет обход с места остановки. Значит состояние поиска — не только массив результатов, но и **курсор на источник**: для каждого источника позиция, с которой продолжать. Структура в §14.

### 5.3 Порядок обхода против порядка показа

Идеальный обход шёл бы по убыванию времени записи. Ближайшее, что есть в схеме без новых индексов, — обратный курсор по первичному ключу `++seq` таблицы `messages`, то есть **порядок локальной вставки**, а не отправки.

Для живого потока они совпадают. Расходятся при догрузке старой истории: сообщение годичной давности, приехавшее сегодня, получит большой `seq` и всплывёт в начале обхода. На корректность это не влияет (множество `M(q)` не меняется), влияет на то, какие именно `k` записей попадут в первую страницу. Приемлемо для v0.1, **но это приближение, а не порядок из матдока**, и это тоже правка в §16.

Для `posts` и `channelMessages` глобального обхода по времени нет вовсе: существующие индексы — `[ownerPubkey+channelId+createdAt]`, то есть внутри канала. Нужен дополнительный индекс `[ownerPubkey+createdAt]` в обеих таблицах. Это единственное изменение схемы, которого требует поиск.

## 6. Главный поток

Полный проход при `n = 10⁵` — секунды процессора (оценка `MEDIA-ALGO.md` §3.8, здесь применима без изменений). Кадр — 16 мс. Разрыв в сотни раз, поэтому вопрос не «успеем ли», а «как не заморозить интерфейс на всё это время».

Два способа, и это настоящий выбор.

**Порционный обход с уступкой управления.** Читать пачками по 100–200 строк, между пачками отдавать управление. Просто, не требует новой инфраструктуры, позволяет показывать результаты по мере поступления и рисовать индикатор прогресса. Цена: каждая пачка всё же выполняется в главном потоке, поэтому анимации будут слегка дёргаться; и вся работа конкурирует с отрисовкой.

**Воркер.** Прецедент в проекте есть — `src/workers/crypto.worker.js` через Comlink уже уносит `batchVerify` и `encryptChunk` из главного потока, ключи через границу воркера уже передаются. Главный поток остаётся полностью гладким. Цена выше, чем кажется: воркеру нужен либо свой доступ к IndexedDB, либо передача расшифрованных строк обратно; а держать кэш стогов **в воркере** означает, что результаты придётся пересылать структурным клонированием на каждый запрос.

**Критерий выбора.** Если замер (§15) покажет, что полный проход при ожидаемом объёме `10⁴` укладывается в несколько сотен миллисекунд — брать порционный обход, воркер не окупает сложности. Если счёт пойдёт на секунды — воркер, потому что дёргающийся интерфейс в течение нескольких секунд читается как зависание.

Решать до замера не нужно, и я не буду.

## 7. Очередь источников

Обход идёт не единым циклом, а по источникам в порядке возрастания стоимости:

| Очередь | Источник | Записей | Ожидаемое время |
|---|---|---|---|
| 1 | контакты, каналы | `10²` | единицы мс |
| 2 | узлы файлов | `10³–10⁴` | десятки мс |
| 3 | посты, комментарии, чат каналов | `10³–10⁴` | десятки–сотни мс |
| 4 | личные сообщения | `10⁴–10⁵` | сотни мс — секунды |

Первая очередь отрабатывает за время, неотличимое от мгновенного, и **закрывает оба примера из постановки задачи**: карточка контакта по имени и канал по слову в правилах находятся до того, как человек успеет заметить задержку. Тяжёлый источник досыпает результаты в уже отрисованный экран.

Это устраняет главную беду медленного поиска — не саму медленность, а пустой экран в ожидании. Группы приходят по готовности, каждая со своим индикатором.

## 8. Кэш стогов

### 8.1 Что это

Массив `{ ключ записи, тип, время, H }`, где `H` — уже **нормализованный** стог (§3.2 матдока). Собирается при первом поиске в сессии, живёт до блокировки.

Это не индекс: структуры доступа у него нет, он не отвечает быстрее линейного прохода. Он снимает единственную дорогую статью — повторное чтение и расшифровку. Первый запрос платит полностью, второй и дальше идут по памяти со скоростью `includes`, то есть отвечают мгновенно.

### 8.2 Объём

При `n = 10⁵` и среднем стоге 300 байт — порядка 30 МБ строк плюс накладные расходы на объекты. Держать можно, но это уже заметно, и это тот же потолок, что назван в `FILES-ALGO.md` §2. Предел, при котором кэш перестаёт быть уместным, назначать после замера (§15), а не сейчас.

### 8.3 Взаимодействие с досрочным прекращением

Тут скрыт неочевидный конфликт. Досрочное прекращение (§5) не читает источник целиком, значит **кэш после первого поиска заполнен частично**. Второй запрос по частичному кэшу вернёт неполный результат, если понадеяться на кэш как на весь корпус.

Поэтому у кэша есть **граница заполнения на источник** — позиция, до которой он достоверен. Запрос обслуживается из кэша до этой границы, дальше продолжает читать хранилище и дописывать кэш. Без явной границы получится тихая потеря результатов, а это худший класс ошибок: выдача выглядит правдоподобной.

- **Инвариант.** Ответ по частично заполненному кэшу обязан совпадать с ответом по полному проходу. Проверяется property-тестом №3 из §9.2 матдока, который для этого надо расширить на случай частичного заполнения.

### 8.4 Поддержка при записи

Новая запись дописывает свой стог в кэш (`Θ(1)`, инвариант I-CACHE-FRESH). Удаление отрабатывается открытым флагом `deleted` при чтении и в кэше ничего не трогает.

Кэш **не переживает блокировку** и не сохраняется: это и есть выполнение I-NO-INDEX-AT-REST.

## 9. Уточнение запроса

I-ANTITONE и I-MONOTONE-EXTEND (§4.3 матдока) дают: если новый запрос получен добавлением части или удлинением существующей, результат — подмножество прежнего. Значит уточнение обходит **прежнюю выдачу**, а не источник: десятки записей вместо десятков тысяч, ответ мгновенный.

Условие применимости проверяется механически: множество частей нового запроса покрывает старое в смысле «для каждой старой части есть новая, её содержащая». Если не покрывает — обычный проход.

Пока в модели нет дизъюнкции, приём безопасен. Появится — отключать вместе с ней, это связанная пара (§4.3 матдока).

## 10. Сопоставление: как именно

```
для каждой части p из P(q):
    если не H.includes(p): запись отброшена
```

Части проверяются **от самой длинной к самой короткой**. Длинная часть избирательнее, отбрасывает больше записей, и цикл выходит раньше. Выигрыш скромный (третье слагаемое, §4), стоит одной строки сортировки при разборе запроса.

Ахо–Корасик нашёл бы все `k` частей за один проход по стогу вместо `k` проходов. Но при `k ≤ 3` и нативном `includes` против интерпретируемого автомата это, **по обоснованной гипотезе**, проигрыш. Если когда-нибудь захочется проверить — это ровно один замер, а не переделка.

---

## 11. Подсветка совпадений

Позиции вхождений нужны только для **показанных** записей, то есть для `k` на группу, а не для всех найденных. Считать их в цикле сопоставления — значит платить за то, что никто не увидит.

Правильный порядок: сопоставление отвечает «да/нет», позиции вычисляются отдельным проходом по уже отобранным записям, при отрисовке. Разница на редком запросе — `10⁵` вычислений позиций против сотни.

## 12. Случайно квадратичное и просто расточительное

Категория ошибок, которые не проявляются на тестовых объёмах и убивают экран на реальных.

| Сценарий | Наивно | Правильно |
|---|---|---|
| `normalize()` стога внутри цикла запроса | `Θ(n·L)` на **каждый** запрос | нормализовать один раз при заполнении кэша |
| Нормализация частей запроса внутри цикла по записям | `Θ(n·k·\|q\|)` | один раз при разборе запроса |
| Склейка полей в стог на каждый запрос | `Θ(n·L)` | стог собирается один раз, в кэше |
| Создание `RegExp` на каждую запись | `Θ(n)` компиляций | `includes`, регулярных выражений нет вовсе |
| Пересортировка выдачи после каждого найденного | `Θ(r² log r)` | обход уже идёт в нужном порядке (§5), сортировка не нужна |
| `unshift` в массив результатов ради обратного порядка | `Θ(r²)` | `push` при обходе от свежих к старым |
| Вычисление позиций подсветки для всех найденных | `Θ(r·L)` | только для показанных (§11) |
| Расшифровка строки целиком ради одного текстового поля | неизбежно | блоб один, полей несколько — не оптимизируется, констатация |
| Полный проход при уточнении запроса | `Θ(n)` на каждую правку | обход прежней выдачи (§9) |

Строка про `unshift` выглядит мелочью, но при `r = 10³` это миллион перемещений элементов — на ровном месте и молча.

## 13. Что делать не надо

| Приём | Почему нет |
|---|---|
| КМП / Бойер–Мур руками на JS | проигрывает нативному `includes` (гипотеза, §3) |
| Индекс n-грамм, суффиксный автомат | нарушает I-NO-INDEX-AT-REST или строится дольше скана |
| Двоичный поиск по отсортированному тексту | множество вхождений подстроки не отрезок (§3.1) |
| Дебаунс вместо Enter | прячет стоимость до худшего момента — решение №10 матдока |
| Порог длины запроса ради скорости | стоимость не зависит от длины запроса (§4) — решение №9 |
| Ранжирование по релевантности | требует досчитать до конца, отменяет §5 |
| Готовая библиотека полнотекстового поиска | сериализованный индекс хранит слова открытым текстом |

## 14. Сводка структур данных

| Структура | Где живёт | Стоимость | Назначение |
|---|---|---|---|
| Кэш стогов | память, до блокировки | `Θ(L)` памяти, `Θ(n)` на заполнение | не расшифровывать дважды |
| Границы заполнения | память, по одной на источник | `Θ(1)` | достоверность частичного кэша (§8.3) |
| Курсоры источников | состояние поиска | `Θ(число источников)` | «показать ещё» (§5.2) |
| Выдача по группам | состояние поиска | `Θ(r)` | показ и база для уточнения (§9) |
| Разобранный запрос | вычисляется при Enter | `Θ(k)` | нормализованные части, отсортированы по убыванию длины |

Ни одна структура не сохраняется на диск. Ни одна не переживает блокировку.

## 15. Что нужно измерить прежде, чем оптимизировать

Ни одна оптимизация из этого документа, кроме §12, не должна применяться до замера. Инфраструктура есть: `scripts/*-bench.mjs`.

1. **Стоимость одной строки, разложенная на три части:** чтение из IndexedDB, `chacha20poly1305`, `JSON.parse` с ревайвером. Это главный замер — от него зависит §4, §6 и §8.2. Разделить обязательно: суммарное число не подскажет, что чинить.
2. **Полный проход** при `n = 10³, 10⁴, 10⁵`. Определяет выбор между порционным обходом и воркером (§6).
3. **`includes` против рукописного КМП** на реальных длинах стога. Одноразовая проверка гипотезы §3, чтобы закрыть вопрос ссылкой на число, а не на мнение.
4. **Объём кэша** при `n = 10⁵` в мегабайтах. Определяет потолок §8.2.
5. **Ревайвер против его отсутствия** на строках без двоичных полей. Если разрыв велик — самая дешёвая оптимизация проекта, и она за пределами поиска.

## 16. Требуемые правки в `SEARCH-MATH.md`

1. **§6.3.** Добавить: обход идёт в том же порядке, что и показ, — это условие корректности досрочного прекращения, а не деталь исполнения. Без него обрыв обхода теряет записи, которые должны были попасть на первую страницу.
2. **§6.** Добавить явно: выдача **не обязана знать мощность** `M(q)`. Показ общего числа найденного несовместим с §5 настоящего документа.
3. **§6.2.** Отметить, что реализация упорядочивает по порядку локальной вставки (`seq`), а не по времени отправки, и что это приближение расходится с моделью при догрузке старой истории (§5.3).
4. **§2.** Уточнить I-NORM-BOTH: нормализация корпуса выполняется один раз при заполнении кэша, а не в момент сопоставления. Формулировка «сопоставляются только нормализованные пары» остаётся верной, но момент применения надо назвать, иначе первая строка таблицы §12 станет неизбежной.
5. **§9.2.** Расширить property-тест №3: согласие кэша с прямым проходом должно проверяться и для **частично** заполненного кэша (§8.3), иначе главный риск этой конструкции остаётся непокрытым.
6. **§12.** Дополнить открытый вопрос о подсветке: позиции считаются отдельным проходом по показанным записям (§11), то есть в модель они не входят вовсе.

## 17. Открытые вопросы

1. **Порционный обход или воркер** (§6). Решается замером №2, не рассуждением.
2. **Стоимость ревайвера** (§4). Если гипотеза верна, из неё следует правка в `db-crypto.js`, влияющая на весь проект, а не только на поиск.
3. **Поведение кэша при смене аккаунта.** Кэш owner-scoped по построению, но переключение локального аккаунта без блокировки — сценарий, который в проекте уже поддержан и здесь не продуман.
4. **Прогрев в простое.** Заполнять кэш заранее, пока приложение бездействует, — заманчиво, но это `Θ(n)` расшифровок ради операции, которая может не состояться. Мерить надо не время, а расход батареи, а такого замера в проекте нет.
5. **Отмена идущего поиска.** Человек нажал Enter, подождал, набрал новый запрос. Прерывание обхода на середине с сохранением уже заполненной части кэша — не проработано.
6. **Виртуализация выдачи.** При сотне записей на группу и нескольких группах список остаётся коротким, но «показать ещё» несколько раз подряд выводит на объёмы, где нужен виртуализованный список. Порог не определён.
