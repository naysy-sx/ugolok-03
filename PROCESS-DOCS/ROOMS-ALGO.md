# ROOMS-ALGO.md — алгоритмический фундамент раздела «Быстрая связь»

Спутник ROOMS-MATH-v2.md. Там — структуры и инварианты, здесь — операции, их

## 0. Метод: частота, а не размер входа

Голосовая часть ограничена пятью участниками (Р4). На пяти элементах разница
между `O(n²)` и `O(n log n)` — двадцать операций против одиннадцати, то есть
ничего. Любой разбор, где эта разница обсуждается всерьёз, был бы украшением.

Полезный критерий здесь другой, и он даёт два вопроса:

1. **Как часто операция выполняется?** Операция на 60 Гц и операция раз в минуту
   находятся в разных вселенных независимо от их сложности.
2. **Что растёт неограниченно?** Не размер входа в моменте, а размер состояния
   во времени.

Таблица операций по фактической частоте:

| Операция | Частота | Размер входа | Где живёт |
|---|---|---|---|
| Отрисовка спектрограммы | **60 Гц** | 1024 бина | §7 |
| Индикатор «кто говорит» | 15–20 Гц | n ≤ 5 | §7.3 |
| Вычисление `Present(t)` | ~1–10 Гц | **растёт во времени** | §2, §3 |
| Приём сообщения чата | ~0.1–2 Гц | вставка в список | §5 |
| Heartbeat своего устройства | 1/15 с | — | §3 |
| Приём чужого heartbeat | n/15 с | — | §3 |
| Переиздание анонса комнаты | 1/15 с × n | — | §4 |
| Пересчёт рёбер mesh | при join/leave | n ≤ 5 | §6 |
| KDF при входе | **1 раз за сеанс** | — | §8 |

Из таблицы сразу видно распределение внимания: три верхние строки — вся
инженерия, остальное пишется наивно и остаётся наивным.

## 1. Что здесь классические алгоритмы **не** решают

Полезно сказать явно, чтобы не искать несуществующее.

**Кратчайшие пути, потоки, покрытия** — граф mesh полный и крошечный, задач на
нём нет. Полный граф — это отсутствие структуры, а не структура.

**Упорядочение медиапакетов, jitter-буфер, коррекция потерь** — всё внутри
WebRTC, реализовано браузером. Твой код к этому не прикасается и не должен.

**Балансировка, шардирование, распределённый консенсус** — n ≤ 5, один релей,
без реплик. Консенсус здесь имеет ровно один случай (§4.3), и тот решается
полурешёткой, а не протоколом.

**Сжатие, кодирование** — Opus делает браузер.

Остаётся четыре настоящих сюжета: рост состояния, подавление дубликатов,
адаптивная сортировка, и константы в реальном времени.

## 2. Главный результат: обрезка монотонного состояния

### 2.1. Проблема

Состояние присутствия `L : D → T × T` (ROOMS-MATH §2.2) — CvRDT, и потому
монотонно: оно никогда ничего не забывает. Участник, зашедший на минуту два часа
назад, остаётся в `L` навсегда.

Отсюда расхождение, которое легко не заметить:

```
|Present(t)| — ограничено (единицы человек)
|D|          — растёт линейно по числу заходов за всю жизнь комнаты
```

Наивное вычисление `Present(t)` — проход по всему `L`, то есть `Θ(|D|)`. Операция
выполняется на каждый входящий heartbeat и на каждую перерисовку списка. Комната,
живущая четыре часа, через которую прошло двести человек, будет платить за двести
записей ради ответа из трёх. Это не катастрофа по абсолютным числам, но это
неограниченный рост при ограниченном ответе — единственная такая величина во всей
фиче.

### 2.2. Утверждение об обрезке

> **Обрезка безопасна.** Удаление из `L` любой записи `d`, для которой
> `a_d < now − τ`, наблюдательно эквивалентно её сохранению: ни при каком
> будущем слиянии удалённая запись не изменила бы ни один ответ `Present(t')`
> для `t' ≥ now`.

Обоснование. Пусть `d` удалена. Возможны два случая.

*Приходит новое событие для `d` со свежим `a'_d ≥ now − τ`.* Запись
переcоздаётся с этим значением. Результат совпадает с тем, что дало бы слияние
`max(a_d, a'_d) = a'_d`, поскольку `a_d < now − τ ≤ a'_d`.

*Приходит запоздалое событие со старым `a'_d < now − τ`.* Запись переcоздаётся
со значением `a'_d`, и предикат `a ≥ t' − τ` для неё ложен при любом
`t' ≥ now`. Сохранённая запись дала бы `max(a_d, a'_d)`, тоже меньше `now − τ`, и
тоже ложь. Ответы совпадают.

Существенно, что монотонность не нарушается: обрезка — не удаление из решётки, а
физическое представление элемента, эквивалентного `⊥` по всем наблюдаемым
предикатам. То же рассуждение, по которому в системах с окном допустима сборка
мусора над CRDT.

**Следствие:** `|L| = O(|Present|)`, то есть состояние ограничено, и `Present(t)`
вычисляется за время, пропорциональное числу реально присутствующих. Рост во
времени исчезает.

### 2.3. Где обрезать

На том же такте, что и sweep (§3.2). Не на каждом входящем событии — обрезка на
приёме даёт лишнюю работу без выигрыша.

**Тест И12 (новый, в дополнение к ROOMS-MATH §8):** после k заходов и выходов
`|L| = |Present|`, а не `k`.

## 3. Присутствие: структуры данных

### 3.1. Честный ответ, а не эффектный

Соблазн: min-куча по времени истечения, или timing wheel (Varghese & Lauck) на
три корзины при `τ = 3δ`. Обе структуры формально подходят, обе классические,
обеих здесь **не надо**.

При `|Present| ≤ 50` линейный проход по массиву раз в секунду — это пятьдесят
сравнений в секунду. Куча даёт `O(log n)` вместо `O(n)` и стоит нетривиальной
логики при обновлении ключа существующего элемента (участник продлевает аренду
каждые 15 с — это `decrease-key`, самая неприятная операция в куче). Обмен
плохой.

Рабочая структура **[К]**:

```
L : Map<pubkeyHex, { a, r, nick, joinedAt }>
```

`Map` даёт `O(1)` на обновление по heartbeat — операцию с самой высокой частотой
среди этой группы. `Present(t)` — проход по `L`, `O(|L|)`, и после §2 это
`O(|Present|)`.

**Когда куча стала бы правильной:** если бы `|Present|` измерялся тысячами, или
если бы срок аренды был индивидуальным для каждого участника. Ни того, ни другого
здесь нет. Записать в документ как отложенное решение, не реализовывать.

### 3.2. Sweep

Один таймер на комнату, период `δ/3 = 5 с` **[Г]**. На каждом такте: проход по
`L`, вычисление `Present`, обрезка (§2.3), сравнение с предыдущим составом,
уведомление UI только при изменении.

Отдельного таймера на участника быть не должно: n таймеров вместо одного дают ту
же точность и n-кратный расход на планировщик, плюс класс багов «таймер не
очищен при выходе».

Точность обнаружения ухода становится `τ + δ/3` вместо `τ`. При 45 и 5 секундах
это несущественно.

### 3.3. Сравнение составов

Уведомлять UI на каждом такте нельзя — перерисовка списка 0.2 раза в секунду без
причины. Нужна дешёвая проверка «изменилось ли».

Наивно: сравнение множеств, `O(n)`. При n ≤ 50 это ничто, и так и надо делать.

**[Э]** Альтернатива для любителей: инкрементальный хеш состава — XOR хешей
pubkey присутствующих. Состав изменился ⟺ хеш изменился (с точностью до
коллизий). `O(1)` на сравнение, `O(1)` на обновление при входе/выходе. Красиво,
но экономит нечего и вводит вероятностную ошибку в место, где её быть не должно.
Упоминаю, чтобы отвергнуть осознанно.

## 4. Подавление дубликатов анонса: Trickle

Единственное место, где классический алгоритм ложится точно.

### 4.1. Проблема

По Р5 анонс комнаты переиздаёт **каждый** участник, потому что комната обязана
пережить создателя. Наивно: каждый публикует анонс каждые `δ`. При n участниках —
n идентичных по смыслу событий каждые 15 секунд. При n = 5 это 20 событий в
минуту вместо одного нужного, и линейный рост по числу участников для информации,
которая от их числа не зависит.

### 4.2. Алгоритм

Trickle (RFC 6206, Levis и др.) **[К]** — придуман ровно для этого: поддерживать
согласованность в группе с минимальным трафиком, подавляя передачу, если то же
самое уже сказал кто-то другой.

Параметры: `Imin`, `Imax`, константа избыточности `k`.

```
на старте интервала:
    c ← 0
    t ← random(I/2, I)                # точка передачи внутри интервала
при получении согласованного анонса:  # тот же s
    c ← c + 1
при наступлении t:
    если c < k:  публиковать анонс
    иначе:       молчать
в конце интервала:
    I ← min(2I, Imax)
при получении несогласованного анонса: # другой s — гонка создания!
    I ← Imin
    начать интервал заново
```

Параметры для нас **[Г]**: `Imin = δ = 15 с`, `Imax = 60 с`, `k = 1`.

При `k = 1` в установившемся режиме анонс публикует примерно один участник за
интервал — тот, чей случайный `t` оказался раньше. Трафик перестаёт зависеть от
n. Интервал растёт до минуты, пока всё спокойно.

### 4.3. Почему это особенно уместно

Сброс интервала на **несогласованности** делает ровно то, что нужно при гонке
создания (ROOMS-MATH §1.4): увидев анонс с другой солью, участники учащают
переиздание и быстро сходятся к одному экземпляру. Механизм, встроенный в Trickle
для другой цели, здесь решает нашу задачу без дополнительного кода.

### 4.4. Что подавлять нельзя

**Heartbeat подавлению не подлежит.** Он утверждает присутствие конкретного
человека, и другой человек его не заменяет. Trickle применяется только к анонсу
комнаты — событию, идентичному у всех.

Отсюда требование к контракту событий: анонс и heartbeat — **разные kind**, а не
одно событие с флагами. Слияние их в одно уничтожает возможность подавления.

## 5. Порядок сообщений чата: адаптивная сортировка

### 5.1. Распределение входа важнее худшего случая

Сообщения приходят почти в порядке возрастания (lamportTs, pubkey, id):
подавляющее большинство — в хвост, изредка что-то запоздало на одну-две позиции.

Три подхода и их цена на реальном распределении:

*Пересортировка всего списка при каждом приёме.* `O(m log m)` на сообщение,
`O(m² log m)` на комнату. Отвергается.

*Сбалансированное дерево.* `O(log m)` гарантированно, но константа велика, а
нужен ещё и последовательный обход для рендера. Не оправдано.

*Вставка с хвоста* **[К]**. Идти от конца назад, пока текущий элемент больше
вставляемого. Для сообщения, пришедшего по порядку, — **одно сравнение**,
`O(1)`. Для запоздавшего на `k` позиций — `O(k)`. Суммарно `O(m + K)`, где `K` —
общее число инверсий во входе; на почти отсортированных данных `K` мал.

Это классическая адаптивная сортировка: сложность выражается через меру
неупорядоченности входа, а не только через его длину. Тот же принцип, что делает
insertion sort правильным выбором на почти отсортированных массивах, при том что
в худшем случае он квадратичен.

**Ограничитель:** прекращать проход после `K_max = 200` шагов назад **[Г]** и
вставлять на достигнутую позицию. Сообщение, опоздавшее на двести позиций, в
эфемерной комнате не имеет смысла ставить точно, а защита от патологического
входа нужна.

### 5.2. Дедупликация

События приходят с релея с возможными повторами (переподключение, две подписки).

Честный ответ: `Set<eventId>`, без изысков. Комната эфемерна и коротка; при
десяти тысячах сообщений это порядка сотен килобайт — приемлемо для сеанса,
который заведомо кончится. LRU, фильтр Блума и прочее здесь — решение
несуществующей проблемы.

Проверка перед вставкой — `O(1)`.

## 6. Турнир: почему алгоритма не нужно

Множество рёбер mesh при n ≤ 5 — не более десяти пар. Пересчёт при каждом
изменении состава — `O(n²) = 25` операций. Инкрементальный пересчёт дал бы
`O(n)`, то есть сэкономил двадцать операций раз в несколько минут.

**Правильное решение — пересчитывать всё с нуля** и сравнивать с текущим
множеством соединений. Причина не в производительности, а в корректности:
инкрементальность здесь — источник рассинхронизации между состоянием mesh и
составом участников, а это ровно тот класс багов, который трудно ловить.

Требование: ориентация — **чистая функция** от отсортированного списка pubkey
присутствующих. Одинаковый вход у всех участников ⟹ одинаковый результат ⟹
инвариант И5 выполняется без согласования.

```
edges(P) = { (i, j) : i, j ∈ sort(P), i < j }     # i инициатор
```

Сортировка пяти hex-строк — `O(n log n)` с несущественной константой; сравнение
64-символьных строк формально `O(64)`, фактически завершается на первом символе с
вероятностью 15/16.

Дельта применяется как разность множеств: рвать соединения из `E_old \ E_new`,
устанавливать из `E_new \ E_old`. Оба множества крошечные, разность через `Set` —
`O(n²)`.

## 7. Визуализатор: единственное место с настоящей частотой

60 кадров в секунду против всего остального, что происходит раз в секунды. Здесь
и только здесь имеют значение константы.

### 7.1. Разделить две задачи

Их путают, а требования у них разные:

*Спектрограмма* — картинка общего звука комнаты. Нужен FFT, нужны 60 Гц,
достаточно **одного** источника.

*Уровень громкости по участникам* («кто говорит») — нужен на каждого, но FFT для
него не нужен вообще, и 60 Гц не нужны.

Наивная реализация ставит `AnalyserNode` на каждого участника и вызывает
`getByteFrequencyData` для всех в каждом кадре: при n = 5 это 300 преобразований
Фурье размера 2048 в секунду. Native-код это выдержит, но работа выброшена
целиком.

### 7.2. Спектрограмма — один анализатор на общую шину

Все входящие потоки сводятся в один `GainNode`, на нём единственный
`AnalyserNode` с `fftSize = 2048` (1024 бина). Один FFT на кадр, `O(N log N)`
внутри браузера.

Отрисовка — вот где наивность дорого стоит. Спектрограмма прокручивается: каждый
кадр добавляется столбец справа, всё остальное сдвигается влево. Перерисовка
всего холста — `O(W · H)` на кадр, при 800×200 это 160 000 пикселей 60 раз в
секунду.

**Кольцевой блиттинг** **[К]**: скопировать холст на себя со сдвигом на пиксель,
затем нарисовать один новый столбец. Стоимость — один аппаратный blit плюс
`O(H)` на столбец. Реализация в лоб — `ctx.drawImage(canvas, -1, 0)`; браузеры
обрабатывают самокопирование корректно, но если поведение окажется неровным,
надёжный вариант — двойной буфер (рисовать в offscreen-холст, менять местами).

**[Э]** Альтернатива, если сдвиг всё равно окажется узким местом: не двигать
пиксели вовсе, а писать столбцы по кругу в буфер фиксированной ширины и рисовать
его двумя `drawImage` — от текущей позиции до конца и от начала до текущей.
Кольцевой буфер вместо сдвига, `O(H)` на кадр без блита. Классический приём из
осциллографов.

### 7.3. Уровень громкости — без FFT

Ключевая деталь: `AnalyserNode` считает FFT **лениво**, при вызове
`getByteFrequencyData`. Если запрашивать только `getByteTimeDomainData`,
преобразование не выполняется вовсе — это просто копия буфера.

Значит уровень считается так: `getByteTimeDomainData` с малым `fftSize` (256),
RMS по выборке — `O(256)` арифметики без FFT, на частоте **15–20 Гц**, не 60.
Индикатор «говорит» на глаз не отличается от 60 Гц, а работы в 3–4 раза меньше и
без единого преобразования Фурье.

Сглаживание — экспоненциальное скользящее среднее, одно умножение на кадр:

```
level ← α · rms + (1 − α) · level        α ≈ 0.3
```

Порог с гистерезисом (включение при 0.15, выключение при 0.10) **[Г]** — иначе
индикатор дрожит на границе.

### 7.4. Дисциплина кадра

Один `requestAnimationFrame` на всю комнату, а не на компонент. Внутри —
спектрограмма каждый кадр, уровни каждый третий-четвёртый. При скрытой вкладке
`requestAnimationFrame` останавливается сам; аудио продолжает идти, и это
правильно.

Регулятор громкости — `GainNode.gain`, изменение через `setTargetAtTime`, а не
присваиванием: мгновенная смена усиления даёт щелчок.

## 8. Один медленный KDF вместо двух

`KDF_slow` (Argon2id) — самая дорогая операция во всей фиче, порядка 100 мс, и
дорога она намеренно (ROOMS-MATH §1.3).

Наивно из формул математического документа получается два вызова: один для
`h_disc` в открытом режиме, другой для `k_rv` с суффиксом. Это лишнее.

Цепочка деривации в один медленный вызов **[К]**:

```
k_base  = Argon2id(n, p)                  # ЕДИНСТВЕННЫЙ медленный шаг
h_disc  = HMAC(k_base, "disc")            # быстро
k_rv    = HKDF(k_base, σ)                 # быстро
h       = HMAC(k_rv, "topic")             # быстро
```

Стойкость сохраняется: знающий `(n, p)` вычисляет `k_base` и `h_disc`, но без `σ`
не получает `k_rv`. Всё, кроме первой строки, — HMAC/HKDF, микросекунды.

**Обязательно в Web Worker.** 100 мс на главном потоке — заметная заморозка
интерфейса ровно в момент, когда пользователь нажал «войти». В проекте воркер
уже есть (`crypto.worker.js`, Comlink) — переиспользовать, не заводить второй.

UI на это время: не спиннер без объяснения, а «подбираем ключ комнаты» —
задержка намеренная, и её стоит показать как работу, а не как тормоза.

## 9. Что не оптимизировать

Список нужен не меньше предыдущих: он экономит время, которое иначе уйдёт в
красивую и бесполезную работу.

- **Множество рёбер mesh** — пять участников. Пересчёт с нуля, §6.
- **Дедупликация событий** — обычный `Set`, §5.2.
- **Сравнение составов участников** — линейное, §3.3.
- **Куча или timing wheel для аренды** — не оправдано при текущих размерах, §3.1.
- **Сжатие или батчинг heartbeat** — событие в сотню байт раз в 15 секунд.
- **Инкрементальный рендер списка участников** — до десятков элементов,
  перерисовка целиком дешевле, чем логика различий.

## 10. Сводка

| Операция | Структура | Сложность | Частота |
|---|---|---|---|
| Обновление аренды по heartbeat | `Map` | `O(1)` | n/15 с |
| `Present(t)` | проход по `Map` | `O(\|Present\|)` после §2 | 0.2 Гц (sweep) |
| Обрезка состояния | тот же проход | амортизированно `O(1)` на запись | 0.2 Гц |
| Публикация анонса | Trickle | `O(1)`, трафик не зависит от n | ~1/интервал |
| Вставка сообщения | вставка с хвоста | `O(1)` при порядке, `O(k)` при инверсии | до 2 Гц |
| Дедупликация | `Set` | `O(1)` | до 2 Гц |
| Пересчёт mesh | сортировка + разность множеств | `O(n²)`, n ≤ 5 | при join/leave |
| Выбор экземпляра при гонке | min-регистр (полурешётка) | `O(1)` на слияние | редко |
| Спектрограмма | один `AnalyserNode` + блит | `O(N log N)` + `O(H)` | **60 Гц** |
| Уровни участников | RMS по времени, без FFT | `O(256)` на участника | 15–20 Гц |
| Деривация ключей | одна цепочка в воркере | один Argon2id | 1 раз за вход |

## 11. Новые инварианты

В дополнение к И1–И11 из ROOMS-MATH-v2.

**И12.** После `k` циклов «вошёл — вышел» размер состояния равен числу
присутствующих, а не `k`. Прямая проверка обрезки (§2).

**И13.** При n участниках в установившемся режиме число публикаций анонса за
интервал не зависит от n (в пределах `k` Trickle). Проверка §4.

**И14.** Вставка `m` сообщений, пришедших строго по порядку, выполняет ровно `m`
сравнений. Проверка адаптивности (§5.1).

**И15.** `getByteFrequencyData` вызывается не более одного раза на кадр
независимо от числа участников. Проверка §7 — регрессия на случай, если кто-то
позже добавит анализатор на участника.
