## 0. Цель и не-цели

### 0.1. Цель

Переделать UX/UI **внутренней страницы канала** (не список каналов) так, чтобы:

1. Лента постов была короткой и устойчивой при любом числе комментариев.
2. Полный текст поста и дерево комментариев жили на **отдельной странице записи**.
3. Шапка канала, правила и кнопка «Написать пост» не занимали 100% ширины уродливыми блоками.
4. Форма нового поста была компактной карточкой ограниченной ширины.
5. У постов в ленте не было плиточного фона `.rec` (`surface-raised` + рамка на каждую карточку).
6. Вложения в посте и в комментарии выглядели **идентично** вложениям личных чатов (те же классы и размеры).
7. Дерево комментариев было ровным, без маркеров списка, без раскрывашки `<details>` как основного каркаса ветки.
8. Кнопка «Ответить» не была крупным `.btn--ghost`, а тихой подписью по наведению.
9. Появились **базовые реакции** на пост и на комментарий (это затрагивает доменный слой, IndexedDB, транспорт, тесты).

### 0.2. Явные не-цели (запрещено делать в этой задаче)

- Реакции в личных чатах, в общем чате канала (`channel-chat.jsx`), в «Быстрой связи».
- Вариант B (мастер-деталь, две колонки). Не верстать split-view.
- Редизайн вкладок «Чат», «Модерация», «Настройки» — их содержимое не перекладывать. Можно только вписать вкладки в новую шапку, не ломая поведение.
- Смена палитры, генератора темы, шрифтов.
- Рефакторинг «заодно»: не переименовывать рабочие классы вне канала, не «чистить мёртвый CSS» за пределами затронутых селекторов, не переписывать markdown-редактор.
- Федеративный NIP-25 (`kind:7`) в публичный Nostr. Реакции канала — **свой** encrypted parameterized-replaceable kind на `channelKey`.
- Уведомления о реакциях, бейдж непрочитанного из-за реакции, реакция как курсор прочтения канала.
- Произвольный эмодзи-каталог, кастомные реакции, анимации Lottie.

Если хочется сделать что-то из не-целей — **не делать**. Зафиксировать в конце отчёта как «вынесено».

## 2. Текущее состояние (что сломано и почему)

Файл экрана: `src/ui/screens/channel.jsx` (`ChannelDetail`).  
Карточка: `src/ui/components/post-card.jsx` (класс `.rec`).  
Комментарии сейчас рендерятся компонентом `PostWithComments` **под постом в ленте**: `expanded` грузит `getCommentsTree` и рисует `.comment-section` в том же скролле.

Следствия, которые надо устранить:

- При сотнях/тысячах комментариев лента раздувается, соседние посты уезжают.
- Кнопка `.channel-post-cta` тянется как баннер на всю ширину колонки.

- Форма `PostComposer` — `.card.box` на всю ширину.
- `.rec` даёт каждой записи фон `var(--surface-raised)` и рамку — «обои из плиток».
- «Ответить» — полноценная `.btn--ghost` с иконкой, всегда видна.
- Ветка ответов — `<details class="replies" open>`.

`place` уже умеет `{ kind: "channel", id, subTab, postId, commentId }`, это используют `today.jsx` и уведомления. Это поведение **заменить**: `postId` становится режимом «страница записи» и живёт, пока пользователь не нажмёт «назад».

## 3. Информационная архитектура и навигация

### 3.1. Два режима одного kind

`place.kind` остаётся `"channel"`. Режим определяется наличием `place.postId`:

| Состояние | Что на экране |
|---|---|
| `{ kind: "channel", id: channelId }` без `postId` | Лента канала (шапка, вкладки, список коротких записей) |
| `{ kind: "channel", id: channelId, postId, commentId? }` | Страница одной записи + комментарии. `commentId` — подсветка и scrollIntoView после загрузки дерева |

`subTab` по-прежнему переключает «Посты / Чат / Модерация / Настройки» **только в режиме ленты**. На странице записи вкладок канала нет (это экран одной записи). Если пришли с `subTab: "chat"` — открывать вкладку чата ленты, `postId` игнорировать.

### 3.2. Функции навигации

В `src/ui/signals/place.js` **не плодить третий сигнал**. Расширить существующее:

```js
openChannel(channelId)                     // лента
openChannel(channelId, { postId })         // страница записи
openChannel(channelId, { postId, commentId }) // страница записи + подсветка
```

Добавить явную функцию (имя фиксировано):

```js
export function openChannelPost(channelId, postId, commentId) {
  place.value = { kind: "channel", id: channelId, postId, commentId };
}
```

`openChannel(null)` по-прежнему ведёт к списку каналов (`kind: "channels"`).

Назад со страницы записи → `openChannel(channelId)` (лента того же канала), **не** к списку каналов.  
Назад с ленты канала → как сейчас, `openChannel(null)`.

Хлебная крошка `Screen.breadcrumb`:

- лента: `{ label: t("nav.channels"), onBack: () => openChannel(null) }`
- страница записи: `{ label: channelName, onBack: () => openChannel(channelId) }`

Заголовок `Screen.title`:

- лента: имя канала
- страница записи: `t("channel.postPageTitle")` (коротко: «Запись»), имя канала не дублировать вторым h1

### 3.3. Что перестаёт существовать

- Состояние `expanded` внутри ленты для показа дерева комментариев.
- Компонентная связка «карточка + comment-section под ней» в списке (`PostWithComments` в текущем виде).
- Эффект, который обнуляет `place.postId` сразу после скролла.

`commentId` после успешного `scrollIntoView` можно обнулить (чтобы повторный ререндер не дёргал скролл), `postId` — нельзя.

### 3.4. Совместимость входов

Все текущие вызовы `openChannel(id, { postId, commentId })` должны начать открывать страницу записи, без правок контракта вызывающих, кроме случая, если какой-то вызывающий рассчитывал на «раскрыть в ленте». Проверить и поправить при необходимости:

- `src/ui/screens/today.jsx`
- `src/ui/signals/notification-nav.js` (или фактический файл навигации уведомлений)
- любые другие `openChannel(..., { postId`

Поведение: пользователь из «Сегодня» / из уведомления попадает на страницу записи, комментарий подсвечен классом `.is-target-comment` (класс уже есть).

Если целевой пост старше загруженного окна ленты — на странице записи грузить **этот пост точечно** (см. §5.3), не раздувая ленту догоняющей пагинацией как сейчас.

## 4. UI ленты канала (режим без postId)

### 4.1. Шапка канала

Под `Screen` header, до вкладок, блок `.ch-head`:

```
[аватар 2.75rem .channel-avatar-thumb] [кикер · описание · мета] [чип «Правила»]
```

- Аватар: существующий `ChannelAvatarThumb` / те же классы `.channel-avatar-thumb`.
- Кикер: роль канала для человека («свой канал» / подписчик) + число читателей, **только если число уже откуда-то считается**. Если готового счётчика читателей в UI нет — не выдумывать запрос; показать роль и «обновлён …» из `updatedAt`. Не блокировать задачу на новый домен счётчика участников.
- Описание: существующий `.channel-description` (курсив, черта слева). Если описания нет — блок не рендерить.
- Правила: **не** `<details class="req">` на всю ширину. Кнопка-чип `.chip` «Правила». По клику — всплывающая панель `.rules-panel` (popover под чипом, `position: absolute`, ширина `min(26rem, 82vw)`, `surface-raised`, рамка, `--shadow`). Повторный клик / Escape / клик снаружи закрывает. Если `channelRow.rules` пусто — чипа нет.

### 4.2. Вкладки

Оставить `.tabs` / `.tab` как сейчас. Не растягивать подпись вкладки настроек в «Редактировать канал {длинное имя}». На вкладке настроек текст: `t("channel.tabs.settings")` («Настройки»). Имя канала уже в h1.

- не `width: 100%`;

По клику открывается `.composer-card` **над лентой**, `max-width: 44rem`. Не на всю ширину колонки. Внутри — существующий `PostEditor` + `AttachmentTray` + кнопки вложить / из хранилища / опубликовать / отмена. Логика `PostComposer` (лимиты 10000/20000, rate-limit `post`, collection при ≥2 вложениях без текста) **не менять**.

Класс `.channel-post-cta` либо переопределить так, чтобы он больше не растягивался, либо перестать использовать.

### 4.4. Элемент ленты (вместо полного `.rec` + комментарии)

Новый компактный вид. Допустимо:

- либо новый компонент `src/ui/components/feed-item.jsx`,
- либо режим `variant="feed"` у `PostCard`.

Предпочтительно **новый компонент** `feed-item.jsx`, чтобы не ломать карточку «Сегодня» (`today.jsx` использует `PostCard` / `.today-record`). **Журнал / Сегодня не перевёрстывать.** `.rec` в «Сегодня» оставить как есть.

Разметка элемента ленты (семантика обязательна):

```html
<article class="feed-item">
  <div>тип + время</div>
  <div>
    <h3 class="feed-title">заголовок или превью</h3>
    <p class="feed-excerpt">до 2 строк</p>
    чипы срока/тегов если есть
  </div>
  <div class="feed-aside">
    миниатюра 3.25rem если есть image/video
    💬 N
    сумма реакций
  </div>
</article>
```

Правила текста:

- `kind === "article"` и есть `title` — заголовок = `title`, excerpt = превью тела (`toPreviewText`, profile rich, разумный maxLength ~ 180).
- иначе заголовок = первая строка / усечённое превью, excerpt = продолжение или пусто.
- Задача (`kind === "task"`): в ленте чекбокс **не** ставить (переключение done — на странице записи / в меню, как сейчас на карточке). В ленте достаточно типа «Дело» + текста + due-chip.
- Клик по элементу (кроме интерактивных чипов, которых в ленте нет) → `openChannelPost(channelId, post.id)`.
- Элемент должен быть доступен с клавиатуры: `button.feed-item` на всю строку **или** `<article>` + `role="link"` + `tabIndex=0` + Enter. Предпочтительно одна `<button type="button" class="feed-item">`, чтобы не плодить вложенные кнопки.

Счётчик комментариев: как сейчас, `countCommentsByPost` на окно ленты, без загрузки дерева.

Реакции в ленте: только текстовая сумма существующих ненулевых эмодзи (`👍18 ❤️7`), без пикера и без кликабельных чипов (клик всё равно открывает запись).

Фон: **никакого** `background: var(--surface-raised)` и рамки на всю карточку. Разделитель — нижняя граница `--border`. Hover — лёгкий mix `surface-raised` в прозрачность.

Пагинация «Загрузить старше» остаётся над или под лентой, не внутри каждой записи. Пустая лента — существующий `t("channel.noPosts")`.

Не рендерит дерево комментариев.  
Не рендерит `CommentComposer`.

## 5. UI страницы записи (режим с postId)

### 5.1. Состав

Один столбец, `max-width: 46rem` у статьи (`.post-page`):

1. Мета: тип записи + дата/время (+ due-chip если есть).
2. Заголовок, если это статья / если есть `title`.
3. Вложения поста — **теми же компонентами, что пузырь чата** (§6).
4. Полный текст: существующий `MarkdownView profile="rich"`.
5. Теги / срок / owner-меню (архив, снять публикацию, удалить, сделать делом, срок) — перенести действия из текущего `PostCard` footer. Меню не обязано жить в ленте.
6. Ряд реакций поста (§8.4).
7. Секция комментариев.

Чекбокс дела на странице записи сохраняется (как в текущем `PostCard`).

### 5.2. Комментарии

Заголовок секции: `t("channel.commentsTitle")` + число (полное, как сейчас считает `countNodes` / `countCommentsByPost` для этого postId).

Сверху секции — `CommentComposer` (корневой, `parentId = postId`), если `canComment`. Иначе существующий read-only notice.

Дерево: `getCommentsTree` **только на этой странице**, один раз на пост (+ обновление после отправки / incoming `messagingActivity`).

Пагинация дерева в этой итерации: если комментариев ≤ 100 — рисовать целиком. Если больше — показать первые 50 корневых веток по `compareComments` (старые сначала, как `buildTree`) и кнопку «Ещё комментарии», догружающую следующие 50 корневых. Вложенные ответы загруженной корневой ветки показывать целиком (не резать середину треда). Этого достаточно, чтобы тысяча комментариев не монтировалась разом. Виртуальный список не обязателен.

### 5.3. Загрузка самого поста

Не полагаться на то, что пост уже есть в `posts` state окна ленты.

Добавить доменную функцию (имя фиксировано) в `src/domain/content/post.js`:

```js
export async function getPost(ownerPubkey, dbKey, postId)
```

Читает `db.table("posts").get([ownerPubkey, postId])`, `fromEncryptedRow`, возвращает пост или `null` (удалён / чужой / нет). Страница записи вызывает её. Если `null` — текст `t("channel.postUnavailable")` и кнопка назад к ленте.

Не тащить на страницу записи всю ленту канала.

### 5.4. Подсветка commentId

Как сейчас: `id="comment-${id}"`, класс `.is-target-comment`, `scrollIntoView({ block: "center" })` после появления узла в DOM. Если комментарий в ещё не раскрытой странице пагинации — догрузить страницы корня, пока узел не найдётся, либо загрузить дерево целиком если пагинация мешает найти цель уведомления (для deep-link цель важнее экономии). Deep-link побеждает пагинацию.

## 8. Реакции — домен + UI

Это новая функциональность. Делать полностью, не заглушкой в UI без записи в БД.

### 8.1. Протокол

Новый kind: **`30067`**.

Обоснование занятости (не занимать чужое):

| kind | уже занят |
|---|---|
| 30060 | метаданные канала |
| 30061 | пост |
| 30062 | комментарий |
| 30063 | сообщение чата канала |
| 30064 | бан |
| 30065 | visibility self-sync |
| 30066 | pinned |
| 30070 / 30074 | read-status чата / канала |

`30067` в коде сейчас не используется. Зафиксировать константу:

```js
export const CHANNEL_REACTION_KIND = 30067;
```

в `src/domain/content/reactions.js` (новый файл).

Тип события: parameterized-replaceable (диапазон 30000–39999).  
Автор события = реактор (`event.pubkey`).  
Один реактор + одна цель = одно событие, повторная публикация **заменяет** предыдущую (NIP-01 d-tag).

Теги:

```js
["d", `${channelId}:${targetType}:${targetId}`]
["h", channelTopic]
```

`targetType`: `"post"` | `"comment"`.  
`targetId`: id поста или комментария.

`content`: `encryptChannelContent(JSON.stringify(payload), channelKey, version)`.

Payload:

```ts
{
  targetType: "post" | "comment",
  targetId: string,
  postId: string,          // для comment = пост-владелец комментария; для post = targetId
  channelId: string,
  emoji: string | null     // null = снять реакцию (замена тем же d-tag)
}
```

`created_at` — обычный unix seconds.

Снятие: опубликовать тот же d-tag с `emoji: null`. Не вводить kind:5 для реакции в этой задаче.

### 8.2. Алфавит эмодзи (закрытый)

Ровно эти пять, в этом порядке, в пикере и в агрегации:

```js
export const CHANNEL_REACTION_SET = ["👍", "❤️", "😂", "🔥", "👀"];
```

Любой другой `emoji` на приёме → событие отбросить (`receiveReaction` возвращает `false`).  
`emoji: null` на приёме → валидное снятие.

Один реактор на одну цель держит **не больше одного** эмодзи. Смена 👍→❤️ = replace того же d-tag, не вторая строка.

### 8.3. Авторизация и приём

Файл: `src/domain/content/reactions.js`.

Публичные функции (имена фиксированы):

```js
export async function setReaction(ownerPubkey, ownerPrivKey, dbKey, channelId, targetType, targetId, postId, emoji, publish)
export async function receiveReaction(ownerPubkey, dbKey, event)
export async function listReactionsForPost(ownerPubkey, dbKey, postId)
export async function listReactionsForTargets(ownerPubkey, dbKey, targetIds)
export function aggregateReactions(rows, viewerPubkey)
```

`setReaction`:

1. Канал существует, ключ текущей версии доступен — иначе `DomainError` / `ChannelContentNotReadyError` по тем же правилам, что `addComment`.
2. `emoji` либо из `CHANNEL_REACTION_SET`, либо `null`.
3. UI-право: вызывающий и так не рисует пикер read-only; на приёме источник истины — allowlist.
4. Шифрует, подписывает, `publish`. Если relay не ок — `requirePublishOk` как в `comments.js` (скопировать локальный helper или вынести, не обязательно выносить).
5. Пишет/обновляет локальную строку Dexie.

`receiveReaction`:

1. Есть `h` и канал с этим `channelTopic` для `ownerPubkey`.
2. Расшифровка текущим (и при необходимости историческим — **как comments/posts уже умеют**; если comments расшифровывают только currentVersion, повторить ровно этот же уровень, не изобретать миграцию ключей).
3. Авторство реакции: `event.pubkey` должен иметь право COMMENT на канал **в том же смысле, что `receiveComment`** (владелец канала всегда можно; иначе `canAuthorComment` по закэшированному allowlist). Кто не может комментировать — не может реагировать. VIEW-only отбрасывается молча (`return false`).
4. Цель должна существовать локально: пост `posts` с этим id и тем же `channelId`, либо комментарий `comments` с этим id, `deleted !== true`. Если цели ещё нет (событие пришло раньше поста) — **допустимо сохранить реакцию всё равно** (иначе потеряем replaceable на relay), но `aggregate` по посту её не покажет, пока не появится цель. Проще и однозначнее для этой задачи: если цели нет — `return false` и не писать (реакция придёт replaceable повторно при ресинке / останется на relay; при открытии поста живой subscriber уже получит её из подписки). Выбрать **отбрасывать, если цели нет**, и покрыть тестом. Не строить очередь «отложенных» реакций.
5. LWW: если локальная строка на тот же `(ownerPubkey, channelId, targetType, targetId, reactorPubkey)` уже есть и входящий `event.created_at` меньше — не откатывать. При равенстве `created_at` тайбрейк по `event.id` как `isNewerVersion` в постах, если хелпер доступен; иначе «больший event.id побеждает». Не расходиться с принятым в `receivePost` приёмом, если он рядом легко переиспользуется.
6. `emoji: null` — удалить локальную строку или пометить `emoji: null` и исключать из агрегации. Предпочтительно хранить строку с `emoji: null` + `updatedAt`, чтобы LWW знал версию снятия.

 Dexie:

Новая версия схемы: `db.version(28)` в `src/core/store/database.js`.

```js
channelReactions: "[ownerPubkey+channelId+targetType+targetId+reactorPubkey], [ownerPubkey+postId], [ownerPubkey+targetId]"
```

Plaintext-поля в `table-fields.js`:

```js
export const CHANNEL_REACTIONS_PLAINTEXT_FIELDS = [
  "ownerPubkey", "channelId", "targetType", "targetId", "postId",
  "reactorPubkey", "emoji", "createdAt", "lastEventCreatedAt", "lastEventId"
];
```

`emoji` в plaintext допустим: закрытый набор из пяти, не секрет. Текст поста по-прежнему в blob постов.

`listReactionsForPost(ownerPubkey, dbKey, postId)` — все строки с этим `postId` у владельца БД, включая реакции на комментарии этого поста (нужно для страницы записи) **и** реакции на сам пост.

`listReactionsForTargets` — батч для ленты: только `targetType === "post"` и `targetId ∈ postIds` окна. Один scan/where, не N запросов.

`aggregateReactions(rows, viewerPubkey)` возвращает:

```js

  counts: { "👍": n, ... },   // только > 0
  mine: "👍" | null

```

Считать только `emoji` из алфавита, игнорировать `null`.
