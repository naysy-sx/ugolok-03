3. **Каждый новый текст — во все двенадцать словарей** `src/ui/i18n/locales/*.json`.

6. **Комментарии «этап N» сохраняй.** Это архитектурная летопись проекта. Если
   правка делает комментарий неверным — перепиши по существу, не удаляй.

## Этап 1. Признаки записи в модели

**Зачем.** Тип записи (заметка, дело, ссылка, статья) не хранится и не
выбирается пользователем — он выводится из того, какие признаки заполнены.
Для этого признаки нужно завести в модели поста.

**Что добавить в пост** (`domain/content/post.js:22-43`, литерал полей 26-37):

| Поле | Тип | Где хранится | Зачем |
|---|---|---|---|
| `dueAt` | `number\|null` (unix seconds) | **открыто** | срок |
| `done` | `boolean\|null` | **открыто** | отметка выполнения; `null` — признака нет вообще |
| `title` | `string\|null` | зашифровано | заголовок, отделённый от тела |
| `linkUrl` | `string\|null` | зашифровано | внешний адрес |

`done === null` и `done === false` — разные состояния: первое означает «это не
дело», второе — «дело, не сделано». Не сводить к булеву.

**Открыто** значит: добавить `dueAt` и `done` в `POSTS_PLAINTEXT_FIELDS`
(`core/store/table-fields.js:40`). Это нужно, чтобы по ним работал индекс.
Плата осознанная: тот, кто прочитает локальную базу, увидит наличие и дату
срока, но не текст.

**Что не менять:** `status` и `post-machine.js` — это состояние публикации
(черновик/опубликован/архив), к признакам записи отношения не имеет.

**Схема** (`core/store/database.js:100`, сейчас v6): подними версию, добавь
индекс `[ownerPubkey+dueAt]` в таблицу `posts`. Индекс по `done` не нужен —
записей со сроком мало, отфильтруешь в памяти.

**Сериализация.** Payload на реле сейчас `{ text, attachments, status }`
(`post.js:71-75` и повтор `post.js:229`) — добавь туда все четыре новых поля.
Приёмник `post.js:173-188` должен их читать и подставлять `null` для старых
событий без этих полей.

**Действия домена** (новые, в `post.js` или соседнем модуле):
`setPostDue(postId, dueAt)`, `clearPostDue(postId)`, `setPostDone(postId, done)`,
`makePostTask(postId)` (ставит `done = false`), `unmakePostTask(postId)`
(ставит `done = null`, срок не трогает).

**Инвариант, который нельзя нарушить:** смена типа ничего не удаляет. Снятие
отметки дела не стирает срок; снятие срока не стирает заголовок. Признаки
независимы, любое их сочетание законно — в том числе «ссылка со сроком».

**Готово, когда:** тесты домена покрывают все четыре действия и инвариант
«ничего не теряется»; `npm test` зелёный; интерфейс не изменился ни на пиксель.

## Этап 2. Вывод типа и карточка записи

**Зачем.** Показать признаки в ленте так, как в макете: слева колонка с
меткой типа и временем, справа тело, под телом — чипы признаков.

**Чистая функция вывода типа** — новый модуль `domain/content/record-kind.js`:

```
kindOf(post) -> "task" | "link" | "article" | "collection" | "note"
```

Порядок разбора жёсткий, первое совпадение выигрывает:

1. `done !== null` → `task`
2. `linkUrl` непустой → `link`
3. `title` непустой → `article`
4. текст пустой и вложений больше одного → `collection`
5. иначе → `note`

Порядок — соглашение, а не следствие модели. Зафиксируй его в `CONTRACTS.md`
и не меняй в разных местах интерфейса: одна запись обязана называться
одинаково везде.

**Карточка** (`ui/components/post-card.jsx`): перестроить по макету.

- Левая колонка (96 px): метка типа заглавными, ниже время.
- `task` — чекбокс перед текстом, зачёркивание при `done === true`.
- `link` — карточка ссылки под текстом.
- `article` — заголовок над текстом.
- Чипы под телом: срок (`до 3 сентября`), просрочка (`просрочено на 2 дня`,
  цветом `--bad`), теги.

**Правило единственного вложения** (идея пользователя):

- ровно одно вложение типа `image` или `video` **и** длина текста ≥ 280 символов
  → миниатюра уходит в левую колонку под время, тело остаётся текстовым;
- одно вложение типа `audio` → **всегда** компактная строка в теле,
  независимо от длины текста; в левую колонку звук не выносится никогда;
- во всех остальных случаях — как сейчас, через `AttachmentView`.

Порог 280 вынеси именованной константой. Раскладка вычисляется из текста
записи, который после публикации не меняется, — перескакивать она не должна.

**Действия записи** — в существующее меню `ActionsMenu`
(`post-card.jsx:62-70`) добавить «Поставить срок», «Сделать делом» и обратные
им. Срок задаётся только у существующей записи, в форме создания поля срока
нет: в момент написания срок обычно ещё не известен.

**Готово, когда:** есть тесты на `kindOf` (все пять исходов плюс приоритет);
карточка визуально совпадает с макетом; аудио никогда не оказывается в левой
колонке.

## Этап 4. «Сегодня»

**Зачем.** Мягкий вход органайзера: отдельного раздела нет, есть кнопка в
шапке экрана и экран списка.

**Выборка** — новая функция в `domain/content/post.js` или соседнем модуле:
`listDueRecords(ownerPubkey, dbKey, { until })` — по индексу
`[ownerPubkey+dueAt]` из этапа 1, без полного перебора. Возвращает записи с
непустым `dueAt` и `done !== true`, отсортированные по сроку.

**Правило появления:** пока ни у одной записи не было срока, кнопки нет

исчезает, даже когда дел ноль. Флаг «срок хоть раз ставили» храни в
настройках; мигающий туда-сюда элемент хуже лишней кнопки.

**Экран** «Сегодня»: группы «просрочено», «сегодня», «дальше», внутри —
те же карточки, что в ленте. Клик по записи ведёт в её канал, к самой записи.

**Готово, когда:** в чистой учётной записи кнопки нет; после первого срока она
появляется и считает верно; выборка не читает таблицу целиком.

## Чего не делать во всём редизайне

- Не строить производный индекс медиа по всем лентам. Решение принято: срезы
  только по текущему месту.
- Не объединять личный чат и чат канала в общий компонент. Отчёт B1/B3:
  разные kind'ы, разное шифрование, разный набор возможностей — общим у них
  может быть только показ сообщения (этап 11, п. 1).
- Не добавлять выбор типа записи в форму создания. Тип выводится, а не
  задаётся.
- Не заводить настройку «показывать верхнюю полосу / не показывать». Раскладка
  выбрана одна.
