# Приложение к REDESIGN-SPEC: правила вёрстки

Прикладывается к каждому этапу, где меняется разметка или стили.

---

## 1. Разделение труда

Разметку и стили пишет владелец проекта. Задача исполнителя — **подключить
готовую разметку к данным**: подставить значения, обработчики, условный рендер,
переводы.

Разрешено:
- заменять текст-заглушку на `t("…")`;
- заменять статические значения на данные из сигналов и состояния;
- добавлять `onClick`, `onInput`, `disabled`, `aria-*`;
- оборачивать блоки в `{condition && …}` и `.map(…)`.

Запрещено без отдельного разрешения:
- добавлять, удалять и переименовывать классы;
- менять вложенность элементов;
- добавлять правила в CSS-файлы;
- писать инлайновые стили, кроме передачи переменных слоя композиции
  (`style={{ "--gap": "var(--space-s)" }}` — можно; `style={{ width: "320px" }}` — нельзя).

Если разметки под задачу нет — **остановись и спроси**, не сочиняй свою.

---

## 2. Жёсткие запреты в CSS и разметке

Проверяются поиском по разнице кода, нарушение — возврат этапа:

| Нельзя | Почему |
|---|---|
| `width` / `height` в пикселях у блоков | ломает узкие экраны; размер задаёт содержимое и слой композиции |
| `100vw` | не учитывает полосу прокрутки, даёт горизонтальный сдвиг |
| `position: absolute` для раскладки | для наложения есть `.layer` (REGLAMENT.md §3 п.3) |
| `!important` | признак того, что правило добавлено вслепую |
| новые `@media` | точки перелома уже заданы: `47.99em` / `48em` |
| `overflow: hidden` как средство от переполнения | прячет симптом, оставляет причину |
| фиксированный `font-size` в px | шкала задана `--step-*` |

Исключение возможно для каждого пункта, но только с разрешения владельца и
с комментарием в коде, объясняющим, почему обычный приём не подошёл.

---

## 3. Узкий экран — первым

Сначала раскладка для 360 px, потом расширение через `@media (min-width: 48em)`.
Обратный порядок («сделаю на широком, потом добавлю адаптив») запрещён: он
даёт заплатки поверх готовой раскладки вместо раскладки, которая работает.

---

## 4. Что должно происходить на каждой ширине

Проверяется вручную и скриптом (раздел 5). Ширины: **320, 360, 390, 768,
1024, 1440**.

Для каждого экрана на каждой ширине:

1. Горизонтальной прокрутки нет.
2. Ни один элемент не выходит за границы окна.
3. Текст не обрезан и не наезжает сам на себя.
4. Все кнопки нажимаемы: сторона не меньше 44 px на ширинах до 768.
5. Ничего не перекрывает содержимое: подложка панели, всплывающие меню и
   медиа-просмотрщик закрываются и не оставляют перехвата нажатий.

Дополнительно, по нашей раскладке:

- **до 48em:** боковая панель скрыта и выезжает по бургеру; подложка
  закрывается нажатием и клавишей Esc; ряд срезов в шапке экрана
  прокручивается вбок или сворачивается в одну кнопку — но не переносится в
  три строки; из трёх кнопок в шапке («Сегодня», «Что произошло», «＋ Запись»)
  видимой остаётся только «＋ Запись», остальные уезжают в панель.
- **от 48em:** панель на месте, ширина `15rem`, бургер скрыт.

## 5. Автоматическая проверка

Добавить в `scripts/` и в `package.json` командой `check:layout`. Этап не
считается сданным, пока проверка красная.

Что делает: поднимает сборку, открывает каждый экран на каждой ширине,
проверяет отсутствие переполнения и складывает снимки в `artifacts/layout/`.

```js
// scripts/check-layout.mjs
import { chromium } from "playwright";

const WIDTHS = [320, 360, 390, 768, 1024, 1440];
const SCREENS = ["journal", "people", "channels", "channel", "chat", "storage", "today"];
const BASE = process.env.BASE_URL ?? "http://localhost:4173";

const browser = await chromium.launch();
let failed = 0;

for (const screen of SCREENS) {
  for (const width of WIDTHS) {
    const page = await browser.newPage({ viewport: { width, height: 800 } });
    await page.goto(`${BASE}/?screen=${screen}`, { waitUntil: "networkidle" });

    // 1. горизонтальной прокрутки нет
    const overflow = await page.evaluate(() =>
      document.documentElement.scrollWidth - document.documentElement.clientWidth);

    // 2. ни один элемент не вылезает за окно
    const wide = await page.evaluate(() => {
      const limit = document.documentElement.clientWidth + 1;
      return [...document.querySelectorAll("body *")]
        .filter((el) => el.getBoundingClientRect().right > limit)
        .slice(0, 5)
        .map((el) => el.tagName.toLowerCase() + "." + (el.className || "").toString().split(" ")[0]);
    });

    if (overflow > 0 || wide.length > 0) {
      failed++;
      console.error(`✗ ${screen} @ ${width}: перелив ${overflow}px, виновники: ${wide.join(", ") || "—"}`);
    }

    await page.screenshot({ path: `artifacts/layout/${screen}-${width}.png`, fullPage: true });
    await page.close();
  }
}

await browser.close();
process.exit(failed > 0 ? 1 : 0);
```

Проверка намеренно грубая: она ловит переполнение, а не красоту. Красоту
смотрит владелец по снимкам из `artifacts/layout/`.

---

## 6. Что приложить к отчёту по этапу

1. Вывод `npm run check:layout` целиком.
2. Снимки для затронутых экранов на 360 и 1280.
3. Список добавленных правил CSS — если он не пуст, объяснение по каждому.

---

## 7. Формулировка, которой быть не должно

В задании исполнителю не должно встречаться слов «сделай адаптивно»,
«позаботься о мобильных», «чтобы хорошо смотрелось». Это не критерии: их
нельзя проверить, и любой результат им формально соответствует. Вместо них —
раздел 4 и проверка из раздела 5.
