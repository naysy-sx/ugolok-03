## Этап 4 — валидатор событий + CRDT-примитивы

### `src/domain/events/validators.js` — `validateEventId`

Триаж (п.13a): **рутинная (а)** — применение готовой библиотеки.
`nostr-tools/pure` уже экспортирует `getEventHash(event)` — эталонная
реализация NIP-01 canonical serialization (`JSON.stringify([0, pubkey,
created_at, kind, tags, content])`) + SHA-256
(`node_modules/nostr-tools/lib/esm/pure.js`, проверено чтением
исходника, не документации). Переизобретать сериализацию вручную —
запрещено (риск тонкого расхождения с relay/другими клиентами; это
ровно тот сорт ошибки, которую рутинная обёртка над проверенной
библиотекой исключает). Design-записка не нужна, сразу к контракту/тестам.

### `src/core/sync/g-set.js` — CRDT G-Set (`mergeEvent`)

Триаж: **алгоритмическая (б)** — CRDT, явный триггер правила 13a.

**Формализация.** Пусть `S ⊆ EventId` — множество `id` уже сохранённых
журнальных событий (kind 1059, kind 5 — см. TECH.md §5.х), физически
это столбец `id` таблицы `events` (этап 3, `hasEvent`/`appendEvent`).
Абстрактная операция G-Set: `add(S, e) = S ∪ {e}` — объединение
коммутативно, ассоциативно, идемпотентно (стандартное свойство `∪`).
Наша `mergeEvent` — не чистая функция над `S`, а операция с side
effect (запись в Dexie); поэтому инвариант, который обязан
сохраниться при переходе от абстракции к side-effect-реализации:

- **Инвариант G1 (идемпотентность эффекта).** `mergeEvent(e)` дважды
  подряд с одним и тем же `e` → в таблице `events` ровно ОДНА строка
  с этим `id` (не полагаемся на то, что `id` — unique-индекс Dexie,
  проверяем явно через `hasEvent` до `appendEvent`).
- **Инвариант G2 (независимость от порядка/повторов).** Для любой
  последовательности вызовов `mergeEvent` (в любом порядке, с любыми
  повторами) над конечным набором событий `{e1..en}` (различные `id`),
  итоговое множество `id`, присутствующих в `events` после того как
  вызовы завершились — равно `{e1..en}.map(e => e.id)` как МНОЖЕСТВО
  (без дублей), независимо от порядка и количества повторов вызовов.

Структура данных: не вводится — операция уже O(1) через индекс `id`
из этапа 3, доп. структуры не нужны.

**Псевдокод ядра** (единственная часть с нетривиальным инвариантом —
порядок проверки-затем-вставки, не сам вызов):

```
async function mergeEvent(event):
  if await hasEvent(event.id):
    return { added: false }
  await appendEvent(event)
  return { added: true }
```

Обвязку (импорт из `../store/event-log.js`, форму объекта) пишет
воркер по контракту в CONTRACTS.md — здесь важен только порядок
check-then-act и его смысл.

**Материализация:**
- G1 → юнит-тест "двойной merge одного и того же события — одна строка"
- G2 → property-based тест: случайная перестановка + случайные
  повторы входной последовательности из N синтетических событий →
  финальный набор `id` в `events` равен `Set(ids)` независимо от
  порядка/повторов.

### `src/core/sync/lww.js` — CRDT LWW-Register (`lwwWinner`, `pickLatest`)

Триаж: **алгоритмическая (б)** — CRDT, явный триггер правила 13a.

**Формализация.** События `a, b`, конкурирующие за один "слот"
state-snapshot (`pubkey`+`kind`+`d-tag`, этап 20+), сравниваются
отношением тотального порядка `≺`:

```
a ≺ b  ⟺  a.created_at < b.created_at
        ∨ (a.created_at = b.created_at ∧ a.id < b.id)
```

`id` сравнивается как строка (лексикографически), `created_at` —
как число. Порядок тотален и антисимметричен: событий с одинаковыми
`(created_at, id)` быть не может, т.к. `id` — криптографический хеш
(коллизия исключена практически). Источник правила — TECH.md §4.4/4.6
и AC-18: "тайбрейкер LWW при равном `created_at` — лексикографический
`eventId`", "побеждает большее `id`".

`lwwWinner(a, b) = max(a, b)` по `≺`.

**Инварианты** (обязаны выполняться для `max` над тотальным порядком —
иначе состояние двух устройств одного пользователя не сойдётся, см.
TECH.md §4.6 "Следствие"):
- **L1 (идемпотентность):** `lwwWinner(a, a) = a`.
- **L2 (коммутативность):** `lwwWinner(a, b) = lwwWinner(b, a)`.
- **L3 (ассоциативность):** `lwwWinner(lwwWinner(a,b), c) = lwwWinner(a, lwwWinner(b,c))`.
- **L4 (явное требование TECH.md §17.5 / AC-18):** при равных
  `created_at` побеждает больший `id` (строковое сравнение).

Структура данных: не нужна (чистая функция сравнения, O(1)).
`pickLatest(events)` — свёртка непустого массива через `lwwWinner`
(`Array.prototype.reduce` без начального значения — на пустом массиве
бросает `TypeError` штатным поведением `reduce`, отдельно не
обрабатываем: вызов с пустым массивом — ошибка вызывающего кода, не
достижимый в реальном пайплайне сценарий). Это обвязка без
дополнительного нетривиального инварианта — пишет воркер.

**Псевдокод ядра:**

```
function lwwWinner(a, b):
  if a.created_at !== b.created_at:
    return a.created_at > b.created_at ? a : b
  return a.id > b.id ? a : b   // строковое сравнение
```

**Материализация:**
- L4 → обязательный юнит-тест из TECH.md §17.5/AC-18 (равные
  `created_at` → больше `id` побеждает)
- L1–L3 → property-based тест (идемпотентность/коммутативность/
  ассоциативность на случайных наборах синтетических событий)

## Этап 13 — MLS-спайк

Триаж (п.13a): **алгоритмическая** — из явных триггеров правила:
пространство состояний (эпохи/участники группы MLS) с неочевидными
переходами, плюс единственное место в TECH.md (§13.1.1), где заранее
назван архитектурный запасной путь на случай провала. Криптографическая
часть (выбор ciphersuite/примитивов) — по исключению из п.13b решается
здесь же, напрямую, не выносится пользователю.

### Что делает этот этап, а что — нет

TECH.md формулирует MLS-INTEGRATION-SPIKE широко (5 пунктов, §13.1).
В разбивке PLAN.md этот этап — фундамент протокольного уровня,
транспортно-независимый (как `sign.js`/`nip44.js`/`nip59.js` в этапе 9):
сессия MLS, кодирование сообщений, деривация ключей для двойного
шифрования. Не входит и осознанно отложено:
- фактическая обвязка Dexie-таблиц под персист состояния групп —
  этап 14 (там же генерик `encrypted-table`, туда и MLS-состояние);
- публикация/подписка событий kind 443/444/445 через relay —
  требует транспорта (этапы 16–18), ещё не построен;
- интеграция в `chat.js` (send/receive, commit/proposal в реальном
  сценарии переписки) — этап 24.

Этот этап поставляет **проверяемый в изоляции** (`node --test`, без
DOM/сети) модуль `mls-session.js`, который: (1) корректно использует
`ts-mls`, (2) инкапсулирует опасное управление ресурсами (обнуление
одноразовых ключей) так, чтобы вызывающий код физически не мог его
забыть, и (3) даёт кодеки для kind 443/444/445 по NIP-EE.

### Эмпирическая проверка вместо веры в документ

TECH.md заявляет «785/785 официальных тест-векторов IETF MLS» для
`ts-mls`. Не принято на веру — воспроизведено лично:

```
git clone https://github.com/LukaJCB/ts-mls.git
git checkout v2.0.0-rc.14   # тег точно совпадает с "ts-mls": "2.0.0-rc.14" в package.json проекта
pnpm install --frozen-lockfile
npx vitest run test/test-vectors
  → Test Files  14 passed (14)
  → Tests       785 passed (785)
npx vitest run   # полный набор (юнит + векторы)
  → Test Files 123 passed (123)
  → Tests      2052 passed (2052)
```

Прогнано в Node v24.12.0 (реальный рантайм тестов проекта, не
абстрактная среда авторов библиотеки) 18 июля 2026. Число, версия
тега и результат совпадают с TECH.md §13.1 дословно — R6-8 подтверждён
независимо, не переписан со слов документа.

**Важная находка про AC-MLS-VEC.** `package.json` библиотеки объявляет
строгий `"exports"` (только `.` → `dist/src/index.js`); тестовые файлы
`test/test-vectors/*.test.ts` импортируют внутренние модули исходников
(`../../src/crypto/ciphersuite.js`, `../../src/treemath.js` и т.д.),
которых нет в опубликованном npm-пакете и которые Node физически не
даст импортировать в обход `exports`-карты даже при наличии файлов на
диске. **Вывод:** 785-векторный набор нельзя встроить в `npm test`
этого проекта как автоматический regression-гейт — у проекта и так
нет CI (только ручной `npm test`/`npm run build` по конвенции этапов),
а векторный набор требует полного дерева исходников библиотеки со
всеми dev-зависимостями (vitest, playwright, ~500 пакетов). Тянуть это
в зависимости проекта ради одной проверки противоречит бюджетной
дисциплине CLAUDE.md. **Практическое решение:** AC-MLS-VEC закрывается
как **ручная, но воспроизводимая процедура** (команды выше) — выполняется
сейчас (гейт этого этапа) и обязательна перед ЛЮБЫМ апгрейдом версии
`ts-mls` (см. TECH.md §19, таблица сопровождения) — команды фиксируются
здесь и в `docs/`, а не только в истории чата. Отдельно, для
повседневного `npm test`, добавляется собственный лёгкий smoke-тест
(ниже) по прецеденту §16.1–16.4 — он не заменяет 785 векторов, а ловит
более грубую поломку (сломанная установка/несовместимый апгрейд) на
каждом прогоне, без внешних зависимостей.

### Решение: ciphersuite

`MLS_128_DHKEMX25519_AES128GCM_SHA256_Ed25519` (ID `0x0001`). Основания:
(1) единственная строка в таблице `ts-mls` README без ДОПОЛНИТЕЛЬНЫХ
npm-зависимостей — при и так плотном бюджете (см. PLAN.md, `ts-mls`
уже стоит 65 КБ) не добавлять веса ради экзотики; (2) базовый,
наиболее аудированный/используемый набор в экосистеме MLS-реализаций,
не post-quantum и не редкая кривая — «не изобретай», выбор скучного
проверенного примитива; (3) постквантовые наборы (`ML-KEM`, `X-Wing`)
осознанно не выбраны — модель угроз TECH.md §1.6 не называет
quantum-adversary в числе T1–T5, вводить их сейчас — необоснованное
усложнение и лишний вес; путь апгрейда остаётся открытым (`ts-mls`
поддерживает переключение ciphersuite per-group), не тупик.

### Решение: credential и identity-биннинг (NIP-EE)

Проверено по первоисточнику (github.com/nostr-protocol/nips/blob/master/EE.md,
не угадано): `BasicCredential`, `identity` = байты **hex-строки**
64 символа (UTF-8 `TextEncoder().encode(hexPubkey)`), НЕ сырые 32
байта — так же, как это делает референсный пример `ts-mls` (`identity:
new TextEncoder().encode("alice")`). Подписывающий ключ MLS-члена
**обязан отличаться** от identity-ключа Nostr (secp256k1/schnorr,
NIP-06) — сам протокол MLS (RFC 9420) не поддерживает secp256k1/schnorr
среди подписных схем ciphersuite (только Ed25519/P256/Ed448/P521/P384/
ML-DSA, см. таблицу README). Это не наше архитектурное решение, а
математическое ограничение набора шифров — Nostr-идентичность и
MLS-leaf-идентичность физически разные ключевые пары, связанные только
полем `credential.identity`. `generateKeyPackage()` генерирует
Ed25519-пару сама (`ts-mls`, ciphersuite `impl`) — отдельная
деривация с нуля не нужна, только персист `privatePackage` (этап 14).
Проверено вживую (см. smoke-скрипт ниже): `credential.identity`
корректно совпадает с исходным hex pubkey после кодирования/декодирования
через `mlsMessageEncoder`/`Decoder`.

### Пробел в TECH.md, закрытый по первоисточнику (не угадано)

TECH.md §4.9/§13.1 упоминает только kind 445. Реальный NIP-EE
(нащёл через WebSearch/WebFetch, github.com/nostr-protocol/nips/blob/master/EE.md)

| 444 | Welcome (приглашение в группу) | БЕЗ подписи, gift-wrap NIP-59 | свободен |

### Двойное шифрование kind 445 (NIP-44 поверх MLS)

Проверено по спецификации и вживую (smoke-скрипт): `content` события
kind 445 = `NIP-44.encrypt(serialize(MLSMessage), senderKey, receiverKey)`,
где `senderKey` = сырые 32 байта `exporter_secret` эпохи (трактуются
как secp256k1 privkey), `receiverKey` = `getPublicKey(senderKey)` —
то есть шифрование «самому себе» через уже существующий `nip44.js`
(этап 9) и `getPublicKey` из `keys.js` (этап 7). `exporter_secret`
достаётся ТОЛЬКО через публично экспортированную `mlsExporter(exporterSecret,
label, context, length, cs)` (`ts-mls`, реализует `MLS-Exporter` из
RFC 9420 §8.5 — проверено чтением `dist/src/keySchedule.js`, не
предположено), label = `"nostr"` (NIP-EE), `context` = пустой массив,
`length` = 32. Ключевой архитектурный плюс: НЕ нужна отдельная
реализация NIP-44-конверсации для MLS — переиспользуются модули этапа 9
как есть, только источник ключа другой.

### Инварианты `mls-session.js` (формализация ДО кода)

**SM-1 (обязательное обнуление одноразовых ключей).** Каждый вызов
`ts-mls`, возвращающий поле `consumed: Uint8Array[]`
(`createCommit`/`createApplicationMessage`/`processMessage`), обязан
пройти обнуление (`zeroOutUint8Array`) КАЖДОГO элемента — это и есть
«остаточная ось 1» TECH.md §4.9 (корректность удаления ключей, от
которой прямо зависит forward secrecy; официальные векторы протокол
проверяют, но НЕ проверяют, что клиент реально стирает память).
Инвариант нарушается, если обнуление стоит ПОСЛЕ шага, который может
бросить исключение (энкодинг, запись в БД) — тогда при ошибке ключ
остаётся в памяти неопределённо долго. Решение: `mls-session.js`
не отдаёт `consumed` вызывающему коду вообще — обнуление происходит
ВНУТРИ обёртки, в `finally`, до return. Так инвариант держится
конструкцией модуля, а не дисциплиной каждого будущего вызывающего
(этап 24 и далее) — ошибка одного `chat.js`-вызова не может его
нарушить.

**SM-2 (persist-before-ack).** Новое состояние группы (`newState` из
`createCommit`/`createApplicationMessage`/`processMessage`) обязано
быть сериализовано и **durable-персистировано** (encrypted-table,
этап 14) ДО того, как соответствующее Nostr-событие считается
отправленным/обработанным. Обоснование: MLS не имеет
общего механизма ресинхронизации состояния, кроме external join или
remove+re-add участника — крах между продвижением состояния в памяти
и его записью на диск необратимо рассинхронизирует эту сторону с
реальным протокольным состоянием (она либо повторно обработает уже
применённое сообщение, либо потеряет отправленное). Тестируется через
инъекцию сбоя между шагами (аналог адверсарного захода этапа 3 на
`event-log`, где падение до `hasEvent`-проверки уже один раз находило
реальный баг).

**SM-3 (owner + device-members, модель по требованию TECH.md §4.9).**
Единица членства в MLS-группе — **устройство**, не пользователь:
`deviceId` (локально сгенерированный стабильный идентификатор
установки, НЕ Nostr pubkey) отдельно от `credential.identity`
(Nostr pubkey, для отображения «чьё это устройство»). Одна Nostr-
идентичность = произвольное число независимых MLS-leaf-участников
(по одному на устройство). Удаление устройства = MLS Remove-proposal
против конкретного leaf, не затрагивает других устройств того же
pubkey. Эта модель фиксируется здесь; UX последствий (NF-15) касается
этапа 22+ (список контактов/устройств), не в скоупе кода этого этапа.

### Персист — форма решена, проводка отложена (этап 14)

Концептуально: таблица `mlsGroups` — по одной строке на группу,
ключ `groupId` (наш `nostr_group_id`, 32 байта), значение — сериализованное
через `clientStateEncoder`/`clientStateDecoder` (`ts-mls`, публичный
экспорт) состояние + `ownDeviceId`. Шифруется `dbKey` тем же
`encrypted-table`, что и остальные materialized views (§5.13 TECH.md,
уже установленный паттерн) — MLS-состояние не более и не менее
чувствительно, чем `messages`/`permissions`. Точная Dexie-схема —

### Находка: `ts-mls` не даёт "настоящей" `authService` из коробки

Единственный публичный экспорт интерфейса аутентификации —
`unsafeTestingAuthenticationService` (`dist/src/authenticationService.js`,
прочитано в исходнике): `validateCredential` **всегда возвращает
`true`**, без единой проверки — сам `ts-mls` честно называет её
"unsafeTesting", не для продакшена. Интерфейс:
`{ validateCredential(credential, signaturePublicKey): Promise<boolean> }`.

**Разбор по существу, не формальная замена заглушки на заглушку.**
Настоящая проверка «это действительно Nostr-pubkey X ручается за этот
MLS-подписной ключ» физически не может быть завершена ВНУТРИ
`ts-mls` — у `validateCredential` на входе только `credential`
(содержит заявленный `identity`) и `signaturePublicKey` (Ed25519), но
НЕТ доступа к внешнему Nostr-событию (kind 443), которое единственно
доказывает контроль над `identity` (обычная Nostr-подпись
`event.sig`/`event.pubkey`, уже умеем проверять — `verify()` из
`sign.js`, этап 9). Значит настоящая проверка биннинга — это
**граница вызывающего кода** (этап 24, `chat.js`/event handlers), а
не забота `mls-session.js`: любые байты KeyPackage/Welcome/Commit,
переданные в этот модуль, ОБЯЗАНЫ на момент вызова уже происходить из
Nostr-события, чья подпись проверена, и `event.pubkey` уже сверен с
`credential.identity` ДО вызова. Тот же паттерн границы, что у
`mnemonicToPrivateKey` (этап 7): функция не валидирует вход, вызывающий
код обязан был проверить раньше — задокументировано явно, не
подразумевается.

**Что модуль делает сам (минимум, который реально доступен на этом
уровне):** собственный `authService` вместо "unsafeTesting" —
структурная проверка `credential.credentialType === defaultCredentialTypes.basic`
и `credential.identity` — ровно 64 hex-символа. Это не заменяет
внешнюю проверку подписи (не может, см. выше), но ловит явно
испорченные/не-NIP-EE credential на уровне самого MLS-протокола, а не
молча пропускает всё подряд как исходная "unsafe" заглушка. Названо
`nostrCredentialAuthService` в коде — не "unsafe", чтобы не создавать
ложного ощущения тестового кода в production-пути.

## Этап 14 — шифрование БД + конечные автоматы

### `src/core/fsm/machine.js`

Триаж (п.13a): формально — дискретная математика (детерминированный
конечный автомат), но конкретная реализация — рутинная (табличный
lookup), кроме одной содержательной тонкости ниже. Полная запись не
нужна, но структура фиксируется явно — по прямой просьбе
(конечные автоматы — широкая область, формализовать, не хендвейвить).

**Формализация.** Автомат — пара `(δ, q)`, где `q ∈ Q` (states) —
текущее состояние, `δ: Q × Σ ⇀ Q` (частичная функция) — таблица
переходов, `Σ` (events) — конечный алфавит событий. Частичность —
не деталь реализации, а часть контракта: `δ(q, e)` НЕ определено для
большинства пар `(q, e)` (в 4 автоматах TECH.md §9 плотность заполнения
таблицы — единицы переходов из десятков возможных пар), и это
намеренно — недопустимый переход обязан быть отклонён (`throw`), а не
проигнорирован (silent no-op) или принят как identity-переход. Это
единственное, что отличает автомат от произвольного роутера/switch:
**закрытость относительно алфавита событий не гарантирована, отказ —
часть спецификации, не баг**.

**Инвариант F1 (детерминизм).** Для фиксированной пары `(q, e)` — не
более одного `q' = δ(q, e)`. Гарантируется структурой самой таблицы
(обычный JS-объект: ключ → одно значение), не требует отдельной
проверки в рантайме — это свойство ФОРМЫ данных, не поведения функции.

**Инвариант F2 (partial function → reject, не no-op).** `δ(q,e)`
не определено → функция ОБЯЗАНА бросить, не возвращать `q`
(оставить как есть) и не возвращать `undefined` молча — TECH.md
прямо формулирует "недопустимый переход бросает" для каждого из 4
автоматов §9. Это главный тестируемый инвариант: для каждого
конкретного автомата (этапы 16/24/28/31) тест обязан покрыть НЕ только
happy path, но и хотя бы по одному недопустимому `(q,e)` на каждое
состояние — уже зафиксировано в PLAN.md ("Уроки").

**Инвариант F3 (чистота, марковское свойство).** `δ(q, e)` зависит
ТОЛЬКО от текущих `q` и `e` — не от истории переходов, не от времени,
не мутирует саму таблицу `transitions`. Это то, что делает 4 будущих
конкретных автомата (message/post/relay/transfer) безопасно
параллельными: множество одновременных чатов/постов/загрузок читают
ОДНУУ И ТУ ЖЕ таблицу переходов без гонки, потому что вызов не имеет
побочных эффектов на саму таблицу — состояние живёт СНАРУЖИ (поле
записи в Dexie), не внутри модуля.

**Инвариант F4 (wildcard-состояние, реальная необходимость, не
гипотетическая).** Автомат соединения relay (TECH.md §9.3) содержит
переходы вида `* + CLOSE → disconnected` и `* + ERROR → disconnected`
— то есть `δ` определена не по паре конкретных `(q,e)`, а по правилу
"для ЛЮБОГО `q`, событие `CLOSE` ведёт в `disconnected`". Без
поддержки этого в дженерик-движке SEЙЧАС, этап 16 пришлось бы либо
руками разворачивать wildcard в explicit-таблицу на все 5 состояний
(дублирование, источник рассинхронизации при добавлении состояния),
либо возвращаться и менять уже принятый контракт этого этапа —
дешевле заложить сразу. Семантика: конкретное состояние ИМЕЕТ
ПРИОРИТЕТ над `"*"` для той же пары событие-в-любом-состоянии (если
для `q` явно задан отдельный переход по `e` — он побеждает; `"*"` —
только фоллбэк). Проверено, что остальные 3 автомата (message/post/
transfer, TECH.md §9.1/9.2/9.4) не используют wildcard — F4 не портит
их семантику (для них `"*"` в таблице просто отсутствует, фоллбэк
никогда не сработает).

**Псевдокод ядра:**

```
function transition(transitions, state, event):
  next = transitions[state]?.[event] ?? transitions["*"]?.[event]
  if next is undefined:
    throw Error(`недопустимый переход "${event}" из состояния "${state}"`)
  return next
```

Обвязку (сохранение состояния в Dexie-запись, вызов `transition` из
доменных функций типа `sendMessage`) пишут соответствующие будущие
этапы (16/24/28/31) — здесь только двигатель.

### `src/core/crypto/db-crypto.js`

Триаж (п.13b): криптография — примитив уже зафиксирован TECH.md §13.4
(`ChaCha20-Poly1305` на `dbKey`, тот же `dbKey`, что выведен в этапе 8
`derivation.js`). Design-записка по примитиву не нужна — но контракт
формата данных фиксируется здесь, т.к. от него зависит `encrypted-table.js`.

Формат зеркалит уже принятое решение этапа 10 (`file-crypto.js`):
случайный nonce на каждое шифрование (не detached-хранение — нельзя
переиспользовать nonce с одним и тем же `dbKey` без разрушения
семантики AEAD), результат — `{nonce, ciphertext}` (не единый блоб —
здесь, в отличие от файлов, оба поля хранятся в Dexie раздельными
полями объекта, а не сериализуются в один бинарник — Dexie нативно
хранит `Uint8Array` полями структурного клона, конкатенация не даёт
выгоды, только читаемость хуже).

**Контракт сериализации (решение Claude, не в TECH.md явно):**
`encryptRow`/`decryptRow` работают ТОЛЬКО с JSON-сериализуемыми
значениями (`JSON.stringify` → UTF-8 → шифр). Сырые `Uint8Array`
внутри значения (например, сериализованное состояние MLS-группы из
этапа 13, `serializeState()`) ДОЛЖНЫ быть base64-обёрнуты вызывающим
кодом ДО передачи в `encryptRow` — тот же паттерн границы, что уже
установлен в этапе 13 для NIP-44 (переиспользуется, не изобретается
заново). `db-crypto.js` не пытается быть универсальным сериализатором
произвольных JS-типов (Map/Set/TypedArray) — это осознанное сужение
контракта, не пробел.

### `src/core/store/encrypted-table.js`

Триаж: рутина (склейка Dexie + `db-crypto.js`), но с одним
содержательным инвариантом безопасности — формализован явно, т.к. его
нарушение — это утечка plaintext, не абстрактный баг.

**Инвариант E1 (allowlist, не blocklist — default-deny).** Обёртка
принимает ЯВНЫЙ список полей, которые остаются plaintext (обязаны
совпадать с полями, реально участвующими в Dexie-индексе таблицы —
только по ним возможен `.where()`), и шифрует ВСЁ ОСТАЛЬНОЕ. Поле,
которое разработчик забыл явно объявить plaintext (например, при
добавлении нового поля к таблице в будущем этапе), автоматически
уходит в зашифрованный блок — это и есть "безопасно по умолчанию".
Обратный порядок (blocklist "что шифровать") был бы safety-антипаттерном:
забытое поле по умолчанию утекало бы в plaintext, и ошибка обнаружилась
бы только аудитом/инцидентом, а не структурой кода.

**Инвариант E2 (прозрачность/round-trip).** Для любой записи `r`,
`get(put(r).key) deepEqual r` — обёртка не меняет форму данных с
точки зрения вызывающего кода, только физическое хранение. Соответствует
формулировке TECH.md §13.4 ("прозрачная обёртка").

**Инвариант E3 (AC-16, проверяется адверсарно, не только юнит-тестом).**
Сырой дамп таблицы Dexie В ОБХОД обёртки (`db.table(name).toArray()`
напрямую) — зашифрованные поля видны ТОЛЬКО как `{nonce, ciphertext}`
байты, из которых не восстановить исходный plaintext без `dbKey`
(структурная проверка: `ciphertext` не содержит валидный
JSON/UTF-8-текст оригинала как подстроку/префикс).

### Перенос решения из этапа 13: таблица `mlsGroups`

Правка контракта этапа 3 (`database.js`, п.13 skill — явное решение +
полная регрессия, без миграции версии: проект в разработке, боевых
записей нет, `db.version(1)` правится напрямую, прецедент — мультиаккаунт
в этапе 11). Схема — как решено в DESIGN.md этапа 13:
`mlsGroups: "groupId"`. `groupId` — единственное поле в allowlist
plaintext (это Dexie primary key, физическое требование индексации;
конфиденциальность не теряется — `groupId` и так публикуется в
`h`-теге kind 445 на relay, см. этап 13). Остальное (сериализованный
`clientState`, `ownDeviceId`) — зашифровано. Таблица добавляется СЕЙЧАС
(в соответствии с явным обещанием DESIGN.md этапа 13), но реально
используется (через `encrypted-table.js`, построенный этим же этапом)
только в этапе 24 — та же ситуация, что `outbox`/`keystore` существовали
в схеме с этапа 3 до появления реального потребителя.

**Осознанно НЕ в скоупе этого этапа:** применение `encrypted-table.js`
к остальным 16 таблицам materialized views (`contacts`, `messages`,
`permissions`, `channels` и т.д., TECH.md §5.13/§13.4 пункт 3.3
буквально). Причина: `plaintextFields` для каждой из них — решение,
завязанное на реальные query-паттерны конкретного домена, которого
ещё не существует в коде (contacts.js — этап 22, messages — этап 24/26,
channels/posts/comments — этапы 30/31, permissions — этап 21).
Придумывать этот список сейчас, без потребителя — гадание, а не
инженерное решение (создаёт риск неверного выбора, который откроется
только когда реальный запрос понадобится). Каждый последующий этап,
добавляющий домен с реальными таблицами, оборачивает СВОИ таблицы
`encrypted-table.js` сам, в контексте собственного query-паттерна —
примитив (этот этап) от конкретного применения (последующие этапы)
разделены явно.

## Этап 15 — P-SPIKE (перформанс риск-гейт)

Триаж: измерение, не алгоритмическая задача — формализуется методология
замера, не инвариант кода.

**Почему это не может быть просто `node --test`.** Реальный пайплайн
TECH.md §13.1 (P.2) — "проверка id+подписи (**batch**) → расшифровка →
fold → запись через `encrypted-table`". Batch-проверка — это конкретно
`crypto.worker.js` (этап 10, Comlink), а он принципиально не
инстанцируется в чистом Node (`globalThis.addEventListener` отсутствует
— уже установленное ограничение). Плюс `fake-indexeddb` (in-memory JS)
даёт оптимистичные тайминги, не сопоставимые с реальным IndexedDB
браузера — гейт NF-09 про реальное устройство, не про синтетическую
среду тестов. Поэтому замер идёт через Playwright на **реальном
браузере**, тем же путём, что уже единственный способ вообще
протестировать `crypto.worker.js` (этап 10) — не новое решение, а
применение уже принятого прецедента к новой задаче.

**Методология "мобильного множителя 1.5×" — решение в пользу
РЕАЛЬНОГО замера, не арифметики.** TECH.md формулирует "замерить...
и на мобильном множителе 1.5×" — можно было бы тривиально взять
`measuredTime * 1.5` (арифметика постфактум). Это НЕ выбрано: линейное
масштабирование — плохое допущение для пайплайна со смешанными
издержками (часть операций — фиксированные накладные расходы: открытие
IndexedDB, старт Worker, — не линейно зависят от CPU, часть —
CPU-bound крипто, которая линейно зависит). Вместо арифметики —
**реальный замер под управляемым CPU-троттлингом** через Chrome DevTools
Protocol (`Emulation.setCPUThrottlingRate`, доступно из Playwright через
`page.context().newCDPSession(page)`), `rate: 1.5` — честное замедление
исполнения JS в 1.5 раза на уровне V8, не постфактум-умножение
результата. Два независимых прогона (1× и throttled 1.5×), каждый
проверяется против порога NF-09 (30с) отдельно.

**Событийная смесь — обоснование пропорций (решение Claude, TECH.md
не даёт точных долей, только "микс kind 0/1059/30051/30061"):**
реалистичная модель холодного старта — один профиль на контакт (мало),
основной объём — переписка и посты каналов (много), правила доступа —
среднее количество. Пропорции: kind 0 — 10% (500), kind 1059 — 50%
(2500, доминирующий трафик разговоров), kind 30051-подобные — 15%
(750), kind 30061-подобные — 25% (1250). Итого 5000, как того требует
P.1.

**Упрощения для kind 30051/30061 (задокументировано явно, не скрыто).**
Настоящая журнальная модель прав (R6-5) — этап 21; настоящая
`channel-key.js`-деривация — этап 30. Ни то, ни другое ещё не
существует в коде. Для бенчмарка используются ПРОКСИ той же весовой
категории: 30051-подобные события — `nip44.encrypt` себе (тот же
примитив/вес, что будет в реальном коде), 30061-подобные — прямой
`chacha20poly1305` (`@noble/ciphers`, тот же примитив, что уже в
`db-crypto.js`/`file-crypto.js`) со случайным синтетическим ключом
канала. Это осознанно не точная доменная семантика будущих этапов —
цель P-SPIKE НЕ в этом (см. TECH.md: "проверить самое дорогое-необратимое
допущение архитектуры хранения", то есть вес крипто-примитивов и
throughput fold/записи), а не корректность ещё не спроектированной
бизнес-логики.

**Fold-стратегия по типу kind (уже принятые примитивы, не новые):**
kind 0 и оба 300xx-прокси — LWW (`lwwWinner`/`pickLatest`, этап 4),
сгруппированы по синтетическому "логическому ключу" (не все 3750 из
них уникальны — специально сгенерирован пересекающийся набор из ~80
синтетических identity, чтобы LWW реально выбирал победителя, а не
просто добавлял всё как новое — иначе throughput-профиль был бы
нереалистично лёгким, PICK-логика LWW не была бы нагружена вовсе).
kind 1059 — G-Set (`mergeEvent`, этап 4, идемпотентное добавление в
журнал `events`) — реалистично: gift wrap'ы не заменяют друг друга,
каждый — новое сообщение.

**Не входит в постоянный `npm test`.** Полный 5000-событийный
browser-driven прогон — минуты, не миллисекунды; не относится к
быстрой регрессии, которая должна оставаться дешёвой на каждом этапе
(уже установленный принцип — `crypto.worker.js`/`service-worker.js`
тоже вне `node --test` по тем же причинам). Отдельный скрипт
(`scripts/p-spike-bench.mjs`), запускается по требованию (сейчас — как
гейт этого этапа; в будущем — вручную, при пересмотре решений
хранения). Генератор синтетических событий частично тестируем
отдельно (валидность формы/подписи сгенерированных фикстур) — это
уже быстрая, дешёвая проверка, годная для `node --test`.

### Побочная адверсарная находка: реальный баг session-reset (не в скоупе этапа, но реальный)

При построении Playwright-гейта (клик по кнопке диагностики после
логина) обнаружено: переход на вкладку "Диагностика" ПОСЛЕ входа
безусловно сбрасывал сессию (`currentUser` в null, экран падал на
"Разблокировка") — без единой ошибки в консоли, что затрудняло
диагностику. Причина — НЕ логика P-SPIKE, а два независимых
пред-существующих дефекта, оба нашлись эмпирически (беспорядочные
догадки исключены: `beforeunload`/`framenavigated`-инструментация
Playwright дала однозначный ответ, а не косвенные признаки):

1. **Дублирующийся код.** `diagnostics.jsx` содержал СОБСТВЕННЫЙ
   `navigator.serviceWorker.addEventListener("controllerchange", …
   location.reload())` на уровне модуля — независимая копия того же
   кода, что уже есть в `main.jsx`. Судя по всему — остаток раннего
   устройства проекта (до разделения shell на `app.jsx`/`main.jsx` в
   этапе 5), не вычищенный при рефакторинге. Выполнялся безусловно
   при загрузке бандла (статический импорт `diagnostics.jsx` из
   `app.jsx`), независимо от того, показан ли реально экран
   диагностики.
2. **Отсутствие различения "первая установка" vs "настоящее
   обновление".** И дублированный код, И оригинал в `main.jsx`
   перезагружали страницу на ЛЮБОЙ `controllerchange` — включая
   самый первый `clients.claim()` в свежей вкладке (когда обновлять
   нечего, controller меняется с `null` на что-то, а не с одной
   версии SW на другую). Поскольку регистрация SW в `useServiceWorker()`
   ленивая (только при первом реальном показе диагностики — экран
   теперь спрятан за логином с этапа 12), этот "первый claim" стал
   практически достижим ПОСЛЕ настоящей пользовательской сессии —
   раньше (когда диагностика была стартовым экраном, этапы 1-11) он
   срабатывал ДО входа, и сброс несуществующей сессии был незаметен.

**Фикс:** дублирующийся блок в `diagnostics.jsx` удалён целиком (SW
lifecycle — забота bootstrap-файла `main.jsx`, не UI-экрана).
`main.jsx` запоминает `navigator.serviceWorker.controller !== null`
ДО регистрации — если controller уже был (значит это отработавший SW
обновляется на новую версию — законный повод перезагрузить и
подтянуть свежий код), перезагрузка нужна; если controller не было
(первая установка в этой вкладке — обновлять нечего), `controllerchange`
от `clients.claim()` больше не триггерит `reload()`.

**Почему это находка именно ЭТОГО этапа, а не отдельный незапланированный
баг-фикс:** без построения P-SPIKE-гейта (первого места в проекте,
где логин идёт programmatically ПЕРЕД реальным заходом на
диагностику через Playwright) этот дефект не проявлялся ни в одном
предыдущем интеграционном скрипте — типичный случай, когда адверсарная
инфраструктура одного этапа вскрывает дефект, посаженный совсем в
другом (этап 2/5/12). Регрессия здесь особенно важна: `npm test`
этот класс багов в принципе не ловит (это межмодульное DOM/SW-поведение,
не юнит-тестируемая логика) — только реальный browser-driven прогон.

## Этап 16 — Relay pool + pluggable транспорт

Триаж (п.13a): **алгоритмическая** для автомата соединения (TECH.md
§9.3, явный триггер — конечный автомат с неочевидными переходами,
уже отмечено в PLAN.md). `transport.js` (список endpoint + фоллбэк) —
рутинная (retry-паттерн, не требует формализации сверх описания
политики выбора).

### Автомат соединения — правка контракта TECH.md §9.3 (не буквальная реализация)

**Формализация проблемы.** TECH.md §9.3 определяет
`connecting + OPEN → authenticating` БЕЗУСЛОВНО и
`authenticating + TIMEOUT → disconnected`. Если реализовать буквально:
клиент, подключившийся к relay, который никогда не шлёт AUTH-challenge
(наш собственный тестовый strfry — см. ниже), обязан зависнуть в
`authenticating` до TIMEOUT, затем `disconnected` → реконнект-логика
пробует заново → снова `connecting → authenticating` → снова TIMEOUT
→ **бесконечный цикл отказов против relay, который работает
корректно**. Это не гипотетический край, а измеримый баг против уже
поднятого тестового окружения проекта.

**Два независимых источника, оба проверены, не угаданы:**

1. **NIP-42 (официальная спецификация, github.com/nostr-protocol/nips/blob/master/42.md,
   проверено WebFetch):** "At any moment the relay may send an `AUTH`
   message to the client containing a challenge" — challenge МОЖЕТ
   прийти в любой момент соединения, спецификация НЕ требует
   отправки сразу после открытия сокета. Таймаут ожидания challenge
   протоколом не определён вовсе — это app-level политика, не
   протокольное требование.
2. **strfry (реальный relay проекта, server/strfry/, исходники
   прочитаны, не предположено):** `sendAuthChallenge()` имеет РОВНО
   ОДИН call site во всём кодовом дереве
   (`src/apps/relay/RelayIngester.cpp:163`) — срабатывает
   ИСКЛЮЧИТЕЛЬНО при попытке опубликовать "protected event" (NIP-70,
   `-`-тег на самом событии) без предварительной аутентификации
   соединения. На простое открытие WebSocket-соединения, на REQ, на
   публикацию обычного (не protected) события — challenge НЕ
   отправляется никогда. Подтверждено живым прогоном (log.md,
   довесок "Инфраструктура"): событие от непроверенного ключа принято
   без единого AUTH-сообщения за весь коннект.

**Решение (правка контракта, не гадание — обоснование выше):**
`connecting + OPEN` ведёт СРАЗУ в `connected`, не в `authenticating`.
`authenticating` — состояние, в которое входят РЕАКТИВНО (из
`connected` ИЛИ `subscribed`, по событию `AUTH_CHALLENGE`, в любой
момент жизни соединения — не только сразу после открытия), и из
которого ВСЕГДА возвращаются в `connected` (по `AUTH_OK`, `AUTH_FAIL`
ИЛИ `TIMEOUT` — все три ведут в один и тот же `connected`, не в
`disconnected`). Обоснование: неудачная/незавершённая аутентификация
в общем протокольном смысле не обязана аннулировать всё соединение —
она просто означает, что операции, требующие `auth`, останутся
недоступны (`OK ... false "auth-required: …"` на конкретные попытки),
пока аутентификация не пройдёт успешно при следующей возможности.
Решение ПРИНУДИТЕЛЬНО закрыть соединение при провале AUTH (например,
если relay whitelist-only и провал означает "вас тут не ждут") —
это app-level политика уровня `relay-auth.js`/`publisher.js` (этап 17),
НЕ должна быть зашита в транспортный автомат — их явно разделяю
(автомат описывает, В КАКОМ СОСТОЯНИИ соединение находится, не что
приложение решает ДЕЛАТЬ в ответ).

**Инвариант A1 (authenticating — временный, не терминальный, для
любого исхода).** Из `authenticating` нет исходящего перехода назад
в `disconnected` ни по одному из "внутренних" AUTH-событий
(`AUTH_OK`/`AUTH_FAIL`/`TIMEOUT`) — только по wildcard `CLOSE`/`ERROR`
(реальный обрыв соединения). Тестируется явно: для каждого из трёх
AUTH-исходов автомат обязан вернуться в `connected`.

**Формальная таблица (полная, для `machine.js` из этапа 14, с
wildcard-фоллбэком):**

```
States:  {disconnected, connecting, connected, authenticating, subscribed}
Events:  {CONNECT, OPEN, AUTH_CHALLENGE, AUTH_OK, AUTH_FAIL, TIMEOUT,
          SUBSCRIBE_OK, CLOSE, ERROR}
Initial: disconnected

disconnected   + CONNECT        → connecting
connecting     + OPEN           → connected
connecting     + TIMEOUT        → disconnected   // зависшее WS-рукопожатие — сигнал реконнект-логике снаружи
connected      + AUTH_CHALLENGE → authenticating
connected      + SUBSCRIBE_OK   → subscribed
authenticating + AUTH_OK        → connected
authenticating + AUTH_FAIL      → connected
authenticating + TIMEOUT        → connected
subscribed     + AUTH_CHALLENGE → authenticating
subscribed     + ERROR          → connected        // не полный реконнект — просто пере-REQ (сохранено из TECH.md, не менялось)
*              + CLOSE          → disconnected
*              + ERROR          → disconnected
```

**Явно НЕ в скоупе `relay-pool.js` (этот файл, этот этап):** разбор
проводного протокола (какое именно сообщение `OK`/`NOTICE`/`CLOSED`
соответствует событию `AUTH_FAIL` — это `relay-auth.js`, этап 17,
интерпретирует сырые сообщения relay и вызывает `transition(...)` с
уже определённым именем события). `relay-pool.js` принимает готовые
имена событий, не парсит protocol-фреймы сам.

### `transport.js` — список endpoint + фоллбэк (рутина)

Политика (TECH.md §4.1b, NF-17): список endpoint пробуется по
порядку; текущий endpoint используется, пока `relay-pool.js` не
сообщит об исчерпании попыток реконнекта (после N неудачных попыток
подряд с backoff — не с первой же ошибки, транзиентный сетевой сбой
не повод сразу считать endpoint заблокированным); тогда — следующий
в списке; после последнего — снова с начала (список конечен, но
блокировка может быть временной). Backoff — экспоненциальный с
джиттером (стандартная практика against thundering herd, TECH.md не
задаёт параметры явно — решение Claude: база 1с, множитель 2, потолок
30с, джиттер ±20% — консервативные, широко используемые значения, не
критичный для протокола выбор).

## Этап 17 — NIP-42 AUTH

Триаж (п.13a): рутина для самого `relay-auth.js` (тонкая обёртка —
собрать+подписать kind 22242, разобрать ответ). Но обнаружился реальный
пробел знания на границе TECH.md/выбранной инфраструктуры — эскалирован
пользователю (п.9a), не угадан.

### Пробел, эскалированный пользователю: whitelist ↔ NIP-42, не совпадает с strfry

**Формулировка расхождения.** TECH.md F-RL-02: "Все WebSocket-соединения
с relay обязательно проходят NIP-42 AUTH перед операциями чтения/
записи". Но strfry (выбранный relay, CLAUDE.md) устроен иначе —
подтверждено ДВУМЯ независимыми источниками (не одним, не догадкой):

1. Чтение исходников (этап 16): `sendAuthChallenge()` — ровно один
   call site во всём дереве, срабатывает только на попытку
   опубликовать NIP-70 "protected event".
2. Официальная документация strfry (`docs/plugins.md`, этот этап):
   собственный рекомендуемый пример whitelist-плагина проверяет
   `event.pubkey` НАПРЯМУЮ (уже криптографически подтверждён подписью
   события) — без единого упоминания `authed`/NIP-42 в whitelist-сценарии.
   Философия strfry прямым текстом: "keep policy logic out of core
   relay functionality" — whitelist на запись и NIP-42 AUTH — два
   независимых, ортогональных механизма в архитектуре этого relay,
   не один зависящий от другого.

**Вопрос пользователю (не решён самостоятельно — реальный форк
архитектуры, не деталь):** как реализовать AC-14 (whitelist на запись)
с учётом этого расхождения? Варианты, представленные пользователю:
(а) whitelist по `event.pubkey`, AUTH — честный отдельный механизм
(для чтения/protected events), F-RL-02 трактуется как "соединение
СПОСОБНО пройти AUTH", не "запись невозможна без AUTH"; (б) пометить
все свои события как NIP-70 protected, чтобы заставить strfry слать
challenge на каждую запись — семантически не по назначению NIP-70,
больше сложности на каждое событие; (в) патчить strfry, чтобы слал
challenge проактивно при `auth.enabled=true` — точнее по букве F-RL-02,
но ломает принцип "тестовый relay = тот же, что в проде" (пришлось бы
поддерживать патч при апгрейдах strfry).

**Решение пользователя: (а).** Write-policy плагин проверяет
`event.pubkey` напрямую (см. ниже, конфигурация relay). `relay-auth.js`
реализует NIP-42 честно и полностью (кладёт основу для будущего
использования — чтение/защищённые события), но НЕ как условие записи
обычных событий. F-RL-02 в контексте выбранной инфраструктуры (strfry)
читать как "клиент обязан уметь пройти AUTH, когда relay его требует"
— не как "любая операция технически заблокирована без AUTH" — это
правка контракста, фиксируется здесь, чтобы вопрос не поднимался
заново в будущих сессиях.

### `relay-auth.js`

**F-RL-03 (replay-окно) — проверено фактическое поведение relay, не
предположено.** strfry для эфемерных kind (22242 входит в диапазон)
использует `events__rejectEphemeralEventsOlderThanSeconds` (наш
конфиг: 60с — совпадает с TECH.md) для НИЖНЕЙ границы, но ВЕРХНЮЮ
границу берёт из общего `events__rejectEventsNewerThanSeconds` (наш
конфиг: 900с) — то есть фактическое окно strfry
несимметрично: `[now−60с, now+900с]`, не `±60с`, как буквально
написано в TECH.md. Не блокирующее расхождение (более широкое
будущее-окно не ослабляет защиту — replay всё равно требует точного
совпадения `challenge`, привязанного к конкретному соединению;
challenge одноразовый, генерируется relay заново на каждый
`connIdToAuthStatus`-цикл) — зафиксировано как факт для будущих
сессий, не как проблема, которую нужно чинить сейчас. Клиентский код
не обязан ничего проверять сам — всегда подписывает `created_at =
now()`, что по построению проходит любое разумное окно.

**Контракт message-interceptor (согласуется с этапом 16: "разбор
проводного протокола — забота relay-auth.js").** `createAuthHandler`
возвращает функцию-перехватчик, а не подписывается на `onMessage`
напрямую — позволяет составлять несколько обработчиков сообщений
(этот + будущие `publisher.js`/`subscriber.js`, этап 18) в простую
цепочку "первый, кто опознал сообщение как своё — обработал", без
единой точки, монопольно владеющей `onMessage`.

**Таймаут ожидания ответа на AUTH — решение Claude, TECH.md не
задаёт число (F-RL-05 говорит про backoff реконнекта, не про этот
таймаут).** 10 секунд — консервативное значение, совпадает
(случайно, не намеренно) с дефолтным `writePolicy.timeoutSeconds`
strfry, не протокольное требование, чисто UX-соображение (не
подвешивать пользователя дольше, чем разумно ждать ответа relay).

### Два реальных бага автомата этапа 16, найдены только реальной стыковкой (не фейковым WS)

Тесты `relay-pool.test.js` (этап 16, фейковый `WebSocketImpl`) прошли
101%, но не могли поймать эти два — они требуют РЕАЛЬНОГО сценария
"отправить AUTH-ответ во время authenticating", которого этап 16 сам
по себе не производил (никто не вызывал `send()` из `authenticating`).
Нашлись, как только `relay-auth.js` начал реально дёргать оба API
друг друга:

1. **`send()` запрещал состояние `authenticating`.** Но именно в этом
   состоянии `relay-auth.js` обязан отправить AUTH-ответ — WS реально
   открыт, операция легитимна. Правка контракта: `send()` разрешён в
   `connected`/`subscribed`/`authenticating`.
2. **Отсутствовал self-loop `authenticating + AUTH_CHALLENGE →
   authenticating`.** Был в оригинальном автомате TECH.md §9.3, потерян
   при переработке автомата на этапе 16 (фокус был на исправлении
   OPEN/TIMEOUT, this transition просто забыт). NIP-42 прямо допускает
   повторный challenge, пока предыдущий не разрешён ("challenge валиден
   до следующего challenge") — без self-loop второй `AUTH_CHALLENGE`
   подряд бросал бы "недопустимый переход".

Оба найдены проверенным путём (тест, воспроизводящий сценарий, не
инспекция кода), исправлены точечно, закреплены регрессионными
тестами в обоих файлах (`relay-pool.test.js` и `relay-auth.test.js`).
Дополнительно — оба сценария подтверждены ЖИВЫМ прогоном против
реального strfry (не только фейковый WS): AUTH-handshake на настоящем
NIP-70 protected event прошёл от challenge до успешной повторной
публикации.

## Этап 18 — Publisher + subscriber + outbox

Триаж (п.13a): рутина (очередь + таймер флаша, bulk-транзакция —
известные инженерные паттерны, не требуют формальных инвариантов
уровня CRDT/автомата). Но три содержательных решения фиксируются явно
— TECH.md не даёт их буквально, додумывать молча нельзя.

### Батчинг публикации (`publisher.js`) — что именно значит "100 evt/200мс"

Nostr wire-протокол не имеет батч-сообщения — `["EVENT", event]` несёт
РОВНО одно событие. "Батчинг 100/200мс" (TECH.md §13.5) — не сжатие
нескольких событий в одно сообщение, а управление ЧАСТОТОЙ отправки:
локальная очередь копится, сбрасывается (по одному `send` на событие,
синхронно все сразу) при достижении 100 элементов ИЛИ по таймеру
200мс — что раньше. Смысл: не создавать отдельный `setTimeout`/тик
event loop на каждый одиночный `publish()`, естественная точка для
будущей дедупликации/приоритизации (не в этом этапе).

`publish(event)` возвращает `Promise`, резолвящийся ответом `OK` от
relay — реальная задержка резолва = время до флаша очереди (до 200мс)
+ сетевой round-trip. Это осознанный компромисс латентность/throughput,
не изъян: `outbox.js` (ниже) — единственный потребитель этого этапа,
и там задержка в доли секунды не критична (drain — фоновый процесс).

### Батчинг подписки (`subscriber.js`) — F-CS-06/07/08

Симметрично публикации, но с одним важным отличием: EOSE ("конец
начального снапшота") — тоже триггер флаша, независимо от
размера/времени, иначе последний неполный батч (меньше 100, младше
200мс) молча зависнет в очереди до следующего события (которое может
не прийти вовсе, если подписка исчерпана). Порядок флаша:
size(100) ИЛИ time(200мс) ИЛИ EOSE — первое, что наступит.

`verifyBatch`/`onBatch` — инъекции (не хардкод `crypto.worker.js`
внутрь `subscriber.js`): тестируется без Worker/браузера (этап 10 —
воркер принципиально не поднимается в `node --test`), реальная
проводка (Comlink-обёрнутый `batchVerify`, `mergeEvents` в
IndexedDB) — забота вызывающего кода (bootstrap, этап 19, первый
реальный потребитель).

### Bulk-вставка одной транзакцией (F-CS-08) — правка контракта этапа 4

`g-set.js` (этап 4) имел только `mergeEvent(event)` — одна транзакция
НА событие. Для батча из 100 это 100 отдельных Dexie-транзакций
(накладные расходы на каждую) — не то, что требует F-CS-08. Добавлена
`mergeEvents(events)` — ОДНА `db.transaction("rw", db.events, ...)`
на весь батч, `hasEvent`+`appendEvent` для каждого события ВНУТРИ неё
(та же check-then-insert идемпотентность, что у `mergeEvent`, п.13
skill — амендмент принятого контракта, не новый файл). Существующий
`mergeEvent` не трогается (используется там, где батч из одного
события — например, `mergeEvent` внутри `relay-auth.js`-подобных
одиночных потоков не нужен, но контракт остаётся для обратной
совместимости и точечных вызовов).

### Outbox drain — retry-семантика (уточнение уже принятого контракта этапа 5)

`drain(publishFn)` берёт ВСЕ `listPending()` (уже FIFO по `seq`,
контракт этапа 5), пытается опубликовать каждое ПОСЛЕДОВАТЕЛЬНО (не
параллельно — простая, предсказуемая семантика для локальной очереди
одного пользователя; параллельный drain не даёт измеримой выгоды при
объёмах одного клиента и усложняет обработку частичного отказа).
Успех → `markSent`. Отказ → `markFailed` (уже увеличивает
`retryCount`, этап 5) — drain НЕ реализует свой backoff/повтор внутри
себя: следующий `drain()` вызывается извне при следующем `connected`
(естественный повод — реконнект уже даёт паузу через `relay-pool.js`,
дублировать retry-таймер здесь избыточно).

### Адверсарная находка: `drain()` падал целиком на исключении одной записи

Тест "publishFn бросает, не просто возвращает `{ok:false}`" (сетевой
сбой посреди batch — реалистичный сценарий, не надуманный) вскрыл
реальный баг в коде воркера: без `try/catch` вокруг `publishFn(record)`
исключение на ОДНОЙ записи прерывало весь цикл — все записи ПОСЛЕ
неё оставались в `pending` навсегда (до следующего внешнего вызова
`drain()`, но и тогда упавшая when-то запись сама по себе не считалась
`failed`, просто повторно бросила бы то же исключение). Исправлено:
`try/catch` вокруг `publishFn`, исключение трактуется как `ok:false`
(та же семантика, что explicit `{ok:false}` — не должно быть двух
разных путей отказа с разным поведением).

### Явная граница: `verifyBatch`/`onBatch` в `subscriber.js` — ошибки не перехватываются модулем

`flush(subId)` внутри `handleMessage` вызывается БЕЗ `await`
(намеренно — обработка входящих сообщений не должна блокироваться
на потенциально медленной верификации/записи одной подписки, другие
подписки и остальной протокол должны продолжать работать). Следствие:
исключение внутри `verifyBatch`/`onBatch` становится unhandled
promise rejection, не перехватывается `subscriber.js`. Это осознанная
граница ответственности инъекции (вызывающий код, этап 19+, обязан
делать свои `verifyBatch`/`onBatch` устойчивыми к ошибкам сам —
тот же принцип, что уже применён к `buildAuthEvent`/`sign()` в
`relay-auth.js`, этап 17), а не пробел — добавлять здесь ловушку
"на всякий случай" без конкретного потребителя, которому она нужна,
было бы преждевременной абстракцией.

## Этап 19 — Lamport-часы + bootstrap cold start

Триаж (п.13a): **алгоритмическая** для `lamport.js` — логические часы
Лэмпорта (1978), явный триггер "синхронизация с неочевидными
переходами". `bootstrap.js` формально рутина (склейка уже готовых
`subscriber.js`/`relay-pool.js`/`mergeEvents`), но со СЛОЖНОСТНЫМ
скоупингом — TECH.md §12.2 описывает процедуру из 12 шагов, половина
из которых зависит от доменов, которых физически ещё нет в коде.

### Lamport-часы — формализация (TECH.md §4.4, Lamport 1978, адаптация под single-user)

**Модель.** Одна неотрицательная целочисленная переменная `t` на
пользователя (не per-process — явное упрощение MVP, TECH.md §4.4:
"единый счётчик на пользователя", группы — backlog). Операции:

```
tick():           t ← t + 1; вернуть t
receive(remote):  t ← max(t, remote) + 1; вернуть t
```

**Инвариант L1 (монотонность / happens-before-согласованность).**
Для любой последовательности вызовов `tick`/`receive`, значение `t`
строго растёт при каждом вызове; `receive(remote)` гарантирует
результат `> remote` и `> предыдущего t`. Отсюда — если событие A
каузально предшествует B (то же устройство — последовательно, или
другое — через `receive`), то `L(A) < L(B)`. Стандартное свойство
логических часов, не изобретается заново — переносится из
Lamport (1978) буквально.

**Инвариант L2 (безопасность "in-memory tick без транзакции" —
ПРОВЕРЕНО рассуждением, не переписано с доверием к TECH.md).**
TECH.md утверждает: crash между `tick()` и persist — не проблема,
следующий `init()` восстановит корректно. Это верно НЕ само по себе,
а благодаря уже принятой в проекте архитектуре outbox-first (этап 18):
исходящее сообщение сначала пишется ЛОКАЛЬНО (`outbox.enqueue`),
потом уходит в сеть (`drain`). Если crash случился между `tick()` и
локальной записью — сообщение с этим `lamportTs` НИКУДА не ушло (сеть
ещё не тронута), значит переиспользование этого же `lamportTs` при
следующем `tick()` после `init()`-восстановления безопасно: нет
второго сообщения с тем же штампом где-либо во внешнем мире. Если бы
порядок был обратный (сеть, потом локально) — это было бы небезопасно.
Явно записано, т.к. TECH.md заявляет вывод, но не пруф.

**Инвариант L3 (важное решение, не в TECH.md буквально): `receive()`
обязан вызываться ТОЛЬКО для реально НОВЫХ событий, не для каждого
входящего сообщения.** Relay могут передоставлять одно и то же
событие (переподключение, несколько relay, ретраи) — G-Set
(`mergeEvent`/`mergeEvents`, этапы 4/18) уже даёт чёткий сигнал
"добавлено/дубль". Если гонять `receive()` на КАЖДОЕ входящее
сообщение независимо от дублирования — часы будут инфлировать без
пользы (не ломает корректность порядка — монотонность и
happens-before сохраняются при инфляции, но это неряшливо и
бессмысленно тратит пространство счётчика). Решение: `receive()`
вызывается вызывающим кодом (будущий `chat.js`, этап 24) ТОЛЬКО для
событий, где G-Set fold вернул "добавлено", не для дублей. Не
зашито в `lamport.js` — часы сами по себе не знают о fold, это
ответственность оркестрирующего кода, задокументирована здесь явно.

**Init/recovery — ВСЕГДА пересчитывается от фактических данных, не
доверяет последнему persisted значению.** `computeInitialLamportValue()`
сканирует `messages` (материализованное представление, не сырые
события) на `max(lamportTs)`, возвращает `max(0, max) + 1`. Отдельной
функции "прочитать последнее сохранённое значение из таблицы `clock`
и доверять ей" — НЕТ намеренно: persisted-значение может отставать
из-за ровно того сценария, что описывает инвариант L2 (crash до
persist) — единственный источник истины при старте — то, что РЕАЛЬНО
лежит в `messages`, не кэш последнего известного `t`.

### Правка контракта этапа 16: `relay-pool.js` не давал способа скомпоновать несколько message-interceptor'ов

**Реальный, серьёзный архитектурный пробел — не поймать юнит-тестом,
только настоящей стыковкой.** `createRelayConnection` (этап 16)
принимал ровно один `options.onMessage` при конструировании —
единственный получатель входящих сообщений. `relay-auth.js` (17),
`publisher.js`/`subscriber.js` (18) все реализуют message-interceptor
паттерн (`handleMessage(msg): boolean`), но их СОБСТВЕННЫЕ тесты
(`relay-auth.test.js`, `publisher.test.js`, `subscriber.test.js`) во
ВСЕХ случаях вызывали `handleMessage` НАПРЯМУЮ как обычную функцию —
ни один из них не проверял, что `handleMessage` реально ЧЕМ-ТО
подключена к живому соединению. Реальная стыковка НИКОГДА не
тестировалась вплоть до `bootstrap.js` — первого кода, которому
понадобилось реально подписать `subscriber.handleMessage` на
входящие сообщения существующего, уже созданного `connection`.

**Симптом:** тест `bootstrap.test.js` завис (не упал — именно завис,
`await` на промисе, который никогда не резолвится) — `subscriber`
никогда не получал `EOSE`, потому что `connection`'s `ws.onmessage`
вызывал только `options.onMessage` (не заданный в тесте), а
`subscriber.handleMessage` нигде не был к нему подключён — физически
некуда было подключить: `onMessage` — одно фиксированное значение,
заданное один раз при конструировании, не список.

**Решение.** `onMessage` из `options` теперь — сырой наблюдатель
(видит ВСЕ сообщения, ни на что не влияет, для логирования/отладки).
Добавлен `connection.addMessageHandler(handler)` — реальная точка
композиции: обработчики пробуются по очереди, первый вернувший `true`
("моё") останавливает цепочку — тот же first-match-wins, что уже
используют сами interceptor'ы между собой. `bootstrap.js` — первый
реальный потребитель: `connection.addMessageHandler(subscriber.handleMessage)`.

**Урок процесса (важно для будущих этапов, не только описание бага).**
Тестирование interceptor-функций напрямую (вызов `handleMessage(msg)`
как обычной функции) — быстро, детерминированно, но **не проверяет
реальную проводку**. Три этапа подряд (17: `send()` в `authenticating`
и потерянный self-loop; 18: `drain()` без `try/catch`; 19: этот
пробел) находились ИМЕННО там, где разные, по отдельности
протестированные модули впервые реально заработали вместе — не в
логике одного модуля. Для оставшихся транспортно-зависимых этапов
(20+) — обязательно минимум один живой сквозной прогон против
реального relay (уже установившаяся практика, но здесь стоит
проговорить явно, почему она не опциональна: изолированные unit-тесты
систематически такое пропускают, это не невезение).

## Этап 24 — Личные сообщения: ядро

состояний с неочевидными переходами, самая рискованная часть проекта

### 1. ДКА сообщения (TECH.md §9.1) — буквально, без отклонений

```
States: {created, sending, sent, read, failed, discarded}
Events: {SEND, ACK, READ, FAIL, RETRY, DISCARD}
Initial: created
Final: {read, discarded}

created  + SEND    → sending
sending  + ACK     → sent
sending  + FAIL    → failed
sent     + READ    → read
failed   + RETRY   → sending
failed   + DISCARD → discarded
```

Реализуется через уже принятый `core/fsm/machine.js` (`transition(transitions, state, event)`,
этап 14) — `domain/messaging/machine.js` только объявляет таблицу выше
как данные, ничего не решает сам. Недопустимые переходы (не
перечисленные явно) обязаны бросать — уже гарантировано `machine.js`
(`throw`, если `transitions[state]?.[event]` не определён и нет `"*"`
фоллбэка). Тесты — исчерпывающий перебор ВСЕХ пар (state, event),
не только happy path (урок из "Уроки предыдущих этапов" в PLAN.md):
6 состояний × 6 событий = 36 пар, 7 валидных (включая начальное
created как стартовую точку для SEND), 29 обязаны бросать.

### 2. Модель chatId — pubkey контакта, НЕ MLS groupId

`messages`/`chatSyncState` (схема этапа 3) используют `chatId` как
внешний, человеко-осмысленный идентификатор — уже так задумано (UI
этапа 23 вызывает `openChat(pubkey)`, не `openChat(groupId)`). MLS же
оперирует `groupId` (opaque `Uint8Array` в терминах `ts-mls`). Чтобы
не городить отдельную таблицу-маппинг "pubkey контакта → groupId" (лишняя
мультипликация мест истины, лишний риск рассинхронизации), `groupId`
для 1:1 чата вычисляется ДЕТЕРМИНИРОВАННО из пары pubkey, а не хранится
отдельно:

```
groupId = SHA-256(UTF8(sorted([myPubkeyHex, theirPubkeyHex]).join(":")))
```

`sorted(...)` — лексикографическая сортировка двух hex-строк, поэтому
ОБЕ стороны независимо вычисляют ОДИН И ТОТ ЖЕ 32-байтный `groupId`,
не дожидаясь синхронизации/обмена явным идентификатором группы. Это
именно то значение, что передаётся в `mls-session.js`'s `createGroup(...,
groupIdBytes)`. Отдельной таблицы-маппинга "chatId → groupId" не
заводится — `groupId` пересчитывается на лету везде, где известен
контакт (отправка, установление разговора).

**Уточнение, найденное при написании тестов (не в исходном плане):**
обратное направление — "дан `groupId` из `h`-тега входящего kind 445,
какой это контакт?" — НЕ решается пересчётом (`groupId` — однонаправленный
хэш, pubkey из него не восстановить). Поэтому `mlsGroups` (схема этапа
13) получает одно дополнительное поле `contactPubkey` РЯДОМ с уже
существующим `state` (не новая таблица, тот же ряд, тот же ключ
`groupId`) — записывается один раз при установлении разговора
(`ensureChatEstablished`/`acceptWelcome`, п.3) и обязан переноситься
каждым последующим `put()` (`sendMessage`/приём сообщения тоже
перезаписывают всю строку целиком — Dexie `put` не делает partial
update).

### 3. Установление 1:1-разговора (нет готового рецепта в NIP-EE — своя, обоснованная последовательность)

Реальный NIP-EE (проверено WebFetch, github.com/nostr-protocol/nips/blob/master/EE.md,
этот этап) НЕ описывает пошаговый handshake для старта 1:1-беседы —
только форматы KeyPackage/Welcome/Group Event по отдельности.
Последовательность ниже — решение этого этапа, не домысел протокола:

1. **Публикация своего KeyPackage** (лениво, один раз на identity):
   `createOwnKeyPackage(myPubkeyHex)` → `wireBytes` → kind 443, content =
   `base64(wireBytes)` (тот же паттерн кодирования, что уже применяется
   для kind 445, см. п.5), подписано обычной identity-подписью (`sign()`,
   НЕ MLS-credential). `privatePackage` персистируется (`encrypted-table`,
   dbKey) — без него нельзя обработать чужой Welcome, использующий этот
   KeyPackage. Таблица `ownKeyPackage` (новая, схема ниже) — одна строка
   на identity, не per-chat.
2. **Инициатор (A) хочет написать B впервые**: `groupId = computeGroupId(A,B)`.
   Если `mlsGroups.get(groupId)` уже есть — разговор уже установлен,
   переходим к п.5 (отправка). Иначе:
3. Забрать KeyPackage B (одноразовый REQ `{authors:[B], kinds:[443]}`,
   тот же паттерн, что `transport.fetchProfiles`, этап 23 — не

## Этап 21 — Битовая маска прав + журнальный движок

Триаж (п.13a): **алгоритмическая** — PLAN.md явно требует DESIGN.md:
решётка join/meet над битовой маской ACTIONS + нетривиальный инвариант
монотонности отзыва (R6-5). `bitset.js` сам по себе почти рутина
(побитовая арифметика), но алгебраические свойства решётки должны быть
доказаны тестами, не молчаливо предполагаться. `engine.js` (свёртка
журнала, `rebuildCache`) — ядро с реальным риском тонкой ошибки
(порядок применения решает корректность, R6-5) — псевдокод ниже уходит
воркеру через `--ctx` буквально, не пересказом.

### Модель прав (TECH.md §4.2)

$A = \{VIEW, COMMENT, WRITE, MODERATE, ADMIN\}$, $|A|=5$. Кодирование —
степени двойки (`1,2,4,8,16`), $2^A \cong \{0,1\}^5$ — булева решётка
относительно $\cup=\text{OR}$, $\cap=\text{AND}$.

**Правило** — пара `(allowMask, denyMask)`. **Эффективная маска**
правила: `effective(allow, deny) = allow & ~deny`. **Fail-closed**:
`effective(0, 0) = 0` — отсутствие явного правила = отказ, не разрешено
по умолчанию (`can` на undefined subject/resource обязан вернуть
`false`, не бросать).

`bitset.js` предоставляет решётку как переиспользуемый примитив:
`join(a,b) = a|b`, `meet(a,b) = a&b`, `complement(a) = ~a & ALL`,
`can(mask, action) = (mask & action) !== 0`. Свойства, обязательные к
тестированию (не допущение, а проверяемый инвариант каждого прогона):

- коммутативность/ассоциативность/идемпотентность `join` и `meet`;
- поглощение (absorption): `join(a, meet(a,b)) = a`, `meet(a, join(a,b)) = a`;
- де Морган относительно `complement`: `complement(join(a,b)) = meet(complement(a), complement(b))`.

Формальное обоснование не ново — это стандартные свойства булевой
решётки подмножеств $A$ (TECH.md §4.2 напрямую ссылается на изоморфизм
$2^A \cong \{0,1\}^{|A|}$); тесты фиксируют это как контракт, не
переоткрывают алгебру.

### Журнальная модель — формализация (R6-5, закрывает L-16/Q-09)

**PermissionRecord** (абстрактная запись, НЕ nostr-событие — парсинг
kind/подписи/тегов остаётся вне этого этапа, см. границы скоупа ниже):

```
{ subject, resource, allowMask, denyMask, lamportTs, eventId }
```

`subject`/`resource` — opaque-строки (в реальности pubkey/opaque d-tag
— решается доменом-потребителем, этап 22). Журнал `J` — произвольно
упорядоченный список таких записей (порядок ПОСТУПЛЕНИЯ не значим,
только `lamportTs`+`eventId`).

**Тотальный порядок** внутри группы `(subject, resource)` —
`(lamportTs, eventId)` лексикографически: тот же паттерн, что уже
принят в TECH.md §4.4 для сообщений (`(lamportTs, pubkey, eventId)`),
без `pubkey`-компоненты — issuer всегда владелец `resource`, различать
уже нечем, `eventId` один даёт уникальный тайбрейкер при равном
`lamportTs` (два устройства владельца одновременно меняют одно и то же
правило).

**rebuildCache — псевдокод (уходит воркеру буквально через `--ctx`):**

```
rebuildCache(records):
  groups ← group records by (subject, resource)
  cache ← new Map()
  for (key, group) in groups:
    sorted ← sort group by (lamportTs asc, eventId asc)
    acc ← 0
    for record in sorted:
      acc ← (acc | record.allowMask) & ~record.denyMask
    cache.set(key, acc)
  return cache
```

$O(n \log n)$ за счёт сортировки (группировка — $O(n)$ проход с Map).
10000 записей — сортировка миллисекунды на референсном железе, порог
AC-PERM-AUDIT (<100мс) выполняется с большим запасом, отдельный
perf-тест фиксирует это эмпирически, а не полагается на нотацию.

**Инвариант R6-5 (монотонность отзыва, формально).** Пусть
`last(b, key)` — последняя (по `(lamportTs, eventId)`) запись группы
`key`, где бит `b` встречается в `allowMask` ИЛИ `denyMask`. Тогда:

$$b \in \text{effective}(key) \iff \text{last}(b, key)\text{ упоминает } b \text{ в } allowMask$$

Следствие 1 (то, что буквально требует R6-5): если `revoke` записи `r`
с `b ∈ r.denyMask` и `grant` записи `g` с `b ∈ g.allowMask`, где
`g.lamportTs < r.lamportTs` (grant причинно РАНЬШЕ revoke) — то после
применения `r`, `b ∉ effective`, и это состояние **не может измениться
из-за `g`** ни при каком порядке физического поступления `g`/`r` по
сети (сортировка перед fold делает результат порядок-поступления-
независимым — свойство детерминированной сходимости, устраняет L-16:
раньше решал `created_at`/wall-clock, подверженный рассинхрону часов
между устройствами одного владельца).

Следствие 2 (revoke не абсолютен НАВСЕГДА — иначе владелец физически не
смог бы заново открыть доступ, что не модель прав, а необратимый бан):
`grant`-запись `g'` с `g'.lamportTs > r.lamportTs` для того же `b`
ПОБЕЖДАЕТ `r` — восстанавливает бит. R6-5 запрещает воскрешение
**более ранним** grant, не запрещает более поздний. Оба следствия —
прямая консеквенция псевдокода выше (fold строго по возрастанию
`(lamportTs, eventId)`, каждый шаг детерминирован предыдущим
накоплением); тесты покрывают оба сценария явно (revoke побеждает
более ранний grant; более поздний grant побеждает revoke), плюс тест
на **порядок-независимость**: `rebuildCache(shuffle(J))` даёт тот же
результат, что `rebuildCache(J)` для любой перестановки.

**Идемпотентность при дублях.** Если один и тот же `eventId` встречается
в `records` дважды (relay redelivery до дедупликации на слое выше) —
fold безопасен без явной защиты: `(acc | a) & ~d`, применённое дважды
подряд с теми же `(a, d)`, даёт тот же результат вторым применением
(`((acc|a)&~d | a) & ~d = (acc|a)&~d`) — тест фиксирует это как
регресс-гарантию, а не как то, что нужно защищать отдельным кодом.
Дедупликация по `eventId` — ответственность G-Set слоя (этап 4/18,
уже существует), не `engine.js`.

### Явное сужение скоупа этапа 21 (по прецеденту `bootstrap.js`/`incremental-sync.js`)

`bitset.js`/`permissions.js`/`engine.js` работают НАД уже готовыми
`PermissionRecord` — не разбирают nostr-события (kind, теги, подпись,
шифрование содержимого), не решают вопрос "какой конкретно kind несёт
permission-событие" (TECH.md §10 сам явно отмечает: форма kind/тегов
"финализируется в фазе 5" — но это фаза 5 по TECH.md, разбитая PLAN.md
на этапы 21-23; конкретно kind/парсинг/публикация — задача `handlers.js`
этапа 22, где явно значится "fold для kinds 3, 30050, 30051"). Проверка
"issuer действительно владелец resource" — тоже ответственность
вызывающего кода (handlers.js, этап 22), не `engine.js`: `rebuildCache`
доверяет тому, что ему передали уже отфильтрованные/провалидированные
записи, ровно как `mergeEvent`/`g-set.js` доверяет валидности `id`
(проверяется `validateEventId` ДО вызова, не внутри).

## Этап 25 — Личные сообщения: периферия + multi-device

Триаж (п.13a): **алгоритмическая**, три независимые причины: (а)
распознавание "устройство-siblings" и массовое добавление в уже
активные MLS-группы — пространство состояний с неочевидными
переходами (та же категория риска, что MLS-оркестровка этапа 24); (б)
зеркало истории — новый секрет (`mirrorKey`) и новый инвариант
идемпотентности слияния ДВУХ независимых путей доставки одного
логического сообщения (live-MLS и zеркало) — прямой аналог
G-Set/LWW-класса задач (этап 4); (в) явное решение пользователя
поднять приоритет multi-device (см. log.md) расширило исходный скоуп
"периферии" (TECH.md §13.7 6.7–6.9) — нужна отдельная формализация,
которой не было в исходном плане.

**Контекст решения (важно для будущих этапов, не домысел):**
исходный TECH.md §13.7 (6.7) описывал "двойной gift wrap (для
получателя + self-mirror)" — рассчитан на pre-MLS baseline (NIP-17
без MLS), где "себе" означает второй gift-wrap той же rumor. При
переходе на MLS (этап 13/24) это перестало работать буквально:
MLS-ratchet секреты предназначены РОВНО для той группы, где были
согласованы (forward secrecy = старые эпохи преднамеренно
недоступны) — нет способа "переслать себе" копию, расшифровываемую
устройством, не бывшим участником эпохи в момент отправки. Это и есть
конфликт, из-за которого этап был приостановлен и обсуждён с
пользователем. Решение пользователя (после обсуждения trade-off):
завести ОТДЕЛЬНЫЙ канал зеркалирования с ключом, производным от
мнемоники (не от MLS-ratchet), принимая потерю forward secrecy ИМЕННО
для зеркалированных копий — раздел 2 ниже.

### 1. Multi-device — модель и её причина

Профиль/контакты/группы/права УЖЕ синхронизируются между устройствами
одной identity (проверено живьём, этап 23) — они завязаны на
`authors:[myPubkey]` fold, а не на MLS-членство. Единственный
качественно другой случай — переписка: MLS привязывает участника к
конкретному **leaf** (пара credential+keypackage), а не к Nostr
identity как таковой. Раз одна и та же мнемоника может быть введена
на НЕСКОЛЬКИХ физических устройствах (в отличие от Signal/WhatsApp,
где "основное" устройство держит секрет, недоступный "привязанным"
— здесь ВСЕ устройства обладают ПОЛНЫМ секретом identity), паринг
через QR/секретный код не нужен и был бы избыточным теантроном
поверх уже имеющегося общего секрета. Вместо этого:

- каждое устройство имеет собственный `deviceId` (локальный, случайный,
  не является секретом — просто различитель "чьё это MLS-leaf");
- каждое устройство публикует СВОЙ собственный MLS KeyPackage (kind
  443, тот же кind, что уже принят этапом 24) с тегом `["device",
  deviceId]` — множественные kind 443 от одного pubkey это штатно
  (kind 443 обычный, не адресуемый/replaceable, NIP-01 диапазон
  1000-9999 — журналируется весь);
- любое УЖЕ активное устройство, увидев чужой (не свой) `deviceId` в
  потоке `{authors:[myPubkey], kinds:[443]}` (который оно уже получает
  — тот же bootstrap/incremental-sync поток, что для kind 3/30050 с
  этапа 20/22, новых подписок заводить не нужно), распознаёт **нового
  сиблинга** и добавляет его как MLS-участника в КАЖДУЮ свою активную
  группу (`mlsGroups`), рассылая Welcome тем же gift-wrap механизмом,
  что и обычным контактам (этап 24, DESIGN.md п.3, шаг 6) — адресат
  Welcome та же shared identity pubkey, которую и новое, и старое
  устройство могут расшифровать (обе стороны владеют privKey).

**Инвариант "не задвоить добавление".** Каждая пара `(deviceId,
groupId)` обрабатывается РОВНО один раз за всё время жизни группы —
не при каждом bootstrap повторно (иначе MLS commit на уже
существующего участника — ошибка протокола, не идемпотентная
операция, в отличие от `mlsGroups.put`). Формально:

```
knownDevices: Map<deviceId, { wireBytes, addedGroupIds: Set<groupIdHex> }>

on kind443Event (authors=me):
  deviceId ← tag(event, "device")
  if deviceId undefined or deviceId === myOwnDeviceId: skip   // легаси/собственный анонс
  if deviceId not in knownDevices: knownDevices[deviceId] ← { wireBytes: decode(event.content), addedGroupIds: {} }
  for (groupIdHex, row) in mlsGroups:
    if groupIdHex not in knownDevices[deviceId].addedGroupIds:
      { newState, welcomeWireBytes } ← addMember(deserialize(row.state), knownDevices[deviceId].wireBytes)
      persist mlsGroups.put({ groupId: groupIdHex, contactPubkey: row.contactPubkey, state: serialize(newState) })  // SM-2, contactPubkey перенесён
      welcomeEvent ← nip59.wrap({ kind: 444, content: base64(welcomeWireBytes), tags: [] }, privKey, myPubkey)
      requirePublishOk(publish, welcomeEvent)
      knownDevices[deviceId].addedGroupIds.add(groupIdHex)   // ПОСЛЕ успешной публикации, не до
      persist knownDevices row (новая таблица, ниже)
```

`addedGroupIds` фиксируется по факту успешной публикации Welcome (не
раньше) — при обрыве сети между `addMember` и `publish` состояние
`mlsGroups` уже продвинуто (SM-2, как и везде в проекте), но
`addedGroupIds` НЕ отмечен — следующий заход повторит `addMember` для
той же пары. Это осознанно избыточно (лишний commit допустим, MLS
проекция терпит несколько commit-ов подряд), но не пропускает
участника молча — предпочтение отдано "продублировать попытку", а не
"тихо потерять устройство", по прецеденту `requirePublishOk` (этап 24:
`sendMessage` тоже не считает операцию успешной без подтверждения
relay).

**Явное сужение скоупа (MVP, зафиксировано, не молчаливое упрощение):**
распознавание нового сиблинга и массовое добавление запускается ТОЛЬКО
в момент `connect()` (bootstrap уже читает весь `authors:[me]` поток
целиком, включая исторические kind 443 — реального устройства,
подключившегося офлайн, догонит на следующем coldstart), НЕ как
живой push немедленно в момент публикации нового устройства, пока
старое устройство уже открыто. Обоснование: kind 443-анонс — редкое
событие (только при установке нового устройства), живая реактивность
здесь не даёт заметной пользы соразмерно риску вплетения в уже
хрупкий live-dispatch (этап 24 п.6) лишней веткой. Если понадобится
позже — добавление кind 443 в тот же switch диспетчера п.6
тривиально, но не в скоупе.

### 1a. Найдено ТЕСТАМИ devices.js (не домысел) — конфликт credential-идентичности, правка контракта этапа 13

`mls-session.js`'s `createOwnKeyPackage(nostrPubkeyHex)` кодировал
`credential.identity` как ГОЛЫЙ hex pubkey — единственный на identity,
не на устройство. `ts-mls` (`defaultKeyPackageEqualityConfig.compareKeyPackageToLeafNode`,
node_modules/ts-mls/dist/src/keyPackageEqualityConfig.js) при добавлении
участника сравнивает НЕ ТОЛЬКО `signaturePublicKey`, но, если тот не
совпал, ЕЩЁ И закодированный `credential` целиком — а два устройства
одной identity вызывают `createOwnKeyPackage` с ОДНИМ И ТЕМ ЖЕ
`nostrPubkeyHex`, получая ИДЕНТИЧНЫЙ credential при разных
signature-ключах. Результат: `addMember` бросал `ValidationError:
Commit cannot contain an Add proposal for someone already in the
group` при попытке добавить sibling-устройство в уже существующую
группу — обнаружено 3 упавшими тестами devices.js, не гипотетически.

Представлено пользователю два варианта (AskUserQuestion): (а) сделать
`credential.identity = "${nostrPubkeyHex}:${deviceId}"` — каждое
устройство честно РАЗНЫЙ MLS-участник; (б) переопределить
`keyPackageEqualityConfig`, сравнивать только `signaturePublicKey`,
никогда не сравнивать credential. Пользователь выбрал (а) — сохраняет
защиту ts-mls от настоящих дублей (тот же KeyPackage дважды всё ещё
отклоняется), не ослабляет протокольную проверку глобально.

**Правка контракта этапа 13** (`mls-session.js`, полная регрессия
обязательна — самый рискованный файл проекта): `createOwnKeyPackage`
получил обязательный второй параметр `deviceId`; `nostrCredentialAuthService.
validateCredential` теперь разбирает `"${64hex}:${deviceId}"`
(`CREDENTIAL_IDENTITY_RE = /^([0-9a-f]{64}):(.+)$/`) вместо голого
64-hex. Все существующие вызовы `createOwnKeyPackage` (в `chat.js` и
во всех тестах `mls-session.test.js`/`chat.test.js`) получили второй
аргумент — `getOrCreateDeviceId()` там, где вызывающий код представляет
"моё устройство", тестовые строковые id там, где тест играет роль
другого участника (Bob/Carol не нуждаются в реальном deviceId — это не
их устройство, а тестовая fixture identity).

### 1b. Найдено ПРИ ПОДГОТОВКЕ живой проверки (не домысел) — диспетчер должен различать Welcome-от-контакта и Welcome-от-себя

`acceptWelcome(ownerPubkey, welcomeSenderPubkey, welcomeWireBytes)` (этап
24) вычисляет `groupId = computeGroupId(ownerPubkey, welcomeSenderPubkey)`,
полагая, что `welcomeSenderPubkey` (обычно `rumor.pubkey`) — это И ЕСТЬ
контакт, с которым устанавливается 1:1. Для sibling-Welcome (раздел 1)
это неверно: отправитель Welcome — МОЁ ЖЕ устройство, `rumor.pubkey ===
ownerPubkey`, а `computeGroupId(owner, owner)` был бы бессмысленным.
Решение — БЕЗ правки `acceptWelcome`/`chat.js`: `syncDeviceMembership`
(devices.js) кладёт `["contact", group.contactPubkey]` тегом в rumor
Welcome (тэги надёжно проходят через `nip59.wrap`/`unwrap`, проверено
`tests/nip59.test.js`); диспетчер входящих gift-wrap (`transport.js`)
при `rumor.pubkey === pubkeyHex` (Welcome от самого себя) берёт
`contactPubkey` из этого тега вместо `rumor.pubkey`, дальше вызывает
`acceptWelcome` ровно как раньше — функция не знает и не должна знать
о существовании multi-device вовсе.

### 1c. Найдено ПРИ ПОДГОТОВКЕ живой проверки (не домысел, до фактического запуска) — коммит обязан дойти до contactPubkey, не только Welcome до сиблинга

`addMember` возвращает `{newSessionState, welcomeWireBytes, commitWireBytes}`.
В `ensureChatEstablished` (этап 24, брендовая 2-местная группа)
`commitWireBytes` оправданно отбрасывается — группе, кроме создателя,
не с кем делиться коммитом (единственный новый участник узнаёт
состояние из Welcome). В `syncDeviceMembership` это НЕ так: в группе
уже есть `contactPubkey` (напр. Bob) — существующий участник, которому
Welcome НЕ адресован (Welcome — только для нового сиблинга) и который
обязан получить именно КОММИТ, чтобы продвинуть свою эпоху. Без этого
`contactPubkey` навсегда застревает на старой эпохе — тихая порча
канала (не throw нигде), обнаружено трассировкой сценария ДО первого
запуска верификационного скрипта, не после сбоя.

Решение — БЕЗ правки `chat.js`: коммит публикуется ТЕМ ЖЕ каналом, что
обычные сообщения (kind 445, тег `#h`), под ключом конверта СТАРОЙ
(пред-коммитной) эпохи — `contactPubkey` уже подписан на этот `#h` и
уже обрабатывает такие события через `receiveGroupMessageEvent`
(этап 24) — commit ветка `result.kind === "control"` там УЖЕ
реализована и просто продвигает состояние без показа UI (`processMessage`
из `ts-mls`, вызываемый внутри `decryptApplicationMessage`, сам
распознаёт commit/proposal и применяет их — не отличается от обычного
приёма для вызывающего кода).

### 2. Зеркало истории (полный паритет чатов между устройствами)

**Инвариант, который должен выполняться:** любое устройство той же
identity — будь то устройство, установившее MLS-группу изначально,
устройство, добавленное как сиблинг ПОСЛЕ начала переписки (раздел 1),
или ВООБЩЕ ЕЩЁ не являющееся MLS-участником данной группы — способно
восстановить ПОЛНУЮ историю каждого чата, если знает мнемонику. MLS
даёт это только "вперёд" (раздел 1); зеркало даёт это "назад" — ценой
forward secrecy для зеркалированных копий (согласовано с пользователем
явно, см. log.md).

**Ключ зеркала — не MLS-секрет, а HKDF от той же цепочки, что уже
использует `derivation.js` (этап 8):**

```
mirrorKey = HKDF-SHA256(masterSecret, salt=utf8("Ugolok/v1/mirror"), info=utf8(""), length=32)
```

Параллельно уже принятой `deriveDbKey(masterSecret)`. Поскольку
`masterSecret = HKDF(privKey, ...)`, а `privKey` детерминированно
деривируется из ОДНОЙ И ТОЙ ЖЕ мнемоники на любом устройстве (этап 7),
`mirrorKey` автоматически совпадает на всех устройствах одной identity
БЕЗ какого-либо обмена/согласования — не нужно ни публиковать его, ни
передавать через MLS. Это прямое следствие уже существующей
архитектуры, не новое допущение.

**Формат зеркалированного события** — новый kind, не пересекается с
занятыми (см. CONTRACTS.md, полный список): `KIND_MESSAGE_MIRROR =
446` (соседствует с 443-445 тематически — тот же "чат"-кластер, но НЕ
часть NIP-EE, приватный кind приложения). Публикуется ОБЫЧНОЙ
identity-подписью (`sign()`, НЕ MLS-credential, НЕ эфемерный ключ —
в отличие от kind 445): зеркало читают только МОИ СОБСТВЕННЫЕ
устройства через `{authors:[myPubkey], kinds:[446]}` — тот же паттерн
подписки, что уже используется для kind 443/3/30050 (этапы 20/22/25
раздел 1), устойчивый эфемерный ключ здесь не даёт метаданных-защиты
(зеркало и так публично привязано к моему pubkey самим фактом
подписки — в отличие от kind 445, где h-тег обязан быть
непривязываемым к паре собеседников).

**Payload зеркала — самодостаточный, не зависит от локального
`mlsGroups`:**

```
plaintext = JSON.stringify({ text, lamportTs, senderPubkey, contactPubkey })
{ nonce, ciphertext } = ChaCha20-Poly1305(mirrorKey, nonce=random(12), plaintext)   // формат как file-crypto.js, этап 10: nonce ‖ ciphertext+tag одним блобом
content = base64(nonce ‖ ciphertext)
event = sign({ kind: 446, tags: [["h", groupIdHex]], content, created_at }, privKey)
```

Критическое инженерное решение: `contactPubkey` кладётся ВНУТРЬ
зашифрованного payload, а не восстанавливается из `mlsGroups` по
`groupIdHex` (как для входящих kind 445, этап 24 DESIGN.md п.2) —
потому что зеркало обязано быть читаемым на устройстве, у которого
ЕЩЁ НЕТ строки `mlsGroups` для этой группы (устройство, не успевшее
получить Welcome по разделу 1, но уже способное восстановить историю).
`h`-тег (`groupIdHex`) остаётся как необязательный аксессуар для
будущей windowed-подгрузки по чату (этап 26), authoritative источник —
всегда payload.

**Два триггера записи зеркала** (правка контракта этапа 24, `chat.js`,
см. CONTRACTS.md) — оба best-effort (сбой публикации зеркала НЕ
блокирует и не откатывает основную MLS-отправку/приём, только
`console.warn`/лог, по прецеденту `profile.jsx`'s best-effort kind 0
publish, этап 23-довесок):

1. `sendMessage` — после успешной MLS-публикации (kind 445) — зеркалит
   {text, lamportTs, senderPubkey: ownerPubkey, contactPubkey}.
2. `receiveGroupMessageEvent` — после успешной MLS-расшифровки — тоже
   зеркалит (распространяет то, что узнало ЭТО устройство, на ОСТАЛЬНЫЕ
   устройства той же identity — иначе устройство B узнало сообщение
   через живой MLS, а устройство C той же identity никогда не увидит
   его, если у C нет собственного MLS-leaf в этой группе).

**Catch-up (новое/переподключившееся устройство):** новая функция
`syncMirroredHistory` — one-shot REQ `{authors:[myPubkey], kinds:[446]}`
(инъекция fetch-функции, тот же паттерн, что `fetchProfiles`/
`fetchKeyPackage`, этап 23/24), для каждого события — расшифровать
`mirrorKey`, upsert в `messages` (идемпотентно, см. п.3).

### 3. Идемпотентное слияние двух путей доставки — новый инвариант `messages`

Одно и то же логическое сообщение теперь может материализоваться в
таблице `messages` ДВУМЯ независимыми путями (живой MLS kind 445/
приём, и зеркало kind 446/catch-up), в любом порядке, любое число раз
(EOSE-повторы, повторный bootstrap). Текущий примитивный ключ
(`++seq`, автоинкремент) не даёт дедупликации — прямое `add()` из
обоих путей задвоило бы строку.

**Найдено ПЕРЕД кодом, тестами уже принятого этапа 24 (не домысел):**
`(chatId, lamportTs, senderPubkey)` НЕ годится как ключ дедупликации —
`tests/chat.test.js` (этап 24, `getChatHistory` тест на tiebreak)
намеренно проверяет сценарий, где ДВА РАЗНЫХ сообщения от одного
senderPubkey в одном чате имеют ОДИНАКОВЫЙ `lamportTs` (тайбрейк по
`id`, F-MS-05/AC-05) — это не тестовый артефакт, а прямое следствие
того, что при multi-device (раздел 1) два устройства ОДНОЙ identity
могут независимо тикнуть один и тот же lamport-момент до синхронизации
друг с другом. Дедуп по `(chatId, lamportTs, senderPubkey)` превратил
бы этот легитимный сценарий в отброшенное второе сообщение —
обнаружено адверсарным прогоном существующего теста ПРИ проектировании
схемы, до вызова воркера.

**Исправленный инвариант:** каждое логическое сообщение получает
`msgId` (16 случайных байт, hex, генерируется ОДИН РАЗ в `sendMessage`
в момент отправки) — кладётся ВНУТРЬ application-message plaintext
(`{text, lamportTs, msgId}`, правка формата этапа 24 п.7) И внутрь
mirror-payload (раздел 2: `{text, lamportTs, senderPubkey,
contactPubkey, msgId}`). `msgId` — единственное поле, тождественное
между обоими путями доставки одного и того же сообщения (`event.id`
НЕ тождественен между путями: kind 445 — эфемерный ключ на событие,
kind 446 — идентичность автора — как и раньше решено, `id` не годится).
`(chatId, msgId)` — уникальный ключ дедупликации:

```
upsertMessage(row):                              // общий хелпер, 4 места вызова (см. CONTRACTS.md)
  try: db.table("messages").add(row)
  catch ConstraintError: return                  // уже есть (тот же msgId в том же чате) — тихий no-op
```

Требует unique compound index (правка схемы, `db.version(3)`):
`&[chatId+msgId]` (Dexie-нотация `&` — unique index). Существующий
индекс `[chatId+lamportTs+senderPubkey+id]` (этап 3/24, неуникальный)
не трогается — остаётся сортировочным индексом `getChatHistory`
(порядок, не дедупликация — оба назначения теперь чётко разделены).
Строки, вставленные ДО этого этапа без `msgId` (тестовые фикстуры
`bulkAdd` в уже принятых тестах этапа 24), не участвуют в
unique-индексе вовсе — IndexedDB не индексирует запись по
compound-индексу, если хотя бы одно поле key path отсутствует
(стандартное поведение, не наше исключение) — обратная совместимость
со старыми тестами сохраняется без их правки.

### 4. Новые/изменённые таблицы (`db.version(3)`, аддитивно)

```js
deviceIdentity: "id",                            // одна строка, id="self": { id, deviceId }
knownDevices: "[ownerPubkey+deviceId], ownerPubkey", // { ownerPubkey, deviceId, wireBytes, addedGroupIds: string[] }
messages: "++seq, &[chatId+lamportTs+senderPubkey], [chatId+lamportTs+senderPubkey+id], chatId, id, status, deleted"
```

`addedGroupIds` хранится как обычный массив hex-строк (не `Set` —
Dexie/IndexedDB структурно клонирует, `Set` тоже можно, но массив
проще для будущей ручной инспекции в DevTools, нет причин
усложнять).

### 4. `inbox-requests.js` — whitelist-after-unwrap для Welcome от НЕ-контакта (F-CSL-03/AC-IB-01)

Диспетчер входящих gift-wrap (`transport.js`, п. выше) на `rumor.kind
=== 444` до этого этапа безусловно принимал ЛЮБОЙ Welcome — реальный
открытый гэп, отмеченный ещё в конце этапа 24 ("сообщения от
НЕ-контактов, whitelist-after-unwrap — этап 25"). Разбор по трём
случаям (`welcomeContactPubkey` — уже вычислен диспетчером, раздел 1b):

```
sibling-Welcome (rumor.pubkey === pubkeyHex)              -> всегда acceptWelcome (раздел 1, свой же identity)
welcomeContactPubkey ∈ мои contacts                        -> acceptWelcome как раньше (этап 24, ожидаемый разговор)
welcomeContactPubkey НЕ в contacts (настоящий незнакомец)  -> НЕ acceptWelcome; storeInboxRequest — Welcome
                                                               сохраняется НЕРАСПАКОВАННЫМ (welcomeWireBytes),
                                                               MLS-группа НЕ создаётся, пока пользователь явно
                                                               не примет решение (accept/reject, UI — этап 27)
```

`ownKeyPackage.self` не ротируется между попытками (этап 24, известное
упрощение) — значит отложенный `acceptInboxRequest` (когда бы он ни
случился) использует ТУ ЖЕ приватную половину, что была активна на
момент получения — `joinFromWelcome` сработает синхронно с этим
упрощением, без дополнительной логики.

Схема (правка `db.version(3)`, аддитивно — таблица `inboxRequests`
НЕ использовалась нигде с этапа 3, переопределение безопасно):
`[owner+senderPubkey], owner, senderPubkey, createdAt` — тот же
owner-scoping, что `contactRequests` (этап 24); version(1)'s голый
`id` был пробелом для мультиаккаунта (два владельца на одном
устройстве схлопнули бы pending-запросы в одну строку) — тем же
классом, что уже был исправлен для contactRequests, просто раньше не
замечен, т.к. таблица не использовалась.

### 5. `deletions.js` — удаление DM (kind 5 логически, физически — маркер поверх уже существующего kind 445 канала)

`validateDeletion` (этап 22, `e`-тег по id конкретного regular-kind
события) НЕ подходит буквально: `messages`-строка одного и того же
логического сообщения может быть материализована ЛИБО из kind 445
(живой путь), ЛИБО из kind 446 (зеркало) — `event.id` НЕ тождественен
между путями (то же основание, что и `msgId`-дедупликация, раздел 3).
Публичный, нешифрованный kind 5 с `e`-тегом на конкретный
kind-445-event тоже раскрывал бы метаданные (`h`-тег, участников) — то,
что MLS-конверт специально скрывает.

Решение — переиспользовать УЖЕ существующий зашифрованный канал
(kind 445, `sendMessage`/`receiveGroupMessageEvent`, этап 24) как
транспорт для delete-запроса, БЕЗ правки `chat.js`: `text`-поле
application-message несёт зарезервированный маркер вместо обычного
текста:

```
buildDeletionText(msgId)  = "__ugolok_delete__:" + msgId
parseDeletionText(text)   = text без префикса, если он есть, иначе null
```

`deleteMessage(...)` вызывает уже готовый `chat.sendMessage(...)` с
таким текстом (никакого нового kind/tags/шифрования — весь
криптографический путь этапа 24 переиспользуется буквально) и
синхронно помечает СВОЮ локальную строку (`deleted:true, text:""`) —
не дожидаясь подтверждения доставки (UX «Сообщение удалено» мгновенно
на устройстве автора, как в WhatsApp/Telegram).

На приёмной стороне — `applyIncomingDeletionIfMarker(event,
receivedResult)` вызывается ПОСЛЕ `receiveGroupMessageEvent` (в
диспетчере `transport.js`, не внутри `chat.js`): если `receivedResult.
text` — маркер, резолвит `deleterPubkey` из `mlsGroups.get(hTag(event)).
contactPubkey` (тот же способ, что `receiveGroupMessageEvent`
резолвит `contactPubkey` — НЕ параметр, из строки БД) и **авторизует
удаление сравнением `targetRow.senderPubkey === deleterPubkey`** —
прямой аналог `validateDeletion`'s `deleteEvent.pubkey ===
targetEvent.pubkey` (F-EV-08), просто по локально известному
`contactPubkey`, а не по полю самого delete-события (у которого,
помним, `event.pubkey` эфемерен на kind 445 и не годится для этой
проверки — та же находка этапа 24 п.7, "senderPubkey определяется НЕ
из event.pubkey").

**Явное упрощение MVP (не молчаливое):** строка самого
delete-маркера (промежуточное "сообщение" с текстом
`__ugolok_delete__:...`) НЕ удаляется/не скрывается на этом этапе —
остаётся в `messages` как обычная строка с этим текстом. Фильтрация
маркерных строк из отображаемой истории — ответственность UI
(`chat.jsx`, этап 27), не домена; задокументировано как backlog, не
забыто.

### Явное сужение скоупа (по прецеденту предыдущих этапов)

Не в скоупе этого этапа: живой (не bootstrap-only) push нового
устройства в уже открытые старые устройства (раздел 1, зафиксировано
как backlog); windowed/lazy-подгрузка зеркала по конкретному чату
(этап 26, `h`-тег зеркала уже готов для этого); UI управления
устройствами (список "мои устройства", отзыв устройства — не входит,
`knownDevices` пока служебная таблица без экрана); ротация/удаление
устройства как MLS-участника (симметричный "remove" при компрометации
устройства — backlog, тот же класс, что per-device MLS remove из этапа
13 SM-3); UI входящих запросов (`inboxRequests` accept/reject — данные
готовы, экран — этап 27, тот же принцип, что "Запросы" в contacts.jsx);
скрытие маркерных строк удаления в UI (раздел 5).

## Этап 27-довесок-6 — редактирование сообщения (маркер поверх MLS-канала)

Пожелание пользователя, явно названное им сложным — по прецеденту
`deletions.js` (раздел 5 выше), но с ОДНИМ отличием, которого нет у
удаления: удаление идемпотентно (применить дважды — не отличить от
одного раза), а редактирование — нет, сообщение можно поправить
несколько раз, и правки от сети могут прийти в любом порядке
(переподключение, ретраи relay). Это единственное место в задаче с
нетривиальным инвариантом — остальное (обёртки, UI) рутина по
прецеденту.

### Формализация

- У каждого сообщения M есть НЕИЗМЕНЯЕМЫЙ `lamportTs` — позиция в
  хронологии чата (сортировка `getChatHistory`/`loadChatWindow`).
  Редактирование НЕ имеет права его менять — иначе отредактированное
  сообщение "прыгало" бы по ленте, что хуже для UX, чем сам факт
  правки.
- Правка E — событие `(msgId, newText, editLamportTs)`, где
  `editLamportTs` — ОТДЕЛЬНЫЙ тик `nextLamportTick()` в момент отправки
  правки (не переиспользует исходный `lamportTs` сообщения).
- Инвариант LWW (last-writer-wins, register semantics): для сообщения
  M, получившего последовательность правок E_1..E_n В ЛЮБОМ порядке
  доставки, итоговый видимый текст равен тексту правки с МАКСИМАЛЬНЫМ
  `editLamportTs` среди уже применённых — сходимость не зависит от
  порядка прихода (свойство CRDT LWW-register, тот же класс, что уже
  используется в проекте для `profiles`/kind-0, только здесь СВОЙ
  компаратор, т.к. kind 445 не replaceable на уровне relay).
- Хранение: новое поле строки `messages.editedAt` (последний
  ПРИМЕНЁННЫЙ `editLamportTs`, `undefined` пока правок не было) +
  `messages.edited: true` (косметика UI — пометка "изменено").
  `lamportTs` строки не трогается.
- Применение правки E на строку с текущим `editedAt = cur`:
  применяется ⟺ `cur === undefined || editLamportTs > cur` (строго
  больше — при РАВНЫХ `editLamportTs` вторая правка отбрасывается;
  коллизия равных тиков возможна только если один и тот же автор
  правит с ДВУХ активных устройств одновременно — мультиустройственное
  редактирование одного сообщения вне скоупа этого пожелания,
  backlog, тот же принцип, что "многоустройственный push", раздел 1).
- Авторизация — тот же паттерн F-EV-08/deletions.js: применяет правку
  ТОЛЬКО автор ОРИГИНАЛЬНОГО сообщения (`targetRow.senderPubkey ===
  editorPubkey`), сравнение по локально резолвленному `contactPubkey`
  из `mlsGroups`, не по `event.pubkey` (эфемерен на kind 445).
- Граничные случаи (оба — по прямому прецеденту deletions.js, тот же
  класс уже принятого ограничения, не расширяется):
  - Правка на уже удалённое сообщение (`targetRow.deleted === true`) —
    отклоняется.
  - Правка, доставленная РАНЬШЕ оригинала (`targetRow` не найден) —
    тихо отбрасывается (тот же принцип, что `applyIncomingDeletionIfMarker`
    делает для `!targetRow`).
- Локальное (авторское) применение — ОПТИМИСТИЧНО и синхронно, не
  дожидаясь подтверждения доставки (тот же UX-паттерн, что `deleteMessage`).

### Псевдокод ядра (единственная функция с нетривиальным инвариантом)

```
function applyEdit(targetRow, editorPubkey, newText, editLamportTs):
    if targetRow is None: return false          # правка раньше оригинала
    if targetRow.deleted: return false           # нельзя редактировать удалённое
    if targetRow.senderPubkey != editorPubkey: return false   # F-EV-08
    if targetRow.editedAt is not None and targetRow.editedAt >= editLamportTs:
        return false                              # LWW: устаревшая правка, игнорируется
    targetRow.text = newText
    targetRow.edited = true
    targetRow.editedAt = editLamportTs
    return true
```

Обвязку (сериализация маркера, поиск строки по `[ownerPubkey+chatId+msgId]`,
локальное оптимистичное применение, вызов из диспетчера `transport.js`)
пишет Claude напрямую (не воркер) — те же основания, что и для
`deletions.js`: файл несёт авторизационную логику поверх
криптографического канала, ошибка здесь не поймается тестами
поверхностно, а мигрирует в протокольный баг.

### Явное сужение скоупа

Не в скоупе: мультиустройственное редактирование одного сообщения
(коллизия равных `editLamportTs`, см. выше); правка, прибывшая раньше
оригинала (тот же класс ограничения, что уже принят для delete);
применение правок в `syncMirroredHistory` (mirror/multi-device catch-up,
этап 25) — та же уже принятая граница, что и `applyIncomingDeletionIfMarker`
сейчас применяется ТОЛЬКО в живом пути `refreshGroupMessageSubscription`,
не в мультиустройственном зеркале.

## Этап 28 — Автомат transfer (TECH.md §9.4)

По прямому указанию "Уроки предыдущих этапов" (PLAN.md): все 4 конечных
автомата TECH.md §9 формализуются ДО кода и тестируются на КАЖДЫЙ
недопустимый переход, даже когда состояний мало — transfer (5 состояний)
не исключение, несмотря на тривиальность.

### Формализация

Множество состояний `S = {idle, encrypting, uploading, completed, failed}`.
Множество событий `E = {START, ENCRYPTED, UPLOADED, ERROR, RETRY}`.
Функция перехода `δ: S × E → S`, ЧАСТИЧНАЯ (не определена для большинства
пар — недопустимый переход обязан бросать, не быть no-op и не молча
оставаться в текущем состоянии, тот же принцип, что генерик-движок
`core/fsm/machine.js` уже даёт через `transition()`).

Ровно 5 определённых пар (буквально TECH.md §9.4, без добавлений):

```
δ(idle,       START)     = encrypting
δ(encrypting, ENCRYPTED) = uploading
δ(uploading,  UPLOADED)  = completed
δ(uploading,  ERROR)     = failed
δ(failed,     RETRY)     = encrypting
```

`completed` — терминальное состояние (нет исходящих рёбер вообще, как
`read`/`discarded` в message-machine, этап 24).

**Явно НЕ формализуется (сознательная граница, не пробел):** переход
`encrypting + ERROR → failed` в спецификации ОТСУТСТВУЕТ — TECH.md §9.4
не предусматривает явного события "шифрование не удалось". Это
согласуется с прецедентом message-machine: сам FSM — чистая функция
состояния передачи протокола, а не универсальный обработчик всех
исключений вызывающего кода. Если `encryptFile` бросает синхронно
(редкий случай — недоступен Web Crypto/недостаточно памяти), вызывающий
код (`upload.js`/будущий UI этапа 29) ловит исключение СВОИМ try/catch
и решает, что делать (например, оставить state в `idle`, показать
ошибку, не вызывая `transitionTransfer` вовсе) — FSM не обязан покрывать
путь, которого нет в спецификации; расширение выходило бы за рамки
"буквально как в TECH.md", тот же принцип, что message-machine.test.js
формулирует явно ("ровно N валидных переходов, буквально как в
спецификации").

### Инвариант для тестов

Исчерпывающий перебор всех `|S| × |E| = 25` пар (state, event): ровно
5 бросают `false` (т.е. НЕ бросают — валидны), ровно 20 обязаны
бросать. Прямой прецедент `tests/messaging-machine.test.js` (36 пар,
6 валидных/30 невалидных) — тот же тестовый шаблон, только меньше
состояний.

### Псевдокод (тривиален, но фиксируется для воркера)

```
TRANSFER_TRANSITIONS = {
  idle:       { START: "encrypting" },
  encrypting: { ENCRYPTED: "uploading" },
  uploading:  { UPLOADED: "completed", ERROR: "failed" },
  failed:     { RETRY: "encrypting" }
  // completed отсутствует как ключ вовсе -> любое событие в completed бросает
}

function transitionTransfer(state, event):
    return transition(TRANSFER_TRANSITIONS, state, event)  // core/fsm/machine.js, этап 14
```

Обвязку (файл `transfer-machine.js`, буквальное переложение таблицы
выше + вызов уже существующего generic `transition()`) пишет воркер —
рутинная механическая работа по уже formalized таблице, тот же
паттерн, что `domain/messaging/machine.js`.

## Этап 30 — Каналы: создание + группы-видимость + VIEW/подписка

Пожелание пользователя, расширяющее исходный TECH.md §4.7 (ключи
каналов + comment allowlist) до полного UX: видимость по группам
контактов, различение "Доступные"/"Подписки", навигация. Архитектура
подтверждена пользователем — существующая relay-broadcast модель
(TECH.md §4.7.1/4.7.2), НЕ звёздчатая топология из его референсной
спецификации (см. CONTRACTS.md за объяснением конфликта).

### Формализация 1 — найденный пробел: распространение метаданных канала

TECH.md §10/§4.8 буквально: kind 30060 (метаданные канала) — "NIP-44
для себя", читает ТОЛЬКО владелец. Это была модель "локальный индекс
своих каналов для мультиустройственной синхронизации владельца" (тот
же принцип, что kind 30070/30071/30072 — все "для себя"). Но теперь
нужно, чтобы ЧУЖИЕ VIEW-получатели тоже видели название/описание/
правила/аватар канала (иначе "Доступные"/"Подписки" нечего
отображать) — буквальная схема TECH.md этого не даёт.

**Решение (правка контракта, найдено рассуждением до кода, не
доменом):** kind 30060 шифруется НЕ "для себя", а `channelKey[v_current]`
— тем же способом, что посты (F-CH-03, версионированный конверт
`base64(uint32BE(v) ‖ nonce(12) ‖ ChaCha20-Poly1305(...))`). Событие
остаётся replaceable (NIP-01, d-tag = UUID канала) — владелец может
переиздать его в любой момент (переименование канала, смена аватара)
БЕЗ повторной раздачи ключей всем читателям: у них уже есть
`channelKey[v_current]`, они просто перечитывают событие с relay.
kind 30053 (per-reader грант) при этом несёт ТОЛЬКО ключевой материал
`{channelId, channelTopic, channelKey}` — не метаданные: единственный
источник истины для имени/описания/правил/аватара — kind 30060,
не дублируется. Апдейт TECH.md-контракта: 30060 переходит из "NIP-44
для себя" в "ChaCha20-Poly1305(channelKey[v])" — та же строка таблицы
§10, что 30061/30062.

### Формализация 2 — VIEW vs COMMENT: что даёт "видимость по группам"

При создании канала владелец выбирает контакт-группы → раскрываются в
список pubkey (объединение членов всех выбранных групп, дедуп) →
КАЖДОМУ отправляется kind 30053 (VIEW-грант, F-CH-04). Если группы не
выбраны — грантов ноль, канал существует только локально у владельца
("заметочник", буквально по ТЗ пользователя) — не отдельный код-путь,
просто пустой список получателей.

Получив VIEW (kind 30053), клиент читателя:
1. Персистит `channelKey[v]` + `channelTopic` локально, создаёт
   локальную запись канала с `role: "available"`.
2. Может СРАЗУ читать посты/комментарии (расшифровать может — есть
   ключ) — буквально по ТЗ: "ознакомиться с содержимым, почитать
   комментарии... писать не может".
3. НЕ может комментировать/писать в чат канала, пока его pubkey не
   попадёт в comment allowlist (kind 30054, F-CH-05) — это
   криптографически проверяется получателями (§4.7.2), не UI-заглушка.

**Переход available → subscriber ("Подписаться"):** читатель
отправляет запрос на COMMENT-доступ владельцу (новый rumor kind,
gift-wrap — тот же паттерн, что contact-request, kind 3001).
Владелец, получив запрос, **автоматически** (без второго
подтверждающего клика в UI — group-видимость уже была осознанным
решением владельца допустить ИМЕННО этих людей) добавляет pubkey
заявителя в allowlist и переиздаёт kind 30054 с новой версией списка
(НЕ новая эпоха channelKey — ротация ключа нужна только для REVOKE
VIEW, добавление COMMENT-права не требует менять channelKey вообще,
F-CH-05 буквально: "при назначении COMMENT: дополнительно
перевыпускается kind 30054... без нового channelKey"). Получив
обновлённый allowlist, где обнаруживает СЕБЯ — читатель локально
помечает роль `role: "subscriber"`, канал переезжает из "Доступные" в
"Подписки" (чисто локальный UI-эффект, не отдельное сетевое событие).

**Новый kind (rumor, gift-wrap kind 1059, тот же принцип, что
contact-request 3001):** `CHANNEL_SUBSCRIBE_REQUEST_KIND = 3002`.
Содержимое rumor — `{channelId}`. Подписан заявителем, gift-wrap для
владельца — владелец узнаёт, КТО просит (через `seal.pubkey`/rumor,
как и везде в NIP-59), релей не видит содержимого запроса.

### Формализация 3 — инвариант L-07 (эпохи ключа, из TECH.md, не меняется)

Тот же принцип, что уже в TECH.md §4.7.1: `v_current` — монотонно
растущий счётчик версии `channelKey`. Отзыв VIEW у читателя ⇒
`v_current += 1`, новый `channelKey[v_current]`, новый allowlist[v_current]
БЕЗ отозванного, kind 30053 рассылается ТОЛЬКО оставшимся читателям.
Инвариант: отозванный читатель, уже скачавший события эпох `≤
v_revoke`, СОХРАНЯЕТ к ним доступ (ключи эпох он не выбрасывает) —
но новых `channelKey` (эпох `> v_revoke`) не получает и не может
расшифровать новый контент. **Отзыв VIEW — не в скоупе этого этапа**
(нет UI для "убрать группу из видимости после создания") — сама
модель (versioned `channelKeys` таблица, `keyVersion`-индекс) уже
корректно поддерживает будущий revoke без правки схемы.

### Модель данных (owner-scoping — найдено рассуждением ДО кода, по прецеденту этапов 25-27)

`channels`/`channelKeys`/`channelKeyMeta`/`commentAllowlists` в схеме
`db.version(1)` (TECH.md §10) объявлены БЕЗ `ownerPubkey` в индексе —
тот же класс пробела, что уже был найден и исправлен для
`messages`/`mlsGroups`/`ownKeyPackage`/`chatSyncState` (этапы 25-27):
при мультиаккаунте на одном устройстве второй локальный аккаунт видел
бы чужие каналы/ключи. Эти таблицы НИКОГДА не использовались кодом
(объявлены, не заполнялись) — правка схемы БЕЗ риска миграции данных.
`db.version(5)` переопределяет их с `ownerPubkey` в составном индексе,
по прямому прецеденту `db.version(4)`. `channelTopics` (отдельная
таблица `channelId→topic`, TECH.md §10) сворачивается В `channels`
(поле `channelTopic` там же, с собственным индексом) — та же
информация, не нужна отдельная таблица: прямой запрос "мои
channelTopics" уже даёт `channels.where('ownerPubkey').equals(...)`,
обратный запрос "topic → канал" — по индексу `channelTopic`.

```js
channels: "[ownerPubkey+id], ownerPubkey, channelTopic",
// value: { channelId, creatorPubkey, name, description, rules,
//          avatar: {sha256,blossomUrl,encryptionKey,mime} | null,
//          channelTopic (hex), role: "owner"|"available"|"subscriber",
//          createdAt }
channelKeys: "[ownerPubkey+channelId+keyVersion], [ownerPubkey+channelId]",
// value: { channelKey (hex) }
channelKeyMeta: "[ownerPubkey+channelId]", // value: { currentVersion }
commentAllowlists: "[ownerPubkey+channelId+keyVersion], [ownerPubkey+channelId]",
// value: { allowedAuthors: [pubkey,...] } — верифицированный кэш ПОСЛЕ проверки подписи
```

### Псевдокод (только нетривиальные функции)

```
function decryptChannelContent(base64Content, channelKeysByVersion):
    bytes = base64decode(base64Content)
    v = readUint32BE(bytes[0:4])
    nonce = bytes[4:16]
    ciphertext = bytes[16:]
    key = channelKeysByVersion[v]
    if key is None: return None   // эпоха неизвестна — не наша (никогда не было VIEW) или ещё не эта версия
    return ChaCha20Poly1305Decrypt(ciphertext, key, nonce)

function verifyCommentAuthor(commentEvent, allowlistForVersion, channelOwnerPubkey, allowlistEventPubkey):
    if allowlistEventPubkey != channelOwnerPubkey: return false   // allowlist не владельцем подписан
    return commentEvent.pubkey in allowlistForVersion.allowedAuthors

function handleIncomingSubscribeRequest(currentAllowlist, requesterPubkey):
    // владелец: добавление в allowlist той же эпохи (COMMENT не ротирует channelKey)
    if requesterPubkey in currentAllowlist.allowedAuthors: return currentAllowlist  // идемпотентно
    return { ...currentAllowlist, allowedAuthors: [...currentAllowlist.allowedAuthors, requesterPubkey] }
```

## Этап 31 — Посты + комментарии + lazy-load канала

TECH.md §9.2 (автомат поста) + §5.9 (F-CH-03/07/08/09/10) + §4.7.2
(F-EV-06, allowlist-верификация комментариев). Триаж 13a: автомат
поста формально маленький (3 состояния), но взаимодействие с
broadcast/replaceable-семантикой Nostr нетривиально — формализуется
здесь, не оставляется на интуицию воркера. Комментарии — верификация
авторства уже полностью спроектирована в этапе 30
(`comment-allowlist.js`), здесь только применение к реальным kind 30062.

### Формализация 1 — автомат поста и его отображение на broadcast-модель

Буквально TECH.md §9.2:
```
States:    {draft, published, archived}
Events:    {PUBLISH, ARCHIVE, UNPUBLISH}
Initial:   draft
Final:     {archived}
Transitions:
  draft     + PUBLISH   → published
  published + ARCHIVE   → archived
  published + UNPUBLISH → draft
```

**Найденный вопрос, требующий решения (не в буквальном тексте
TECH.md):** kind 30061 — параметризованно-replaceable (диапазон
30000-39999, NIP-01) с d-tag `{channelId}:{postId}`. Что означают
переходы ARCHIVE/UNPUBLISH на уровне СЕТИ, если контент уже был
разослан relay'ем всем VIEW-держателям?

**Решение:** статус — ЧАСТЬ синхронизируемого payload'а поста (не
только локальное поле), а не отдельное сетевое действие:
- `draft`: строго ЛОКАЛЬНОЕ состояние, НИКАКОЕ событие не публикуется
  вообще — черновик не должен утекать на relay до первого PUBLISH.
- `PUBLISH`: шифрует и публикует kind 30061 с `{text, attachments,
  status:"published"}` в payload'е. d-tag тот же на весь жизненный
  цикл поста — republish с тем же d-tag ЗАМЕНЯЕТ предыдущую версию у
  relay (NIP-01 replaceable) и у всех, кто её перечитывает.
- `ARCHIVE`/`UNPUBLISH`: republish ТОГО ЖЕ d-tag с обновлённым
  `status` ("archived"/"draft" соответственно) — единственный способ
  донести смену статуса до подписчиков, раз событие уже разошлось.
  Подписчики обязаны трактовать `status !== "published"` как "не
  показывать в основной ленте" (архив — отдельная вкладка/фильтр,
  draft чужого автора — не показывать вообще, это не про меня).

**Присущее ограничение (раскрывается пользователю, не прячется — тот
же принцип, что §4.7.3 для forward secrecy каналов):** "unpublish" —
конвенция клиента, не крипто-гарантия. Любой VIEW-держатель, уже
скачавший событие ДО того, как статус сменился на `draft`, технически
способен расшифровать контент прежней версии (channelKey у него уже
есть) — Nostr не даёт настоящего "отозвать из сети". Честные клиенты
перестают ПОКАЗЫВАТЬ, не гарантируют исчезновение данных отовсюду.
Аналогично kind 5 (NIP-09, F-CH-10, полное удаление) — relay МОЖЕТ
проигнорировать запрос на удаление, это уже известное и принятое
ограничение самого протокола Nostr, не новая находка этого этапа.

### Формализация 2 — найденная адверсарная угроза: авторство ПОСТА

TECH.md явно формализует защиту от подделки КОММЕНТАРИЕВ (F-EV-06,
allowlist) и allowlist-события (F-EV-07), но НЕ formalises защиту от
подделки самого ПОСТА. Рассуждение: kind 30061 шифруется
`channelKey[v]` — ЛЮБОЙ VIEW-держатель (не только владелец!) технически
способен зашифровать валидный, полностью расшифровываемый kind 30061 с
тем же `#h`-тегом топика. Без дополнительной проверки злонамеренный
подписчик мог бы "опубликовать статью от имени владельца канала" —
подделка через тот же канал шифрования, но не полномочие писать
(только владелец пишет статьи, F-CH-03/по ТЗ пользователя — "публикует
только владелец").

**Правка (найдено рассуждением ДО кода, тот же класс, что F-EV-06/07):**
`receivePost` обязан проверять `event.pubkey === channelRow.creatorPubkey`
(уже хранится локально с этапа 30) — событие НЕ от создателя канала
отбрасывается, независимо от того, что оно корректно расшифровывается.
Тот же принцип верификации, что F-EV-07 уже применяет к kind 30054.

### Формализация 3 — дерево комментариев и верификация авторства (F-EV-06)

`parentId` комментария — ЛИБО `postId` (комментарий верхнего уровня),
ЛИБО `commentId` другого комментария (ответ, вложенность). Дерево
строится рекурсивно на клиенте из плоского списка (`buildTree`,
группировка по `parentId`) — не хранится предвычисленным, дёшево для
объёма одного поста.

Верификация на приёме (буквально §4.7.2, шаги 1-5, уже реализованные
в `comment-allowlist.js` этапа 30 — этот этап только ПРИМЕНЯЕТ их к
реальным kind 30062):
```
on receive(event kind 30062):
    channelRow = найти по event #h-тегу (topic)
    if channelRow is None: discard   // не наш канал
    decrypted = decryptChannelContent(event.content, ownKeys[channelRow.id])
    if decrypted is None: discard    // неизвестная эпоха
    allowlist = локальный кэш commentAllowlists[channelRow.id][текущая версия]
              // уже верифицирован НА ПРИЁМЕ kind 30054 этапом 30 — здесь
              // просто читаем закэшированный allowedAuthors, не парсим заново
    if not canAuthorComment(event.pubkey, allowlist): discard  // F-EV-06
    upsert comments-строка
```
**Явно НЕ проверяется здесь заново** подпись самого allowlist-события
(kind 30054) — она уже верифицирована `receiveAllowlistUpdate` (этап
30) ДО того, как результат попал в локальный кэш `commentAllowlists`;
повторная проверка на каждый комментарий была бы избыточной работой
над уже доверенными локальными данными.

### Модель данных — owner-scoping (найдено рассуждением, тот же класс, что этап 30)

`posts`/`comments` в `db.version(1)` объявлены БЕЗ `ownerPubkey`
(`posts: "id, [channelId+created_at]..."`, `comments:
"[authorPubkey+commentId]..."`) — тот же класс пробела, что уже
исправлен для messages/mlsGroups/.../channels (этапы 25-27, 30).
Никогда не использовались кодом — переопределение (`db.version(6)`)
без риска миграции.

```js
posts: "[ownerPubkey+id], [ownerPubkey+channelId+createdAt], deleted",
// value: {ownerPubkey, id (postId), channelId, authorPubkey, text,
//         attachments: [], status: "draft"|"published"|"archived",
//         keyVersion, createdAt, deleted}
comments: "[ownerPubkey+id], [ownerPubkey+postId], deleted",
// value: {ownerPubkey, id (commentId), postId, parentId, channelId,
//         authorPubkey, text, attachments: [], keyVersion, createdAt, deleted}
```
Сортировка ленты — по `createdAt` (простая хронология одного автора
для постов; для комментариев `createdAt` — самозаявленное время
события, строгий Lamport-порядок здесь не нужен — не приватный 1:1
разговор с причинными гарантиями, публичный тред достаточно
сортировать по времени публикации, тот же уровень строгости, что
большинство Nostr-клиентов уже принимают для kind 1).

### Явное сужение скоупа

Не в скоупе: экран канала полностью (владелец-only вкладки
"Управление"/"Модерация" — этапы 32-33); общий чат канала (этап 32);
редактирование уже опубликованного поста ОТДЕЛЬНО от статусных

UI-функция "редактировать текст" — backlog, PUBLISH после UNPUBLISH

одного комментария (F-CH-10 покрывает и посты, и комментарии
одинаково, но UI на удаление комментария — backlog, только пост
получает кнопку в этом этапе).

## Этап 33 — Модерация: жалобы + бан + игнор + rate-limiting

Триаж: алгоритмическая задача (PLAN.md) — состояния бана/игнора и
видимость контента после каждого перехода нетривиальны, формализуются
здесь ДО кода. Оригинальное ТЗ пользователя ("v0.1", звёздчатая
топология, владелец = relay-хаб) описывало бан буквально как "перестать
релеить" — тривиально в топологии, где владелец физически стоит на
пути каждого сообщения. В нашей архитектуре (relay-broadcast,
end-to-end channelKey) такого центрального узла нет — бан нужно
формализовать заново на терминах уже принятой крипто-модели (VIEW/
COMMENT, channelKey[v], F-CH-06 revoke), это и есть содержание этого
раздела.

### Найденный протокольный барьер: владелец НЕ может удалить чужое событие

NIP-09 (уже реализовано в проекте, `validateDeletion`,
`domain/events/handlers.js:75`): `deleteEvent.pubkey ===
targetEvent.pubkey` — удалить событие может ТОЛЬКО его автор.Бан
владельцем канала не даёт ему права стереть комментарии/сообщения
чата забаненного участника через kind 5 — это фундаментальное свойство
протокола, не пробел реализации. **Следствие:** "удаление всего его
контента" (буквально из ТЗ) не может быть криптографической/сетевой
операцией — реализуется как ЛОКАЛЬНОЕ скрытие на КАЖДОМ честном
клиенте по broadcast-сигналу от владельца (см. ниже), не подделка
чужой подписи. Нечестный клиент, не уважающий сигнал, всё равно не
получает НИЧЕГО нового от забаненного благодаря ротации ключа (см.
следующий пункт) — два независимых рубежа: крипто-доступ (жёсткий,
навязать нельзя обойти) и локальная видимость уже полученного (мягкий,
best-effort, как и весь остальной "for me" контент проекта).

### Состояния доступа (формализация 1)

Отношение `access(channel, pubkey) ∈ {none, view, subscriber, banned}`
(banned — терминальное, без исходящих переходов в этом этапе — "разбан"
не в ТЗ и не реализуется). Переход, релевантный этому этапу:

```
{view, subscriber} --BAN(владелец)--> banned
```

Побочные эффекты BAN (владелец, единственный кто может его выполнить —
проверка `event.pubkey === channelRow.creatorPubkey` на приёме,
симметрично receivePost/receiveComment):
1. `v_new = v_current + 1`, новый `channelKey[v_new]` (F-CH-06
   буквально).
2. Переиздать kind 30053 (VIEW) для ВСЕХ читателей канала КРОМЕ
   забаненного. Требует знать полный список читателей — **найденный
   пробел этапа 30**: `createChannel` вычисляет `readerPubkeys` как
   ЛОКАЛЬНУЮ переменную для однократной раздачи грантов, нигде не
   сохраняя список. Без него бан не может корректно переиздать ключ
   оставшимся. Правка (аддитивная, не меняет контракт этапа 30):
   новая таблица `channelReaders` — `createChannel` теперь ТАКЖЕ
   персистит `{ownerPubkey, channelId, readerPubkey}` на каждого
   читателя из group-snapshot, рядом с уже существующей отправкой
   гранта.
3. Если у забаненного было COMMENT — переиздать kind 30054 (allowlist)
   версии `v_new` без него (переиспользует `buildAllowlistEvent`,
   уже принятый в этапе 30).
4. Опубликовать НОВЫЙ kind 30064 ("ban-announcement", parameterized-
   replaceable, d-tag=`${channelId}:ban:${targetPubkey}`, тег `h`) —
   контент шифруется `channelKey[v_OLD]` (не v_new!) — это ЕДИНСТВЕННЫЙ
   способ, которым забаненный участник (у него больше НЕТ v_new) тоже
   сможет прочитать объявление о собственном бане, раз оно приходит
   тем же broadcast-каналом, что и всё остальное. Все ОСТАВШИЕСЯ
   читатели тоже имеют v_old в локальном кэше (историчные эпохи не
   удаляются, тот же принцип, что уже принят в § 4.7.3 TECH.md) —
   декодируют без проблем.
5. Локально у владельца: `bannedMembers` (запись), удаление
   `targetPubkey` из `channelReaders`.

**Почему это ДОСТАТОЧНО без правки decrypt-пути.** `receiveComment`/
`receiveChannelMessage` уже декодируют ТОЛЬКО через
`meta.currentVersion` (не перебирают все исторические ключи) —
найдено чтением кода, не домыслом. Значит: после ротации
ВСЕ текущие читатели используют `v_new` как current; любое НОВОЕ
сообщение забаненного (зашифрованное единственным известным ему
ключом `v_old`) для них не расшифруется вовсе (`decryptChannelContent`
вернёт `null` — неизвестная версия) и будет отброшено ДО проверки
allowlist. Крипто-рубеж закрывает "написать новое" полностью, без
дополнительного explicit-check "автор забанен".

### Приём kind 30064 (`receiveBanAnnouncement`) — видимость после каждого перехода

1. `h`-тег → `channelRow` (как везде); неизвестен → discard.
2. Собрать ВСЕ локально известные версии `channelKeys[ownerPubkey,
   channelId,*]` в map `{version: keyHex}` (не только current — единственное
   место в этом этапе, где нужны ИСТОРИЧЕСКИЕ ключи, поскольку
   объявление шифруется `v_old`, который уже не current) →
   `decryptChannelContent(content, versionsMap)` → `null` → discard
   (никогда не имел доступа к этой эпохе — рутинный случай, не
   исключение, тот же принцип, что везде).
3. `event.pubkey !== channelRow.creatorPubkey` → discard (F-EV-07-класс
   — не владелец не может банить, объявление подделано).
4. `parsed.targetPubkey === ownerPubkey` (я сам забанен) → удалить
   ЛОКАЛЬНО канал целиком: строку `channels`, все `posts`/`comments`/
   `channelMessages`/`channelKeys`/`channelKeyMeta`/
   `commentAllowlists`/`channelReaders`/`channelIgnores` этого
   `channelId` у СЕБЯ. "Уведомление" (ТЗ) — сам факт исчезновения
   канала из списка при следующем рендере (`messagingActivity` уже
   бампается диспетчером), отдельного toast не требуется — экран
   `ChannelDetail`, если он был открыт на этом канале, обязан отличать
   "канал ещё грузится" от "канала больше нет" (см. ниже, UI).
5. Иначе (я не забаненный) — локально пометить `deleted:true` во ВСЕХ
   строках `comments`/`channelMessages` этого канала, где
   `authorPubkey === parsed.targetPubkey` (мягкое, best-effort скрытие
   уже полученного контента — единственный доступный владельцу рычаг,
   см. найденный барьер выше). Также upsert `bannedMembers` (у ВСЕХ
   получателей, не только владельца — дешёвая, но полезная запись:
   отфильтровать забаненного из будущих локальных списков без
   повторного вывода из allowlist).

### Игнор (формализация 2) — чисто локальный, необратимый в этом этапе

`ignored(viewerPubkey, channelId, targetPubkey)` — булево отношение,
хранится ТОЛЬКО локально (`channelIgnores`), никогда не передаётся по
сети как таковое (только КОСВЕННО — см. авто-репорт ниже). Переход
`false → true` доступен любому участнику через кнопку у конкретного
сообщения/комментария; обратного перехода `true → false` в UI НЕТ ни
для кого в этом этапе (ТЗ: "снять может только владелец" — буквально
нереализуемо в модели, где игнор живёт в приватном IndexedDB другого
человека: у владельца физически нет доступа к чужому локальному
состоянию, чтобы его "снять". Явное сужение скоупа: разбан игнора —
backlog, требует отдельного сетевого механизма "запрос на снятие",
не специфицированного пользователем). Видимость: `loadCommentsWindow`/
`loadChannelChatWindow` дополнительно фильтруют строки, чей
`authorPubkey` есть в `ignored(мой pubkey, channelId, ·)` — фильтр
применяется ТОЛЬКО у смотрящего, автор и остальные участники не видят
разницы.

### Авто-репорт при игноре и явная жалоба — один канал доставки

Оба — gift-wrap (kind 1059) рюмор нового kind `CHANNEL_REPORT_KIND =
3003` (прецедент: `CHANNEL_SUBSCRIBE_REQUEST_KIND = 3002`), адресован
ЛИЧНО владельцу канала — не транслируется остальным участникам (жалоба
приватна между жалующимся и владельцем, буквально по ТЗ: "жалоба
отображается У ВЛАДЕЛЬЦА"). Тег `reason` различает `"report"` (явная
жалоба) от `"ignore"` (авто-репорт) — оба несут одинаковый контекст
(`content_type`, `content_id`, текст сообщения/комментария), панель
модерации показывает оба вида в одном списке (буквально по ТЗ:
"список отчётов о жалобах И игнорах"). Владелец хранит их локально
(`channelReports`) после `nip59Unwrap` — не re-broadcast, не
verification цепочка сложнее, чем уже есть у `CHANNEL_SUBSCRIBE_
REQUEST_KIND` (unwrap уже даёт аутентичного отправителя).

### Rate limiting (формализация 3, тривиальная)

Не автомат в строгом смысле — монотонный guard: `tryAction(actionType,
now)`: если `now - lastActionAt[actionType] < 5000` → `false`
(отклонить), иначе записать `now` и вернуть `true`. Инвариант:
для любого actionType два последовательных успешных вызова разделены
≥ 5000мс. "Живёт как актор, спавнится/убивается" (ТЗ, из
star-topology-мира с явными акторами) — адаптация: обычный JS-объект,
созданный `useState(() => createRateLimiter())` при монтировании
`ChannelDetail`, выбрасывается при размонтировании (React/Preact
lifecycle уже даёт ровно то же самое, отдельного actor-фреймворка не
требуется — ещё одна сознательная архитектурная адаптация ТЗ).

### Схема БД — `db.version(8)`

```js
channelReaders: "[ownerPubkey+channelId+readerPubkey], [ownerPubkey+channelId]",
channelReports: "[ownerPubkey+id], [ownerPubkey+channelId], viewed",
channelIgnores: "[ownerPubkey+channelId+ignoredPubkey], [ownerPubkey+channelId]",
bannedMembers: "[ownerPubkey+channelId+pubkey], [ownerPubkey+channelId]",
```

`channelMessages` не меняет первичный ключ (аддитивно) — получает
поле `deleted` (не индексируемое, как `attachments` у постов/
комментариев не индексируется; фильтрация — в памяти, тот же паттерн,
что `loadPostsWindow`/`loadCommentsWindow` уже используют для своего
`deleted`).

### Явное сужение скоупа

"Массовая рассылка предупреждений" (буквально из первого сообщения
ТЗ, "отправить предупреждения нарушителям, причём в массовом порядке")
— отдельная от бана функция, не в этом этапе (бан уже покрывает
основной защитный сценарий; предупреждение без бана — backlog, нужен
ещё один тип уведомления и UI для массового выбора получателей).
Разбан (снятие бана) и снятие игнора владельцем — backlog (см. выше).
Владелец банит САМ СЕБЯ — не проверяется отдельно (бессмысленное, но
безвредное действие, если когда-нибудь случится — не специальный
случай).

## Этап 36 — отзыв VIEW при выходе из группы, давшей видимость канала

Алгоритмика (PLAN.md backlog п.1: "эпохи/версии — состояние",
skill правило 13a/13b). Формализация ДО тестов/кода.

### Условие и найденный пробел в существующей модели

`createChannel` (channel.js, этап 30) резолвит `groupIds → pubkeys`
ОДИН РАЗ в момент создания канала и рассылает VIEW (`channelReaders`)
этому снимку — само множество `groupIds`, которое дало видимость,
НИГДЕ не персистируется после создания (уже задокументированный,
принятый на этапе 31 снимок "не ретроактивен", см. CONTRACTS.md).
Значит `removeGroupMemberAction` (signals/contacts.js) сегодня в
принципе не может узнать, видимость КАКИХ каналов зависела от группы,
из которой только что удалили участника — этой связи нет в БД. Первый
шаг этого этапа — не ротация ключа (та часть уже есть, см.
`banMember`, этап 33), а восполнение утраченной связи "канал ←
множество групп, давших ему видимость при создании".

### Формализация

Множества и отношения:
- `Group` = группы контактов (`groups`/`groupMembers`, уже существуют).
- `Channel` = каналы владельца.
- НОВОЕ отношение `visibilityGroupsOf: Channel → 2^Group` — множество
  групп, использованных при создании канала (снимок САМОГО СПИСКА
  групп фиксирован навсегда после создания; снимок ЧЛЕНОВ каждой
  группы — нет, членство продолжает меняться, ровно это и есть повод
  для отзыва).
- Инвариант доступа (не хранится явно, ВЫЧИСЛЯЕТСЯ по запросу):
  `hasAccess(channel, pubkey) ⟺ ∃ g ∈ visibilityGroupsOf(channel) :
  pubkey ∈ members(g)`.
- `channelReaders` (этап 30/33) — материализованный, потенциально
  УСТАРЕВШИЙ кэш этого предиката (обновляется только в момент
  создания канала и при бане/выходе из группы — НЕ реактивно на
  каждое изменение членства, иначе любое добавление/удаление контакта
  в группе стоило бы O(каналы×читатели) немедленно; вместо этого
  пересчёт — лениво, только в момент `removeGroupMemberAction`).

### Инвариант, который обязан держать `removeGroupMemberAction`

Удаление `pubkey` из `groupId` обязано отозвать VIEW у `pubkey` на
канале `c` **тогда и только тогда**, когда `groupId ∈
visibilityGroupsOf(c)` И после удаления `¬hasAccess(c, pubkey)` (т.е.
не осталось НИ ОДНОЙ другой группы из `visibilityGroupsOf(c)`, где
`pubkey` всё ещё состоит). Если тот же человек виден каналу ещё и
через вторую привязанную группу — отзыва НЕ происходит (иначе доступ
из ТЗ был бы более хрупким, чем задумано: "состоит хотя бы в одной
видящей группе" — дизъюнкция, не конъюнкция).

### Псевдокод (только основной инвариант; обвязка — воркеру по контракту)

```
function revokeIfNoLongerVisible(ownerPubkey, ownerPrivKey, pubkey, removedFromGroupId, publish):
  channels = channelsWhoseVisibilityIncludes(ownerPubkey, removedFromGroupId)
  for channel in channels:
    otherGroups = visibilityGroupsOf(channel) \ {removedFromGroupId}
    stillVisible = exists g in otherGroups where pubkey in members(g)
    if not stillVisible and pubkey in channelReaders(channel):
      revokeViewFromMember(ownerPubkey, ownerPrivKey, channel, pubkey, publish)
```

`revokeViewFromMember` — СТРОГОЕ ПОДМНОЖЕСТВО `banMember` (этап 33):
ротация `channelKey` (v_old→v_new), переиздача VIEW ОСТАВШИМСЯ
`channelReaders` (исключая `pubkey`), удаление `pubkey` из allowlist
той же новой версии (если был), удаление строки `channelReaders`. БЕЗ
бан-специфичных частей: НЕТ `CHANNEL_BAN_KIND`-объявления (это не
модерация, человек не нарушил правил — просто вышел из группы), НЕТ
`bannedMembers`, НЕТ локального скрытия его постов/комментариев (его
контент остаётся видимым тем, кому он остаётся видим по другим
каналам/группам — вышедший из ОДНОЙ группы не "забанен всюду").

### Схема БД — новая таблица (следующий `db.version`)

```js
channelVisibilityGroups: "[ownerPubkey+channelId+groupId], [ownerPubkey+channelId], [ownerPubkey+groupId]"
```

Заполняется ОДИН РАЗ в `createChannel` (аддитивная правка — по одной
строке на каждый groupId из уже существующего параметра `groupIds`,
до этого момента отбрасывавшегося сразу после резолва в pubkeys).
Индекс `[ownerPubkey+groupId]` — обратный поиск "какие каналы зависят
от этой группы", нужен `removeGroupMemberAction` без полного скана
`channels`.

### Явное сужение скоупа

Каналы, СОЗДАННЫЕ ДО этого этапа, не имеют строк в
`channelVisibilityGroups` (таблица пуста для них) — `removeGroupMemberAction`
для такого канала не найдёт ни одной связи и не отзовёт доступ никому.
Это НЕ регрессия: до этого этапа отзыва не было вообще ни для одного
канала — миграция задним числом (реконструкция "какая группа дала
видимость" для уже существующих каналов) невозможна в принципе (сама
информация никогда не сохранялась) и не нужна (dev-стадия, локальная
сеть, без прод-данных, см. CLAUDE.md). Добавление/удаление ГРУППЫ
целиком из уже существующего канала (не член группы, а сама группа
как источник видимости) — вне ТЗ и вне этого этапа, backlog.

## Этап 39 (готовится) — шифрование локальной БД (dbKey), закрытие AC-16

Найдено пользователем живым осмотром IndexedDB через DevTools (не
домысел, не тест — реальный дамп показал `text`, `content`, `name` в
открытом виде): TECH.md прямо требует шифрование всех materialized
views на `dbKey` (F-LE-01/F-LE-02/F-LE-03, NF-07, критерий приёмки
AC-16 — "прямой dump IndexedDB без ключа не выдаёт plaintext"). Крипто-
примитивы существуют с этапа 14 (`db-crypto.js`'s `encryptRow`/
`decryptRow`, ChaCha20-Poly1305) и протестированы изолированно
(`tests/db-crypto.test.js`, `tests/encrypted-table.test.js`), но
`encrypted-table.js`'s `wrapEncryptedTable` (put/get-only обёртка)
НИКОГДА не была подключена ни к одному реальному доменному модулю —
единственный потребитель это diagnostics.jsx-самопроверка. Собственная
запись PLAN.md за этап 14 честно фиксировала это как "будет применено
доменными модулями начиная с этапа 21+" — обещание, которое так и не
было выполнено ни на одном из последующих 24 этапов. Это единственный
пробел в этой сессии, который является не "недоделанной обвязкой"
(как AC-09/AC-06), а полноценным архитектурным решением, требующим
формализации до кода (skill, правило 13a/13b).

### Инвентарь (фоновый агент, аудит всех `db.table(X)` в `src/`, 216 вызовов)

Полный список таблиц и как именно они используются (методы Dexie,
поля в `.where`/`.get`, наличие партиальных `.update()`/`.modify()`)
зафиксирован в CONTRACTS.md, раздел "Этап 39". Ключевой вывод аудита,
меняющий изначальную (более пессимистичную) оценку сложности:

**Инвариант места конфиденциальности.** Dexie строит индексы ТОЛЬКО
по полям, реально присутствующим как top-level свойства хранимого
объекта — ему всё равно, есть ли у объекта ДРУГИЕ поля помимо
индексируемых. Значит шифрование НЕ требует переизобретать Dexie-
запросы (`.where().equals()`, compound-индексы) — достаточно:
1. Разбить каждую строку на `plaintextFields` (индексируемые ПЛЮС
   несекретные enum/флаги/счётчики — `status`, `deleted`, `viewed`,
   `role`, `currentVersion` и т.п., не являющиеся пользовательским
   контентом) и `sensitiveFields` (всё остальное — реальный текст).
2. `sensitiveFields` целиком уходят в один blob `{nonce, ciphertext}`
   (та же форма, что уже даёт `encryptRow`).
3. Любой существующий вызов `.where(индекс).equals(...).toArray()`/
   `.get(key)`/`.delete(...)`/`.bulkDelete(...)` — РАБОТАЕТ БЕЗ
   ИЗМЕНЕНИЙ, потому что оперирует только plaintext-полями. Delete
   вообще не требует расшифровки НИКОГДА (можно удалить непрочитанный
   blob по индексу).
4. Партиальные `.update()`/`.modify()`, где изменяемое поле —
   `plaintextFields` (статус/флаг/счётчик) — тоже работают БЕЗ
   ИЗМЕНЕНИЙ (поле остаётся настоящим top-level свойством строки, вне
   зашифрованного blob).
5. Партиальные `.update()`/`.modify()`, где изменяемое поле —
   `sensitiveFields` (аудит нашёл ТОЛЬКО 3 таких места во всём
   проекте: `messages.text` при редактировании/удалении, `posts.text`
   при редактировании черновика, `channels.{name,description,rules,
   avatar}` при редактировании метаданных канала) — заменяются на
   явный decrypt→merge→encrypt→put (несколько строк вместо одной
   `.modify()`, но механически одинаково в каждом месте).

Вывод: изначальная оценка "перепишем большую часть кода" была
пессимистична — Dexie-запросы ПОЧТИ ВСЕ переживают шифрование без
изменений; переписать нужно только точки ЗАПИСИ/ЧТЕНИЯ (put/get/
toArray) плюс ровно 3 места партиальных модификаций sensitive-полей.

### Пересмотр контракта `encrypted-table.js`

Было: `wrapEncryptedTable(table, plaintextFields, dbKey)` — объект с
`put`/`get`, требующий обернуть ВЕСЬ table-инстанс. Проблема: реальное
использование гораздо разнообразнее (`.where().toArray()`, `bulkAdd`,
`.first()`, `.and()`) — оборачивать под это целый Dexie Collection API
не нужно и избыточно. Новый контракт — два stateless-хелпера вместо
объекта-обёртки:

```js
export function toEncryptedRow(record, plaintextFields, dbKey);
// -> { ...только поля из plaintextFields, nonce, ciphertext }
// sensitiveFields (все остальные поля record) шифруются ВМЕСТЕ одним
// вызовом encryptRow — не по отдельности, экономия на количестве
// AEAD-вызовов и на размере nonce-оверхеда.

export function fromEncryptedRow(row, dbKey);
// -> { ...plaintext-поля row как есть, ...расшифрованные sensitiveFields }
// row === undefined -> undefined (проброс "не найдено" как есть, не throw)
```

Доменный код продолжает вызывать РЕАЛЬНЫЙ `db.table(X)` напрямую
(никакой инстанс не оборачивается) — просто пропускает объект через
`toEncryptedRow` перед записью и через `fromEncryptedRow` после чтения:

```js
// запись (было): await db.table("messages").add(row);
await db.table("messages").add(toEncryptedRow(row, MESSAGES_PLAINTEXT_FIELDS, dbKey));

// чтение (было): return rows;
const raw = await db.table("messages").where("[ownerPubkey+chatId]").equals([...]).toArray();
return raw.map((r) => fromEncryptedRow(r, dbKey));

// партиал по sensitive-полю (было: .modify({text, edited, editedAt})):
const raw = await db.table("messages").where("[ownerPubkey+chatId+msgId]").equals([...]).toArray();
for (const row of raw) {
  const merged = { ...fromEncryptedRow(row, dbKey), text: newText, edited: true, editedAt };
  await db.table("messages").put(toEncryptedRow(merged, MESSAGES_PLAINTEXT_FIELDS, dbKey));
}
```

### Протяжка `dbKey`

Тот же явный DI-стиль, что уже принят для `privKey` (никаких скрытых
модульных секретов в доменном слое, домен остаётся чисто тестируемым
без импорта сигналов). `dbKey` добавляется НОВЫМ параметром сразу
после `privKey` в сигнатуре каждой затронутой функции — оба всегда
доступны вместе (оба производятся один раз при логине в

только `privKey`). Контракты изменятся у ~15 файлов домена — список
файл-в-файл в PLAN.md/этап 39.

### Влияние на тесты

Каждый тест, который сейчас читает/пишет таблицу НАПРЯМУЮ через

голый объект, если тестируемая функция сама вызывает
`toEncryptedRow`/`fromEncryptedRow` внутри (тест не меняется, только
сигнатура вызова функции получает лишний `dbKey`-аргумент), либо (б)

убедиться, что что-то реально сохранилось) — обязан либо расшифровать
её сам через `fromEncryptedRow`, либо ассертить только на plaintext-
поля (`status`/`deleted`/PK), а факт наличия контента проверять ЧЕРЕЗ
доменную read-функцию (которая уже расшифрует), не через прямой dump.

## Этап 43 — локальный кэш вложений: формализация (13b, алгоритмическая задача)

Нетривиальный инвариант — вытеснение под бюджетом объёма + TTL,
поэтому записка нужна (в отличие от рутинной обвязки самого кэша).

**Вход/выход.** `putCachedAttachment(ownerPubkey, dbKey, sha256Hex, mime,
bytes)` — запись; `getCachedAttachment(ownerPubkey, dbKey, sha256Hex)` —
чтение, `undefined` на промах.

**Инварианты:**

1. **Owner-scoping.** Ключ строки — `[ownerPubkey+sha256]`, не голый
   `sha256`. Без этого — тот же класс бага, что Lamport-часы
   (этап 42-довесок, найдено реальным использованием): два локальных
   аккаунта в одном браузере делят один физический кэш.
2. **Бюджет.** После `putCachedAttachment` суммарный объём (`Σ size`)
   строк ОДНОГО `ownerPubkey` ≤ `budgetBytes`. Вытеснение — часть
   синхронного пути записи, не отложенная фоновая задача (иначе
   бюджет может быть превышен произвольно долго между проверками).
3. **TTL сначала.** Строки с `now - lastAccessedAt > ttlMs` удаляются
   ДО расчёта бюджета — протухшие не должны "защищать" себя от LRU
   тем, что якобы недавно занимали место.
4. **LRU при превышении бюджета.** Сортировка оставшихся строк по
   `lastAccessedAt` по возрастанию, удаление с начала (самые давние
   обращения), пока `Σ size ≤ budgetBytes`. `getCachedAttachment`
   обновляет `lastAccessedAt` на КАЖДОЕ попадание — "посмотрели
   ещё раз" продлевает жизнь строки, это и есть LRU, не просто FIFO
   по времени создания.
5. **Идемпотентность записи.** `put`, не `add` — повторная запись
   того же `[ownerPubkey+sha256]` (например, два разных сообщения
   ссылаются на один и тот же файл) перезаписывает, не дублирует и
   не бросает `ConstraintError`.

**Структура данных.** НЕ отдельный индекс `[ownerPubkey+lastAccessedAt]`
для честного упорядоченного B-tree-обхода — на масштабе личного
мессенджера (не публичный сервис) число закэшированных вложений одного
владельца остаётся низким, `.where('ownerPubkey').equals(...).toArray()`
+ сортировка в памяти по `lastAccessedAt` (`O(n log n)` от количества
закэшированных вложений ОДНОГО владельца — не от размера всей БД)
достаточна и не связывает схему лишним составным индексом.

**Псевдокод (`evictIfNeeded` — единственная функция с нетривиальным
инвариантом, остальное в cache.js — рутинная обвязка `toEncryptedRow`):**

```
function evictIfNeeded(ownerPubkey, budgetBytes, ttlMs):
    rows = SELECT * FROM attachments WHERE ownerPubkey = ownerPubkey
    now = Date.now()

    expired = [r for r in rows if now - r.lastAccessedAt > ttlMs]
    DELETE expired
    rows = rows - expired

    total = sum(r.size for r in rows)
    if total <= budgetBytes: return

    rows.sort(by lastAccessedAt ascending)   // старые обращения — первые кандидаты
    toDelete = []
    for r in rows:
        if total <= budgetBytes: break
        toDelete.append(r)
        total -= r.size
    DELETE toDelete
```

Инварианты 1-5 → тесты `tests/attachment-cache.test.js` (owner-scoping
изоляция, TTL-вытеснение, LRU-вытеснение именно самого старого по
`lastAccessedAt`, touch на чтении продлевает жизнь, идемпотентность
put, `getOrDownloadAttachment` не бьёт в сеть повторно на cache hit).
Псевдокод выше → `--ctx` воркеру буквально при задании на `cache.js`.

### Правка (ревью Claude Opus, до коммита) — честная мотивация + слой в памяти

Формализация выше (owner-scoping/TTL/бюджет/LRU) остаётся верной для
ДИСКОВОГО слоя, но её МОТИВАЦИЯ была неверной — см. CONTRACTS.md,
раздел "Правка": `dbKey`-расшифровка стоит столько же CPU, сколько
расшифровка контентным ключом при обычном скачивании, реального
CPU-выигрыша между "кэш шифротекста" и "кэш плейнтекста под dbKey" нет.
Хуже — попытка провести байты вложения через общий
`toEncryptedRow`/`encryptRow` (JSON + `btoa(String.fromCharCode.apply(...))`
на весь массив разом) **падает `RangeError`** на реалистичных размерах
(проверено: 2 МБ уже бросает, лимиты вложений до 50 МБ) — это была не
просто субоптимальная реализация, а нерабочая. Исправление — прямой
`chacha20poly1305(dbKey, nonce)` поверх сырых байт (тот же примитив,
что `file-crypto.js`, просто dbKey вместо случайного ключа), без
JSON-слоя вообще; `nonce`/`ciphertext` — сырые `Uint8Array`-поля
строки, Dexie хранит их через structured clone нативно.

Настоящая причина воспринимаемых тормозов — `URL.revokeObjectURL` на
каждом размонтировании `attachment-view.jsx`'s компонентов: вложение
переисполняется сеть+расшифровка при КАЖДОМ повторном показе, даже
секунду спустя. Это лечит только слой в памяти (`attachment-memory-cache.js`),
не диск. Инвариант слоя в памяти — тот же LRU-по-бюджету, что диск
(§ выше), но структура проще: `Map` в порядке вставки ВМЕСТО
отдельного `lastAccessedAt`-поля и сортировки (переустановка ключа —
`delete` + `set` — уже двигает его в MRU-конец, `for...of` по `Map` уже
идёт в порядке вставки = от LRU к MRU, второй сортировки не нужно).
TTL не нужен вовсе — содержимое живёт ровно до `lock()`/закрытия
вкладки, протухать самому по времени незачем.

## Этап 46 — раздел "Обзор" (публичное знакомство + лёгкий отменяемый запрос)

Триаж: преимущественно рутина (kind-broadcast/gift-wrap — уже принятые
в проекте паттерны), но состояние "заявка на знакомство" имеет
нетривиальный переход (отмена ДО ответа), не покрытый существующей
машиной контактных запросов — формализуется здесь.

### Состояния (со стороны отправителя A → получателя B)

Отношение `outgoing(A, B) ∈ {none, pending}` — источник истины ЛОКАЛЬНАЯ
таблица `outgoingAcquaintanceRequests`: строка есть ⟺ `pending`, строки
нет ⟺ `none`. Никакого отдельного enum-поля не заводится — присутствие/
отсутствие строки И ЕСТЬ состояние (тот же принцип, что
`contactRequests`/`inboxRequests` уже в проекте).

```
none --SEND(A)--> pending
pending --CANCEL(A)--> none              (A отзывает сам)
pending --ACCEPTED_BY(B)--> none          (B принял -> A получил CONTACT_ACCEPTED_KIND,
                                            стал реальным контактом, "Обзор" его больше
                                            не показывает per правилу "скрывать контакты")
```

`REJECT`/блокировка со стороны B НЕ порождает новый переход здесь —
получатель обрабатывает входящую заявку существующей веткой
`rejectContactRequestAction` (блокировка), которая при следующей
синхронизации contact-list на стороне A естественно уберёт B из
видимости (существующий путь, не новый).

Симметрия на стороне B: `incoming(B, A)` — это УЖЕ существующее
состояние `contactRequests` (тот же самый `CONTACT_REQUEST_KIND`,
получатель не отличает "заявку из формы 'Добавить контакт'" от "заявки
из Обзора" — намеренно, чтобы не удваивать приёмный код). Единственный
НОВЫЙ переход на стороне B — `pending --CANCELLED_BY(A)--> none`,
удаляющий строку `contactRequests` по приходу нового rumor
`ACQUAINT_CANCELLED_KIND` (см. CONTRACTS.md).

**Инвариант.** `outgoing(A,B)=pending` НЕ подразумевает `contacts(A)
∋ B` — в отличие от существующего `sendContactRequestAction` (форма
"Добавить контакт"), который добавляет адресата в контакты
ОПТИМИСТИЧНО, ещё до ответа. Разделение обязательно: иначе "отжать"
заявку в Обзоре не могло бы честно "исчезнуть без следа" — контакт
остался бы добавленным.

## Этап 47 — гибкие уведомления (обсуждение с пользователем)

Триаж: смешанная задача. Read-tracking каналов — рутина (прямая аналогия
уже принятого `chatSyncState`-паттерна, см. `read-status.js`). Разрешение
уровня уведомления (глобальный дефолт vs per-entity override) — короткая,
но нетривиальная логика приоритета, формализуется здесь, чтобы порядок
проверки не расползался по вызывающим местам.

### Уровни уведомления — упорядоченное множество, не 3 независимых флага

`NOTIFICATION_LEVELS = ["off", "badge", "popup", "sound"]` — линейный
порядок, КАЖДЫЙ следующий уровень включает эффекты всех предыдущих:

```
off    — ничего
badge  — только увеличивает счётчик непрочитанного (число в разделе нава)
popup  — badge + всплывающее уведомление (Notification API)
sound  — popup + проигрывание звука (звук — ВСЕГДА отдельное действие
         от всплывашки технически: Web Notification API кастомный звук
         не поддерживает годами, звук — свой <audio>, но в модели
         уровня он остаётся "надмножеством" popup, не самостоятельной
         веткой — нет смысла проиграть звук без бейджа/всплывашки)
```

Инвариант (тестируется впрямую): для любого `level`, `showPopup`
вызывается ⟺ `level ∈ {popup, sound}`; `playSound` вызывается ⟺
`level === sound`; счётчик увеличивается ⟺ `level !== off`. Не 2^3
независимых комбинаций — одна ось, 4 точки.

### Разрешение уровня — приоритет override НАД дефолтом категории

Для категорий с per-entity исключениями (`messages` — по contactPubkey,
`channels` — по channelId × {posts, comments, chat}) порядок проверки
СТРОГО: (1) если для конкретной сущности есть явный override — он
побеждает целиком, ДАЖЕ если это `"off"` (замолчать конкретный канал
насовсем, не заглушая всю категорию); (2) иначе — дефолт категории;
(3) глобальный `notifications.enabled === false` — рубильник ВЫШЕ обоих,
проверяется первым и обнуляет всё разом (тот же принцип, что уже был у
`enabled` до этого этапа).

`moderation` — ИСКЛЮЧЕНИЕ из общей схемы, сохраняет прежнее
(этап 34) поведение ЧАСТИЧНО: подкатегория `"reports"` теперь ходит
через обычное разрешение (настраиваема), ЛЮБАЯ другая подкатегория
модерации (бан/предупреждение/удаление канала) по-прежнему ИГНОРИРУЕТ
settings целиком и уходит с уровнем `"sound"` принудительно — эти
события влияют на статус пользователя в канале, молчать о них нельзя.

### Read-tracking каналов — прямая аналогия `chatSyncState`, три отличия

1. **Курсор ОДИН на канал**, не три (не по posts/comments/chat раздельно)
   — по решению пользователя, ради простоты; открытие ЛЮБОЙ под-вкладки
   канала продвигает курсор для ВСЕХ трёх разом.
2. **Сравнение по `createdAt`** (unix-время), не по `lamportTs` — каналы
   не используют Lamport-часы (только личные чаты). Курсор — значение
   `createdAt`, переданное ВЫЗЫВАЮЩИМ кодом (max среди уже загруженных
   элементов канала), не `Date.now()` — тот же принцип, что
   `markChatAsRead`, избегает рассинхрона по времени устройства.
3. **Подсчёт непрочитанного трогает 3 разные таблицы** с РАЗНОЙ
   доступностью полей без расшифровки (CONTRACTS.md, Tier 0-1):
   `channelMessages` — `channelId`/`authorPubkey`/`createdAt` все
   plaintext, фильтр без расшифровки; `posts` — `channelId`/`createdAt`
   plaintext, но `authorPubkey` sensitive — расшифровка только
   кандидатов (уже прошедших фильтр по каналу+времени), не всех постов
   владельца; `comments` — НИ `channelId`, НИ `authorPubkey` не
   plaintext (Tier 1) — расшифровка ВСЕХ комментариев владельца, фильтр
   в памяти (тот же паттерн, что уже применяется в
   `moderation.js`'s `deleteChannelLocally` — не новая проблема
   производительности, а уже принятый в проекте компромисс для этой
   конкретной таблицы).

Новый kind `30074` (не переиспользование `30070`) — разное поле
сравнения (createdAt vs lamportTs) и разная семантика `d`-tag
(channelId vs contactPubkey) сделали бы общий поток веток `if` менее
понятным, чем отдельный, буквально аналогичный `read-status.js` файл.
Таблица `channelSyncState` — уже объявлена в схеме с этапа 1, НИ РАЗУ
не использована (мёртвый код, тот же класс находки, что `attachments`
до этапа 43) — переопределяется под этот курсор, схема правится на
owner-scoped `[ownerPubkey+channelId]` (была голым `channelId`, тот же
класс пробела, что уже чинился для `clock`/`messages`/etc. в прошлых
этапах).
